# 事故管理 (Incident Management)

> 中文简称：事故管理

## 1. 事故分级

| 级别 | 影响 | 响应时间 | 示例 |
|------|------|---------|------|
| P0 (致命) | 服务完全不可用 | 5 分钟 | 推理集群全挂 |
| P1 (严重) | 核心功能受损 | 15 分钟 | 延迟 >10s / 错误率 >10% |
| P2 (中等) | 部分功能异常 | 1 小时 | 某模型不可用 / 部分用户受影响 |
| P3 (轻微) | 体验下降 | 4 小时 | 非核心功能 bug / 性能轻微下降 |

## 2. 响应流程

```
事故响应生命周期:

检测 → 确认 → 分级 → 响应 → 缓解 → 修复 → 复盘
 │       │       │       │       │       │       │
监控    值班    IM群    作战室  降级    根因    文档
告警    确认    通知    协作    回滚    修复    改进

关键原则:
- 先缓解，后修复 (恢复服务优先)
- 单一指挥 (Incident Commander)
- 实时沟通 (状态页/利益相关者)
- 不追责 (Blameless Postmortem)
```

## 4. Runbook 模板

```python
# Runbook: 推理服务延迟飙升

RUNBOOK_LATENCY_SPIKE = {
    "触发条件": "P99 延迟 > 5s 持续 2 分钟",
    "第一步_确认": [
        "检查 Grafana 延迟面板",
        "确认影响范围 (全部/部分用户)",
        "检查最近变更 (部署/配置)",
    ],
    "第二步_诊断": [
        "nvidia-smi: GPU 利用率/温度/错误",
        "检查请求队列深度",
        "检查 KV Cache 使用率",
        "检查网络延迟 (节点间)",
    ],
    "第三步_缓解": [
        "如果是流量突增 → 启用限流",
        "如果是 GPU 故障 → 隔离节点",
        "如果是模型问题 → 回滚版本",
        "如果持续 → 降级到小模型",
    ],
    "第四步_恢复": [
        "确认延迟恢复正常",
        "逐步解除限流",
        "监控 30 分钟确认稳定",
    ],
    "升级条件": "15 分钟未缓解 → 升级 P1 → 通知管理层",
}
```
