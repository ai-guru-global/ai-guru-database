> 本页是 [[Context_Engineering_Guide]] 的技术深度补充，聚焦具体实现模式、架构决策和反模式治理。

## 1. 记忆架构

### 1.1 认知科学的启发

人类记忆系统是多层次的：工作记忆负责当前任务，长期记忆存储持久知识。AI 系统的记忆架构借鉴这一模型：

- **工作记忆**：容量有限，持续时间短，支持当前思维
- **长期记忆**：
  - **语义记忆**：事实和概念（"巴黎是法国首都"）
  - **情景记忆**：具体经历和事件（"昨天我去了巴黎"）
  - **程序记忆**：技能和方法（"如何骑自行车"）

### 1.2 大模型三层记忆建模

| 层次 | 名称 | 特性 | 实例 |
|------|------|------|------|
| 1 | **参数化记忆（隐性）** | 固化在模型权重中，读取极快，写入成本极高 | 模型权重、LoRA 微调层 |
| 2 | **激活记忆（暂态）** | 暂存在显存中，读写速度居中，可随时丢弃或常驻 | 当前对话上下文、[[kv-cache|KV Cache]] |
| 3 | **明文记忆（显性外部）** | 可显式读取的外部存储，容量大、更新灵活 | 向量数据库、知识检索结果 |

### 1.3 短期记忆：对话历史

短期记忆维持当前会话（Session）的连贯性：

- **存储介质**：Redis 等内存数据库，以 Session ID 为键隔离
- **生命周期**：会话开始时建立，超时（如 30 分钟无交互）或显式结束时销毁/持久化
- **注入方式**：先进先出（FIFO）或滑动窗口

### 1.4 长期记忆与类操作系统管理

MemGPT 提出类操作系统的长期记忆管理隐喻：

- **上下文窗口** = 主内存
- **外部存储** = 磁盘
- **显式分页**：系统在"主存"和"磁盘"之间主动交换数据
- **中断机制**：上下文占满时触发"内存管理中断"
- **读写接口**：模型通过工具调用（API）来读写外部记忆

这种架构允许智能体处理看似"无限"的上下文任务，只要当前活跃集（Working Set）不超过窗口限制。

### 1.5 五层记忆架构（工程落地）

| 层次 | 职责 |
|------|------|
| **存储层** | 为各类记忆量身定制存储媒介（图+向量混合存储） |
| **治理层** | 全生命周期管理、幻觉评估、版本控制、权限与隐私隔离 |
| **调度层** | 记忆系统内核：动态行为预测与预加载 |
| **应用层** | 屏蔽复杂操作，提供标准 API（Memory-as-a-Service） |
| **解码层** | 结合已调度的记忆上下文进行推理生成 |

### 1.6 记忆管理机制

**记忆提取**（从长期记忆到工作记忆）：
- 基于语义相似度（Retrieve）
- 基于时间相关性（Recency）
- 基于重要性评分（Importance）

**记忆巩固**（从工作记忆到长期记忆）：
- 显式保存：用户明确要求记住
- 重要性判断：自动识别（如 Reflection 机制）
- 摘要压缩：提取关键内容存储
- 定期回顾：对已有记忆进行整理

**记忆遗忘**：
- **遗忘曲线**：模拟人类遗忘规律，随时间降低记忆权重 `Weight_t = Weight_0 * e^(-lambda*t)`
- **使用频率（LRU）**：不常用的记忆优先淘汰
- **重要性评估**：LLM 对每条记忆评分（1-10），如"我对花生过敏"（10分）vs "我想吃披萨"（2分）

### 1.7 记忆更新策略

| 策略 | 描述 | 适用场景 |
|------|------|----------|
| 追加式 | 新信息不断追加 | 日志、历史记录 |
| 覆盖式 | 新信息替换旧信息 | 状态信息、配置 |
| 合并式 | 新旧信息智能合并 | 知识累积 |
| 淘汰式 | 按规则删除旧信息 | 容量管理 |

**关键洞察**：记忆系统的效果上限往往不取决于检索算法的优劣，而取决于**目标函数是否准确**。多数系统默认优化语义相似度，但长期记忆场景真正需要优化的是更新正确性、时间正确性、冲突消解和噪声抑制。

### 1.8 Supermemory 案例：从"记忆存储"到"持续状态维护"

Supermemory 将记忆问题从信息检索重新定义为持续状态维护：

| 层次 | 职责 |
|------|------|
| **记忆引擎** | 从对话中抽取事实，处理时间变化、矛盾和自动遗忘 |
| **用户画像** | 维护 `static`（长期稳定事实）和 `dynamic`（近期上下文）两层 |
| **外部连接器** | 实时同步 Google Drive、Notion、GitHub 等外部源 |

核心创新：**不存原文，而是抽取事实并管理状态**。当用户说"我刚搬到旧金山"，系统识别与"我住在纽约"冲突，自动执行覆盖。

## 2. RAG 集成与检索技术栈

### 2.1 RAG 基本架构

```
用户查询 --> 查询处理 --> 信息检索 --> 上下文构建 --> 模型生成 --> 输出响应
                             ^
                          知识库
```

**核心组件**：

| 组件 | 功能 | 关键技术 |
|------|------|----------|
| 文档处理器 | 解析和分块文档 | 分块算法、元数据提取 |
| [[embedding-models|嵌入模型]] | 将文本转换为向量 | 语义嵌入模型 |
| 向量存储 | 存储和索引向量 | 向量数据库 |
| 检索器 | 执行相似性搜索 | ANN 算法 |
| 重排序器 | 优化检索结果排序 | 交叉编码器 |
| 上下文组装器 | 构建最终提示词 | 模板、格式化 |

### 2.2 RAG 发展阶段

**第一代：朴素 RAG**
- 简单的向量相似性检索 + 固定分块策略 + 直接拼接

**第二代：高级 RAG**
- 引入重排序和混合检索
- 优化的分块和嵌入策略
- 查询增强和结果后处理

**第三代：模块化 RAG**
- 灵活组合各种 RAG 技术
- 自适应检索策略
- 与智能体系统集成

### 2.3 文档分块策略

分块是 RAG 系统的关键预处理步骤：

**常见策略**：
- **固定大小分块**：按 Token 数量切分，简单但可能截断语义
- **语义分块**：基于语义边界切分（段落、章节）
- **递归分块**：多级嵌套，从大到小逐步切分
- **结构化分块**：利用文档结构（标题、列表、表格）

**关键参数**：
- `chunk_size`：分块大小（通常 256-1024 Token）
- `chunk_overlap`：相邻块重叠（通常 10-20%）
- 元数据保留：标题路径、页码、来源

### 2.4 嵌入模型与语义搜索

[[embedding-models|嵌入模型]]将文本映射到高维向量空间：

- **选择维度**：维度越高表达力越强，但存储和计算成本也越高
- **多语言支持**：中文场景需要选择对中文优化良好的模型
- **领域适配**：通用模型 vs 领域微调模型

### 2.5 重排序与相关性优化

初次检索后，使用 Cross-Encoder 等重排序模型对结果精排：

- **Bi-Encoder**（初次检索）：速度快，适合大规模候选
- **Cross-Encoder**（重排序）：精度高，适合 Top-K 精排
- **混合策略**：先粗排后精排的两阶段方案

### 2.6 混合检索

结合语义检索和关键词检索的优势：

```
查询 --> 语义检索 (向量相似度) --> 结果A
查询 --> 关键词检索 (BM25)     --> 结果B
                          \      /
                      结果融合 (RRF / 加权)
```

**Reciprocal Rank Fusion (RRF)**：基于排名的融合方法，不依赖分数归一化。

### 2.7 从"被动阻断"到"主动式全时调度"

传统 RAG 的串行流程（提问 --> 检索 --> 拼接 --> 推理）拉长了首 Token 延迟。前沿方案探索**异步预加载**：

- 利用用户思考、打字的碎片时间，后台并行完成记忆检索和组合
- 用户发出查询时，增强上下文已处于"就绪"状态
- 从"请求即时检索"演进到"全时异步调度"

## 3. 上下文压缩技术

### 3.1 信息密度

```
信息密度 = 有效信息量 / Token 数量
```

低效内容的两个来源：
- **冗余信息**：重复表达、过渡词汇、不必要的修饰
- **噪声信息**：与任务无关的背景内容、过时信息、格式化符号

### 3.2 压缩技术分类

| 类型 | 方法 | 特点 |
|------|------|------|
| **抽取式** | 选择原文中的关键句段 | 保持原文表述 |
| **生成式** | 生成新的精简表述 | 更灵活、更精炼 |
| **结构化** | 转换为结构化格式 | 格式紧凑、易解析 |
| **层次化** | 分级别保留细节 | 按需展开 |

### 3.3 压缩时机

| 场景 | 说明 |
|------|------|
| 上下文接近容量上限 | 为新内容腾出空间 |
| 成本敏感场景 | Token 费用是主要顾虑 |
| 延迟敏感场景 | 需要快速响应 |
| 对话历史过长 | 多轮对话积累了大量历史 |
| 检索结果过多 | RAG 检索返回过多内容（"Lost in the Middle"） |

### 3.4 对话历史管理

**滑动窗口**：只保留最近 N 轮对话
- 简单问答：2-5 轮
- 复杂任务：5-10 轮

**选择性保留**：基于重要性判断
- 包含任务关键信息
- 用户明确要求记住的内容
- 定义了重要约束或偏好

**对话压缩**：将冗长对话压缩为摘要
- 保留关键决策和结论
- 丢弃过程细节和寒暄
- 保留用户纠正和反馈（包含重要约束）

**递进式摘要**：
```
最近 3 轮：保留原文
4-10 轮：简短摘要
10 轮以前：高度压缩的会话检查点
```

### 3.5 压缩效果评估

- **直接指标**：压缩率（压缩后/原始）、Token 减少量
- **间接指标**：任务效果、关键信息保留率
- **经验现象**：中等压缩率区间，去除冗余可能带来"去噪效应"；但压缩过度时关键信息丢失导致性能下降

### 3.6 压缩质量权衡

```
压缩率 vs 信息完整性：高压缩率节省空间但可能丢失细节
通用性 vs 针对性：通用压缩可复用 vs 针对具体任务定制
成本 vs 效果：简单截断成本低 vs LLM 摘要效果好但需额外成本
```

## 4. XML 标签与指令分层

### 4.1 XML 标签的优势

- **边界清晰**：标签明确标识内容的开始和结束
- **可嵌套**：支持层级结构
- **自描述**：标签名称说明内容类型
- **模型友好**：主流模型都能很好理解

### 4.2 常用标签体系

| 标签 | 用途 | 示例 |
|------|------|------|
| `<instructions>` | 核心指令 | 任务说明、行为规范 |
| `<context>` | 背景信息 | 知识、文档、数据 |
| `<examples>` | 示例内容 | 输入输出示例 |
| `<constraints>` | 约束条件 | 限制、禁止事项 |
| `<format>` | 格式要求 | 输出格式说明 |
| `<user_input>` | 用户输入 | 当前请求 |

### 4.3 嵌套结构示例

```xml
<system>
  <role>你是一个代码审查助手</role>
  <capabilities>
    <item>代码质量分析</item>
    <item>安全漏洞检测</item>
    <item>性能优化建议</item>
  </capabilities>
  <constraints>
    <item>只分析提交的代码</item>
    <item>不执行代码</item>
  </constraints>
</system>

<code_to_review language="python">
def calculate_sum(numbers):
    return sum(numbers)
</code_to_review>
```

### 4.4 指令分层设计

```
L1: 核心身份    -- 模型的基本角色和身份
L2: 任务框架    -- 任务的整体框架和边界
L3: 具体指令    -- 当前交互的具体指令
L4: 格式约束    -- 输出的格式要求
```

### 4.5 最佳实践

1. **一致的命名规范**：团队统一 snake_case 或 kebab-case，建立标签词汇表
2. **控制嵌套层级**：一般不超过 3 层；过深则考虑扁平化 + 属性标记
3. **平衡结构与 Token 成本**：简单场景用 `---` 分隔符可能比 XML 标签更高效
4. **确保标签正确闭合**：未闭合标签会导致模型对上下文边界的理解混乱
5. **动态内容转义**：程序构建标签时，动态内容必须先 HTML 转义

```python
import html

def build_context(role, knowledge, query):
    role = html.escape(role, quote=False)
    knowledge = html.escape(knowledge, quote=False)
    query = html.escape(query, quote=False)
    return f"""
<role>{role}</role>
<knowledge>{knowledge}</knowledge>
<query>{query}</query>
"""
```

## 5. 多任务上下文隔离

### 5.1 隔离策略

**物理隔离** -- 完全独立的 API 调用：
- 优点：完全隔离，无干扰
- 缺点：无法共享上下文，成本更高
- 适用：任务完全独立、对隔离要求极高

**逻辑隔离** -- 同一调用中用结构隔离：
```xml
<task_1>
  <description>分析销售数据</description>
  <context>销售表格数据...</context>
  <requirements>输出增长趋势</requirements>
</task_1>
<task_2>
  <description>生成营销建议</description>
  <context>竞品分析报告...</context>
  <requirements>输出 3 条建议</requirements>
</task_2>
```

**上下文分区** -- 划分不同区域按需暴露：
```
共享区域：通用规则、基础知识
任务 A 区域：A 专属数据和指令
任务 B 区域：B 专属数据和指令
```

### 5.2 上下文传递控制

**最小信息原则**：
```
从任务 A 传递到任务 B：
x 完整对话历史
v 任务 A 的结论摘要
```

**显式接口**：
```json
{
  "conclusion": "...",
  "key_facts": [...],
  "next_task_hints": [...]
}
```

### 5.3 隔离最佳实践

1. **默认隔离**：宁可多隔离也不要过度共享
2. **清晰边界**：每个任务有明确的输入要求、输出格式和职责范围
3. **最小共享**：只共享真正需要的上下文
4. **显式传递**：信息传递显式且可控，便于追踪信息流向
5. **独立测试**：每个隔离单元可独立测试其输入输出行为

### 5.4 并行智能体的上下文编排

实际工作流中的 Research --> Plan --> Build 循环：

```
研究会话(调查方案) --[结果写入plan.md]--> 规划会话(结构化计划)
   --> 实现会话(按计划编码) --> 测试会话(验证) --> (循环)
```

多个并行会话通过共享文件（plan.md）协调 -- 这是共享黑板模式在开发工作流中的自然应用。

## 6. Graph RAG 与知识图谱

### 6.1 向量检索的局限

当问题**强依赖显式关系结构**时，单靠向量相似度不够：
- 对实体间关系的表达较弱（不天然表达"A 是 B 的子公司"）
- 跨多文档的关系推理需要额外编排
- 多跳查询（"找出所有投资了 AI 公司的 PE 基金合伙人"）不够直接

### 6.2 Graph RAG 架构

将知识图谱与 RAG 结合，通过实体和关系增强检索：

```
用户查询 --> 实体提取 --> 图谱检索 --> 子图提取 --> 上下文构建 --> LLM生成
```

**知识图谱构建流程**：
```
原始文档 --> 文档分块 --> 实体提取 --> 关系抽取 --> 去重合并 --> 知识图谱
```

### 6.3 记忆脑图（Memory Mind Map）

全量构建知识图谱成本高昂且脆弱。工程实践中更具价值的演进形态是**轻量化图结构**：

- 介于松散分块与重度图谱之间
- 通过 **Chain of Memory（主动记忆过程）** 工程模式：系统自觉过滤通识内容，仅保留对当前业务场景具有差异化价值的要点
- 形成以根节点（Root Node）和主题节点（Topic Node）为核心的轻型脑图网络

### 6.4 图检索策略

- **局部子图提取**：以查询相关实体为中心，提取 N 跳范围内的子图
- **路径查询**：查找两个实体之间的关系路径
- **社区检测**：识别高度关联的实体簇，整体提取相关社区

### 6.5 混合增强：图谱 + 向量

```
查询 --> 向量检索 --> 文档片段 --+
查询 --> 图检索   --> 结构化关系 --+--> 结果融合 --> 生成
```

融合策略：
- **互补增强**：向量检索提供详细描述，图检索提供关系结构
- **相互验证**：两种方式的结果相互印证
- **按需切换**：根据查询类型选择主要方法

记忆脑图架构下，为关键树状路径和主题节点预计算 [[embedding-models|嵌入]]，实现"脑图结构 + 向量特征"的双保险。

### 6.6 适用性判断

| 场景 | 推荐方案 |
|------|---------|
| 简单问答 | 向量检索足够 |
| 实体关系查询 | Graph RAG 更强 |
| 多跳推理 | Graph RAG 更自然 |
| 全局理解/摘要 | Graph RAG 的社区检测有优势 |
| 知识密集+关系复杂 | 混合方案最佳 |

## 7. Agentic RAG

### 7.1 从被动到主动

传统 RAG 是被动的（收到查询后检索一次）。**Agentic RAG** 是主动的：AI 智能体自主决定何时检索、检索什么、是否需要多次检索。

```
传统 RAG: 查询 --> 检索 --> 生成

Agentic RAG: 任务 --> 规划 --> 自主检索 --> 分析
                              ^            |
                              +-- 信息不足 --+
```

### 7.2 核心能力

- **自主决策**：简单问题直接回答，复杂问题触发检索，不确定时主动查证
- **迭代检索**：初次结果不足时改进查询再次检索
- **多源整合**：按需访问不同知识库、实时 API、文档搜索

### 7.3 实现模式

**路由模式**：根据查询类型选择检索策略
```python
if query_type == "factual":    retrieve_from_knowledge_base(query)
elif query_type == "recent":   retrieve_from_news_api(query)
elif query_type == "code":     retrieve_from_code_base(query)
else:                          multi_source_retrieve(query)
```

**反馈循环模式**：检索结果不满足时自动改进查询

**查询分解模式**：复杂问题分解为子查询并行检索

### 7.4 实践建议

1. 从简单场景开始（基本路由）
2. 设置迭代上限（防止无限检索）
3. 监控检索效率（跟踪迭代次数和效果）
4. 缓存中间结果（避免重复检索）

## 8. 反模式与常见错误

### 8.1 过度压缩与信息丢失

**现象**：为节省 Token 对信息进行过度压缩或粗暴截断，导致关键约束、实体名称、数值条件被丢弃。

**典型案例**：

| 场景 | 原始信息 | 过度压缩后 | 后果 |
|------|---------|-----------|------|
| 客服退货 | "必须在 7 天内寄回，需附上质检报告照片" | "用户要退货，客服同意了" | 丢失退货时限和质检要求 |
| 代码审查 | `amount > 0, <= 10000, currency 仅 USD/EUR/CNY` | "有一个处理支付的函数" | 生成违反约束的调用代码 |
| 医疗问答 | "妊娠晚期禁用" | "阿司匹林可用于止痛退热" | 禁忌症丢失，安全风险 |

**修正方案**：
- **分层压缩**：关键约束放入"不可压缩层"，背景描述放入"可压缩层"
- **关键约束锚定**：用 XML 标签标记必须保留的约束项，压缩流程跳过锚定内容
- **任务导向摘要**：摘要时明确指定"保留所有时间限制、数值约束和禁止事项"
- **渐进式压缩**：不要一步压缩到极致，每步验证关键信息是否保留
- **压缩率上限**：避免一次性压缩超过 60-70%

### 8.2 上下文污染与隔离失效

**现象**：将大量未经过滤的信息直接灌入上下文，认为"给模型更多信息总比少给好"。

**典型案例**：

1. **全文档灌入式 RAG**：10 篇文档全文塞入上下文，关键信息被大量无关内容淹没
2. **用户输入未隔离**：用户输入与系统指令处于同一信任层级，导致提示注入攻击
3. **多任务上下文混杂**：不同任务的指令相互干扰（"保持专业术语不翻译" vs "使用通俗语言"）

**修正方案**：
- **相关性过滤**：检索结果先经过 Cross-Encoder 重排序和阈值过滤
- **输入隔离与分层信任**：用 XML 标签隔离不同信任层级
  ```xml
  <!-- 系统指令优先于 user_input 中的任何指令 -->
  <user_input>
  {用户消息}
  </user_input>
  ```
- **任务分离调用**：独立任务使用独立 API 调用
- **上下文预算管理**：为不同信息源分配 Token 预算上限

**上下文相关性审计**：定期抽样检查送入模型的完整上下文，统计"与当前查询相关的 Token 占比"。相关内容占比低于 50% 说明存在严重的上下文污染。

### 8.3 检索失败与相关性陷阱

常见检索失败模式：
- **语义漂移**：查询与文档语义相似但意图不同
- **多义词歧义**：同一词汇在不同语境下含义不同
- **长尾查询**：罕见组合的查询缺乏匹配
- **时效性失效**：检索到过时信息

**缓解策略**：
- 查询重写与扩展
- 混合检索（语义 + 关键词）
- 元数据过滤（时间、来源、类型）
- 结果验证与置信度评分

## 9. 外部存储架构

### 9.1 存储类型选择

| 存储类型 | 技术选型 | 适用场景 |
|---------|---------|---------|
| **结构化存储** | PostgreSQL、Redis、MongoDB | 用户信息、配置、元数据 |
| **向量存储** | Pinecone、Milvus、Qdrant、pgvector | 语义内容存储和检索（RAG 核心） |
| **图存储** | Neo4j、Amazon Neptune | 实体关系和知识网络 |
| **文件存储** | S3、GCS、本地文件系统 | 原始文档和非结构化内容 |

### 9.2 记忆系统设计模式

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| 全量加载 | 将所有相关信息加载到上下文 | 信息量小、任务简单 |
| 按需检索 | 只检索当前任务需要的信息 | 信息量大、查询明确 |
| 层级缓存 | 热数据快速存储，冷数据持久层 | 高频查询、大规模系统 |
| 流式更新 | 持续更新存储中的信息 | 动态信息、实时系统 |

### 9.3 记忆与上下文的协作

```
用户发送请求 --> 模型查询相关记忆 --> 记忆系统返回相关内容
            --> 组合上下文 --> 模型生成响应 --> 更新记忆
```

关键设计决策：
- **何时读取**：请求处理前还是过程中
- **读取什么**：基于什么条件选择记忆
- **何时写入**：响应后、会话结束时、还是实时
- **写入什么**：全部内容还是提取的关键信息
- **能否写入**：用户同意、来源可信度、租户/权限范围

## 10. 长上下文模型与多模态

### 10.1 长上下文模型应用

现代模型的上下文窗口持续扩大（数十万到百万 Token），但需注意：
- **有效利用率**不等于窗口大小 -- 上下文腐烂仍然发生
- **首 Token 延迟**随上下文增长而增加
- **成本**随 Token 数量线性增长
- 长上下文是工具，不是银弹 -- 仍需精选和结构化

### 10.2 多模态上下文管理

统一管理文本、图像、代码等不同模态的上下文信息：
- 图像 Token 通常比文本消耗更多空间
- 需要合理的图像压缩和分辨率选择
- 代码需要特殊的分块策略（AST 感知分块）

### 10.3 长时间任务的上下文策略

对于跨越数十甚至数百轮交互的任务：
- **检查点机制**：定期保存任务进度到外部存储
- **分层压缩**：近期详细、早期摘要
- **状态外化**：将任务状态写入文件系统而非全部保持在上下文中
- **子智能体委派**：将独立子任务分配给子智能体处理
