# Build a Multi-Agent System

> **一句话理解**: Manning 出品的"从零构建"系列之一，聚焦多 Agent 系统的底层设计，讲解 Agent 间通信、任务分解与协作编排，适合深入理解多智能体架构。

## 书籍概述

### 作者与出版背景

《Build a Multi-Agent System (From Scratch)》属于 Manning 的"From Scratch"系列，秉承"不依赖高层框架、从底层实现理解原理"的理念。本书诞生于 2024-2026 年多智能体系统（Multi-Agent System, MAS）从研究走向生产的浪潮中——AutoGen、CrewAI、LangGraph 等框架的流行让"多 Agent 协作"成为构建复杂 AI 应用的主流范式，但多数开发者停留在"调用框架 API"层面，缺乏对底层机制的深入理解。

## 核心内容

### Part 1 — 多智能体系统基础

#### Ch 1: 为什么需要多 Agent

- **单 Agent 的局限**:
  - 上下文窗口限制：单 Agent 难以处理超长、超复杂任务
  - 能力边界：一个 Prompt 难以让模型同时擅长多种角色
  - 可靠性：复杂任务的单点失败风险
- **多 Agent 的核心价值**:
  - **专业化分工**: 每个 Agent 专注一个角色/能力（如研究员、编码者、审查者）
  - **并行化**: 多个子任务同时处理
  - **模块化**: 独立开发、测试、替换各 Agent
  - **可扩展性**: 通过增加 Agent 扩展系统能力
- **典型应用场景**:
  - 软件开发团队（PM + 架构师 + 工程师 + 测试）
  - 研究助手（检索 + 分析 + 综合 + 写作）
  - 客服系统（分诊 + 专家 + 升级）
- **多 Agent vs 单 Agent + 工具**: 何时该用多 Agent，何时单 Agent 即可

#### Ch 2: Agent 架构回顾

- **单 Agent 的基本组件**:
  - **大脑（LLM）**: 推理与决策核心
  - **感知（Input）**: 用户输入、环境观察、其他 Agent 消息
  - **行动（Tools）**: 工具调用、API 访问
  - **记忆（Memory）**: 短期上下文 + 长期存储
- **Agent 的执行循环**: 感知 → 思考 → 行动 → 观察 → 循环
- **状态管理**: Agent 内部状态的设计
- **从单 Agent 到多 Agent**: 把"一个全能 Agent"拆分为"多个专业 Agent"的思路

### Part 2 — Agent 间通信

#### Ch 3: 通信协议与模式

- **消息传递（Message Passing）**:
  - Agent 间通过结构化消息通信
  - 消息格式设计：发送者、接收者、内容、元数据
  - 同步 vs 异步消息
- **共享黑板（Blackboard）模式**:
  - 所有 Agent 读写一个共享状态空间
  - 适合需要全局信息共享的场景
  - 优点：解耦；缺点：并发控制复杂
- **事件驱动（Event-Driven）**:
  - Agent 订阅感兴趣的事件
  - 事件触发时自动响应
  - 适合松耦合、可扩展的系统
- **通信协议设计原则**:
  - 消息的幂等性
  - 序列化与版本控制
  - 错误与重试机制

#### Ch 4: 对话与协商机制

- **Agent 对话管理**:
  - 轮次控制（谁在何时发言）
  - 对话历史的共享与隔离
- **协商与共识**:
  - 多 Agent 对同一问题的不同意见
  - 投票、辩论、仲裁机制
- **结构化输出在通信中的作用**: 用 JSON Schema 约束 Agent 间消息格式
- **通信开销控制**: 避免 Agent 间无效"闲聊"消耗 Token

### Part 3 — 任务分解与协作

#### Ch 5: 任务分解与分配

- **任务分解策略**:
  - **层级分解**: 大任务 → 子任务 → 子子任务（树状）
  - **功能分解**: 按功能模块划分（如检索、分析、生成）
  - **流程分解**: 按工作流阶段划分（如规划 → 执行 → 验证）
- **任务分配机制**:
  - 静态分配：预定义每个 Agent 的职责
  - 动态分配：由协调者 Agent 根据能力路由
- **依赖管理**: 子任务间的先后顺序与数据依赖
- **任务粒度权衡**: 太粗（单 Agent 负担重）vs 太细（通信开销大）

#### Ch 6: 协作与协调模式

- **层级式协调（Hierarchical）**:
  - 一个"管理者" Agent 统筹全局，下属 Agent 执行
  - 类似公司组织结构
  - 代表：CrewAI 的 hierarchical process
- **对等式协调（Peer-to-Peer）**:
  - Agent 间平等，通过协商达成一致
  - 无中心节点，去中心化
- **市场式协调（Market-Based）**:
  - 任务"拍卖"，Agent "竞标"
  - 适合异构 Agent 能力差异大的场景
- **顺序式协作（Sequential）**:
  - Agent 按流水线顺序处理（A → B → C）
  - 简单可靠，适合明确流程
- **模式选择指南**: 按任务复杂度、Agent 数量、可靠性要求选择

### Part 4 — 编排引擎

#### Ch 7: 从零实现编排引擎

- **编排器（Orchestrator）的职责**:
  - 管理 Agent 生命周期
  - 路由消息与任务
  - 维护全局状态
  - 控制执行流程
- **状态机与图结构**:
  - 用有向图（DAG/循环图）建模工作流
  - 节点 = Agent 或操作，边 = 流转条件
  - 条件分支、循环、并行的实现
- **执行引擎设计**:
  - 调度循环：读取状态 → 决定下一步 → 执行 → 更新状态
  - 检查点（Checkpoint）与恢复
- **与 LangGraph 的对照**: 理解框架背后的图编排思想

#### Ch 8: 记忆与状态管理

- **全局状态（Global State）**:
  - 跨 Agent 共享的上下文
  - 状态的设计与最小化原则
- **共享上下文管理**:
  - 哪些信息该共享，哪些该隔离
  - 上下文的压缩与摘要（避免 Token 爆炸）
- **记忆类型**:
  - 工作记忆（当前任务上下文）
  - 情景记忆（历史交互）
  - 语义记忆（知识库，常配合向量存储）
- **状态一致性**: 多 Agent 并发修改状态的冲突处理

### Part 5 — 可靠性与生产化

#### Ch 9: 容错与评估

- **Agent 失败处理**:
  - 重试策略（指数退避）
  - 降级（用更简单的 Agent 或规则替代）
  - 超时与熔断
- **错误传播控制**: 防止单个 Agent 失败导致整个系统崩溃
- **多 Agent 系统评估**:
  - 端到端任务成功率
  - 各 Agent 的独立评估
  - 协作效率（通信轮次、Token 消耗）
- **可观测性**: 追踪多 Agent 的完整执行链路（Trace）
- **调试挑战**: 多 Agent 系统的非确定性与调试难度

#### Ch 10: 生产化部署

- **部署架构**:
  - 单体 vs 微服务化的 Agent 部署
  - 容器化与编排（Kubernetes）
- **扩展性**:
  - Agent 的水平扩展
  - 异步队列处理长任务
- **成本控制**:
  - 多 Agent 的 Token 成本叠加问题
  - 模型路由（关键 Agent 用强模型，辅助 Agent 用弱模型）
- **监控与告警**: 系统级健康度、Agent 级性能、成本追踪
- **安全**: Agent 权限隔离、工具调用的最小权限原则

## 关键概念与公式

### 多 Agent 通信复杂度

```
全连接通信复杂度: O(N²)  — N 个 Agent 两两通信
层级式通信复杂度: O(N)    — 通过中心协调者
黑板模式:        O(N)    — 各 Agent 读写共享状态

设计原则: 通信复杂度随 Agent 数量增长应尽量保持线性
```

### 多 Agent 成本模型

```
总成本 = Σ (Agent_i 的调用次数 × 每次 Token 数 × 单价)
       + 通信开销 (Agent 间消息的 Token)
       + 协调开销 (编排器的 Token)

优化关键:
- 减少无效通信轮次
- 辅助 Agent 使用小模型
- 缓存重复的子任务结果
```

### 任务成功率与 Agent 可靠性

```
顺序协作: P(成功) = Π P(Agent_i 成功)  — 短板效应，Agent 越多越脆弱
并行冗余: P(成功) = 1 - Π P(Agent_i 失败)  — 冗余提升可靠性

启示: 顺序链路要精简，关键节点可加冗余/验证
```

## 多 Agent 设计模式速查

下表汇总本书涉及的多 Agent 协调模式，便于架构选型时查阅：

| 协调模式 | 结构 | 优势 | 劣势 | 适用场景 |
|----------|------|------|------|----------|
| **顺序式（Sequential）** | A→B→C 流水线 | 简单可靠、易调试 | 无并行、短板效应 | 明确流程的任务 |
| **层级式（Hierarchical）** | 管理者+下属 | 全局统筹、分工清晰 | 中心瓶颈、单点故障 | 复杂任务分解 |
| **对等式（Peer-to-Peer）** | 平等协商 | 去中心化、灵活 | 协调开销大、难收敛 | 无明确主导的场景 |
| **市场式（Market-Based）** | 任务拍卖竞标 | 适配异构能力 | 机制设计复杂 | Agent 能力差异大 |
| **黑板式（Blackboard）** | 共享状态空间 | 解耦、易扩展 | 并发控制难 | 需全局信息共享 |

### 选型决策树

```
任务流程是否明确固定?
├─ 是 → 顺序式协作（最简单可靠）
└─ 否 → 是否需要全局统筹?
        ├─ 是 → 层级式（管理者 Agent）
        └─ 否 → Agent 能力是否同质?
                ├─ 是 → 对等式协商
                └─ 否 → 市场式竞标
```

## 常见误区与陷阱

构建多 Agent 系统时常见的错误：

| 误区/陷阱 | 问题 | 正确做法 |
|-----------|------|----------|
| **过度拆分 Agent** | 通信开销 > 收益 | 优先单 Agent，确实需要才拆分 |
| **Agent 间无效闲聊** | 消耗 Token、拖慢响应 | 设计明确的终止条件 |
| **共享过多上下文** | Token 爆炸、信息噪声 | 最小化共享、按需传递 |
| **忽视失败处理** | 单点失败拖垮全系统 | 重试、降级、熔断 |
| **缺乏可观测性** | 多 Agent 难调试 | 全链路 Trace |
| **盲目追求并行** | 协调复杂度激增 | 从顺序开始，按需并行 |
| **成本失控** | 多 Agent 成本叠加 | 模型路由 + 成本监控 |

### 多 Agent 系统的成熟度

```
Level 1: 单 Agent + 工具 — 多数场景的最优起点
Level 2: 顺序多 Agent — 流水线式分工
Level 3: 层级多 Agent — 管理者统筹
Level 4: 动态编排 — 根据任务自适应协调
Level 5: 自组织系统 — Agent 自主协商与演化
```

**核心建议**: 不要为了"多 Agent"而多 Agent。从 Level 1 开始，只有当单 Agent 确实无法胜任时，才升级到多 Agent。本书的价值在于让你**理解每一层的设计原理**，从而做出明智的架构决策。
