# 大模型上下文工程权威指南

> **核心命题**：如何在正确的时间，将正确的信息，以正确的格式，提供给模型？

上下文工程（Context Engineering）是 AI 时代最核心的工程能力之一。它从 [[Prompt_Engineering_Complete_Guide|提示词工程]] 演进而来的系统性学科，研究如何设计、组织、优化和管理大语言模型所需的全部信息环境。

---

## 1. 定义与内涵

**上下文工程**是一门系统性的工程学科，研究如何设计、组织、优化和管理大语言模型所需的全部信息环境，以确保模型能够在正确的时间获得正确的信息，从而产生准确、可靠、符合预期的输出。

### 1.1 上下文的多维构成

大模型应用中的"上下文"是一个多层次概念：

| 组成要素 | 说明 |
|---------|------|
| **系统指令** | 定义模型角色、行为准则和输出格式的基础设定 |
| **用户输入** | 当前任务的具体请求和参数 |
| **对话历史** | 多轮对话中的历史交互记录 |
| **外部知识** | 通过检索或其他方式引入的领域知识、事实信息 |
| **工具定义** | 模型可调用的外部工具、API 的描述 |
| **示例样本** | 用于引导模型行为的 Few-shot 示例 |

### 1.2 三大核心挑战

1. **有限的上下文窗口** -- 尽管现代模型已扩展到数十万甚至百万 Token，窗口仍是有限资源，需要精选最相关内容
2. **信息质量与密度** -- 冗余、噪声或不相关信息会干扰模型判断；过度填充（Context Stuffing）会带来性能波动和成本上升
3. **动态与实时性** -- 许多场景需要实时更新的信息，如何构建动态的上下文管理系统是持续挑战

### 1.3 核心价值

- **模型能力放大器**：相同模型配合精心设计的上下文可展现截然不同的能力
- **可靠性保障**：系统化的上下文管理显著降低幻觉和错误
- **成本效率关键**：优化的上下文策略直接影响 Token 使用量和 API 调用成本
- **可扩展性基础**：良好的上下文架构是构建复杂 AI 应用的技术基石

## 2. 从提示词工程到上下文工程

### 2.1 提示词工程的局限

| 局限性 | 具体表现 |
|--------|----------|
| 静态性 | 提示词通常是预定义的，难以适应动态变化 |
| 孤立性 | 聚焦单次交互，缺乏对对话历史和外部信息的系统管理 |
| 可扩展性差 | 随任务复杂度增加，提示词变得冗长且难以维护 |
| 缺乏工程化 | 更多依赖直觉和试错，缺乏系统化方法论 |

### 2.2 演进关系

> 提示词工程关注"写什么指令"，上下文工程关注"如何构建完整的信息环境"。

Anthropic 在其工程博客（2025-09-29）中明确把上下文工程定义为"在推理过程中策划与维护最优 Token 集合的一整套策略"，并指出**提示词工程是上下文工程的一个子集**。

### 2.3 核心差异对比

| 维度 | 提示词工程 | 上下文工程 |
|------|------------|------------|
| **关注点** | 单次指令的措辞和格式 | 完整信息环境的设计 |
| **范围** | 提示词文本 | 指令、数据、工具、记忆、策略 |
| **时间维度** | 静态、一次性 | 动态、跨会话 |
| **信息来源** | 手工编写 | 多源融合、自动检索 |
| **工程化程度** | 技巧驱动、经验依赖 | 系统化、可量化、可测试 |
| **应用场景** | 简单任务、单轮对话 | 复杂任务、多轮交互、智能体 |

### 2.4 演进驱动力

1. **任务复杂度提升** -- 从简单问答到代码编写、数据分析、多步推理
2. **智能体的兴起** -- 需要跨时间持续工作、维护工作状态
3. **生产环境要求** -- 可靠性、一致性、可观测性、成本控制
4. **模型能力增强** -- 上下文窗口扩大，需要更高层次的工程方法
5. **从"无状态"到"有状态"** -- 记忆工程成为核心需求

### 2.5 与驭具工程的关系

在智能体工程的完整版图中，**驭具工程（Harness Engineering）** 涵盖让智能体可靠运行的全部工程实践（工具编排、上下文管理、反馈纠错、安全守卫）。上下文工程是其中"上下文动态管理"这一核心支柱 -- 决定在什么时间节点、把哪些记忆和背景信息注入模型的上下文窗口。

> 上下文工程关注"模型看到什么"，驭具工程关注"模型如何安全可靠地执行"。

## 3. 理论框架：信息环境设计

### 3.1 注意力预算与上下文腐烂

**注意力预算（Attention Budget）** -- 工程隐喻：上下文越长，模型需要在更多 Token 和噪声之间做选择，关键信息更容易被干扰。上下文必须被当作**有限资源**来管理。

**上下文腐烂（Context Rot）** -- 随着上下文窗口中 Token 数量增加，模型对关键信息的提取与回忆稳定性可能下降（参考 "Lost in the Middle" 研究）。原因：
- 长上下文增加位置偏置、无关证据和指令冲突的暴露面
- 检索或拼接顺序不佳时，关键证据可能被放在模型不稳定利用的位置

> **核心指导原则**：找到**最小可能的高信号 Token 集**，以最大化实现期望结果的可能性。

### 3.2 七大设计原则

| # | 原则 | 核心理念 |
|---|------|---------|
| 1 | **相关性优先** | 只包含与当前任务直接相关的信息 |
| 2 | **信息密度优化** | 用最少的 Token 传达最多的有效信息 |
| 3 | **结构化组织** | 用清晰结构组织信息，便于模型理解和定位 |
| 4 | **上下文分层** | 按信息重要性和稳定性分层（系统层/知识层/任务层/交互层） |
| 5 | **显式优于隐式** | 明确说明期望，而非依赖模型推测 |
| 6 | **渐进式提供** | 按需提供信息，避免一次性加载全部内容 |
| 7 | **系统提示词高度校准** | 避免过低（硬编码逻辑）或过高（含糊其辞），找到恰到好处的区间 |

### 3.3 上下文分层结构

```
系统层：角色定义、行为准则        -- 最稳定，可缓存复用
知识层：领域知识、参考文档        -- 相对稳定
任务层：当前任务具体要求          -- 随任务变化
交互层：对话历史、用户输入        -- 最动态
```

## 4. 四大核心策略

上下文工程的实践可归纳为 **Write / Select / Compress / Isolate** 四大策略，形成完整的上下文生命周期管理：

```
原始信息 --> Write(写入) --> 存储 --> Select(选择) --> Compress(压缩) --> Isolate(隔离) --> 最终上下文
```

### 4.1 Write -- 写入策略

**解决问题**：如何在上下文窗口之外存储和管理信息？

- **外部记忆系统**：将信息存储到外部供后续检索
- **知识库构建**：组织结构化的领域知识
- **向量数据库**：将文本转换为向量进行存储和检索
- **记忆架构**：多层次记忆结构（工作记忆/短期记忆/长期记忆）

应用场景：企业知识库、跨会话说期记忆、用户偏好存储

### 4.2 Select -- 选择策略

**解决问题**：如何从海量信息中获取与当前任务最相关的内容？

- **语义检索**：基于语义相似度搜索
- **关键词检索**：基于关键词匹配的精确搜索
- **混合检索**：结合语义和关键词优势
- **重排序（Reranking）**：对检索结果二次排序优化

应用场景：文档问答系统、知识库查询、代码检索

### 4.3 Compress -- 压缩策略

**解决问题**：如何在有限上下文空间中容纳更多有效信息？

- **文本摘要**：将长文档压缩为精炼摘要
- **信息提取**：提取关键事实和实体
- **对话压缩**：压缩冗长的对话历史
- **递进式摘要**：分层次逐步压缩

应用场景：长文档处理、对话历史管理、成本优化

### 4.4 Isolate -- 隔离策略

**解决问题**：如何组织和结构化上下文中的不同信息？

- **XML/标签标记**：用标签区分不同类型内容
- **指令分层**：分层组织系统指令
- **任务隔离**：为不同任务创建独立上下文
- **多智能体编排**：在多智能体间分配上下文

应用场景：复杂提示词设计、多任务系统、智能体协作

### 4.5 策略选择指南

| 场景 | 重点策略 | 原因 |
|------|----------|------|
| 知识密集型问答 | Select | 准确检索是关键 |
| 长期助手 | Write | 需要持久记忆 |
| 成本敏感应用 | Compress | 控制 Token 用量 |
| 复杂指令系统 | Isolate | 清晰的结构很重要 |

> 大多数生产级应用需要综合应用全部四个策略，关键是找到适合具体场景的平衡点。

### 4.6 边界泄漏警告

写入层存储的外部内容、选择层召回的文档、压缩层生成的摘要都可能混入看似"指令"的文本。进入隔离层前应保留来源、权限、时间戳和可信等级；进入最终上下文后，要明确把外部内容标记为"数据"而不是"系统指令"。否则四种策略会在边界处相互污染，导致提示注入、旧事实覆盖新事实或跨用户数据串扰。

## 5. 工具调用与能力扩展

### 5.1 Function Calling 机制

函数调用让 LLM 能够决定调用外部函数。模型不直接执行函数，而是生成结构化的函数调用请求，由应用程序执行：

```
用户请求 --> 应用 --> 模型(请求+工具定义)
         --> 模型返回工具调用请求 --> 应用执行工具 --> 返回结果
         --> 模型根据结果生成最终响应
```

**调用模式**：
- `auto`：模型自主决定是否调用
- `forced`：强制调用特定工具
- `none`：禁止工具调用
- **并行调用**：单次响应中调用多个工具

### 5.2 工具定义与上下文

工具定义作为上下文的一部分传递给模型，占用 Token。需要在能力丰富性和上下文效率之间平衡。好的工具设计原则：
- 工具名称自描述
- `description` 清晰说明用途和使用条件
- `parameters` 使用 JSON Schema 精确定义
- 提供 `enum` 约束可选值范围

### 5.3 Model Context Protocol (MCP)

MCP 是标准化 AI 应用与外部工具交互的开放协议规范。

**核心组件**：
- **Host / AI 应用**：用户授权、上下文聚合和安全边界
- **MCP 客户端**：与 Server 建立有状态会话
- **MCP 服务端**：提供工具、资源和提示模板
- **传输层**：stdio 和 Streamable HTTP

**三大基础构件**：

| 构件 | 说明 | 上下文工程价值 |
|------|------|--------------|
| **Tools** | 可执行的函数 | 扩展模型能力，动态获取和操作上下文 |
| **Resources** | 可读取的数据源 | 多源融合，实时数据获取 |
| **Prompts** | 预定义提示模板 | 标准化上下文呈现，版本管理和复用 |

**MCP 与上下文工程的三层架构**：

```
[查询理解与规划] <-- MCP Prompts (标准化)
[上下文获取]     <-- MCP Resources (多源融合)
[上下文变换]     <-- MCP Tools (动态操作：压缩/过滤/增强/翻译)
[推理与生成]
```

MCP 使上下文工程从静态的向量检索演进到**动态、可组合、可扩展**的系统。

## 6. 智能体上下文管理

### 6.1 为什么上下文是智能体的核心

与普通对话不同，智能体需要在**多步执行**中维持一致的上下文。Agent 失败往往不是因为推理能力不足，而是因为：

1. 关键信息在执行过程中被遗忘（上下文管理不当）
2. 环境状态变化，但智能体仍基于过时信息决策（上下文不同步）
3. 历史积累过长导致 Token 溢出（上下文压缩不当）

### 6.2 智能体上下文层级

```
+---------------------------------------------+
| 系统层：Agent 定义、角色、约束              |  稳定不变
+---------------------------------------------+
| 任务层：当前目标、成功标准、约束            |  任务级变化
+---------------------------------------------+
| 状态层：进度、环境观察、动态计划            |  频繁更新
+---------------------------------------------+
| 历史层：执行轨迹、观察、决策（可压缩）      |  需要管理
+---------------------------------------------+
| 交互层：当前步骤、即时输入、观察            |  最新最关键
+---------------------------------------------+
```

### 6.3 单智能体的上下文管理

**四大模式在智能体中的应用**：

| 模式 | 解决的核心问题 | 典型技术 |
|------|---------------|---------|
| **Write** | 窗口容量限制 | Scratchpad、外部笔记、长期记忆 |
| **Select** | 注意力分散/成本 | Just-in-time 检索、RAG |
| **Compress** | 历史累积过长 | Compaction、摘要、轨迹剪枝 |
| **Isolate** | 任务复杂度过高 | 多智能体协作、VM 环境卸载 |

### 6.4 多智能体上下文传递

**子智能体上下文隔离**是核心机制 -- 每个子智能体有独立上下文窗口，只返回精选摘要给父智能体：

```
主智能体 (5K tokens)
  |
  +-- 委派: 搜索日志 --> 子智能体A (200K tokens, 处理完整日志)
  |     返回: 3 个异常摘要 (2K tokens)
  |
  +-- 委派: 分析代码 --> 子智能体B (300K tokens, 处理完整代码)
        返回: 2 个性能瓶颈 (1K tokens)
```

**上下文成本对比**（100页 PDF 处理）：
- 单智能体方案：150K+ tokens（全文加载 + 中间输出膨胀）
- 子智能体隔离方案：约 53K tokens（主智能体仅接收摘要），下降约 65%

**上下文共享机制**：
1. **共享黑板模式**：共享记忆库，所有智能体可读写
2. **通信对话模式**：智能体间直接发送消息
3. **链式协作（Chain-of-Agents）**：分段阅读长文档，接力传递要点

**传递策略**：
- 最小必要原则：只传递完成任务所需的最小信息
- 角色专属记忆：每个智能体维护与自身角色相关的私有记忆
- 接口抽象：定义清晰的信息传递 JSON Schema

## 7. 生产环境最佳实践

### 7.1 上下文工程工作流

```
设计 --> 开发 --> 测试 --> 部署 --> 监控 --> 优化 --> (循环)
```

**各阶段要点**：

| 阶段 | 关键活动 |
|------|---------|
| **设计** | 需求分析、架构设计、模型选择、文档化 |
| **开发** | 模块化实现、配置外置、版本管理 |
| **测试** | 单元测试、集成测试、评估测试、CI/CD 集成 |
| **部署** | 渐进式发布（1%->20%->100%）、配置管理 |
| **监控** | Token 用量、响应延迟、错误率实时监控 |
| **优化** | 数据驱动的持续改进、A/B 测试 |

### 7.2 性能优化

**延迟优化**：
- **减少 Token 数量**：压缩上下文、精准检索、移除冗余
- **并行处理**：并行检索多知识库、并行工具调用
- **缓存策略**：嵌入缓存、检索结果缓存、**提示词前缀缓存**
- **流式输出**：改善用户感知延迟

**前缀缓存的上下文排列策略**（关键优化）：

将不变内容放前部，变化内容放末尾：

| 位置 | 内容 | 缓存状态 |
|------|------|---------|
| 1 | 系统提示词（几乎不变） | 命中 |
| 2 | 工具定义（会话内不变） | 命中 |
| 3 | 检索到的文档（每轮可能更新） | 命中/未命中 |
| 4 | 对话历史（每轮追加） | 未命中 |
| 5 | 用户当前输入（每次不同） | 未命中 |

> 缓存命中的 Token 价格通常远低于未命中（如 Anthropic 的缓存命中价格仅为常规输入的 10%）。

**推理性能核心指标**：
- **TTFT**（Time to First Token）：首 Token 延迟，直接反映系统响应速度
- **TPS**（Tokens Per Second）：每秒 Token 生成速度
- **ITL**（Inter-Token Latency）：Token 间延迟，决定流式输出流畅度

### 7.3 成本控制

**分层模型策略**：根据任务复杂度路由到不同模型
- 简单任务 --> 小模型（低成本）
- 中等任务 --> 中等模型
- 复杂任务 --> 大模型（高能力）

**模型隔离与缓存穿透陷阱**：在积累了大量 Token 的会话中，切换到小模型会导致缓存全部失效（全量 Prefill 重算），此时留在预热完备的大模型中利用缓存复用可能更便宜更快。

**Token 成本优化方向**：

| 方向 | 方法 |
|------|------|
| 减少输入 | 压缩、精简提示词、精准检索 |
| 减少输出 | 控制输出长度、格式约束 |
| 模型选择 | 简单任务用小模型 |
| 缓存复用 | 利用 prompt 前缀缓存 |

### 7.4 可观测性与调试

**关键监控指标**：

| 指标 | 说明 |
|------|------|
| 上下文 Token 数 | 每次请求的上下文大小 |
| 检索延迟 | 检索操作耗时 |
| 检索命中率 | 检索到相关结果的比例 |
| 压缩率 | 压缩后/压缩前的比例 |
| 成本/请求 | 单次请求成本 |

**OpenTelemetry 集成**：
- **Spans**：记录每个操作的时间段和上下文
- **Traces**：通过 Trace ID 关联完整执行链路
- **AI 特定语义**（OpenInference）：检索 Spans、工具调用 Spans、Token 使用情况

**请求追踪示例**：
```
request_123
+-- 接收请求 [0ms]
+-- 查询处理 [10ms]
+-- 知识检索 [120ms]
|   +-- 嵌入计算 [30ms]
|   +-- 向量搜索 [90ms]
+-- 重排序 [50ms]
+-- 上下文构建 [20ms]
+-- 模型调用 [800ms]
+-- 响应返回 [1000ms]
```

### 7.5 生产级查询引擎参考架构

生产级查询引擎的 10 步处理管道：

1. **记忆预取** -- 异步加载会话相关的持久化记忆
2. **技能发现** -- 动态构建可用工具集合
3. **工具结果预算分配** -- 根据 Token 预算限制工具返回规模
4. **历史裁剪** -- 基于重要性和时间衰减删除不必要历史
5. **微观压缩** -- 轻量级压缩（删除冗余空白、合并相邻同类消息）
6. **上下文折叠投影** -- 预测最终上下文大小，判断是否需要更激进压缩
7. **自动压缩** -- 使用 LLM 对历史消息进行摘要压缩
8. **API 调用** -- 向模型发送优化后的请求
9. **工具执行** -- 并行执行模型返回的工具调用
10. **停止钩子** -- 清理、记录、保存关键状态

### 7.6 安全与治理

- **权限过滤**：基于用户角色的文档访问控制（ACL）
- **来源追踪**：每条上下文信息标注来源和可信度
- **提示注入防御**：用户输入与系统指令严格隔离
- **成本预算**：设置每日预算上限和自动限流
- **审计日志**：完整记录上下文构建和模型交互过程
