# 多租户网络隔离

> 中文简称：多租户网络隔离

> **一句话理解**: 共享 GPU 集群里，别人的实验流量不该有本事挤掉你的生产训练——隔离强度从「各买各的交换机」到「各走各的队列」层层递减。

---

## 一、隔离层级与选型

| **隔离层级** | **机制** | **隔离强度** | **适用场景** | **漏洞面** |
|---|---|---|---|---|
| 物理平面隔离 | 独立交换机与布线，独立故障域 | 最强（性能与故障双重隔离） | 生产 vs 实验、训练网 vs 推理网分平面 | 成本最高；平面间如有共享上行链路仍可能互相影响 |
| IB PKey 分区 | 子网管理器划分区，限制端口间可通信关系 | 强（可达性硬隔离） | IB 计算网内的租户/业务分组 | 默认 PKey 配置过宽会放开全互通 |
| VLAN + VRF | 以太二层分段 + 三层路由域隔离 | 中（可达性隔离，性能弱隔离） | RoCE/以太计算网与管理网分段 | VLAN 跳跃、路由泄漏；排队与缓冲仍共享 |
| QoS 队列软隔离 | DSCP→队列映射 + 调度权重 | 弱（只隔离带宽份额，不隔离故障域） | 同一物理网内保训练队、限背景流量 | 队列/缓冲被打满时仍互相影响；依赖遥测发现 |

选型逻辑：先问「要不要故障域隔离」，再问「要不要性能隔离」。两者都要 → 物理平面；只要可达性隔离 → PKey/VLAN；预算只允许共享 → 至少把 QoS 与配额做扎实，并接受「大故障一起扛」的现实。

隔离强度与成本的关系不是线性：从 VLAN 到 PKey 几乎不加硬件，从 PKey 到分平面则直接翻倍 leaf/spine 投资——选型实质是在为「最坏情况下的互相影响」定价。

三类典型平台的落点：科研共享集群多取 VLAN + 配额（成本优先）；商用算力平台按大客户分平面（SLA 优先）；训推一体的自建集群按业务分平面或至少分队列（时延优先）。

演进路径：多数平台从 VLAN + QoS 起步，随租户数与 SLA 要求提升逐步分平面；一步到位的物理隔离只在租户数少、需求明确时划算。

## 二、QoS 保障训练流量

训练流量是「大象流 + 周期性突发」：allreduce 阶段瞬时打满链路，计算阶段静默。保障策略三件套：

- DSCP→队列映射：训练 RoCE 流量统一打标，交换机映射到专用高优先队列，与背景流量分道；
- 带宽预留：高优队列配最小带宽保障 + 加权调度，背景流量再大也挤不掉训练的份额；
- burst 容忍：训练的瞬时突发要留足队列缓冲（headroom），否则突发瞬间被限流反而引发 pause 扩散；
- 队列映射核查：端侧打标值、交换机 TC 映射、队列计数器三者对齐验证，任一环节错位等于没做 QoS；
- 演练常态化：QoS 参数随租户负载结构变化逐季复验，负载变了而参数没变，保障会悄悄失效。

```
# 形态示例（具体命令随厂商 CLI 而异）
# 端侧：RoCE 流量统一打标 DSCP 26；cma_roce_tos 或网卡工具设置
# 交换机：DSCP 26 → TC3 高优先队列；TC3 配 DWRR 权重 70 + 最小带宽保障
# 缓冲：TC3 预留 headroom 容忍 allreduce 突发，其余队列共享剩余缓冲
```

验证命令：`mlnx_qos -i <dev>` 看端侧打标与 PFC 状态，交换机侧核对 TC 映射与队列计数器——两头都要有可见性，只信配置不信计数是 QoS 审计的大忌。

核查口径：QoS 只在拥塞时体现价值——平时看不出来，必须在人为灌背景流量的演练中验证「训练吞吐不降」，演练结果进变更档案。

## 三、训推混部的流量隔离

训练与推理对网络的要求不同：训练吃带宽、能容忍排队；推理对尾延迟敏感——TP 跨节点的一步通信变慢，整个请求的延迟就被拉长。混部时按两条路线走：

- 分区路线：同一计算网内用 PKey/VLAN 把训练与推理划成两个分区，互联只留受控的必要路径；
- 分平面路线：训练与推理各自独立计算平面，物理上不共享 leaf/spine，成本换确定性；
- 无论哪条路线，推理流量必须与训练大象流隔离队列，防止 allreduce 突发造成推理 P99 抖动——用户体感的「卡顿」往往来自这类抖动，而不是平均延迟上升。

推理侧额外的保护手段：推理队列配更严格的时延保障（如优先级调度而非加权轮询）、KV 转移与 token 流量分队列、以及为 PD 分离场景的 KV 搬运预留突发带宽。监控上训推两侧的链路指标分账展示，混部劣化时能立刻分辨是哪一侧引入的压力。

判定标准：混部是否合格看两个指标——训练吞吐不降、推理 P99 不抖；两个都达标才叫隔离成功，只保一头等于没隔离。

## 四、安全边界与准入控制

- 管理面与租户面隔离：交换机与带外管理网独立 VRF 或物理分离，租户网络里不允许出现管理地址；
- 带外网准入控制：管理网只允许跳板机访问，设备登录走堡垒机与双因素，配置变更走审批流；
- 跨租户流量默认拒绝：安全组/ACL 白名单化，租户间需要互通时显式开通并登记有效期，到期自动回收；
- 采集面隔离：SNMP/telemetry 的采集网段与租户面隔离，避免采集凭证暴露在租户可达的路径上；
- 变更面收敛：租户侧的自服务只能改自己的 QoS 配额，不能触达网络设备配置；
- 租户侧可观测性边界：租户只能看到自己的流量与队列指标，全局视图不出管理面；
- 定期渗透验证：按季度做一次「跨租户可达性」扫描，验证默认拒绝真的在拒绝。

## 五、配额与可视化

隔离做没做到位，最终靠数据说话：

- per-tenant 流量统计：每个租户/队列的吞吐、pause、ECN 标记比例独立成曲线；
- 公平性审计：定期核对「份额配置 vs 实际占用」，发现某租户长期超配或某队列长期饿死；
- 配额落地：配额不只写在调度器里，也要落在网络（队列权重/限速）上——否则拥塞时刻调度器的承诺不生效；
- 异常联动：租户维度流量突增、pattern 突变接入告警，与网络遥测基线共用一套采集（见网络遥测与监控基线）；
- 峰值与均值分开管：均值配额防长期侵占，峰值限速防瞬时打爆，两者缺一；
- 计费钩子：per-tenant 流量数据同时服务审计与计费，一套采集两用。

## 六、失败案例定性

共享集群的典型事故：实验租户在共享计算网上跑大规模打流测试，流量打爆 leaf-spine 之间的共享链路，同网的生产训练任务 allreduce 掉速、MFU 骤降；排查半天硬件毫无问题，交换机 counter 只有正常的排队计数。

时间线特征：事故集中在实验打流的时段，生产训练同时间的 busbw 曲线同步凹陷——时间相关性是定性共享链路事故的关键证据。

定性结论：

- 直接原因：共享链路无带宽保障，实验流量可以无界侵占生产流量；
- 根因：隔离层级选低了——只做了 VLAN 可达性隔离，没做性能隔离，也没有配额限速；
- 整改：实验流量限速入网 + 训练队列 QoS 保障 + 租户级流量可视化上线，三件套缺一不可；
- 流程教训：新增租户/新类型的负载（尤其是打流、压测类）必须走网络影响评估，而不是只过调度器配额；
- 制度配套：压测、打流类负载默认认定为高风险操作，需提前报备窗口与限速参数。

案例的普适教训：共享资源的故障不是技术问题而是治理问题——QoS 三件套技术上早就存在，缺的是「谁批准实验流量上生产网」这道流程门。
