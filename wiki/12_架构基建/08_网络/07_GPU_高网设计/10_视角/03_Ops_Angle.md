# 网络运维视角：高网的巡检、分级与协作

> 中文简称：网络运维视角

> **一句话理解**: GPU 集群的网络运维不是「坏了再修」，而是用巡检把故障消灭在降速阶段、用分级把处置变成肌肉记忆。

---

## 一、巡检体系：日/周/月/季

巡检目标只有一个：把故障从「突发断链」提前到「趋势漂移」阶段处理。

| **频率** | **巡检项** | **工具/指标** | **阈值参考** |
| --- | --- | --- | --- |
| 日 | 告警面清理；端口 CRC/pause 计数增量 | ethtool -S、ibqueryport、Prometheus | CRC 日增量 > 0 即建单跟踪 |
| 周 | 光功率趋势；容量水位（端口利用率 P95） | DOM/DDM 读取 | 周漂移 > 1dB 或逼近标称边界 |
| 月 | 全组 nccl-tests 回归；备件盘点 | all_reduce_perf 基线库比对 | busbw 相对基线跌幅 > 5% 告警 |
| 季 | 故障演练（拔线、重启交换机、注入链路降速）；RMA 复盘 | 演练剧本 + 复盘会 | 恢复时间与预案有效性 |

基线库是巡检的灵魂：没有历史基线，月度回归无从判定「跌了」。采集项与留存规范见 [[12_架构基建/08_网络/07_GPU_高网设计/07_运维故障/06_Telemetry_Baseline_Monitoring|遥测基线监控]]。

订阅分级同样要做进体系：CRC/pause 进日告警，光功率只进周报，容量水位进月报——告警面干净，人才会真的看告警。

```bash
# 日巡检最小命令集（抽样到每台交换机/每批模块）
ethtool -S <netdev> | grep -Ei "crc|pause|drop"   # 错误计数快照
ibqueryport -G <guid> 1                            # 端口状态与速率
cat /sys/class/net/<dev>/statistics/rx_errors      # 兜底计数
```

## 二、故障分级与典型网络 case

| **级别** | **典型 case** | **判定特征** | **处置时限** |
| --- | --- | --- | --- |
| P0 | 整 spine down；二层环路/环风暴 | 多机同时失联 + 交换机日志风暴 | 立即隔离/切换，15 分钟内通报 |
| P1 | 单 rail 劣化（busbw 半速）；PFC 风暴（xoff 洪泛） | nccl-tests 单通道掉档；pause 计数飙升 | 小时级 |
| P2 | 单机网卡降速（400G 掉到 100G）；端口反复 up/down | ibstat Rate 字段变化；链路日志 | 天级 |
| P3 | 光模块光功率漂移；单模块偶发 CRC | DOM 趋势缓变 | 周级换补 |

分级依据是故障分布的统计规律：光模块是第一大故障源（数量多、有源器件、对温度敏感），其次才是线缆接触、交换机端口与整机，详见 [[12_架构基建/08_网络/07_GPU_高网设计/07_运维故障/01_Failure_Distribution_Patterns|故障分布模式]]。P1 里的 PFC 风暴要特别警惕——它常被误判为「慢」而非「坏」，判定靠无损配置审计，见 [[12_架构基建/08_网络/07_GPU_高网设计/07_运维故障/04_Lossless_Config_Audit|无损配置审计]]。

分级的意义是对齐处置节奏：P0 动员所有人、P3 进换补队列，避免小事大动、大事拖延。

## 三、变更管理：阈值灰度、窗口、回滚剧本

三条铁律：**灰度按 1 台 → 1 组 → 全组推进；窗口对齐训练 checkpoint 间隙或空闲时段；回滚剧本在变更前写好并演练过**。

```text
变更单示例：spine-12 固件升级 3.9.1400 → 3.9.1500
灰度：先 spine-12 单台 → 观察 24h → 同批次 4 台 → 观察 48h → 全组
窗口：周四 02:00–04:00（训练大队 checkpoint 后的暂停窗口）
基线：变更前全组 all_reduce_perf 存档（busbw 中位数 + P99）
回滚判定：任一回归指标跌幅 > 5%，或出现新 P1 以上告警即回滚
```

固件与阈值类变更（PFC 水位、ECN 门限）一律走同样流程——这类变更的失败模式是「不报错、只变慢」，没有基线对比根本发现不了。

窗口优先级：P0/P1 抢修不受窗口限制，但需双人在场；计划性变更一律走窗口与灰度。

## 四、备件与 RMA 流程

| **环节** | **要点** | **常见坑** |
| --- | --- | --- |
| 库存水位 | 光模块按故障率最高备足（通常远多于交换机板卡） | 只按整机台数备、忽略模块级 |
| 故障件留存 | 模块序列号 + DOM 快照 + 端口日志一并归档 | 只回传器件不传数据，厂家无法归因 |
| RMA 周转 | 到场/换新时限写进 SLA 并按月对账 | 周转期长导致库存水位穿透 |
| 复盘归因 | 厂家分析报告回流到巡检阈值 | 换完就算修完，同类故障重复发生 |

备件率的定法：按近 12 个月分器件故障率 × RMA 周转天数折算安全库存，每季度随盘点校正一次。备件策略与光模块失效模式的对应关系见 [[12_架构基建/08_网络/07_GPU_高网设计/02_物理层硬件/03_Optical_Modules|光模块]]。

## 五、与训练/推理团队的协作界面

「一慢俱慢」谁判定：网络侧用 nccl-tests 回归 + straggler 工具出结论；业务侧提供作业拓扑与 NCCL 日志缩小范围。隔离权责：运维有权隔离故障节点/端口（业务方重拉作业），但以最小影响为原则并同步通报。

| **事项** | **网络运维** | **训练/推理团队** |
| --- | --- | --- |
| 现场保留 | 指导采集 ibstat/计数/日志 | 保留 NCCL 日志与作业现场 |
| 慢链路判定 | 打流与计数证据链 | 提供 rank 拓扑与慢 rank 线索 |
| 隔离决策 | 执行隔离并通报影响面 | 接受重拉、反馈业务影响 |
| 修复验收 | 全组回归 busbw 达标 | 复跑作业确认 MFU/时延恢复 |

例会接口：每周与训练/推理团队过一次慢链路清单，让「慢」有台账、有闭环，而不是散落在各群聊里。训练侧的排查视角见 [[12_架构基建/08_网络/07_GPU_高网设计/10_视角/01_Training_Angle|训练工程师视角]]，推理侧见 [[12_架构基建/08_网络/07_GPU_高网设计/10_视角/02_Inference_Angle|推理工程师视角]]。

## 六、Runbook 骨架：现象→分层命令→判定→处置→复盘

```text
[现象] 1024 卡 allreduce busbw 从 44GB/s 跌到 22GB/s，作业未 hang
[分层命令]
  作业层：NCCL_DEBUG 日志定位慢 rank 所在节点与通道
  主机层：ibstat / ethtool -S 查端口速率与 CRC/pause 增量
  链路层：ib_write_bw 逐链路打流；DOM 读光功率
  交换层：端口计数、ECN/pause 队列、转发表一致性
[判定] spine-07 上联 4 条链路 CRC 增速异常 → 定位到光模块批次
[处置] 隔离受影响端口 → 换模块 → 单链路回归 → 全组回归 → 解除隔离
[复盘] 时间线 / 根因 / 防再发（巡检阈值加密）/ 影响面量化 / 预案修订
```

复盘模板五栏缺一不可：时间线（分钟级）、根因、防再发动作与责任人、影响面量化（GPU·小时）、预案修订项。命令链的完整展开见 [[12_架构基建/08_网络/07_GPU_高网设计/07_运维故障/02_Network_Diagnostics_Command_Chain|网络诊断命令链]] 与 [[12_架构基建/08_网络/05_网络_Diagnostics_命令|网络 Diagnostics 命令]]；慢节点定位方法见 [[12_架构基建/08_网络/07_GPU_高网设计/07_运维故障/03_Straggler_Identification|慢节点定位]]。
