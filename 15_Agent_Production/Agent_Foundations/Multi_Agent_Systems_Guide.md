## 1. 多智能体协作架构

### 1.1 为什么需要多智能体

单体智能体的四大瓶颈:
1. **上下文限制**: 所有角色指令塞进一个 System Prompt, 导致逻辑混乱
2. **幻觉风险**: 缺乏检查机制, 自己产生的错误自己信以为真
3. **能力专业化**: 不同任务需要不同工具和提示词策略
4. **Token 经济性**: 上下文膨胀导致成本激增

**核心洞察**: 架构即政治。设计智能体系统, 实际上是在设计一个人类组织的电子映射。

### 1.2 角色定义与身份构建

每个智能体的完整"身份档案":

| 属性 | 说明 | 示例 |
|------|------|------|
| **Role** | 职位定义 | "首席架构师" |
| **Goal** | 具体 KPI | "设计可扩展的微服务架构" |
| **Backstory** | 背景故事 | "长期从事大型系统开发, 崇尚简洁" |
| **Tools** | 专属工具权限 | HR 可读工资单, Coding 不可 |
| **Constraints** | 行为边界 | "不得讨论竞争对手产品" |

> 背景故事显著影响 LLM 输出风格: "资深律师" 比 "实习生" 输出更谨慎、更规范。

### 1.3 四种协作拓扑

#### (1) 顺序式架构 (Sequential)

```
User -> Product Manager -> Tech Lead -> Developer -> Tester -> Result
```

- 上一个 Output = 下一个 Input
- 线性、确定性
- **局限**: 开环系统, 源头错误级联, 无反馈修正

#### (2) 层级式架构 (Hierarchical)

```
User -> Supervisor (大脑, 不干具体活)
         |-- Search Agent
         |-- Write Agent
         |-- Code Agent
       <- 最终结果
```

- **Supervisor**: 分析需求, 决定任务路由
- **Worker**: 只执行分配的具体指令
- **适用**: 复杂非线性任务, 需要动态调整

#### (3) 联合协作式 (Joint Collaborative)

- 广播通信: A 发言, 其他都能接收
- 轮次控制: Controller 决定发言顺序
- 共识达成: 多轮讨论形成最终决策
- **风险**: 易跑题、死循环争论、Token 消耗高

#### (4) 混合智能体架构 (MoA - Mixture of Agents)

- **提议层**: 多模型/策略并行生成候选解
- **聚合层**: 对比、去噪、融合, 输出最终答案
- **价值**: 提升稳健性与覆盖面
- **代价**: 更高成本与编排复杂度

### 1.4 两种最常见的工程协作模式

#### Orchestrator-Subagent (最主流)

- **Orchestrator**: 理解总目标, 拆解任务, 分派子任务, 汇总结果
- **Subagent**: 只处理负责的子问题

**优势**: 全局目标不漂移, 专业化分工, 易做权限控制
**代价**: Orchestrator 成瓶颈, 通信开销高, 拆解不好下游偏题

**生产案例: Anthropic Research 系统** (2025-06):
- LeadResearcher + 3-5 个并行 Subagents
- 多智能体相对单智能体提升 90.2% (内部评测)
- Token 成本: 普通 agent ~4x, multi-agent research ~15x
- 适合宽度优先查询和信息量超出单上下文的任务

#### Peer-to-Peer

- 智能体间相对平等, 通过协商/辩论/投票达成共识
- 适合: 多视角碰撞、互相纠错、探索性任务
- 工程难点: 发言顺序和仲裁更难, 观测/调试/计费更复杂

**选型原则**: "必须交付、可控回放、可审计" -> 先 Orchestrator-Subagent

### 1.5 架构选型决策矩阵

| 架构 | 复杂度 | 延迟 | 成本 | 适用场景 |
|------|--------|------|------|---------|
| 顺序式 | 低 | 低 | 低 | 固定流程、SOP 任务 |
| 层级式 | 中 | 中 | 中 | 动态路由、复杂决策 |
| 联合协作 | 高 | 高 | 高 | 创意生成、头脑风暴 |
| 混合 (MoA) | 中 | 中 | 中 | 质量优先、模型集成 |

### 1.6 系统级失败模式

多智能体常见的四类系统性故障:

1. **协同饥饿**: 多 Agent 互相等待前置输出, 全局死锁
2. **目标漂移**: 多轮接力中初始意图被逐层稀释或扭曲
3. **无限回文**: 审查者与执行者因判定标准不一致陷入死循环
4. **责任推诿**: 边界定义不清, 模糊任务被跳过

## 2. 角色分工与 SOP 流程编排

### 2.1 SOP 核心要素

一个完整的标准作业程序 (SOP) 包含:

1. **触发条件**: 什么情况下启动
2. **参与角色**: 哪些智能体参与
3. **执行步骤**: 每一步做什么、谁做
4. **交接规则**: 步骤间如何传递信息
5. **终止条件**: 什么情况下结束

**工程化实践示例** (软件开发 SOP):

| 角色 | 输入 | 输出 | 质量标准 |
|------|------|------|---------|
| 产品经理 | 用户原始需求 | PRD 文档 | 需求完整性 |
| 架构师 | PRD | 设计文档 | 架构合理性 |
| 工程师 | 设计文档 | 可运行代码 | 代码质量 |
| QA | 代码 | 测试报告 | 测试覆盖与回归 |

### 2.2 工具权限分配 -- 最小权限原则

```python
PERMISSION_MATRIX = {
    "product_manager": ["search_web", "read_document", "create_prd"],
    "architect":       ["search_code", "draw_diagram", "analyze_dependency"],
    "developer":       ["write_code", "run_tests", "git_commit"],
    "qa":              ["run_tests", "generate_report", "create_issue"],
}
```

### 2.3 角色设计的常见失败模式

| 编号 | 失败模式 | 描述 |
|------|---------|------|
| FM-1.1 | 违反任务规范 | 未遵循用户指定的任务要求 |
| FM-1.2 | 违反角色规范 | 行为超出角色边界 |
| FM-1.3 | 步骤重复 | 陷入重复执行相同步骤的循环 |
| FM-1.4 | 上下文丢失 | 关键信息在执行中被遗漏或覆盖 |
| FM-1.5 | 停止条件不清 | 无法判断任务何时完成 |

> 实践发现: 不更换模型, 仅改进角色规范 (输入输出、约束、停止条件、交接模板), 整体成功率就能显著提升。系统设计往往比模型选择更重要。

### 2.4 高度专业化角色案例: CitationAgent

Anthropic Research 系统中的 CitationAgent:
- 职责: 文档解析与引文映射
- 约束: 只用提供的研究文档, 严禁创造未出现的事实
- 优先级: 准确性 > 完整性 (宁可遗漏, 不要错引)
- **工程价值**: 责任清晰 + 质量保证 + 可追溯性

## 3. 动态组队与自适应编排

### 3.1 动态编排的核心流程

```
任务分析 (需要什么技能) -> 能力注册 (智能体声明能力) -> 智能匹配 (最优团队) -> 自适应执行
```

**智能体能力注册表**:

```python
AGENT_REGISTRY = {
    "researcher": AgentCapability(
        name="资深研究员",
        skills=["搜索", "信息整合", "文献分析"],
        expertise_level=0.9, cost_per_task=0.05
    ),
    "coder": AgentCapability(
        name="Python 专家",
        skills=["编程", "代码测试", "代码审查"],
        expertise_level=0.85, cost_per_task=0.08
    ),
}
```

### 3.2 编排策略

**规则编排** (冷启动):

```python
ORCHESTRATION_RULES = {
    "contains_code": ["coder", "reviewer"],
    "requires_research": ["researcher"],
    "needs_writing": ["writer", "editor"],
}
```

**反馈驱动自适应** (长期运行):
- 失败驱动回退: 连续失败 -> 升级到更强角色
- 成本驱动降级: 低风险 -> 切换低成本成员
- 风控阈值: 异常调用 -> 强制人工审批

**LLM 智能编排**: 让 LLM 根据任务描述和成员能力列表选择最优团队

### 3.3 MoA 边界说明

Mixture of Agents 更像**答案聚合器**, 不是动态组队本身:
- 动态组队: 运行时按任务临时招募团队成员
- MoA: 固定层次结构, 综合多个提议
- MoA 可以嵌入动态组队系统作为答案融合器

## 4. 人机协作 (Human-in-the-Loop)

### 4.1 何时让人类介入

**必须介入的场景**:
- 高风险操作 (删除数据、发送邮件、转账)
- 歧义决策 (多种合理方案需取舍)
- 伦理/合规判断
- 智能体置信度低于阈值

**介入模式**:
- 审批节点: 关键操作前询问确认
- 信息补充: 缺少必要信息时请求输入
- 进度反馈: 实时展示执行状态
- 回退/取消: 执行初期允许撤销

### 4.2 HITL 设计原则

1. **渐进式授权**: 从低权限开始, 逐步扩大
2. **可解释性**: 向用户解释为什么需要确认
3. **最小打扰**: 只在真正需要时才打断用户
4. **批量确认**: 相似操作合并为一次确认

## 5. 智能体间通信协议

### 5.1 通信方式对比

| 方式 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| **自然语言** | 通用、灵活、可解释 | 语义歧义、Token 浪费、解析困难 | 创意/探索性任务 |
| **结构化 JSON** | 语义明确、易解析 | 需预定义 Schema, 灵活性差 | 生产级任务流 |
| **共享黑板** | 解耦、支持异步 | 需状态同步机制 | 长周期任务 |

### 5.2 结构化消息协议设计

```json
{
  "message_type": "task_assignment",
  "from": "PM_Agent",
  "to": "Dev_Agent",
  "payload": {
    "task_id": "uuid",
    "description": "实现用户登录功能",
    "priority": "high",
    "deadline": "2026-06-20T18:00:00Z",
    "constraints": ["必须支持 OAuth2", "添加速率限制"]
  }
}
```

### 5.3 共享状态管理

**黑板架构 (Blackboard)**:
- 所有智能体读写同一个共享数据结构
- 需要锁机制防止并发冲突
- 适合紧密耦合的协作任务

### 5.4 通信最佳实践

1. **明确消息类型**: task_assignment / status_update / query / result
2. **强制结构化**: 在 System Prompt 中约束 JSON 输出
3. **去冗余**: 禁止客套话, 减少 Token 浪费
4. **超时与回退**: 设定消息等待超时, 防止死锁

## 6. 社会模拟与涌现行为

### 6.1 斯坦福小镇: Generative Agents

25 个智能体在虚拟小镇中长期运行, 展现出类人社会行为:

**核心技术架构**:
- **记忆流**: 时间序列记录, 综合 Recency + Importance + Relevance 打分
- **反思机制**: 定期审视记忆, 生成高层次抽象认知
- **规划与反应**: 基于记忆和反思制定每日计划, 动态响应环境

**涌现行为实证** (论文摘要可核验):
- 情人节派对的自主扩散: 智能体自行传播邀请、讨论参与、相约前往
- 关系网络的自发形成
- 时空协同 (在合适时间协调到场)

> 涌现的工程前提: 大容量上下文 + 精准记忆检索 + 高并发调度 + 全局状态一致性

### 6.2 博弈论视角

#### 合作博弈
- 全局奖励共享, 核心挑战: **信用分配问题**
- 解决方案: 夏普利值、个体贡献追踪、对抗性评估

#### 非合作博弈

| 场景 | A 目标 | B 目标 | 均衡 |
|------|--------|--------|------|
| 自动谈判 | 压低价格 | 抬高价格 | 纳什均衡 |
| 资源竞争 | 更多计算资源 | 更多计算资源 | 资源分配均衡 |
| 广告竞价 | 最低价展示 | 最低价展示 | 第二价格拍卖 |

#### 去中心化 Swarm 架构

- 无中心控制, 局部交互, 自组织
- 通过 Handoff (交接) 传递任务
- 容错性强: 单个失败不影响整体
- 适合: 大规模客服、数据清洗、分布式采集

## 7. A2A 互操作协议

### 7.1 两类协议的区别

| 维度 | 工具连接协议 (MCP) | 智能体互操作协议 (A2A) |
|------|-------------------|---------------------|
| 连接对象 | Agent <-> Tool/Data | Agent <-> Agent |
| 协议目的 | 获得外部能力 | 协作完成任务 |
| 交互粒度 | 原子操作 | 任务级工作单元 |
| 核心抽象 | Resources, Tools, Prompts | 能力描述, 任务, 进度, 审计 |
| 生命周期 | 请求-响应 | 跨秒/分钟/小时的任务流 |

### 7.2 A2A 协议核心组件

1. **能力描述文档**: 身份、用途、任务类型、输入输出 Schema、认证方式
2. **任务模型**: id, type, status (queued/in_progress/done/failed), payload (ContextPack), trace_id
3. **进度回传**: 轮询 (pull) 或流式 (SSE/WebSocket push)
4. **审计链**: 全链路 trace_id 透传, 与 ContextPack.trace_id 绑定

### 7.3 互操作最佳实践

- 复用 ContextPack 作为任务载荷
- trace_id 全链路透传 (上游规划 -> 下游执行)
- 任务状态机标准化 (queued -> in_progress -> done/failed/canceled)
- 增量回传: 长任务支持进度推送

## 8. 评估体系: AgentBench 与基准测试

### 8.1 评估核心术语

| 术语 | 定义 |
|------|------|
| **Task** | 单独测试, 含输入和成功标准 |
| **Trial** | 对任务的一次尝试 |
| **Grader** | 对性能某方面评分的逻辑 |
| **Trace** | 一次试验的完整记录 |
| **Evaluation Harness** | 端到端运行评估的基础设施 |

### 8.2 评估独特挑战

- **解法非唯一性**: "订票" 可走航班/高铁/邮件
- **环境副作用**: 操作改变世界状态, 需沙箱 + 状态重置
- **多维度权衡**: 成功率 + 效率 + 安全性 + 鲁棒性

### 8.3 三类评估器

| 类型 | 方法 | 优势 | 劣势 |
|------|------|------|------|
| **代码评估器** | 字符串匹配、单元测试、状态验证 | 快速、客观、可复现 | 对变体脆弱 |
| **模型评估器** | LLM-as-Judge, 量规评分 | 灵活、处理开放任务 | 非确定性、昂贵 |
| **人工评估器** | SME 审查、A/B 测试 | 黄金标准 | 昂贵、缓慢 |

### 8.4 三个测试层次

1. **单元测试**: 工具选择、函数调用格式 (pytest)
2. **轨迹评估**: LLM-as-Judge 评审逻辑性、幻觉、冗余
3. **端到端评估**: 沙箱中验证最终结果

### 8.5 能力评估 vs 回归评估

| 类型 | 初始通过率 | 作用 |
|------|-----------|------|
| **能力评估** | 20-50% | 指导研发方向, 测试能力上限 |
| **回归评估** | 95-99% | 确保已有功能不变差 |

> 随着模型提升, 能力评估中的高通过率任务可"毕业"成为回归评估。

## 9. 持续学习与进化

### 9.1 三条进化路径

| 路径 | 机制 | 是否更新权重 | 成本 |
|------|------|------------|------|
| **运行时适配** | RAG, 记忆检索, 路由, 上下文拼接 | 否 | 低 |
| **配置层优化** | 修改 System Prompt, 工具策略, 工作流配置 | 否 | 中 |
| **权重层持续学习** | 持续预训练, SFT, DPO, RL | 是 | 高 |

### 9.2 经验回放 (运行时适配)

核心: 成功轨迹 -> 压缩为可检索经验 -> 写入外部记忆 -> 下次遇到类似任务时回放

```
经验提取 -> 存储 (Task_Embedding, Key_Insight) -> 回放 (检索并注入 System Prompt)
```

### 9.3 自动提示词优化 (配置层)

1. 收集失败案例
2. 高级智能体分析失败原因
3. 提出 Prompt 修改建议
4. 自动/半自动更新配置

**SkillOpt 方法**: 把 Skill 文档视为可训练状态, scored rollout -> 受控编辑 -> held-out 验证决定是否接受

### 9.4 数据飞轮 (权重层)

冷启动 (通用高能力模型 V1) -> 收集交互数据 -> 人工标注 + 筛选 -> 持续训练 (SFT/DPO) -> 部署 V2 -> 循环
