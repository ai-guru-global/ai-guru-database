# Vibe Coding 生产环境实践指南

> **一句话理解**: 在生产环境中应用 Vibe Coding 不是让 AI 随意写代码，而是建立一套"AI 生成 → 自动化验证 → 分级审查 → 灰度发布"的工程化体系，确保 AI 加速开发的同时不牺牲质量和安全。

## 3. 场景化实战方案

### 3.1 场景一: RESTful API 开发

```
场景: 开发用户管理API
═══════════════════════════════════════════════════════════════

适合度: A级 (完全AI化)

Step 1: 描述需求 (STAR格式)
───────────────────────────
Situation: "在一个NestJS + TypeORM + PostgreSQL项目中"

Task: "实现用户管理API，包含以下端点:
- POST /users (注册)
- GET /users/:id (查询)
- PUT /users/:id (更新)
- DELETE /users/:id (软删除)"

Architecture: "使用Repository模式，
Service层处理业务逻辑，
Controller处理HTTP，
DTO使用class-validator验证，
统一使用AppResponse<T>响应格式"

Requirements:
"1. 密码使用bcrypt (rounds=12)
2. 邮箱唯一性校验
3. 分页查询支持 (page, limit, sort)
4. 软删除使用deletedAt字段
5. 单元测试覆盖所有Service方法
6. 集成测试覆盖所有API端点"

Step 2: AI生成 → 自动审查
───────────────────────────
AI生成文件:
├── src/users/users.controller.ts
├── src/users/users.service.ts
├── src/users/users.repository.ts
├── src/users/dto/*.ts
├── src/users/entities/user.entity.ts
├── test/users/*.spec.ts
└── test/users/*.e2e-spec.ts

Step 3: 验证清单
───────────────────────────
自动化检查:
├── □ lint通过
├── □ 类型检查通过
├── □ 单元测试通过 (覆盖率>80%)
├── □ 安全扫描无高危
└── □ API文档自动生成正确

人工检查:
├── □ 密码是否确实bcrypt加密
├── □ SQL注入防护 (TypeORM参数化)
├── □ 输入验证完整
├── □ 错误信息不泄露内部细节
└── □ 分页逻辑正确 (防越界)

预计耗时: 2-3小时 (传统: 1-2天)
```

### 3.3 场景三: 数据库迁移和重构

```
场景: 将用户系统从MySQL迁移到PostgreSQL
═══════════════════════════════════════════════════════════════

适合度: B级 (AI+强化审查)

Phase 1: 差异分析 (AI辅助)
───────────────────────────
"分析MySQL和PostgreSQL的SQL差异:
1. 数据类型映射 (TINYINT→SMALLINT, DATETIME→TIMESTAMP)
2. 自增ID → SERIAL/IDENTITY
3. LIMIT OFFSET → FETCH NEXT
4. GROUP BY严格模式
5. 字符串连接 (CONCAT→||)
6. JSON处理函数差异"

Phase 2: 迁移脚本生成 (AI生成+人工审查)
───────────────────────────
"生成迁移策略:
1. 创建PostgreSQL schema
2. 数据类型转换脚本
3. 数据迁移脚本 (分批迁移, 每批10000行)
4. 数据验证脚本 (行数/校验和对比)
5. 回滚脚本"

Phase 3: 验证
───────────────────────────
├── 在staging环境完整演练
├── 数据完整性验证
├── 性能基准对比
├── 应用层兼容性测试
└── 回滚演练

关键原则:
├── 永远不要让AI直接操作生产数据库
├── 所有SQL脚本必须人工审查
├── 必须在staging完整验证
└── 准备回滚方案

预计耗时: 3-5天 (传统: 1-2周)
```

## 4. 安全工程体系

### 4.1 AI代码安全审查流程

```
AI生成代码安全审查:
═══════════════════════════════════════════════════════════════

Layer 1: 自动化扫描 (每次提交)
├── SAST (静态应用安全测试)
│   ├── CodeQL / SonarQube
│   ├── 检测: SQL注入/XSS/路径遍历/硬编码密钥
│   └── AI代码标记: 高优先级扫描
├── SCA (软件组成分析)
│   ├── Snyk / Dependabot
│   ├── 检测: 已知漏洞/许可证冲突
│   └── AI引入的依赖额外审查
└── Secret Detection
    ├── GitGuardian / TruffleHog
    ├── 检测: API Key/密码/证书
    └── AI代码高概率泄露检测

Layer 2: 规则化审查 (每个PR)
├── OWASP Top 10 检查
│   ├── A01: 权限控制失效
│   ├── A02: 加密失败
│   ├── A03: 注入
│   ├── A05: 安全配置错误
│   └── A07: 身份认证失败
├── AI特有风险检查
│   ├── AI是否使用了过时的API
│   ├── AI是否忽略了安全配置
│   ├── AI是否硬编码了敏感值
│   └── AI是否跳过了输入验证
└── 合规性检查
    ├── GDPR数据保护
    ├── PCI-DSS (支付相关)
    └── SOC2 (企业环境)

Layer 3: 人工安全审查 (高风险代码)
├── 支付处理代码
├── 用户认证代码
├── 数据加密代码
├── 权限控制代码
├── 第三方集成代码
└── 基础设施配置代码
```

### 4.2 敏感数据处理

```
AI编码时敏感信息保护:
═══════════════════════════════════════════════════════════════

原则: 永远不要将真实数据发给AI

DO:
├── 使用模拟数据 (mock data)
├── 使用环境变量占位符
├── 使用示例数据库 (不含真实数据)
├── 在规则文件中标注敏感字段
└── 使用.local文件排除真实配置

DON'T:
├── 不要粘贴真实API Key
├── 不要使用真实用户数据
├── 不要分享生产数据库schema
├── 不要在提示中包含日志中的敏感数据
└── 不要让AI访问生产环境

.env.example (可以分享):
───────────────────────────
DATABASE_URL=postgresql://user:password@localhost:5432/mydb
REDIS_URL=redis://localhost:6379
JWT_SECRET=your-secret-key
STRIPE_API_KEY=sk_test_xxx

.env (绝不分享):
───────────────────────────
DATABASE_URL=postgresql://prod_user:r3al_p@ss@prod-db:5432/mydb
JWT_SECRET=a7f3b2c1d4e5...
```

### 6.1 AI代码技术债分类

```
AI代码技术债类型:
═══════════════════════════════════════════════════════════════

类型1: 过度工程 (Over-Engineering)
├── AI倾向于添加"看似专业"但不需要的抽象层
├── 识别: 不必要的接口、过多的泛型、过度的错误处理
├── 处理: YAGNI原则，删除未使用的抽象
└── 预防: 在提示中明确"保持简单，不要过度抽象"

类型2: 不一致模式 (Inconsistent Patterns)
├── 不同会话中AI可能使用不同的实现模式
├── 识别: 同一功能多种实现方式
├── 处理: 统一为项目标准模式
└── 预防: 规则文件明确指定设计模式

类型3: 幻觉依赖 (Hallucinated Dependencies)
├── AI可能引用不存在的API或已废弃的方法
├── 识别: 编译错误、运行时错误
├── 处理: 验证所有API和依赖
└── 预防: 指定确切的库版本

类型4: 隐式假设 (Hidden Assumptions)
├── AI基于训练数据做假设，可能与项目不符
├── 识别: 不符合项目约定的代码
├── 处理: 审查每个假设
└── 预防: 在提示中明确约束条件

类型5: 测试幻觉 (Test Hallucination)
├── AI生成看似完整但实际不测试关键行为的测试
├── 识别: 高覆盖率但低变异杀死率
├── 处理: 变异测试验证测试质量
└── 预防: 要求AI解释每个测试验证了什么
```
