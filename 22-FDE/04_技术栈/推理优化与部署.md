# 推理优化与部署

## FDE 为什么需要推理优化？

政企客户最常见的情况：**有服务器但没有 GPU**。FDE 必须在受限硬件上让 AI 跑起来。

## 核心优化技术

### 1. 模型量化

| 量化方式 | 精度 | 内存节省 | 速度提升 | 质量损失 | 适用场景 |
|---|---|---|---|---|---|
| FP16 | 半精度 | 50% | 1.5x | 极小 | 有 GPU |
| INT8 | 8位整型 | 75% | 2x | 很小 | 通用 |
| INT4 (GPTQ) | 4位 | 87% | 3x | 轻微 | GPU 推理 |
| GGUF Q4_K_M | 混合4位 | 85% | 2-3x | 轻微 | CPU 推理 |
| GGUF Q2_K | 2位 | 93% | 4x | 明显 | 极端受限 |

**FDE 实战建议**：
- CPU 环境首选 **GGUF Q4_K_M**（质量/速度最佳平衡）
- GPU 环境用 **GPTQ INT4** 或 **AWQ**
- 永远留一个 FP16 版本做 baseline 对比

### 2. 推理引擎选型

```
场景决策树：

客户有 GPU？
├── 是 → vLLM（最高吞吐）
│        └── GPU 显存不够？→ vLLM + INT4 量化
└── 否 → 只有 CPU？
         ├── llama.cpp（GGUF 格式，CPU 优化）
         ├── Ollama（基于 llama.cpp，易用）
         └── OpenVINO（Intel CPU 特化）
```

### 3. 批处理与并发

| 技术 | 原理 | 效果 |
|---|---|---|
| Continuous Batching | 动态合并请求 | 吞吐 10x |
| PagedAttention | KV Cache 分页管理 | 显存利用率 2-4x |
| Prefix Caching | 复用 System Prompt KV Cache | 首 token 延迟 -50% |
| Speculative Decoding | 小模型"猜" + 大模型"验证" | 延迟 -30% |

### 4. 缓存策略

```
L1: 精确匹配缓存
用户问"请假流程" → 完全匹配 → 直接返回缓存
命中率：10-20%，延迟：<1ms

L2: 语义相似缓存
用户问"怎么请假" ≈ "请假流程" → 相似度>0.95 → 返回缓存
命中率：20-30%，延迟：<10ms（需做 embedding 比较）

L3: 模型推理
L1/L2 都未命中 → 走模型推理
命中率：50-70%，延迟：视模型而定
```

## 部署模式

### 模式 1：单机 All-in-One

```
一台服务器跑所有：
Docker Compose → [API + 向量库 + 推理引擎 + 前端]
适合：<50 用户，POC 阶段
```

### 模式 2：推理服务分离

```
服务器 A：API + 向量库 + 前端
服务器 B：推理引擎（vLLM/Ollama）
适合：50-500 用户，推理密集场景
```

### 模式 3：推理集群

```
K8s 集群：多副本推理服务 + 负载均衡
适合：500+ 用户，需要高可用
```

## 硬件选型参考

| 用户规模 | CPU 方案 | GPU 方案 | 月成本估计 |
|---|---|---|---|
| <10 人 POC | 16 核 32GB | — | 自有机房 |
| 10-50 人 | 32 核 64GB | RTX 4090 | 1-2 万 |
| 50-200 人 | 64 核 128GB | A100/2x4090 | 3-5 万 |
| 200-1000 人 | 128 核 256GB | 2xA100/H800 | 8-15 万 |

> **优化第一原则**：**先跑起来，再优化。** 不要花 2 周调优一个还没验证过价值的系统。
