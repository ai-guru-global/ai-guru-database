# Delivery（交付执行阶段）

## 目标

把"技术方案"转化为"可运行的生产系统"。这是 FDE **写代码最多**的阶段，也是客户**最能感知进度**的阶段。

## 三阶段交付法

### Stage 1: 快速原型（1-2 周）

```
目标：最快速度让客户"看到"东西
原则：丑没关系，但核心流程必须跑通
心态：这是"砖头"，不是"精装修"

Day 1-3: 搭环境
├── 安装依赖（Docker/Ollama/Python 包）
├── 拉取模型（离线或在线）
├── 初始化数据库/向量库
└── 跑通 "Hello World"

Day 4-7: 核心功能
├── 实现最核心的 1-2 个 API
├── 做一个最简前端（能输入输出就行）
├── 连上真实数据（哪怕只有 100 条）
└── 内部测试

Day 8-10: Demo 准备
├── 准备 3 个最能体现价值的演示场景
├── 排练演示流程（顺滑很重要）
└── Demo 给客户 → 收集反馈
```

### Stage 2: 试点部署（2-4 周）

```
目标：在真实环境中验证系统
用户：3-5 个种子用户（选最积极的）
关键：收集真实的、可行动的反馈

部署清单：
□ 生产环境部署（非开发环境）
□ 监控接入（Prometheus + Grafana）
□ 日志收集（ELK/Loki）
□ 备份策略执行
□ 安全加固（防火墙/权限最小化）
□ 种子用户培训（手把手）

反馈收集方法：
├── 每日：用户使用日志
├── 每周：15 分钟 1-on-1 访谈
├── 每两周：满意度问卷
└── 随时：微信群/钉钉群
```

### Stage 3: 生产上线（2-4 周）

```
目标：全量用户正式使用
要求：稳定 > 功能完整

上线检查清单（Go-Live Checklist）：
□ 性能压测通过（目标并发量 + 30% buffer）
□ 安全扫描通过（无高危漏洞）
□ 备份恢复测试通过
□ 监控告警已配置（磁盘/内存/CPU/服务健康）
□ 运维手册已完成
□ 用户手册已完成
□ 全量用户培训完成
□ 应急预案已演练
□ 对接人已签署上线确认
□ 7x24 支持排班已确定（上线第一周）
```

## 交付中的常见问题

| 问题 | 应对 |
|---|---|
| 客户环境与开发环境不一致 | 用 Docker 标准化环境 |
| 数据量远超预期 | 分批导入 + 性能优化 |
| 用户反馈"不好用" | 回 Stage 2 迭代，别强行上线 |
| 客户临时加需求 | 走变更流程，不在上线前加 |
| 性能不达标 | 降级方案（减功能保性能） |

## 知识转移

```
不只是给文档，而是：

1. 我操作，你看着（第一遍）
2. 你操作，我看着（第二遍）
3. 你独立操作，我抽查（第三遍）
4. 留文档，留联系方式（兜底）
```

---

> **交付铁律**：**宁愿推迟上线，不要带着已知问题上线。** 一个带着 bug 的上线，比推迟上线更伤害信任。
