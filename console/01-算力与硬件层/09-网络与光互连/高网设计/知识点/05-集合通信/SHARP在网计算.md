# SHARP在网计算

> 把 AllReduce 的求和搬进交换机 ASIC：网内流量近似减半、跳数减少，代价是算子集合受限、累加精度约束与 IB 生态绑定。

## 解决什么问题

传统集合通信里交换机只做转发，聚合计算全部发生在端点 GPU。SHARP（Scalable Hierarchical Aggregation and Reduction Protocol，Mellanox/NVIDIA，2016 起随 EDR 一代进入产品）让 IB 交换机在转发路径上直接做多流累加，回答：同样的 AllReduce，能否少传数据、少占跳数、少占端点算力。

## 核心原理

**机制**：AllReduce 被改写为"沿拓扑树上行聚合 + 下行分发"：数据块上行经过聚合交换机时，多入端口的块就地相加，只把部分和继续上传；完整和在树根/各聚合层形成后下行分发。收益：
- 流量：多进一出的网内聚合使交换 fabric 总转发量明显下降，常见口径为相对 Ring 近似减半（实际随树形与并发流布局）；端点收发量与 Ring 同量级或略低。
- 跳数与时延：聚合提前发生，等效减少端到端转发跳数；端点 GPU 卸载部分规约计算。

**演进代际**：SHARP v1（EDR 世代，2016）主打 HPC；v2（HDR/Quantum 一代，约 2019—2020）面向深度学习扩展数据类型与小消息，FP16 累加进入实用（待核实）；Quantum-2/NDR 一代继续增强（"v3"提法见于 NVIDIA 材料，具体能力清单待核实）。

**限制**：
- 算子集合：仅支持可结合、可交换的加法类规约（sum 类 AllReduce/Reduce）；AllGather、All-to-All 及顺序敏感操作不适用。
- 累加精度：交换机内累加以 FP16/FP32 为主（BF16 支持随代际演进，最新精度矩阵待核实）；FP32 训练若走 FP16 累加需先验证误差。
- 生态绑定：依赖 IB 交换机（Quantum 系）、SHARP 拓扑管理守护（sharpd 等），主机侧经 NCCL CollNet 接入；RoCE/常规以太网交换机无此能力。机内对应物是 NVSwitch 上的 NVLS。
- 与 UEC 的关系：UEC 1.0（2025-06）把网内计算（INC）列为超以太路线的正式目标之一，可视为"以太网追平 IB 在网聚合"的方向声明，落地节奏待观察。

## 关键数字

| 项 | 数值/状态 | 锚点 |
|---|---|---|
| 网内流量收益 | 相对 Ring 近似减半（常见口径） | 理论估算，随拓扑/流布局 |
| SHARP v1 | EDR 世代 IB 交换机 | 2016 |
| SHARP v2 | HDR/Quantum，FP16 累加实用化 | 约 2019—2020（待核实） |
| Quantum-2/NDR 代增强 | 在网聚合能力随带宽代际延续 | 2022（H100/NDR 同期） |
| 累加精度 | FP16/FP32 为主 | 最新矩阵待核实 |
| UEC 1.0 纳入 INC | 规范目标之一 | 2025-06 |

## 设计要点与权衡

- 开启路径：NCCL 侧 CollNet + sharpd 拓扑管理，先在子集群灰度，与 Ring/NVLS 的 busbw 对照后再全量。
- 精度先行：用真实训练任务做 loss 曲线对照（FP16 累加 vs 端点 FP32），不能只看压测带宽。
- 拓扑约束：聚合树依赖拓扑发现，非对称拓扑与跨轨流量会削弱收益；与轨道优化设计联动。
- 成本视角：SHARP 不减少交换机数量，收益是同等交换容量下 AllReduce 时间缩短，属性能杠杆而非资本开支杠杆。
- 以太网路线的空窗与后手：UEC 落地前 RoCE 集群拿不到同类收益，只能靠分层 Ring/端点优化；2026+ 选型把 UEC INC 能力列为交换机问项。

## 常见坑

- 开了 CollNet 但 sharpd 缺失或交换机不支持：静默回退 Ring，性能"正常"而收益为零，只有 NCCL INFO 日志能看出。
- FP16 累加遇上大梯度量级：规约精度损失在 loss 尖刺时才暴露，回滚成本高。
- 把 SHARP 收益外推到 A2A/AllGather：算子不支持，MoE 主负载不受益。
- 混插不同代交换机：聚合能力不一致可能使树构建退化，需实验室先行验证。
