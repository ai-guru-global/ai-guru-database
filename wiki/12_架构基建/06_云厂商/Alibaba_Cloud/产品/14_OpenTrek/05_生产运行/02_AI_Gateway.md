# AI 网关（OpenTrek）

> 中文简称：AI 网关

> **一句话理解**: 网关是企业用大模型的「总闸门」——所有模型请求从一个口子进出，密钥统一管、用量看得见、成本能算到每个部门头上。

---

## 一、AI 网关的职责：统一接入大模型

官网口径是「AI 网关统一接入大模型」。定性展开，网关在企业侧承担三件事：

1. **多模型路由**：一个入口后面挂多个模型，按任务类型、成本、可用性把请求路由到合适的目标（可接入的模型范围以官方文档为准）；
2. **协议适配**：不同模型的 API 在请求格式、参数、流式行为上存在差异，网关在上游抹平差异，应用侧一次接入、处处可用（具体支持的协议清单官网未列，待核实）；
3. **故障切换**：主模型或渠道异常时自动切到备用目标，单点故障不放大成业务事故。

私有化场景里这一层尤其关键（分析视角）：企业内的模型来源往往异构——本地推理集群、专线接入的商用模型、按需调用的公有云 API——没有网关，每个应用都要独自面对这张异构矩阵。

```yaml
# 网关侧接入配置的最小骨架（示意）
gateway:
  上游:
    - {name: 本地推理集群, type: internal}
    - {name: 专线商用模型, type: dedicated}
    - {name: 公有云 API, type: public}
  鉴权: 密钥托管在网关，应用持短期凭证访问
  路由: 按任务类型与成本路由到上游
  熔断: 主渠道异常自动切备用目标
```

网关也是 OpenTrek 生产运行保障的第一跳：全景观测的模型调用数据、成本归集、故障切换动作，都从统一接入这一步产生（见本目录 01 页）。

统一鉴权的流转值得单独说清（分析视角）：上游各模型的密钥只在网关里保存与轮换，应用侧持短期凭证访问网关——密钥泄漏的爆炸半径从「整个模型账户」缩到「一张可撤销的短期凭证」。

三件事有先后（分析视角）：统一入口与鉴权是地基，先解决「乱接」；路由与切换是韧性，解决「单点」；协议适配的深度决定后期接入新模型的边际成本。选型时按这个顺序盘问厂商的能力边界与配置粒度。

## 二、治理价值：无网关 vs 有网关

| **无网关痛点** | **有网关之后** |
|---|---|
| **密钥散落**：API Key 硬编码在各应用里，轮换靠人肉 | **统一鉴权**：密钥托管在网关，应用持短期凭证访问 |
| **用量黑箱**：谁用了多少不知道，出事靠猜 | **可观测**：按调用方/模型/时段的用量视图 |
| **成本无法归集**：账单只有一笔总数，没法分摊 | **业务维度归集**：Token 成本归集到业务线与部门 |
| **重复接入**：每个应用自己适配一遍模型 API | **协议适配**：一次接入，多模型复用 |
| **单点故障**：模型渠道挂了，应用跟着挂 | **故障切换**：备用目标自动接管 |

前三行对应官网给出的治理价值（统一鉴权、可观测、业务维度计费），后两行是网关类产品的通用价值（分析视角）。

三个痛点里最致命的是密钥散落（分析视角）：安全事件的第一现场往往就是硬编码在某处代码里的 API Key——它泄漏的是「整个模型的账户」，而不只是一次调用。统一鉴权因此不只是便利性优化，而是把企业模型访问的攻击面收敛到一个可轮换、可审计的点上。

## 三、与公有云路径的对照（分析视角）

公有云上跑百炼这类平台型服务时，「统一接入」由平台本身承担——应用直连平台 API，密钥、路由、配额都在平台侧；私有化环境里没有这个默认入口，AI 网关把这个角色搬进企业自己手里：

| **对比项** | **公有云平台路径（如百炼）** | **OpenTrek AI 网关** |
|---|---|---|
| **统一入口** | 平台本身就是入口，应用直连平台 API | 企业自建入口，后挂异构模型源 |
| **密钥治理** | 平台侧托管与轮换 | 网关统一鉴权，应用持短期凭证 |
| **模型来源** | 以平台内模型与生态市场为主 | 本地推理、专线商用模型、公有云 API 并存 |
| **适用场景** | 公有云上快速起步的团队 | 私有化、多部门规模化用 AI 的企业 |

两条路径不互斥（分析视角）：公有云跑百炼、私有化跑 OpenTrek 的组合很常见，两套接入各管各的。网关不是公有云平台的替代品，而是私有化环境里补上平台默认能力的等价物。

平台侧的用量与配额体系（百炼 usage/quota）与企业侧 Token 账本的详细对照，见本目录 03 页。

对照的用处是定位价值边界（分析视角）：公有云路径下网关能力被平台吸收，企业自建网关的收益主要来自私有化环境与多部门规模——若企业九成流量都在公有云单一平台上，自建网关的必要性要重新算账。

## 四、实施建议：命名规范、业务标签、预算告警

网关上线只是开始，治理效果取决于三件配套：

1. **命名规范先行**：调用方标识按「部门-应用-环境」三段式命名；无标签的裸请求默认打 unknown 标签并告警，倒逼接入方规范接入；
2. **业务标签体系**：标签与财务成本中心对齐，否则月度出账还要人肉映射；标签变更走评审，避免历史成本序列断裂；
3. **预算告警分级**：80% 预警、100% 限流是常见起点（示意阈值），关键业务可申请白名单，但白名单本身也要进观测看板；
4. **先观测后治理**：上线第一个月只看不罚，摸清各业务线真实水位再收紧预算——一上来就熔断，只会把用户赶回影子 IT。

三件配套的共同点是把治理动作前置到接入时（分析视角）：命名与标签在接入那一刻定形，预算阈值在用量跑起来之前声明——事后补标签、补口径的代价是事前的数倍。

---

## 五、落地顺序：网关先行，四步爬坡

落地顺序：网关先行（统一接入）→ 用量视图跑一个月（建立基线）→ 打标签出账（内部结算）→ 收紧预算。跳过前两步直接上预算管控，是这类项目最常见的翻车原因。

每一步的验收物（分析视角）：统一接入看「全部模型流量过网关」的比例；基线看出账口径能否自洽对上总账；内部结算看业务线认不认账；预算管控看超限事件的处置时长。四步都稳了，网关才从「转发器」变成「治理抓手」——用量账本与计费规则的展开见本目录 03 页，三层观测看板见 01 页。

还要盯一个先行指标：影子接入的比例——绕过网关直连模型的请求量（分析视角）。影子接入不清零，账本与看板都是残卷。
