## 第 1 题｜ReAct vs Chain-of-Thought

**问：** ReAct 和纯 Chain-of-Thought（CoT）的核心区别是什么？ReAct 解决了 CoT 的什么固有缺陷？

**答：** CoT 只是线性的"推理链"——模型一路想下去，全部推理基于参数内的已有知识，无法获取外部或实时信息，容易产生幻觉，且错误会在链条中传播放大。

**ReAct = Reason + Act 交替**：模型先推理（Thought），再执行动作（Action，如调用搜索、查数据库），根据观察结果（Observation）继续推理，循环直到得出答案。

它解决的正是 CoT 的两个固有缺陷：

1. **知识截断** — 通过 Action 接入外部知识源，突破训练数据截止时间的限制；
2. **幻觉失控** — 每一步推理都有 Observation 作为证据锚点，可验证、可纠错。

一句话总结：CoT 是"闭卷想"，ReAct 是"边查边想"。

## 第 2 题｜Function Calling 的本质

**问：** Function Calling（工具调用）的本质是什么？描述一次完整的 Function Calling 循环中模型与宿主程序各自的职责分工。

**答：** 本质是**结构化的意图输出**：模型并不真正"执行"函数，而是把用户的自然语言意图翻译成一个结构化的 JSON 调用草案（函数名 + 参数），真正执行的是宿主程序（Agent runtime）。

完整循环的职责分工：

1. **模型（决策者）**：收到用户消息 + 可用工具清单（JSON Schema 描述），判断是否需要调用工具；若需要，输出 `tool_calls`（函数名、参数）；若不需要，直接生成最终自然语言回答。
2. **宿主程序（执行者）**：解析模型输出的调用请求 → 本地校验参数 → 真正执行函数（HTTP 请求、查库、跑代码……）→ 把结果包装成 `tool` 角色消息回传。
3. **模型（综合者）**：看到工具返回结果（可能多轮、多个并行调用），继续推理，决定再次调用工具或产出最终答案。

关键点：

- 模型只负责**"决定调什么、传什么参"**，不负责执行——所以工具执行的权限控制、沙箱、审计都在宿主侧做；
- 循环终止条件由模型决定（不再输出 `tool_calls` 即结束），宿主需设置最大轮数兜底防止死循环。

## 第 3 题｜上下文窗口 vs 记忆（Memory）

**问：** 上下文窗口（Context Window）和 Agent 的记忆机制是一回事吗？请区分短期记忆与长期记忆，并各举两种常见实现方式。

**答：** 不是一回事。**上下文窗口是"硬件约束"**——模型单次推理能处理的最大 token 数量，是易失的、有限的工作空间；**记忆是"工程机制"**——在窗口约束之外管理信息的存取策略。Agent 记忆设计的核心矛盾就是：信息总量远超窗口容量，必须决定**什么留在窗口里、什么存出去、什么时候取回来**。

| 类型 | 生命周期 | 常见实现 |
|------|---------|---------|
| **短期记忆** | 当前会话内 | ① 对话历史直接放入上下文；② 超长时截断/滑动窗口、摘要压缩（rolling summary）后回填 |
| **长期记忆** | 跨会话持久 | ① 向量数据库检索（RAG 式回忆，语义召回）；② 结构化存储（文件/知识图谱/SQLite，如 mem0、letta 式记忆块） |

设计要点：

- 短期记忆解决"**这轮对话别忘了前面说的**"，受窗口硬约束，策略是压缩与淘汰；
- 长期记忆解决"**下周再聊还记得你是谁**"，策略是写入提取（什么时候值得存）+ 检索召回（什么时候取回），其中最难的是**写入判断**——存太多是噪声，存太少等于没记忆。

## 第 4 题｜ReAct vs Plan-and-Execute

**问：** 对于"多步骤、长程"任务，纯 ReAct 循环有什么局限？Plan-and-Execute 架构如何改进？两者如何取舍？

**答：** 纯 ReAct 是**"走一步看一步"**的贪心策略：每轮都重新决定下一步。在长程任务中的局限：

1. **缺乏全局观** — 容易在细节里打转、偏离最终目标，或重复已做过的步骤；
2. **上下文膨胀** — 每步的 Thought/Observation 都堆进窗口，长任务中途就撑爆上下文；
3. **规划被淹没** — 早期制定的计划在大量工具输出中被稀释，模型"忘了自己为什么出发"。

**Plan-and-Execute 的改进**：先用一次（或几次）推理产出**完整计划**（步骤列表 + 预期产出），然后逐步执行；执行时只携带"当前步骤 + 必要上下文"，必要时允许**重规划（re-plan）**——根据中间结果修正后续计划。代表实现：LangGraph 的 Plan-and-Execute 节点、BabyAGI 式的 task list + executor。

**取舍准则：**

- **任务可预分解、步骤间弱耦合**（如"写研究报告""部署流水线"）→ Plan-and-Execute，省 token、轨迹清晰、可中断恢复；
- **路径高度依赖中间观察、分支多**（如调试、探索性搜索）→ 纯 ReAct，计划赶不上变化，硬做计划反而错；
- 实践中常见**混合式**：粗粒度用计划（顶层 3-5 步），每个计划步内部用 ReAct 细化执行。

一句话：**ReAct 是战术级反应，Plan-and-Execute 是战役级调度**，好 Agent 两者都有。

## 第 5 题｜Reflection（自我反思）模式

**问：** Agent 的 Reflection（反思）模式是怎么工作的？它和 ReAct 的 Thought 有什么区别？为什么说反射机制能让 Agent"越做越好"？

**答：** Reflection 是让 Agent **对自己的产出做批判性评估并迭代修正**的模式，代表实现是 Reflexion 论文的"演员-评论家"结构和 LangGraph 的 self-critique 节点。

它和 ReAct 的 Thought 的区别：

| 维度 | ReAct 的 Thought | Reflection |
|------|------------------|------------|
| 对象 | **下一步该做什么**（面向行动） | **刚才的结果好不好**（面向产出） |
| 时机 | 每步执行前 | 阶段性产出后（生成→评估→修订循环） |
| 依据 | 当前观察 | 评估标准（rubric / 测试 / 批评者反馈） |

标准循环：**Generate（生成）→ Evaluate（按标准打分/找缺陷）→ Reflect（形成改进要点存入记忆）→ Regenerate（带反思重做）**。代码型 Agent 的典型形态就是"写代码 → 跑测试 → 读报错 → 改代码"再循环。

它能"越做越好"的关键：**反思结果会被写回上下文或记忆**，下一轮生成时模型能看到"上次错在哪"，把原本会丢弃的失败尝试转化为增量信号。质量提升有天花板——评估者（自己评自己或弱模型评强模型）的判断力是上限，所以生产上常配合外部可验证信号（测试通过率、单元校验）而非纯自评。

## 第 6 题｜多 Agent 架构模式

**问：** 多 Agent 系统常见的协作模式有哪些？Orchestrator（编排者）模式和 Swarm/去中心化模式各适合什么场景？

**答：** 常见协作模式（以 LangGraph / AutoGen 的分类为基准）：

| 模式 | 结构 | 典型场景 |
|------|------|---------|
| **Orchestrator（编排者-工作者）** | 中心节点拆任务、派发、汇总，worker 之间不直接通信 | 目标可分解、需统一质量把关：写研究报告、代码重构 |
| **Sequential / Pipeline（流水线）** | 固定顺序传递，每站做一类事 | 流程稳定：翻译 → 润色 → 排版 |
| **Swarm（去中心化/交接式）** | Agent 之间通过 handoff 直接移交控制权，无中心 | 对话式分流：客服按问题类型在专业席位间转接 |
| **Hierarchical（层级）** | 编排者之上还有管理者，树状委派 | 大规模任务、多层审批 |
| **Debate / Evaluator-Optimizer（辩论/评估优化）** | 多个 Agent 互相批评或一个生成一个评审 | 需要高可靠：事实核查、方案评审 |

**Orchestrator vs Swarm 的取舍：**

- **Orchestrator**：中心节点掌握全局状态，可控性强、易审计、易设兜底；代价是中心节点成为瓶颈和单点，上下文压力大。适合**任务可预分解、需要统一标准**的场景。
- **Swarm（handoff）**：无中心、延迟低、每个 Agent 只带自己领域的上下文（窗口干净）；代价是全局状态分散，容易"转来转去丢问题"，需要清晰的转接协议。适合**路由型、领域分工明确**的场景。

实践共识：**结构化任务用 Orchestrator，对话分发用 Swarm，关键产出用 Evaluator-Optimizer 兜质量**；纯自由协作（无结构的多 Agent 讨论）效果常不如单 Agent + 好工具，因为协调成本会吃掉收益。

## 第 7 题｜MCP 协议与 Function Calling 的关系

**问：** MCP（Model Context Protocol）和 Function Calling 是什么关系？MCP 解决了 Function Calling 生态的什么问题？

**答：** 两者是**不同层面**的东西：Function Calling 是**模型能力层**——模型输出结构化调用请求的机制；MCP 是**工具接入层**——一套开放协议，规定工具（MCP Server）如何向 Agent（MCP Client）标准化地暴露能力。

没有 MCP 之前的问题：每个工具对每个模型/框架都要写一套定制集成，N 个工具 × M 个平台 = N×M 组适配代码——典型的"点对点连线"地狱。工具的鉴权、schema、调用方式各家各异，接入成本极高。

MCP 的解法是**引入 USB-C 式的统一接口**：

| 角色 | 职责 |
|------|------|
| **MCP Server** | 把工具/资源封装成标准协议（tools、resources、prompts 三类原语），一次开发到处接入 |
| **MCP Client** | Agent 侧适配器（内嵌在 Claude Code、Cursor 等宿主里），发现并调用 Server |
| **传输层** | 本地 stdio 或远程 HTTP/SSE，支持跨机器、跨信任域 |

分工关系一句话说清：**MCP 负责"工具怎么被发现和描述"，Function Calling 负责"模型怎么发起这次调用"**——MCP Server 提供的 tool schema 最终还是通过 Function Calling 机制被模型消费的。MCP 把 N×M 简化为 N+M，且天然支持动态发现（连接时才知道有哪些工具）、能力协商和权限边界。

## 第 8 题｜Agent 的终止条件与死循环防护

**问：** 一个常见的 Agent 故障是"无限循环调工具"（比如反复搜索同一个问题、反复读同一个文件）。请分析这类死循环的成因，并给出至少三种工程上的防护手段。

**答：** 成因分析——Agent 循环的终止由模型自主决定（不再输出 tool_calls 才停），这个机制天然脆弱：

1. **上下文遗忘** — 早期工具结果被挤出/稀释出窗口，模型"忘了已经查过"，重复发起同一调用；
2. **结果不可判读** — 工具返回空结果、报错或噪声，模型无法从中获得"该换路子"的信号，只能原地重试；
3. **目标欠约束** — 提示词没有定义完成标准，模型不知道什么算"做完了"，一直在"做更多"。

工程防护手段（层层设卡）：

| 手段 | 层级 | 说明 |
|------|------|------|
| **硬性步数/轮数上限** | 运行时兜底 | 全局 max_iterations + 单工具调用次数配额，触顶强制总结收尾 |
| **重复调用检测** | 运行时 | 对 (tool, args) 做哈希，命中近期记录则拦截/警告，强制模型换策略 |
| **工具结果回执压缩** | 上下文 | 大结果摘要化，保留"已查过什么"的痕迹，防止历史被彻底淹没 |
| **明确的完成标准** | 提示词 | 系统提示中定义 done 的判据（如"找到 3 个来源"而非"继续研究"） |
| **超时与预算护栏** | 运行时 | 墙钟时间上限、token 预算上限，超限优雅降级 |
| **循环检测信号可观测** | 监控 | trace 里记录每步工具调用序列，CI/线上检测周期性模式并告警 |

核心思想：**不能信任模型自觉停机**——终止保证必须由宿主程序的确定性代码兜底，模型的"判断力"只负责优雅程度，不负责安全性。

## 第 9 题｜Prompt Injection 与 Agent 安全

**问：** 什么是 Prompt Injection？它和传统 Web 安全里的 SQL 注入、XSS 有什么本质区别？Agent 场景下为什么危害被放大？请给出纵深防御思路。

**答：** Prompt Injection 是**用恶意输入劫持模型指令遵循**的攻击：攻击者把指令藏在模型会读取的内容里（网页正文、工具返回值、邮件正文），让模型执行攻击者的意图而非用户的意图。

与传统注入的本质区别：SQL 注入、XSS 的"解释器"是确定性的——同样的 payload 必然触发同样的解析行为；而 LLM 的"解释器"是概率性的，**数据和指令在 token 层面没有语法边界**——模型靠语义猜测哪段是"命令"、哪段是"材料"，这就是无法根除的结构性弱点（甜甜圈与内馅无法分离）。

Agent 场景危害放大，因为三点叠加：

1. **攻击面扩大** — Agent 主动抓网页、读文件、收邮件，每个外部内容都是注入载体（间接注入 indirect prompt injection）；
2. **从"说"到"做"** — 被劫持的不只是回答，而是工具调用：读通讯录、发邮件、转账、删文件；
3. **权限继承** — 模型以用户的权限运行，注入成功 = 攻击者继承用户全部授权。

纵深防御思路：

| 层 | 措施 |
|----|------|
| **架构层** | 数据/指令分离标记；不可信内容进 sandbox 隔离通道，永远不与系统提示拼接 |
| **权限层** | 最小权限、工具白名单；高危操作（发送/删除/支付）强制 Human-in-the-Loop 确认 |
| **检测层** | 输出侧扫描（指令外泄模式、异常 tool_calls 意图审核） |
| **预算层** | 限速、单次会话影响范围限制，防止注入后横向扩散 |

核心认知：**检测只能提高门槛，架构隔离才是根**——凡是"模型不能看的内容也能影响模型"的通道，都必须按不可信输入对待。

## 第 10 题｜Agent 评估（Evaluation）方法

**问：** 传统 NLP 的准确率/F1 直接套用在 Agent 评估上有什么问题？Agent 评估通常从哪几个维度展开？什么是端到端任务成功率评估（trajectory-based eval）？

**答：** 传统指标的问题：它们假设**单次、静态、有唯一正确答案**的输入输出映射，而 Agent 是**多步、动态、路径不确定**的过程——同一个任务可以走完全不同的轨迹达成，且中间每步都可能出错但最终结果正确（或反之）。

Agent 评估的典型维度：

| 维度 | 评估对象 | 方法举例 |
|------|---------|---------|
| **任务成功率** | 最终结果 | 端到端跑 benchmark（如 SWE-bench、WebArena），判断是否达成目标 |
| **轨迹质量** | 中间过程 | 步数效率、是否绕路、是否重复调用、工具选择合理性 |
| **单步决策** | 每步动作 | 与专家轨迹对比、单步准确率（teacher forcing 式） |
| **成本效率** | 资源消耗 | token 用量、延迟、工具调用次数 |
| **安全合规** | 行为边界 | 是否越权调用、是否触发拦截、红队对抗测试 |

**端到端任务成功率（trajectory-based eval）**：给 Agent 一个完整任务和可自动验证的判据（测试通过、页面状态正确、检索到指定事实），让它自主跑完全程，**只看最终状态是否达标**——不约束中间路径。这是最贴近真实使用的评估方式，优点是允许不同策略殊途同归、无需标注"标准轨迹"；缺点是粗粒度（失败了不知道错在哪一步），所以实践中常配合轨迹层面的过程归因：失败样本再拆解到具体步定位原因。

评估基础设施三件套：**可复现的任务集 + 自动判分器（rubric 或程序化 verifier）+ 轨迹日志回放**。注意评估集要防污染（模型可能在训练数据里见过 benchmark 答案），生产上更可信的是从真实会话里采样的私有评估集。

## 第 11 题｜Structured Output 与 JSON Mode

**问：** 让 LLM 输出结构化数据（JSON）有哪几种手段？JSON Mode、Function Calling（强制调用）、以及提示词里贴 Schema + 解析重试，这三者在可靠性上有什么差别？

**答：** 三种常见手段，可靠性依次递进：

| 手段 | 机制 | 可靠性 | 局限 |
|------|------|--------|------|
| **提示词贴 Schema + 解析** | prompt 里描述目标 JSON 结构，输出后用代码 parse，失败则带错误重试 | 最低，靠"人肉"约束 | 常见破损：多余文本包裹、引号转义、截断、字段幻觉；需自建重试逻辑 |
| **JSON Mode / constrained decoding** | API 层开启（如 `response_format: json_object`），解码时强制 token 流符合 JSON 语法 | 中高，语法必然合法 | 只保证**语法**合法，不保证**结构**符合你的 Schema——键名、字段类型、嵌套形状仍可能错 |
| **Function Calling 强制工具** | 定义一个"返回结果"的虚拟函数 + JSON Schema，强制模型必须调用它（tool_choice 指定），由 API 按 Schema 校验/约束生成 | 最高 | 依赖具体 API 的实现质量；复杂嵌套 Schema 各家支持度不一 |

关键区分：**语法合法 ≠ 结构合法 ≠ 语义正确**。JSON Mode 只跨过第一道坎；Function Calling 的 Schema 约束（部分厂商在解码层做 grammar-constrained decoding，按 Schema 逐字段限制候选 token）能跨过第二道；第三道（数值合理、引用真实）永远需要业务层校验兜底。

实践建议：**凡是进程序的数据一律走 Function Calling/Schema 约束，别裸用 JSON Mode**；解析失败时带具体错误信息重试（而非盲目重发）；对关键字段加业务校验（枚举、范围、外键存在性），把模型输出当"不可信外部输入"处理。

## 第 12 题｜Context Engineering（上下文工程）

**问：** 为什么说"Agent 工程的本质是上下文工程"？在构建一个生产级 Agent 时，如何决定哪些信息放进系统提示词、哪些放进工具结果、哪些动态注入？

**答：** Agent 的一切能力最终都通过**当前上下文窗口**这一个通道影响模型决策——工具再强、模型再好，如果关键信息没在正确的时机出现在上下文里，行为就是错的。所以 Agent 工程的核心手艺是**管理窗口里的每一个 token：放什么、什么时候放、以什么形式放**。

三大信息通道的分工决策：

| 通道 | 放什么 | 决策依据 |
|------|--------|---------|
| **系统提示词（静态）** | 角色定义、行为规则、工具使用总则、安全边界 | **每个会话都需要且不变**的内容；放进去的每条规则都在消耗所有请求的 token，要克制 |
| **工具结果（动态、模型触发）** | 外部事实：检索内容、API 返回、文件内容 | **只在需要时才在场**的信息；模型自己决定何时获取——这是 Agent 化的核心，静态塞进 prompt 会浪费窗口且过时 |
| **动态注入（宿主触发）** | 当前用户画像、会话摘要、上一步失败原因、记忆召回 | **时机由程序控制**的信息：用户切换话题时注入新背景、窗口将满时注入摘要、检测到循环时注入提示 |

判断一个问题该走哪条通道，问三个问题：

1. **是否每次都需要？** 是 → 系统提示词；否 → 往后两条通道找。
2. **模型能否自己判断何时需要？** 能 → 工具化，让模型主动取（retrieval）；不能 → 宿主在特定事件点动态注入（injection）。
3. **信息量是否可预测且小？** 大块且不可预测 → 绝不常驻，按需检索 + 摘要压缩。

常见反模式：把 RAG 检索结果硬塞系统提示词（时机错位）、工具返回整页 HTML 不做摘要（噪声挤占窗口）、用户画像从不更新（陈旧注入比没有更糟）。一句话总结：**上下文是稀缺资源，每个 token 都要证明自己此刻在场的必要性。**

## 第 13 题｜Agentic RAG vs 传统 RAG

**问：** 传统（朴素）RAG 的"一次检索-生成"流水线有什么局限？Agentic RAG 引入了哪些改进？核心区别在哪一层？

**答：** 传统 RAG 是**固定流水线**：query → 向量检索 top-k → 拼进 prompt → 生成。一次执行、无分支、检索策略写死。局限：

1. **query 天真** — 用户问题可能是多跳的（"A 公司创始人上一家公司估值多少"），直接向量化整句检索，召回质量差；
2. **检索失败无感知** — 召回的段落可能根本不含答案，模型照样"硬答"，或该拒答时幻觉；
3. **策略单一** — 没有重写、没有混合检索（关键词+向量）、没有多轮补充，也不会判断"知识库里到底有没有"。

**Agentic RAG 的核心区别在"控制层"**：把检索从固定流水线变成**模型可自主决策的工具**——ReAct 循环里的一个 action。Agent 可以动态编排：

```text
传统 RAG:  query → 检索 → 生成（固定一步）
Agentic:   query → [改写/分解] → 检索A ─┐
                              ↘ 检索B ─┼→ 判断够不够 → 不够：换关键词重检/查别的源
                                        └→ 够了 → 生成（带引用）或判定"库中无此知识"
```

典型增强能力：

| 能力 | 做法 |
|------|------|
| **查询改写/分解** | 多跳问题拆成子问题，逐个检索再汇总 |
| **自适应检索** | 先判断是否需要检索、知识库是否可能有，避免无谓调用 |
| **结果自评** | 检查召回段落是否支撑回答，不支撑则换策略重检（对应 Reflection） |
| **多路混合** | 向量 + 关键词 + 图谱 + 外部 API 按需组合 |
| **可修正** | 生成后发现引用对不上，回退重检 |

取舍提醒：Agentic RAG 多轮决策带来**更高延迟和 token 成本**，且循环需要第 8 题的护栏。简单事实查询场景，朴素 RAG 的性价比仍然更高——**按问题复杂度分流**（简单直达、复杂进循环）是生产常态。

## 第 14 题｜Agent 的可观测性（Observability）

**问：** 为什么说"没有 trace 的 Agent 是不可调试的"？一个 Agent 可观测性体系应该记录哪些信号？LLM 调用的 trace 和传统微服务 trace 有什么不同？

**答：** Agent 的行为是**概率性多步决策**——同一个输入两次运行可能走不同轨迹，日志里只有一堆孤立的 prompt/response 对，根本无法回答"它为什么在第 4 步选了这个工具"。传统微服务的因果链是代码写死的（A 调 B 调 C），Agent 的因果链是模型现场生成的，**只有把每步决策连同其上下文完整记录下来，才能回放和归因**。

该记录的信号（按一次 run 的轨迹组织）：

| 信号 | 内容 | 用途 |
|------|------|------|
| **轨迹（trajectory）** | 每步的 Thought/决策、tool_calls、工具结果、耗时 | 复盘"它做了什么、为什么" |
| **上下文快照** | 每次模型调用实际收到的完整 prompt（含注入的记忆/摘要） | 排查"它当时看到了什么"——上下文 bug 的唯一证据 |
| **LLM 调用元数据** | 模型版本、温度、token 用量、provider 延迟、重试 | 成本归因、延迟分析、模型回归检测 |
| **工具侧信息** | 工具入参、出参、错误码、权限判定结果 | 定位"是模型决策错还是工具坏" |
| **宿主动作** | 死循环拦截、HITL 拦截、摘要压缩触发 | 观察护栏是否误伤/漏拦 |

和传统微服务 trace 的关键差异：

1. **记录对象多了"非确定性中间态"** — 微服务 trace 记调用链；Agent trace 还必须记**每步的完整上下文和模型输出**，否则无法重放归因（同一个 tool_call 因为上下文不同可能是对的也可能是错的）；
2. **token 是新的黄金指标** — 微服务看 QPS/延迟，Agent 还要看每步 token 消耗、上下文增长曲线；
3. **"请求"边界模糊** — 一次用户交互可能横跨数十次 LLM 调用 + 多次外部 IO，需要 run_id/session_id 两级组织。

实践形态：OpenTelemetry GenAI 语义约定 + LangSmith/Langfuse 类平台，核心验收标准是**任意失败样本能回放到当时的确切上下文**。
