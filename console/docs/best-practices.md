# 最佳实践指南

> 面向两类读者：**内容维护者**（如何写出高质量线索）与 **工具开发者**（如何写出符合项目规范的 Go 代码）。

## 第一部分：内容维护最佳实践

### 1. 线索的准入标准

不是每条新闻都值得建线索。建线索前先问三个问题：

1. **它会持续演进吗？** 一次性事件（某场演讲、某篇论文）通常登记到已有线索的时间线即可；只有会持续产生后续动态的对象（产品、模型系列、公司、技术方向）才值得独立线索
2. **它有清晰的边界吗？** 线索名应指向一个明确对象。「OpenAI」太宽，「OpenAI-Sora」合适
3. **它归属唯一主题吗?** 若一条线索横跨两个主题，选择其"主战场"，并在另一主题的相关线索里用双链引用

### 2. 时间线条目的写法

**好的条目**（事实完整、可溯源、一句话说清）：

```markdown
- 01-15 · Anthropic 发布 Claude 3.5 Haiku · https://www.anthropic.com/news · 小杯模型达到上代旗舰 Claude 3 Opus 的基准水平，价格为其 1/4
```

**坏的条目及原因**：

```markdown
- 01-15 · Claude 更新了 · （无 URL，无法溯源）
- 01-15 · Anthropic 发布了震撼业界的新模型 · …… （"震撼业界"是观点，进了事实区）
- 某天 · …… （日期缺失，时间线失去意义）
```

规则清单：

- 日期格式 `MM-DD`，归入对应的 `### YYYY-MM` 月份小节，**新月份小节加在文件最上方**
- 每条必须有可访问的 URL（优先官方博客/公告，其次权威媒体）
- 摘要限一句话，只写事实：发布了什么、数字是多少、谁参与了
- 转述数字要精确：「性能提升 2 倍」不能写成「大幅提升」

### 3. 概述与分析的边界

| 段落 | 允许 | 禁止 |
|---|---|---|
| 概述 | 对象是什么、谁开发、关键版本节点 | 任何评价性形容词 |
| 分析 | 趋势判断、竞品对比、影响预测 | 无出处的"据传""内部消息" |

分析段的观点应可被时间线中的事实支撑。写分析时自查：「我引用的每个论据，时间线里找得到对应条目吗？」

### 4. 双链的使用时机

- 线索 A 的事件直接影响线索 B → 在 A 的条目末尾加 `（关联 [[主题/B]]）`
- 两条线索属于同一竞争格局 → 在各自「关联线索」小节互相引用
- 不要为了链接而链接：双链密度以每条线索 2-5 个为宜

### 5. 大事记的收录门槛

`_2026大事记.md` 只收四类事件：**重大发布**（新模型/产品的首发）、**格局变化**（并购、关键人事、市占率逆转）、**政策监管**（法案生效、重大处罚）、**技术突破**（公认的能力跃迁）。判断标准：一年后回看，这件事还重要吗？

### 6. 使用 CLI 辅助内容生产的工作流

```bash
ai-news-database sync            # 1. 同步官方源到本地库
ai-news-database enrich          # 2. LLM 生成摘要与质量评分
ai-news-database curate          # 3. 查看今日必读推荐
ai-news-database search "Agent"  # 4. 按关键词回溯（已支持中文检索）
ai-news-database export --starred # 5. 导出收藏为 Markdown，人工整理进线索
```

关键点：**工具产出的是素材，不是成品**。`export` 出的内容必须经过人工核实 URL、改写摘要、判断归属线索后才能进入内容库。

## 第二部分：工具开发最佳实践

### 1. 分层纪律

- 依赖方向自上而下：`cmd → 业务编排（curator/rag/…）→ 外部适配（crawler/llm/…）→ 基础设施（db/config/…）`，禁止反向引用
- 新业务模块一律提供 `New()`（生产装配）与 `NewWithDeps()`（测试注入）两个构造器
- `cmd/` 层只做参数解析、装配与输出渲染，业务逻辑必须下沉到 `internal/`

### 2. 数据库操作规范

- 一律使用占位符参数（`?`），任何动态拼接仅限白名单常量（如 `ORDER BY` 字段）
- **修改 `articles` 表中被 FTS 索引的字段（title/summary/llm_summary）后，必须调用 `reindexArticle`** 保持索引一致；删除行前先清理 `articles_fts` 对应 rowid
- schema 变更走 `migrate()` 幂等迁移：`CREATE TABLE IF NOT EXISTS` + `ALTER TABLE ADD COLUMN`（容忍列已存在错误）

### 3. 错误处理与日志

- 错误信息用中文、带上下文：`fmt.Errorf("加载配置失败: %w", err)`，保留 `%w` 链
- 用户可感知的失败必须返回 error 由 cobra 输出；仅内部可容忍的异常才用 `slog.Debug` 记录
- 网络与 LLM 调用必须接收 `context.Context` 并传递到底层，支持 Ctrl-C 取消

### 4. 测试策略

| 层级 | 手段 | 要求 |
|---|---|---|
| internal 业务包 | 单元测试 + mocks | 新功能必须带测试；外部 HTTP 用 `httptest` |
| db 包 | 真实 SQLite（`t.TempDir()`） | 覆盖迁移、CRUD、FTS 同步 |
| cmd 层 | `e2e_test.go` 子进程驱动 | 新命令至少加一个 e2e 子用例；HOME 必须隔离 |
| 全量 | `make test`（含 -race） | 提交前必须通过 |

### 5. 安全红线

- 永不打印/记录明文 API Key（包括 debug 日志）
- 配置文件写入权限 0600，数据目录 0755
- 新增网络访问范围（如扩展的 host_permissions、新采集源域名）需在 PR 中说明必要性
- 引入新依赖前评估：是否纯 Go（保持无 CGO）、维护活跃度、传递依赖数量

### 6. 提交与发布

- Commit message 使用约定式前缀：`feat:` / `fix:` / `docs:` / `content:` / `refactor:` / `build:`；**禁止无信息量的 "update"**
- 内容库变更用 `content:` 前缀，与代码变更分开提交
- 每个用户可见变更在 `docs/changelog.md` 的 `[Unreleased]` 下登记一行
- 发布：打 tag 触发 release workflow，发布前本地跑 `make quality`（fmt+vet+lint+test）

### 7. 性能注意事项

- 列表查询必须带 `LIMIT`；新查询路径先确认命中现有索引（`EXPLAIN QUERY PLAN`）
- LLM 批处理（enrich）串行执行并尊重限流，不要并发打爆免费额度
- TUI 渲染避免在 `Update` 循环里做 IO；耗时操作放 `tea.Cmd` 异步执行
- 大文件红线：单个 Go 源文件超过 500 行时考虑按职责拆分（参照 deep_research 的拆分方式）
