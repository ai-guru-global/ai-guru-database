# 从提示词工程到上下文工程到 Harness 工程的三阶演进

> 中文简称：从提示词工程到上下文工程到 Harness 工程的三阶演进

> **核心洞察**：AI 工程正在经历从"如何写好一条指令"到"如何构建一个可靠系统"的范式跃迁。三阶演进不是替代关系，而是层层递进、层层包含的关系——每一层都将前一层作为子系统内化。

---

## 1. 三阶演进时间线

```
2023 初                2024-25                2025-26+
┌──────────────┐     ┌──────────────┐     ┌──────────────────┐
│   Prompt     │     │   Context    │     │   Harness        │
│  Engineering │ ──→ │ Engineering  │ ──→ │  Engineering     │
│              │     │              │     │                  │
│ "这一轮怎么答"│     │ "模型看到什么"│     │ "智能体如何在     │
│ 单次输入文本  │     │ 指令+检索+   │     │  环境中持续运行"  │
│              │     │ 工具+历史    │     │ 工具+状态+安全+   │
│              │     │              │     │ 生命周期          │
└──────────────┘     └──────────────┘     └──────────────────┘
     技巧驱动             系统化方法             系统工程学科
```

### 演进驱动力

三次跃迁背后的四大推力（参见 [[Context_Engineering_Guide]]、[[AgentOps_Production_Guide]]）：

1. **任务复杂度提升**：从简单问答到代码编写、多步推理、数据分析
2. **智能体兴起**：从无状态函数到有状态、跨时间持续工作的 Agent
3. **生产环境要求**：可靠性、一致性、可观测性、成本控制
4. **模型能力增强**：上下文窗口扩大，需要更高层次的工程方法

## 2. 第一阶段：提示词工程（Prompt Engineering）

### 核心关注

> "如何写好一条指令，让模型在这一轮给出最好的回答？"

参见 [[Prompt_Engineering_Complete_Guide]] 和 [[Prompt_Engineering_Advanced_Apps]]。

### 六大核心要素

| 要素 | 说明 |
|------|------|
| 角色/身份 | 设定专业领域和行为风格 |
| 任务指令 | 定义目标和具体操作 |
| 上下文 | 提供背景知识和约束条件 |
| 输入数据 | 待处理的具体内容 |
| 输出格式 | 定义回复的结构和风格 |
| 示例 | 展示期望的输入输出对 |

### 关键技术

- **思维链（CoT）**：引导模型展示中间推理步骤（[[Prompt_Engineering_Complete_Guide#6]]）
- **少样本学习**：通过 2-6 个示例定位任务模式（上下文学习的本质）
- **ReAct 框架**：思考-行动-观察闭环（[[Prompt_Engineering_Advanced_Apps#1]]）
- **提示词链**：顺序链、分支链、并行链、循环链、验证链、层级链

### 局限性

| 局限 | 具体表现 |
|------|---------|
| **静态性** | 提示词预定义，难以适应动态变化 |
| **孤立性** | 聚焦单次交互，缺乏对话历史和外部信息的系统管理 |
| **可扩展性差** | 任务复杂度增加时，提示词冗长且难以维护 |
| **缺乏工程化** | 更多依赖直觉和试错 |

## 3. 第二阶段：上下文工程（Context Engineering）

### 核心关注

> "如何在正确的时间，将正确的信息，以正确的格式，提供给模型？"

参见 [[Context_Engineering_Guide]] 和 [[Context_Engineering_Patterns]]。

### 从"写指令"到"构建信息环境"

Anthropic 在其工程博客（2025-09）中明确把上下文工程定义为"在推理过程中策划与维护最优 Token 集合的一整套策略"，并指出**提示词工程是上下文工程的一个子集**。

### 核心差异对比

| 维度 | 提示词工程 | 上下文工程 |
|------|-----------|-----------|
| **关注点** | 单次指令的措辞和格式 | 完整信息环境的设计 |
| **范围** | 提示词文本 | 指令、数据、工具、记忆、策略 |
| **时间维度** | 静态、一次性 | 动态、跨会话 |
| **信息来源** | 手工编写 | 多源融合、自动检索 |
| **工程化程度** | 技巧驱动、经验依赖 | 系统化、可量化、可测试 |

### 四大核心策略

参见 [[Context_Engineering_Guide#4]]：

```
原始信息 → Write(写入) → 存储 → Select(选择) → Compress(压缩) → Isolate(隔离) → 最终上下文
```

| 策略 | 解决的问题 | 典型技术 |
|------|-----------|---------|
| **Write** | 窗口之外的信息存储和管理 | 向量数据库、记忆架构、知识库 |
| **Select** | 从海量信息获取最相关内容 | 语义检索、混合检索、重排序 |
| **Compress** | 有限空间容纳更多有效信息 | 文本摘要、对话压缩、递进式摘要 |
| **Isolate** | 组织和结构化不同类型信息 | XML 标签、指令分层、多智能体编排 |

### 上下文预算分配（128K Token 典型）

| 组件 | 预算分配 | 说明 |
|------|---------|------|
| 系统提示词 | 5K | 核心指令和规则 |
| 工具定义 | 5K | 函数签名和说明 |
| 检索内容 | 50K | RAG 返回的知识 |
| 对话历史 | 30K | 最近的对话轮次 |
| 工作记忆 | 20K | 任务相关记忆 |
| 用户输入 + 输出 | 18K | 当前请求和生成空间 |

### MCP：上下文工程的标准化

[[Context_Engineering_Guide#5]] 指出 MCP 使上下文工程从静态向量检索演进到**动态、可组合、可扩展**的系统。三大基础构件：

| 构件 | 说明 | 上下文工程价值 |
|------|------|--------------|
| **Tools** | 可执行的函数 | 扩展模型能力，动态获取和操作上下文 |
| **Resources** | 可读取的数据源 | 多源融合，实时数据获取 |
| **Prompts** | 预定义提示模板 | 标准化上下文呈现，版本管理和复用 |

## 4. 第三阶段：Harness 工程（Harness Engineering）

### 核心关注

> "智能体如何在真实环境中持续、安全、可靠地运行？"

参见 [[Harness_Engineering_Complete_Guide]]、[[Harness_Core_Subsystems]]、[[Harness_Production_Security]]。

### 核心公式

```
Agent = Model + Harness
```

> **模型决定了智能体的思维上限，Harness 决定了智能体的工程下限。**

一个没有 Harness 的大模型只是一台发动机；一个经过 Harness 工程化的智能体才是一辆能够可靠载人行驶的汽车。

### 为什么 Harness 比模型更重要

[[Harness_Engineering_Complete_Guide#2]] 汇总了多项实证研究：

| 来源 | 发现 |
|------|------|
| OpenAI Codex 团队 | 引入 Harness 层后准确率提升 30-40 个百分点，**零模型改进** |
| Bölük "15-LLM-下午"实验 | 仅改变编辑工具接口设计，16 个模型一致提升，最高 +61.6pp |
| LangChain Deep Agents | 纯 Harness 改进，Terminal Bench 从 52.8% 到 66.5%（+13.7pp） |
| Anthropic 反向验证 | 固定模型只改基础设施配置，成功率漂移 +6pp |

**数学论证**：假设 N=100 步，每步成功率 p=90%，无系统工程时整体成功率仅 0.0026%。引入验证+重试 3 次，有效 p' = 99.99%，整体 ≈ 99%。

### Harness 五大核心子系统

| 子系统 | 核心职责 | 参见 |
|--------|---------|------|
| **运行时引擎** | 感知-推理-行动循环，状态机管理 | [[Harness_Core_Subsystems#1]] |
| **工具层** | 注册、发现、参数验证、权限检查、隔离执行 | [[Harness_Core_Subsystems#2]] |
| **记忆子系统** | 工作记忆、短期记忆、长期记忆 | [[Harness_Core_Subsystems#3]] |
| **模型集成与输出治理** | 多模型故障转移、结构化输出解析、幻觉检测 | [[Harness_Core_Subsystems#4]] |
| **编排引擎** | 任务分解、DAG 依赖、多智能体协作 | [[Harness_Production_Security#1]] |

### 五大设计原则

| 原则 | 核心理念 |
|------|---------|
| **约束优先** | 首先定义"不能做什么"，然后在约束内赋能 |
| **可验证性** | 每个行为可观察、可审计、可重放 |
| **渐进信任** | 6 级信任等级，从"每步批准"到"完全自主" |
| **故障假设** | 主动假设每步可能失败，提前设计处理方案 |
| **智能体工学** | 为 Agent（而非人类）设计更好用的软件 |

## 5. 三阶范式的关系：递进包含，非替代

### 层级关系图

```
┌─────────────────────────────────────────────┐
│           Harness Engineering               │
│  ┌─────────────────────────────────────┐    │
│  │       Context Engineering           │    │
│  │  ┌─────────────────────────┐        │    │
│  │  │   Prompt Engineering    │        │    │
│  │  │  指令设计、CoT、Few-shot │        │    │
│  │  └─────────────────────────┘        │    │
│  │  RAG、记忆、压缩、隔离、MCP         │    │
│  └─────────────────────────────────────┘    │
│  工具执行、安全、状态、编排、可观测性        │
└─────────────────────────────────────────────┘
```

### 三阶共存：何时用哪个

| 场景 | 主力范式 | 说明 |
|------|---------|------|
| 一次性查询、API 调用 | 提示词工程 | 关注单次指令的措辞和格式 |
| RAG 系统、多轮对话 | 上下文工程 | 关注完整信息环境的动态管理 |
| 自主智能体、多步任务 | Harness 工程 | 关注系统级的执行控制与验证 |
| 生产级 Agent 系统 | 三者结合 | Prompt 是基础，Context 是核心，Harness 是保障 |

### 关键认知

1. **提示词工程不死**：它是上下文工程的原子单元，写好一条指令永远是基本功
2. **上下文工程是桥梁**：连接"提示词技巧"和"系统工程"的关键过渡层
3. **Harness 工程是终局**：真正可靠的 AI 系统必须用系统工程方法保障

> **核心定律**："中等模型 + 精心设计的 Harness" 远胜于 "顶级模型 + 混乱的架构"。参见 [[Agentic_AI_Complete_Guide#4]]、[[Harness_Engineering_Complete_Guide#2]]。

## 6. 实践演进路线图

```
原型验证 (单 Agent + Prompt Engineering + 基础护栏)
    │
    v
内部测试 (+ Context Engineering: RAG/记忆/压缩)
    │
    v
灰度发布 (+ Harness: 可观测性/评估/成本控制)
    │
    v
生产运行 (+ 多智能体编排/深度防御/持续学习)
```
