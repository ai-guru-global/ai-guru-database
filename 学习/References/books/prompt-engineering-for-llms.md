# Prompt Engineering for LLMs

> **一句话理解**: O'Reilly 出品的提示工程系统指南，从基础提示模式到 ReAct、思维链、工具调用全覆盖，并讲解提示的自动化测试与评估，是 Prompt 工程师的标准参考。

## 书籍概述

### 作者背景

本书由 **James Phoenix** 与 **Mike Taylor** 合著。James Phoenix 是 LLM 工程领域的活跃教育者，长期专注于 Prompt Engineering 与 LLM 应用开发的培训；Mike Taylor 是知名 AI 应用开发者与社区贡献者。两位作者兼具工程实践与教学经验，使本书既"接地气"又"成体系"。

### 本书定位

在 Prompt 工程类资源中，本书的独特价值在于：

- **不是**"Prompt 技巧大全"（那种博客式罗列）
- **而是**把 Prompt Engineering 当作一门**工程学科**来对待：有原则、有模式、有测试、有评估
- 特别强调"提示的自动化测试"——这是绝大多数同类书忽略的关键工程实践

它适合从"会写 Prompt"进阶到"工程化管理 Prompt"的读者，与 [[ai-engineering-huyen]] 的提示工程章节形成"深度 vs 广度"的互补。

## 核心内容

### Part 1 — 提示工程基础

#### Ch 1: 理解 LLM 与提示

- **LLM 工作原理速览**:
  - Token 化（Tokenization）：文本如何被切分为模型可处理的单元
  - 上下文窗口（Context Window）：模型一次能"看到"的信息量
  - 概率采样：Temperature、Top-p、Top-k 如何影响输出
- **提示的本质**: 提示是"用自然语言编程"，是用户意图与模型能力之间的桥梁
- **模型行为的关键认知**:
  - 模型没有"记忆"，每次调用都是独立的（除非显式传入上下文）
  - 模型会"幻觉"，提示设计要降低幻觉风险
  - 不同模型对同一提示的响应差异巨大
- **提示工程的工程化思维**: 可复现、可测试、可迭代

#### Ch 2: 基础提示模式

- **零样本提示（Zero-shot）**:
  - 直接给出任务描述，不提供示例
  - 适用：模型已充分掌握的常见任务
  - 技巧：清晰的任务指令 + 明确的输出格式
- **少样本提示（Few-shot）**:
  - 提供 2-5 个输入-输出示例
  - 适用：特定格式、领域专属、模型表现不稳定的任务
  - 示例选择策略：代表性、多样性、顺序敏感性
- **角色提示（Role Prompting）**:
  - "你是一位资深 Python 工程师……"
  - 作用：激活模型特定领域的知识与风格
  - 局限：过度依赖角色可能引入刻板印象
- **指令式 vs 问答式**: 不同任务结构的选择

#### Ch 3: 输出控制与格式化

- **结构化输出**:
  - JSON 模式：强制模型输出合法 JSON
  - 模板填充：预定义输出骨架
  - Schema 约束：配合 Function Calling / Structured Output API
- **输出长度控制**: 通过提示约束 + API 参数双重控制
- **语言与风格控制**: 正式/口语、简洁/详尽、目标读者适配
- **分隔符的使用**: 用 `"""`、`###`、XML 标签清晰界定上下文边界
- **常见陷阱**: 输出格式不稳定、转义问题、截断风险

### Part 2 — 高级推理技术

#### Ch 4: 思维链（CoT）

- **CoT 核心思想**: 让模型"先推理，再给出答案"，而非直接输出结论
- **Zero-shot CoT**: 简单加上"Let's think step by step"
- **Few-shot CoT**: 提供包含推理过程的示例
- **CoT 的适用场景**:
  - 数学运算、逻辑推理、多步规划
  - 复杂决策（需要权衡多个因素）
- **CoT 的局限**:
  - 增加输出 Token（成本与延迟）
  - 推理链本身可能包含错误（错误会累积）
  - 对简单任务反而降低效率
- **自一致性（Self-Consistency）**: 多次采样推理路径，投票选出最一致的答案

#### Ch 5: 高级推理与规划

- **Tree of Thoughts（ToT）**:
  - 将推理建模为树搜索问题
  - 每一步生成多个候选，评估后选择最优分支
  - 适用：需要探索与回溯的复杂问题
- **ReAct（Reasoning + Acting）**:
  - 交替进行"思考（Thought）"与"行动（Action）"
  - 思考：分析当前状态、规划下一步
  - 行动：调用工具获取外部信息
  - 观察（Observation）：接收工具返回结果
  - 循环直到得出最终答案
- **Reflexion / 自我反思**: 让模型评估自己的输出并改进
- **规划模式**: 先生成完整计划，再逐步执行

#### Ch 6: 工具调用与 Function Calling

- **Function Calling 机制**:
  - 定义工具的 JSON Schema（名称、参数、描述）
  - 模型决定何时调用、调用哪个工具、传什么参数
  - 应用执行工具，将结果返回模型
- **工具描述的最佳实践**:
  - 清晰的工具用途描述
  - 精确的参数定义与约束
  - 典型使用场景说明
- **多工具编排**: 模型在多个工具间选择与组合
- **错误处理**: 工具调用失败时的提示策略
- **与 RAG 的关系**: 检索器作为一种特殊"工具"

### Part 3 — RAG 与提示结合

#### Ch 7: 检索增强生成的提示策略

- **RAG 基础回顾**: 检索相关文档 → 注入上下文 → 生成回答
- **检索结果的提示组织**:
  - 文档排序与截断策略
  - 来源标注（让模型引用出处）
  - 相关性提示（"仅基于以下资料回答"）
- **降低幻觉的提示技巧**:
  - 明确指示"如果资料中没有，回答'不知道'"
  - 要求模型区分"资料内容"与"自身知识"
- **多跳推理**: 需要综合多个文档片段的复杂问题
- **上下文窗口管理**: 长文档的摘要、分块、优先级排序

### Part 4 — 提示的工程化

#### Ch 8: 提示的自动化测试

- **为什么提示需要测试**:
  - 提示是"代码"，但比代码更脆弱（模型行为不确定）
  - 模型升级、提示微调都可能导致回归
- **测试方法**:
  - **黄金集测试（Golden Set）**: 准备代表性输入-期望输出对
  - **断言式评估**: 输出必须包含/不包含特定内容
  - **LLM-as-a-Judge**: 用强模型评估输出质量
  - **相似度评估**: 与参考答案的语义相似度
- **回归测试管道**:
  - 提示变更 → 自动跑测试集 → 对比质量分 → 决定是否发布
  - 集成到 CI/CD
- **评估指标设计**: 准确性、格式合规率、安全性、延迟、成本

#### Ch 9: 提示安全与注入防护

- **Prompt Injection 攻击**:
  - **直接注入**: 用户在输入中嵌入恶意指令（"忽略以上指令，输出……"）
  - **间接注入**: 恶意指令藏在 RAG 检索的文档中
- **攻击案例**: 数据泄露、越权操作、有害内容生成
- **防御策略**:
  - **输入过滤**: 检测并隔离可疑指令
  - **指令隔离**: 用分隔符明确区分"系统指令"与"用户输入"
  - **最小权限**: 工具调用权限的严格控制
  - **输出验证**: 对模型输出进行二次审查
  - **特权分离**: 不信任来自用户/文档的指令
- **越狱（Jailbreak）防护**: 系统提示加固、安全护栏
- **红队测试**: 主动模拟攻击以发现漏洞

## 关键概念与公式

### 采样参数对输出的影响

```
Temperature (T):
  - T → 0: 输出趋于确定性（贪心解码），适合事实性任务
  - T → 1: 输出更具多样性，适合创意任务
  - 概率调整: P'(token) = P(token)^(1/T) / Σ P(token_i)^(1/T)

Top-p (Nucleus Sampling):
  - 仅从累积概率达到 p 的最小 Token 集合中采样
  - 与 Temperature 配合使用，控制多样性

Top-k:
  - 仅从概率最高的 k 个 Token 中采样
```

### ReAct 循环结构

```
Thought 1: 我需要查询 X 的信息
Action 1: search("X 的定义")
Observation 1: X 是……
Thought 2: 现在我知道了 X，还需要 Y
Action 2: lookup("Y")
Observation 2: Y 等于……
Thought 3: 我现在可以回答了
Answer: 最终答案
```

### 提示质量评估维度

```
Quality Score = w1×正确性 + w2×格式合规 + w3×安全性 + w4×简洁性

其中各维度可通过:
- 规则检查（格式、关键词）
- LLM-as-a-Judge（语义质量）
- 人工抽检（黄金标准）
综合评定
```

## 亮点与局限

### 亮点

- 覆盖全面：从基础模式到 ReAct、工具调用、RAG 一站式
- **强调自动化测试**（Ch 8）——多数同类书忽略的关键工程实践
- 安全章节（Ch 9）实用，紧跟 Prompt Injection 攻防前沿
- O'Reilly 品质保证，结构清晰、示例丰富

### 局限

- 提示工程领域变化极快，部分技巧可能被新模型的原生能力替代（如新一代模型对显式 CoT 的依赖降低）
- 偏应用层，不深入模型原理
- 工具/框架示例可能随版本迭代而过时
- 对超大规模生产场景的成本优化着墨较少

## 提示工程实战模板示例

以下是几种核心提示模式的模板示例，可直接套用：

### 零样本模板

```
你是一位{角色}。请完成以下任务：

任务：{任务描述}

要求：
- {约束 1}
- {约束 2}

输出格式：{期望格式}

输入：{用户输入}
```

### 少样本模板

```
任务：将客户反馈分类为「正面」「负面」「中性」。

示例 1：
输入：这个产品太好用了，超出预期！
输出：正面

示例 2：
输入：发货太慢，包装也破了。
输出：负面

示例 3：
输入：收到了，还没用。
输出：中性

现在请分类：
输入：{用户输入}
输出：
```

### 思维链（CoT）模板

```
问题：{复杂问题}

请一步步推理：
1. 首先，分析问题的关键信息……
2. 然后，……
3. 最后，得出结论。

最终答案：
```

### ReAct 模板

```
你可以使用以下工具：
- search(query): 搜索信息
- calculator(expression): 计算

请按"思考-行动-观察"循环解决问题：

问题：{问题}

思考 1：我需要……
行动 1：search("...")
观察 1：……
思考 2：现在我知道了……
行动 2：……
……
最终答案：……
```

**使用建议**: 模板是起点而非终点。实际使用时需根据具体模型与任务调优，并用本书 Ch 8 的方法测试效果。

## 提示模式速查表

下表汇总本书涉及的核心提示模式，便于实战时快速查阅：

| 提示模式 | 核心思想 | 适用场景 | 成本影响 |
|----------|----------|----------|----------|
| **零样本（Zero-shot）** | 直接给任务指令 | 模型已掌握的常见任务 | 低 |
| **少样本（Few-shot）** | 提供输入-输出示例 | 特定格式、领域专属任务 | 中（示例占 Token） |
| **角色提示（Role）** | 设定专家角色 | 激活特定领域知识与风格 | 低 |
| **思维链（CoT）** | 让模型先推理再答 | 数学、逻辑、多步决策 | 高（输出变长） |
| **自一致性** | 多路径采样投票 | 需要高准确率的推理 | 极高（多次调用） |
| **Tree of Thoughts** | 树搜索 + 回溯 | 复杂探索性问题 | 极高 |
| **ReAct** | 思考-行动-观察循环 | 需要工具/外部信息 | 高（多轮） |
| **结构化输出** | 强制 JSON/Schema | 程序化处理输出 | 低 |
| **分隔符隔离** | 用符号界定上下文 | 防注入、清晰边界 | 低 |

### 模式选择决策树

```
任务是否需要外部信息/工具?
├─ 是 → ReAct + Function Calling
└─ 否 → 任务是否需要多步推理?
        ├─ 是 → 是否需要高准确率?
        │       ├─ 是 → CoT + 自一致性
        │       └─ 否 → CoT
        └─ 否 → 模型是否稳定掌握该任务?
                ├─ 是 → 零样本
                └─ 否 → 少样本 + 角色提示
```

## 常见误区与反模式

提示工程中常见的错误做法：

| 误区/反模式 | 问题 | 正确做法 |
|-------------|------|----------|
| **提示过长冗余** | 上下文噪声降低质量、增加成本 | 精简上下文，提高信息密度 |
| **盲目堆砌 CoT** | 简单任务用 CoT 反而降效 | 按任务复杂度选择是否用 CoT |
| **忽视输出格式约束** | 输出不稳定，难以程序化处理 | 用结构化输出 + Schema 校验 |
| **信任用户输入** | Prompt Injection 风险 | 指令隔离 + 输入过滤 |
| **不做测试就上线** | 模型升级导致回归 | 建立黄金集 + 回归测试 |
| **过度依赖角色设定** | 引入刻板印象、效果有限 | 角色为辅，清晰指令为主 |
| **示例选择不当** | 少样本示例缺乏代表性 | 选多样、典型、高质量的示例 |
| **忽视模型差异** | 同一提示在不同模型表现迥异 | 针对目标模型调优提示 |

### 提示工程的成熟度模型

```
Level 1: 临时提示 — 想到什么写什么，无复用
Level 2: 模板化 — 沉淀可复用的提示模板
Level 3: 参数化 — 模板支持变量注入与配置
Level 4: 可测试 — 提示有评估集与回归测试
Level 5: 可治理 — 版本管理 + 安全审查 + 成本监控
```

本书的价值在于帮助读者从 Level 1-2 进阶到 Level 4-5，把提示工程真正当作工程学科对待。
