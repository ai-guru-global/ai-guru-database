# AI 系统故障响应 (Incident Response for AI)

> **TL;DR**: AI 系统的故障与传统软件不同——模型漂移是渐进的、幻觉是概率性的、Prompt 注入是人为攻击。建立 AI 专属的故障分类体系、标准化 Runbook、明确升级路径和 Blameless Post-Mortem 流程，是保障 AI 系统生产可靠性的关键。

## 1. AI 特有故障模式

### 1.1 故障模式分类表

| 类别 | 故障模式 | 触发原因 | 检测方式 | 严重度 |
|------|----------|----------|----------|--------|
| **模型退化** | Model Drift (模型漂移) | 数据分布变化 | 性能指标缓慢下降 | P2-P3 |
| **模型退化** | Concept Drift (概念漂移) | 标签含义变化 | 评估集准确率下降 | P2-P3 |
| **模型退化** | 幻觉激增 (Hallucination Surge) | Prompt 变化/模型更新 | 幻觉率突增告警 | P1-P2 |
| **安全威胁** | Prompt 注入 (Prompt Injection) | 恶意用户输入 | 安全过滤器触发 | P1-P2 |
| **安全威胁** | 数据泄露 (Data Leakage) | 模型记忆训练数据 | 输出审计 | P1 |
| **安全威胁** | 越狱攻击 (Jailbreak) | 对抗性 Prompt | 拒绝率异常 | P1-P2 |
| **数据管线** | 特征存储故障 (Feature Store) | 上游数据源变化 | 特征缺失告警 | P1-P2 |
| **数据管线** | 训练数据污染 | 错误标注/数据源问题 | 数据质量检查 | P2 |
| **数据管线** | 实时特征延迟 | 流处理系统故障 | 特征延迟告警 | P1 |
| **推理服务** | 模型加载失败 | 模型文件损坏/OOM | 健康检查 | P1 |
| **推理服务** | 推理延迟飙升 | GPU 资源争用 | 延迟 P99 告警 | P1-P2 |
| **推理服务** | 输出格式异常 | 模型版本不匹配 | Schema 校验 | P2 |
| **依赖服务** | LLM API 故障 | 供应商宕机/限流 | 错误率告警 | P1 |
| **依赖服务** | 向量数据库故障 | RAG 检索失败 | 检索延迟/错误率 | P1-P2 |
| **依赖服务** | 缓存穿透 | Redis 故障 | 缓存命中率下降 | P2 |

### 1.2 AI 故障的特殊性

```
AI 故障 vs 传统软件故障:
═══════════════════════════════════════════════════════════════

  传统软件故障                   AI 系统故障
  ┌──────────────────┐          ┌──────────────────┐
  │ 二元的: 工作/不工作 │          │ 渐进的: 质量缓慢退化│
  │ 确定性的: 可复现    │          │ 概率性的: 偶发出现  │
  │ 告警明确: 500 错误  │          │ 告警模糊: "质量下降" │
  │ 回滚即可: git revert│          │ 回滚复杂: 数据已变  │
  │ 影响可控: 该功能挂   │          │ 影响扩散: 所有功能  │
  └──────────────────┘          └──────────────────┘
```

## 2. 故障分类体系

### 2.1 按影响范围分类

| 影响级别 | 描述 | 示例 |
|----------|------|------|
| **全局** | 所有用户受影响 | 推理服务宕机、LLM API 不可用 |
| **部分** | 特定用户群/功能受影响 | 特定 prompt 模板幻觉率高 |
| **个体** | 单个请求异常 | 某次推理输出无意义 |
| **隐性** | 无即时用户感知，但影响长期质量 | 模型漂移、训练数据偏差 |

### 2.2 按紧急度分类

| 紧急度 | 描述 | 响应时间 |
|--------|------|----------|
| **即时** | 正在造成持续损害 | < 5 分钟 |
| **紧急** | 影响用户体验但不扩散 | < 30 分钟 |
| **常规** | 质量退化但业务可容忍 | < 4 小时 |
| **计划** | 需要修复但不紧急 | 下个迭代 |

## 3. 事故分级

| 等级 | 定义 | 示例 | 响应要求 |
|------|------|------|----------|
| **SEV-1** | 核心服务不可用，大量用户受影响 | 推理服务全面宕机；模型输出严重有害内容 | IC 指挥，全员响应，15 分钟更新 |
| **SEV-2** | 核心功能降级，用户明显受影响 | 幻觉率 > 30%；主要功能延迟 > 10s | On-call 主导，1 小时更新 |
| **SEV-3** | 非核心功能异常，用户轻微不便 | 次要模型漂移；非关键 API 间歇失败 | On-call 评估，工作日处理 |
| **SEV-4** | 无用户感知的内部问题 | 日志缺失；监控指标异常但不影响输出 | 记录 + 下迭代修复 |

## 4. Runbook 模板

### 4.1 通用 Runbook 结构

```markdown
## Runbook: [故障名称]

### 触发条件
- 告警名称 + 阈值

### 第一步: 确认影响
1. 检查 [监控看板 URL]
2. 确认影响范围: 全局 / 部分 / 个体
3. 确定事故等级 (SEV-1 ~ SEV-4)

### 第二步: 缓解 (止血)
1. [具体操作命令]
2. [回滚/降级/限流步骤]
3. 验证缓解效果

### 第三步: 根因定位
1. 检查 [日志/追踪/指标]
2. 对比最近变更 (模型版本、Prompt、数据)
3. 确认根因

### 第四步: 修复与验证
1. [修复步骤]
2. [验证测试]
3. 解除缓解措施

### 回滚方案
- [模型版本回滚命令]
- [配置回滚步骤]

### 升级路径
- 30 分钟未缓解 → 升级到 [人员/团队]
- 涉及安全 → 立即通知 [安全团队]
```

### 4.2 AI 特故障 Runbook 示例: 幻觉率激增

```
Runbook: 幻觉率激增 (Hallucination Surge)
═══════════════════════════════════════════════════════════════

  触发: hallucination_rate > 15% (基线 5%)

  第一步: 确认 (5 分钟内)
  ├── 检查 LangFuse/LangSmith 的幻觉率趋势
  ├── 确认影响范围: 所有 Prompt? 特定模板?
  └── 检查最近 24h 的变更: 模型版本? Prompt 模板? 检索策略?

  第二步: 止血 (15 分钟内)
  ├── 如果是模型版本更新导致 → 回滚到上一版本
  ├── 如果是 Prompt 变更导致 → 回滚 Prompt 模板
  ├── 如果是检索质量下降 → 切换到 fallback 检索源
  └── 如果无法快速定位 → 启用保守模式 (降低 temperature, 加 grounding)

  第三步: 根因分析
  ├── 对比故障前后 Prompt 差异
  ├── 检查检索文档质量 (是否返回无关文档)
  ├── 分析幻觉样本: 事实错误? 逻辑错误? 虚构内容?
  └── 检查模型供应商是否有静默更新

  第四步: 修复
  ├── 修复根因后灰度发布
  ├── 监控 30 分钟确认稳定
  └── 更新评估集，加入故障样本
```

## 6. Post-Mortem 流程

### 6.1 Blameless Post-Mortem 原则

1. **不追责，只追因**: 关注系统和流程缺陷，而非个人失误
2. **时间线驱动**: 从告警到恢复的完整时间线
3. **数据说话**: 用指标和日志佐证每个时间点的状态
4. **Action Items 必须可执行**: 每个改进项有 Owner 和 Deadline

### 6.2 Post-Mortem 模板

```markdown
# Post-Mortem: [事故标题]

## 概要
- 日期/时间: YYYY-MM-DD HH:MM - HH:MM (持续 X 分钟)
- 事故等级: SEV-X
- 影响范围: [哪些用户/功能/地区]
- IC (事故指挥官): [姓名]

## 时间线
| 时间 | 事件 | 负责人 |
|------|------|--------|
| HH:MM | 告警触发: [告警名] | 系统 |
| HH:MM | On-call 确认，开始排查 | [姓名] |
| HH:MM | 确认 SEV-X，启动 War Room | [姓名] |
| HH:MM | 执行缓解措施: [措施] | [姓名] |
| HH:MM | 缓解生效，指标恢复 | 系统 |

## 根因分析
[详细描述根因，包括技术细节]

## 影响评估
- 受影响用户数: X
- 受影响请求数: X
- 错误请求占比: X%
- 财务影响: $X (如可估算)

## 做得好的
- [列出响应中做得好的地方]

## 需要改进的
- [列出响应中的不足之处]

## Action Items
| 编号 | 改进项 | 类型 | Owner | Deadline |
|------|--------|------|-------|----------|
| 1 | [具体改进] | 预防/检测/响应 | [姓名] | YYYY-MM-DD |
| 2 | [具体改进] | 预防/检测/响应 | [姓名] | YYYY-MM-DD |
```

### 6.3 AI 系统 Post-Mortem 额外关注

| 关注点 | 检查项 |
|--------|--------|
| 模型版本 | 故障期间运行的是哪个模型版本? 是否有静默更新? |
| Prompt 变更 | 故障前后 Prompt 模板是否有变更? |
| 数据质量 | 检索文档/训练数据是否出现质量问题? |
| 评估覆盖 | 现有评估集能否检测到此故障? 需要补充什么? |
| 安全影响 | 故障期间是否产生了有害/不当输出? |
