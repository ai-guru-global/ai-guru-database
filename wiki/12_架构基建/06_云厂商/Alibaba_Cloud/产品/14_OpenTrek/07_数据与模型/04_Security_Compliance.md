# OpenTrek 安全合规体系：隔离、护栏与审计

> 中文简称：安全合规体系

> **一句话理解**: 让 Agent 在企业里安全落地：代码关进沙箱、钥匙统一管、内容有护栏、数据不出门、事事可追溯。

---

## 一、官网安全能力清单

官网安全表述可拆为五项能力，各自对应一类真实风险：

| **能力** | **官网口径** | **对应的真实风险** |
| --- | --- | --- |
| Agent 沙箱级隔离 | 执行环境隔离防逃逸 | Agent 执行代码/调用工具时逃逸出受控环境 |
| 凭证统管 | 密钥集中管理不散落 | API Key 等散落在代码、配置、日志中泄露 |
| 多模态安全护栏 | 输入输出内容跨模态检测 | 文本、图像等多模态内容的违规输入与输出 |
| 防泄漏 | 数据不出域设计 | 敏感数据随模型调用或 Agent 外联流出企业 |
| 可审计 | 全链路审计留痕 | 操作不可追溯、出事后无法定责 |

五项能力组合的意图：把 Agent 体系最常见的三类事故——执行失控、凭证泄露、数据外流——分别用隔离、统管、不出域兜住，再用护栏拦内容风险、用审计兜底追责。

按作用层归纳：

```text
- 执行层：沙箱隔离、凭证统管
- 内容层：多模态安全护栏
- 数据层：防泄漏（数据不出域）
- 横切层：可审计（全链路留痕）
```

执行层两项与本系列 [[12_架构基建/06_云厂商/Alibaba_Cloud/产品/14_OpenTrek/05_生产运行/04_AgentRuntime_Sandbox|AgentRuntime 沙箱]] 页直接相关；护栏与防泄漏作用在内容与数据层；审计横跨全链路。

## 二、行业合规映射

官网按行业场景给出安全能力的组合方式：

| **行业** | **合规关注点** | **OpenTrek 能力组合（官网口径）** |
| --- | --- | --- |
| 政务 | 网络隔离、内容安全、行为留痕 | 网络隔离 + 内容安全检测 + 审计日志 |
| 金融 | 监管框架下的数据治理 | 数据治理框架满足监管要求 |
| 泛企业 | 数据主权与落地成本 | 数据本地闭环 |

分析视角：这张映射表回答「能力有没有」，不等于「合规评估过没过」。落地仍要按具体监管文件逐条对齐，能力项只能作为技术响应项，不能替代合规评估结论。

```text
分行业落地提示（分析视角）：
- 政务：网络隔离常要求专网级，部署架构评审要先行确认
- 政务：内容安全检测需同时覆盖生成侧与检索侧
- 金融：数据治理对齐字段级监管要求（留存、分级、脱敏）
- 泛企业：本地闭环优先级高于极致性能，先守住数据边界
```

行业方案细节可对照 [[12_架构基建/06_云厂商/Alibaba_Cloud/产品/14_OpenTrek/02_部署与行业/02_Government_Solution|政务解决方案]] 与 [[12_架构基建/06_云厂商/Alibaba_Cloud/产品/14_OpenTrek/02_部署与行业/03_Finance_Solution|金融解决方案]]。

## 三、认证口径辨析：信通院认证

对「认证」类表述，库内一贯做法是区分营销渠道与官方口径——这是 AI Stack 营销口径纠偏传统的延续。

```text
认证口径辨析：
- 事实：部分宣传渠道（新闻稿/媒体报道）提及 OpenTrek 相关「信通院认证」
- 核对：官网产品页（2026-11 检索）安全能力清单未列明该项认证
- 处理：按「营销渠道提及、官方产品页未列、以官方最新资质文件为准」记录
- 动作：采购/投标引用认证时，要求供应商出示证书原件或官方资质页
```

同一条纪律适用于「等保」「密评」等其他资质表述：渠道说得再满，引用前一律回到官方资质文件核对。

口径纪律的意义：投标文件里写了一条拿不出原件的认证，澄清成本由方案方承担；引用前多一步核对，代价远小于事后补救。

## 四、私有化安全边界：数据不出域 vs 公有云共享责任

OpenTrek 的安全叙事建立在私有化「数据不出域」之上，与公有云共享责任模型是两种责任结构（分析视角）：

| **维度** | **OpenTrek 私有化（数据不出域）** | **公有云共享责任模型** |
| --- | --- | --- |
| 数据边界 | 数据留在企业域内处理 | 数据上云，双方按责任分界各管一层 |
| 安全控制权 | 企业自主掌控全套安全栈 | 云厂商负责平台安全，客户负责配置与数据 |
| 审计 | 全链路审计留痕落在本地 | 依赖云平台审计服务与客户侧开启配置 |
| 边界代价 | 安全栈自建自运维，上限取决于自身能力 | 底层安全由厂商规模化提供，需划清信任边界 |

一句话对比：私有化把安全边界收窄到企业域内，换来控制权，代价是自运维；公有云把底层安全交给厂商，换来规模化能力，代价是责任分界线必须划清。OpenTrek 选前者，安全能力清单正是给「自持安全栈」补齐产品化组件。

## 五、落地 checklist

把官网能力清单转成可执行动作：

```text
凭证台账
- [ ] 所有 Agent 使用的密钥/API Key 统一登记入台账
- [ ] 定义轮换周期与撤销路径，杜绝散落在代码/配置里
护栏策略灰度
- [ ] 多模态护栏策略先灰度小流量，监控误杀率再全量
- [ ] 输入/输出两侧护栏分开评估，跨模态内容单独测
审计日志留存周期
- [ ] 按所属行业监管要求确定留存时长（政务/金融口径不同）
- [ ] 明确日志存储位置与防篡改措施
- [ ] 定期演练审计日志的检索与回放
沙箱逃逸演练
- [ ] 定期红队演练：诱导 Agent 越权访问文件/网络/凭证
- [ ] 演练结果回流，加固沙箱策略与护栏规则
```

checklist 四组动作分别对应凭证统管、多模态护栏、可审计、沙箱隔离四项官网能力；防泄漏由私有化部署形态本身承担，架构评审里确认所有外联通道走受控网关即可——网关侧能力可对照本系列 [[12_架构基建/06_云厂商/Alibaba_Cloud/产品/14_OpenTrek/05_生产运行/02_AI_Gateway|AI 网关]] 与 [[12_架构基建/06_云厂商/Alibaba_Cloud/产品/14_OpenTrek/05_生产运行/03_Token_Governance|Token 治理]] 页。
