# Context Engineering (上下文工程)

## 定义

上下文工程是一门系统性的工程学科，研究如何设计、组织、优化和管理大语言模型所需的全部信息环境，以确保模型在正确的时间获得正确的信息，从而产生准确、可靠、符合预期的输出。核心命题是：**在正确的时间，将正确的信息，以正确的格式，提供给模型。**

## 核心机制

### 从提示词工程到上下文工程的演进

| 维度 | 提示词工程 | 上下文工程 |
|------|------------|------------|
| **关注点** | 单次指令的措辞和格式 | 完整信息环境的设计 |
| **范围** | 提示词文本 | 指令、数据、工具、记忆、策略 |
| **时间维度** | 静态、一次性 | 动态、跨会话 |
| **信息来源** | 手工编写 | 多源融合、自动检索 |
| **工程化程度** | 技巧驱动、经验依赖 | 系统化、可量化、可测试 |

Anthropic 在其工程博客（2025-09-29）明确把上下文工程定义为"在推理过程中策划与维护最优 Token 集合的一整套策略"，并指出**提示词工程是上下文工程的一个子集**。

### 四大核心策略 (Write / Select / Compress / Isolate)

```
原始信息 --> Write(写入) --> 存储 --> Select(选择) --> Compress(压缩) --> Isolate(隔离) --> 最终上下文
```

1. **Write（写入）**：在上下文窗口之外存储和管理信息——外部记忆系统、知识库、向量数据库、多层记忆架构
2. **Select（选择）**：从海量信息中获取最相关内容——语义检索、关键词检索、混合检索、重排序
3. **Compress（压缩）**：在有限空间中容纳更多有效信息——文本摘要、信息提取、对话压缩、递进式摘要
4. **Isolate（隔离）**：组织和结构化不同类型的信息——XML 标签标记、指令分层、任务隔离、多智能体编排

### 上下文分层结构

```
系统层：角色定义、行为准则        -- 最稳定，可缓存复用
知识层：领域知识、参考文档        -- 相对稳定
任务层：当前任务具体要求          -- 随任务变化
交互层：对话历史、用户输入        -- 最动态
```

### 注意力预算与上下文腐烂

- **注意力预算（Attention Budget）**：上下文越长，关键信息越容易被噪声干扰，必须当作有限资源管理
- **上下文腐烂（Context Rot）**：随 Token 数量增加，模型对关键信息的提取稳定性下降（"Lost in the Middle"效应）
- **核心指导原则**：找到最小可能的高信号 Token 集，以最大化实现期望结果的可能性

## 关键设计决策

- **前缀缓存排列策略**：将不变内容（系统提示词）放前部享受缓存命中，变化内容（用户输入）放末尾——缓存命中价格通常仅为常规输入的 10%
- **边界泄漏防御**：写入层存储的外部内容、选择层召回的文档可能混入"指令"文本，需在隔离层前保留来源、权限和可信等级标记
- **压缩率上限**：避免一次性压缩超过 60-70%，关键约束放入"不可压缩层"
- **上下文相关性审计**：定期抽样检查送入模型的完整上下文，相关内容占比低于 50% 说明存在严重污染
