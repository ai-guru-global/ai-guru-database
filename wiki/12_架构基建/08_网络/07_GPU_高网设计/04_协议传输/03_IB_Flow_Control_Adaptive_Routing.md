# IB 流控与自适应路由：协议内建的无损与选路

> 中文简称：IB 流控与自适应路由

> **一句话理解**: InfiniBand 把“不许丢包”和“自动绕开堵点”直接写进协议与交换机，不必像以太那样外挂 PFC/ECN 一堆补丁。

---

## 一、credit-based 链路层流控：从源头杜绝丢包

IB 在链路层就解决“接收方 buffer 会不会被灌爆”的问题，机制是 credit（信用额度）：

1. 链路两端的接收 buffer 按 **VL（Virtual Lane，虚通道）** 划分成独立份额（规格上最多 15 条数据 VL）；
2. 接收方把各 VL 当前可用的 credit 通告给发送方，捎带在链路层包里；
3. 发送方每发一个包消耗一个 credit，收到补充 credit 才能继续发；
4. 结果：发送速率被接收能力实时钳制，**缓冲溢出这种丢包在协议层面不可能发生**。

它与 PFC 的本质区别：

- PFC 是**事后反压**：快满了才向上游发 pause 帧喊停，pause 还要跨设备传播、逐级放大；
- credit 是**事前准入**：拿到许可才能发，全程融在协议数据单元内，没有专门的控制帧风暴；
- credit 的补充通告持续捎带在数据包里，不占额外带宽预算，也不需要独立的控制报文格式；
- 误码不等于拥塞丢包：逐跳 CRC 校验加本地重传把坏包在当前跳修好，不向端点传播。

再配合 SL（Service Level）到 VL 的映射，不同服务等级的流量互不挤占对方 buffer，隔离是结构性的，不靠配置自律。

类比记忆：PFC 像先泼水再喊停，credit 像凭票供水——票发多少收多少，永远不会漫出来。

## 二、为什么 IB 不需要 PFC/ECN/DCQCN 那套

- **无损**由链路层 credit 流控内建，不依赖每台交换机的配置哲学；
- **拥塞管理**同样协议内置：拥塞交换机给包打 **FECN**（前向显式拥塞通知），目的端回送 **BECN**（后向显式拥塞通知），源端网卡（CA，Channel Adapter）据此执行拥塞控制降速——功能上等价于把 DCQCN 的三角色闭环原生写进协议；
- **SL/VL 映射**提供流量隔离与防死锁的结构性手段，配合路由引擎的 VL 分配，从拓扑层面避免环等待；
- 死锁防御也是结构性的：路由计算时避免循环依赖，配合 VL 约束，从源头上不让环等待出现；
- 重传在链路层逐跳完成，端到端看不到丢包，也不会像 RoCE 那样把单点丢包放大成整段回退；
- 工程含义：IB 省掉了“逐台交换机逐端口调 PFC/ECN 阈值”的苦活，代价是整套栈只能向极少数厂商采购。

| **能力** | **以太 RoCE 方案** | **IB 方案** |
|---|---|---|
| 不丢包 | 外挂 PFC + headroom 精调 | 链路层 credit 流控内建 |
| 拥塞控制 | ECN 打标 + DCQCN 外挂闭环 | FECN/BECN + CA 侧原生拥塞控制 |
| 流量隔离 | 优先级队列 + PFC 分类 | SL/VL 映射 |
| 调参负担 | 每台交换机每端口审计 | 交换机基本免调，SM 统一算路 |

对照着看：以太三件套解决的所有问题（不丢包、早预警、降速率），IB 都在协议内部给了原生答案，这也是 IB 交换机“免调参”口碑的来源。

## 三、Adaptive Routing：交换机自己绕开堵点

- 原理：交换机转发时依据**本地队列占用状态**动态选输出端口——发现某出口排队变深，就走别的等价路径；
- 粒度权衡：逐包（per-packet）最均衡但乱序重排压力大；逐流（per-flow）实现简单、无乱序，但仍可能撞热点；产品通常两种都提供、按场景配；
- 乱序到达由**目的端网卡（HCA）重排序**，上层软件无感；
- 收益：链路利用率显著更均衡，incast 与大象流场景不会像静态哈希那样把热点链路压死；
- 直观例子：几十台服务器同步做 AllReduce，若流哈希集中到同一条上行，那条链路瞬间过载；AR 会把其中一部分包改道空闲上行，当整体完成时间由最慢链路决定时，收益立现；
- 对 GPU 负载尤其有效：训练流量高度同步，成百上千张卡同一时刻打向同一目标，正是静态选路最容易撞热点的形态；
- 与拥塞控制互补：AR 处理空间维度的负载不均，FECN/BECN 处理时间维度的突发，两者配合而不是替代；
- 提示：与 SHARP 等在网特性同时启用时存在互斥或约束，按厂商兼容矩阵核对（见 SHARP 页）。

## 四、与以太 ECMP 的对比

| **维度** | **以太 ECMP** | **IB Adaptive Routing** |
|---|---|---|
| 决策依据 | 五元组哈希，路径静态 | 本地队列状态，逐包/逐流动态 |
| 均衡性 | 大流可能哈希撞同一条链路（极化），热点无法自愈 | 队列感知，热点自动绕开 |
| 乱序 | 同一流恒定路径，天然有序 | 允许乱序，HCA 重排序 |
| 可观测性 | 依赖逐台采集与流量采样 | 队列与选路状态内建于转发路径，SM 可全局查询 |
| 依赖 | 标准以太即可 | IB 交换机与 HCA（以太侧要 Spectrum-X 类增强才有近似能力） |

ECMP 的短板在 GPU 集群被放大：训练流数量少、单流大，几条 elephant 流就可能把某条上行打满，而其余上行闲着。这也是以太阵营后来纷纷补自适应路由的原因（见路线之争页）。

## 五、Subnet Manager：拓扑发现与路由计算

- 每个 IB 子网必须有一个活动 **SM（Subnet Manager）**；开源实现是 opensm，商用如 UFM；
- SM 通过管理包遍历子网，发现所有交换机、主机与链路（拓扑发现），为端口分配 **LID**；
- 再按所选路由引擎（如 **ftree** 胖树算法）计算并下发每台交换机的转发表；
- 路由引擎选择要与物理拓扑匹配：引擎选错会出现负载不均甚至死锁风险，ftree 只适合结构匹配的胖树；
- 拓扑变化（链路故障、设备增删）触发 SM 重算路由；
- 多 SM 实例通过选举产生主备，主 SM 故障后备用接管，期间存量转发表保持稳定；
- SM 完全不可用时子网丧失响应变更的能力，生产环境 SM 高可用是硬要求；
- 转发表与 LID 空间要随集群扩张预留余量，超大规模子网需提前规划分区。

常用命令：

```bash
opensm -F /etc/opensm/opensm.conf   # 启动 subnet manager（生产用托管/高可用方式）
ibdiagnet                           # 子网健康体检：链路、拓扑与一致性
ibroute <LID>                       # 查看指定交换机当前转发表
```

## 六、IB 的代价

- **专网**：NIC 与交换机供应商高度集中（NVIDIA 主导），无法复用以太的白盒与多源采购生态；
- **license 与管理软件**：opensm 免费但大规模运维普遍依赖 UFM 等商业软件，按端口收费；
- **生态封闭**：监控、排障工具链与人才池都远小于以太，团队要专门养人；
- **代际节奏绑定**：带宽升级（HDR → NDR 400G → XDR 800G）跟随 NVIDIA 产品节奏，采购议价空间小；
- **混合现实**：很多集群把 IB 用在训练专网、用以太承载存储与管理面，两套技能栈都得养；
- 一句话：买 IB 买的是“开箱即用的无损 + 原生拥塞管理 + 自适应路由”，付的是溢价与锁定；这笔账怎么算，见本系列路线之争页与容量成本章。
