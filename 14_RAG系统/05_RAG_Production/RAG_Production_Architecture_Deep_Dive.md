## 1. 生产 RAG 的定位与挑战

在企业生产环境中，RAG 系统通常被用作**知识密集型应用的核心基础设施**：内部知识库问答、客服助手、合规审查、研发文档助手等。与原型不同，生产 RAG 需要同时满足以下约束：

| 维度 | 原型阶段 | 生产阶段 |
|------|---------|---------|
| **延迟** | 数秒可接受 | 通常要求 P95 < 2s，复杂查询 < 5s |
| **准确率** | 主观可用 | 检索 Recall@K > 85%，Faithfulness > 90% |
| **可用性** | 本地/单机 | 多可用区、自动故障转移、SLA 99.9%+ |
| **数据更新** | 全量重建索引 | 增量更新、版本回滚、审计追踪 |
| **合规** | 基本不关注 | 权限隔离、数据出境、AIGC 标识、审计日志 |
| **成本** | 不敏感 | 按 Token、按 GPU、按存储精细化核算 |

生产 RAG 最常见的失败模式不是算法问题，而是**工程治理缺失**：文档解析质量不稳定、索引版本与 embedding 模型不一致、检索与生成环节缺乏监控、合规要求未在管线中落地。

### 1.1 五大工程挑战

1. **数据质量不可控**：企业文档格式混杂、版本众多，扫描件、手写批注、复杂表格、PPT 图片化等问题导致解析错误率居高不下。解析阶段的错误会一路传导到检索与生成。
2. **检索与生成耦合**：很多团队把"召回 Top-K"和"LLM 生成"当作两个独立黑盒，缺少端到端的 bad case 归因能力。检索命中但生成失败、检索未命中但生成碰巧正确，都需要分别定位。
3. **延迟与成本的权衡**：Hybrid Search、Rerank、多轮 Agentic 检索都会显著提升效果，但也会线性增加延迟和调用成本。生产环境必须建立明确的延迟 SLO 与成本预算。
4. **多租户与数据隔离**：企业知识库天然涉及不同部门、不同职级、不同项目的权限边界。向量数据库的元数据过滤必须与 IAM (Identity and Access Management) 体系打通。
5. **持续运营与版本管理**：文档会更新、embedding 模型会升级、切分策略会调整。如何在不中断服务的前提下完成索引迁移，是生产 RAG 与原型最大的区别之一。

## 2. 架构演进：经典 RAG → Advanced RAG → Agentic RAG

### 2.1 三个阶段的能力边界

```text
经典 RAG (2023)
├── 固定分块 + 纯向量检索
├── 直接拼接 Top-K 上下文
└── 准确率瓶颈：60-75%

Advanced RAG (2024-2025)
├── 语义分块 / Parent-Document / 结构感知解析
├── Hybrid Search (Dense + Sparse) + Rerank
├── 查询重写 (Query Expansion / HyDE / Step-back)
├── 上下文压缩与引用生成
└── 准确率：80-90%

Agentic RAG (2025-2026)
├── 动态决策：是否需要检索、检索几次、何时停止
├── 工具调用：搜索引擎、数据库、知识图谱、代码仓库
├── 多跳推理与 Self-RAG / Corrective RAG
├── 检索-生成-反思循环
└── 准确率：90%+
```

### 2.2 生产架构推荐

多数企业**不需要一上来就构建完整的 Agentic RAG**。建议按阶段演进：

1. **MVP 阶段**：经典 RAG，验证业务价值；
2. **规模化阶段**：引入 Advanced RAG，解决召回与幻觉；
3. **复杂任务阶段**：引入 Agentic RAG，处理多跳、工具调用、动态决策。

### 2.3 典型生产组件拓扑

```text
┌─────────────────────────────────────────────────────────────┐
│                        API Gateway                           │
│         (鉴权 / 限流 / 路由 / 成本归因 / Fallback)            │
└───────────────────────┬─────────────────────────────────────┘
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│ Query Rewrite│ │   Embedding  │ │  Reranker    │
│   Service    │ │   Service    │ │  Service     │
└──────┬───────┘ └──────┬───────┘ └──────┬───────┘
       │                │                │
       └────────┬───────┴────────────────┘
                ▼
       ┌─────────────────┐
       │   Vector DB     │
       │  + BM25 Index   │
       │  + Metadata     │
       └────────┬────────┘
                │
                ▼
       ┌─────────────────┐
       │  Context Builder│
       │  (压缩 / 引用)   │
       └────────┬────────┘
                │
                ▼
       ┌─────────────────┐
       │      LLM        │
       │  (vLLM/SGLang)  │

```

该拓扑将各组件拆分为独立服务，便于独立扩缩容、灰度发布与故障隔离。

## 3. 文档摄取管线：从原始文件到可检索索引

文档摄取是生产 RAG 的"地基"，其质量决定了检索与生成效果的上限。

### 3.1 管线各阶段职责

```text
原始文档 (PDF/Word/HTML/Excel/图片/视频)
    ↓
文档解析 (Parser / OCR / 表格还原 / 版式识别)
    ↓
文档切分 (Chunking: 固定 / 语义 / 结构 / Agentic)
    ↓
向量化 (Embedding Model，通常配合 Matryoshka 动态维度)
    ↓
索引写入 (Vector DB + BM25 / Sparse Vector / 元数据)
    ↓
版本管理 (索引版本、Embedding 版本、解析规则版本)
```

### 3.2 解析层关键决策

| 文档类型 | 常见陷阱 | 推荐方案 |
|---------|---------|---------|
| **扫描版 PDF** | 纯文本抽取为空或乱序 | OCR + 版式分析 (如 PaddleOCR、Marker、Unstructured) |
| **复杂表格** | 表格被切分为孤立文本 | 表格结构还原为 Markdown/HTML，保留行列关系 |
| **多栏排版** | 阅读顺序错误 | 使用版式感知的解析器，按阅读顺序输出 |
| **代码文档** | 函数签名与实现被切断 | 按 AST 或代码块边界切分 |
| **多模态文档** | 图片信息丢失 | 图文交错索引，必要时使用多模态 embedding |

### 3.3 切分策略

生产中推荐组合策略：

- **通用文本**：递归切分，chunk size 256-512 tokens，overlap 10-20%;
- **技术文档/法律合同**：结构感知切分，按章节、条款、条款编号保留层级;
- **长文档**：Parent-Document Retrieval（小到大的双粒度索引）;
- **表格密集文档**：整张表格或按行切分，并保留表头;
- **代码库**：按函数/类/文件切分，保留 import 与调用关系。

### 3.4 索引版本管理

生产环境必须保证 **Embedding 模型、分块策略、索引数据** 三者版本一致。推荐做法：

```yaml
# 索引版本配置示例
index_version: "v20260702-001"
embedding_model: "BAAI/bge-m3"
embedding_dimension: 1024
chunk_size: 512
chunk_overlap: 64
parser_version: "marker-1.0.2"
allowed_tenants: ["hr", "finance", "rd"]
```

每次重建或增量更新索引时，生成新的版本目录；线上服务通过 alias 切换版本，保留旧版本至少 7 天以便回滚。

### 3.5 增量更新与脏数据治理

生产环境文档持续新增、修改、删除，必须支持增量索引：

- **文档指纹**：为每份原始文档计算内容哈希，避免重复解析;
- **变更检测**：监听文件系统、对象存储事件或 CMS 发布事件，触发增量任务;
- **分段删除**：按文档 ID 删除已失效的 chunk，而非全量重建;
- **索引合并**：Milvus/Qdrant 等数据库支持分区与 segment 合并，定期压缩小文件;
- **脏数据拦截**：建立解析质量门槛，例如 OCR 置信度 < 85% 的页面进入人工复核队列，避免低质量文本污染索引。

推荐将摄取管线拆分为独立服务，通过消息队列解耦，便于横向扩展与失败重试。

## 4. 检索策略：从召回率到精度的全链路优化

### 4.1 混合检索 (Hybrid Search)

单一向量检索在精确术语、产品型号、法律条文等场景下容易"语义漂移"。生产环境普遍采用 **Dense + Sparse** 混合检索：

```python
# 伪代码：RRF 融合 Dense 与 BM25 结果
def hybrid_search(query, top_k=20, final_k=5):
    # 1. Dense 检索
    dense_results = vector_db.search(query_embedding(query), top_k=top_k)
    # 2. Sparse / BM25 检索
    sparse_results = bm25_index.search(query, top_k=top_k)
    # 3. RRF 融合
    fused = reciprocal_rank_fusion([dense_results, sparse_results], k=60)
    # 4. Cross-Encoder 重排序
    reranked = reranker.rerank(query, fused[:final_k*2], top_k=final_k)
    return reranked
```

### 4.2 查询扩展 (Query Expansion)

| 策略 | 原理 | 适用场景 | 成本 |
|------|------|---------|------|
| **Multi-Query** | LLM 生成 3-5 个查询变体，合并检索结果 | 召回率优先、问题表述多样 | 中 |
| **HyDE** | 生成假设答案，用答案向量检索 | 复杂开放性问题 | 中 |
| **Step-back** | 将具体问题抽象为通用概念，再检索 | 需要背景知识的提问 | 低 |
| **Sub-questions** | 分解为多跳子问题，逐次检索 | 多文档推理 | 高 |

### 4.3 Rerank 选型

Rerank 是性价比极高的精度提升手段。生产中常见选择：

- **BGE-Reranker / Cohere Rerank**：通用场景，效果好、延迟可接受;
- **ColBERT / ColBERTv2**：延迟与效果的平衡，适合大规模;
- **LLM-as-Reranker (GPT-4 / Claude)**：效果最好，但成本高、延迟大，仅用于高精度场景或离线评估。

Rerank 的候选数建议控制在 20-50 之间，过多会显著增加延迟与成本。

### 4.4 检索参数调优与 A/B 测试

检索链路中有多个可调参数，建议通过离线评估集 + 线上 A/B 实验共同决策：

| 参数 | 典型范围 | 影响 | 调优建议 |
|------|---------|------|---------|
| **chunk size** | 256-1024 tokens | 语义完整性与信息密度 | 按文档类型分别实验 |
| **top_k (向量召回)** | 20-100 | 召回率 vs 延迟 | 初始 50，结合 Rerank 调整 |
| **RRF k** | 20-80 | 融合权重 | 默认 60，根据 dense/sparse 质量微调 |
| **Rerank 候选数** | 20-50 | 精度 vs 延迟 | 候选数超过 50 收益递减 |
| **相似度阈值** | 0.6-0.85 | 拒绝率 vs 召回率 | 按业务容忍度设定 |

A/B 测试应至少对比两个指标：**答案准确率**与**端到端延迟**。不建议仅优化离线指标，因为某些策略（如 Multi-Query）会显著提升延迟，需要业务侧确认可接受。

### 4.5 GraphRAG

当知识之间存在复杂关系（组织架构、项目依赖、法规引用网络、学术论文引用）时，可引入 GraphRAG：

```text
文档 → 实体抽取 → 关系抽取 → 知识图谱 (Neo4j / NebulaGraph / 原生图数据库)

查询时：
1. 向量检索召回相关文本块
2. 图遍历获取关联实体与子图
3. 将子图序列化为自然语言上下文
4. LLM 基于文本 + 图上下文生成答案
```

GraphRAG 的部署成本较高，适合**多跳问答、根因分析、合规审计**等对关系推理要求高的场景。

## 5. 生成环节：上下文压缩、引用与幻觉抑制

### 5.1 上下文压缩

LLM 上下文窗口虽已达到 128K-1M tokens，但"Lost in the Middle"现象依然存在。生产 RAG 需要：

1. **去重过滤**：使用 embedding 相似度阈值剔除冗余片段;
2. **相关片段提取**：仅保留与查询直接相关的段落;
3. **摘要压缩**：对超长文档先摘要，再送入生成;
4. **动态预算分配**：根据 LLM 上下文窗口与 Token 成本，动态决定送入文档数量。

具体实现上，可引入**重排序分数驱动的截断**：先按 Rerank 分数排序，再依次加入上下文，直到接近上下文预算上限。对于高相关但超长的片段，可先用轻量模型提取与 query 相关的子句，再送入生成。这种"先粗筛、再精剪"的策略，能在不损失关键信息的前提下显著降低 Token 消耗。

### 5.2 引用生成 (Citation)

引用是降低幻觉、提升可信度的关键。推荐实现：

```python
CITATION_PROMPT = """请基于以下资料回答问题。对于答案中的每个关键事实，
请在方括号中标注来源编号，如 [1]、[2]。如果资料不足以回答问题，请明确说明。

资料:
{context}

问题: {query}
"""
```

引用后处理校验：
- 检查引用编号是否存在于提供的上下文中;
- 使用 NLI (Natural Language Inference) 模型验证答案与引用段落之间的蕴含关系;
- 对无法验证的陈述，标记为"模型推断，请人工复核"。

### 5.3 幻觉抑制策略

| 策略 | 实现方式 | 效果 |
|------|---------|------|
| **严格指令约束** | "仅基于上下文回答，不得引入外部知识" | 基础，必须 |
| **引用强制** | 要求每句关键结论都有来源 | 显著降低无据陈述 |
| **NLI 验证** | 用 NLI 模型检测答案与上下文的蕴含/矛盾 | 自动拦截明显幻觉 |
| **Self-RAG / CRAG** | 模型自我评估检索充分性，必要时重写查询 | 动态提升 |
| **置信度阈值** | 当最佳检索分数低于阈值时返回"未知" | 减少胡编乱造 |

## 6. 评估与监控：构建可观测的 RAG 飞轮

### 6.1 离线评估指标

| 阶段 | 指标 | 目标值 | 说明 |
|------|------|--------|------|
| **检索** | Recall@K | > 85% | 相关文档是否被召回 |
| **检索** | MRR / NDCG@K | > 0.75 | 排序质量 |
| **检索** | Context Precision@K | > 80% | Top-K 中相关片段比例 |
| **生成** | Faithfulness | > 90% | 答案是否忠于上下文 |
| **生成** | Answer Relevancy | > 85% | 答案是否切题 |
| **端到端** | 任务成功率 | 按业务定义 | 用户问题是否被正确解决 |

### 6.2 线上监控

生产 RAG 必须建立四块监控：

1. **延迟监控**：Embedding 延迟、检索延迟、Rerank 延迟、LLM TTFT / TPOT;
2. **质量监控**：检索命中率、Faithfulness 抽检、用户反馈（点赞/点踩）;
3. **成本监控**：每 query 的 Token 消耗、Embedding 与 Rerank 调用次数、存储增长;
4. **业务监控**：问答转化率、会话轮次、fallback 到"未知"的比例。

### 6.3 持续迭代

```text
线上日志 → 抽样评估 → 标注 bad case → 定位瓶颈环节
    ↑                                      ↓
  重新部署 ← 调整切分/检索/提示 ← 生成改进方案
```

推荐每周做一次离线评估，每月做一次端到端人工评估，重大业务变更前必须跑回归测试。

### 6.3 评估框架选型

| 框架 | 特点 | 适用场景 |
|------|------|---------|
| **RAGAS** | 开箱即用，覆盖 faithfulness、relevancy、recall 等指标 | 快速建立离线评估基线 |
| **TruLens** | 与 LangChain/LlamaIndex 集成好，提供可解释反馈 | 已有框架生态的项目 |
| **Ares** | 强调 LLM-as-Judge 的鲁棒性，支持自定义评分器 | 需要高度定制评估逻辑 |
| **LlamaIndex Evals** | 与 LlamaIndex 原生集成，支持 batch 评估 | LlamaIndex 项目 |
| **自研 Pipeline** | 完全可控，可结合业务指标 | 规模化、有专门评估团队 |

LLM-as-Judge 虽然方便，但存在模型偏见、位置偏见、长度偏见等问题。生产环境中建议：
- 使用多个 judge 模型投票;
- 对关键指标引入人工标注校准;
- 定期回测 judge 自身的打分一致性 (Kappa 系数)。

## 7. 安全合规：权限、数据出境与 AIGC 标识

### 7.1 权限隔离

生产 RAG 通常面向多租户或多部门，必须在索引阶段就将权限信息写入元数据：

```python
chunk.metadata = {
    "tenant_id": "company_a",
    "department": "finance",
    "clearance_level": "confidential",
    "data_owner": "finance@company.com",
    "retention_days": 2555
}

# 检索时强制带过滤条件
results = vector_db.search(
    query_embedding,
    filter={
        "tenant_id": {"$eq": current_user.tenant_id},
        "clearance_level": {"$in": current_user.allowed_levels}
    }
)
```

同时，在应用层再次校验返回文档的访问权限，防止元数据过滤被绕过。

### 7.2 数据出境与模型托管

- **敏感数据**：优先使用私有化部署的 Embedding 模型与 LLM，避免原始文档出境;
- **跨境场景**：明确向量索引、日志、用户 query 的存储位置，符合 GDPR、中国《数据出境安全评估办法》等要求;
- **第三方 API**：若必须使用 OpenAI / Anthropic / Cohere 等，建议先对敏感内容脱敏或哈希化，或采用"国内模型 + 国外模型 fallback"的分层策略。

### 7.3 AIGC 标识与审计

- **AIGC 标识**：生成内容需标注"由 AI 生成"，尤其在中国境内提供服务时，符合《生成式人工智能服务管理暂行办法》;
- **审计日志**：记录用户 query、检索到的文档 ID、生成答案、模型版本、时间戳，保留期限按合规要求;
- **可追溯性**：答案中的引用必须能反查到原始文档的具体页码/段落/版本。

### 7.4 合规落地清单

- [ ] 已明确原始文档、向量索引、审计日志、用户 query 的物理存储位置;
- [ ] 已评估是否需要数据出境安全评估或标准合同备案;
- [ ] 用户输入与生成输出已接入敏感信息识别与脱敏机制;
- [ ] 多租户场景下，文档访问权限已在元数据与索引过滤两层生效;
- [ ] 生成内容已按当地法规添加 AIGC 标识;
- [ ] 审计日志字段完整，保留期限满足合规要求;
- [ ] 模型供应商合同已明确数据用途、训练排除条款与删除权。

## 8. 生产上线 Checklist

- [ ] **数据准备**：原始文档已清洗，解析质量经人工抽检通过;
- [ ] **切分策略**：已针对主要文档类型确定 chunk size / overlap / 切分边界;
- [ ] **Embedding 模型**：已选型并完成延迟/效果基准测试，模型版本已锁定;
- [ ] **索引版本**：已实现索引版本化与 alias 切换，支持回滚;
- [ ] **检索链路**：已启用 Hybrid Search + Rerank，RRF 参数已调优;
- [ ] **生成策略**：已配置上下文压缩、引用生成、"未知"兜底策略;
- [ ] **评估体系**：离线评估集 ≥ 100 条，关键指标已设定目标值;
- [ ] **监控系统**：延迟、质量、成本、业务四类监控已接入告警;
- [ ] **权限隔离**：多租户/多部门元数据过滤已落地，应用层二次校验已启用;
- [ ] **合规审计**：数据出境路径已确认，AIGC 标识与审计日志已上线;
- [ ] **灾备演练**：向量库故障、Embedding 服务故障、LLM 故障的 fallback 已验证;
- [ ] **成本预算**：单 query 成本已测算，月度预算告警已配置。
