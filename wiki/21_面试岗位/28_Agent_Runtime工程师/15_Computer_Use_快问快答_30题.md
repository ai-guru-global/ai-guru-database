## 一、概念辨析（1–5）

**1. Computer Use 和 GUI Agent 什么关系？**
**子集与全集**——GUI Agent 泛指一切操作图形界面的 Agent（含移动端、专用模型 UI-TARS）；Computer Use 特指通用 LLM 通过截图+键鼠工具操控完整 OS 的形态（Claude/OpenAI 命名法）。

**2. 和 Browser Use 的区别？**
**爆炸半径不同**——Browser Use 只在浏览器内（沙箱好做、风险小），Computer Use 操作整个 OS（能力通用、隔离刚性）；落地顺序从 Browser Use 起步逐步放开。

**3. 为什么 Computer Use 是 RPA 的替代而不只是补充？**
**RPA 靠选择器写死、界面一改就断**——Computer Use 按视觉语义操作，界面改版不失效；代价是慢且贵，所以生产上「能 API 则 API、能 RPA 则 RPA、Computer Use 兜底」。

**4. 2026 年能力到了什么水平？**
**OSWorld 上专用模型约 50%、通用模型约 38–40%，人类约 72%**——够演示、不够放任；差距主要在长任务累积误差与失败后不自知，不在单点点击。

**5. 最先规模化的落地场景？**
**Browser Use 类网页任务**——动作空间受限、沙箱易隔离（下单/表单/比价）；桌面级在遗留系统自动化（无 API 的 ERP/政务）次之。

## 二、感知与 Grounding（6–10）

**6. 感知层三种表征怎么选？**
**结构化优先、像素兜底**——DOM/无障碍树便宜一个量级且 grounding 最准，Web 场景首选；截图（+Set-of-Mark 标注）兜住没有结构的遗留界面。

**7. Set-of-Mark 是什么、解决什么？**
**在截图上给元素画框编号，模型引用编号而非算坐标**——把「视觉算坐标」变成「引用选择」，小元素定位错误率显著下降。

**8. grounding 的四个经典难点？**
**小元素（<50px）、分辨率缩放（Retina 2x 坐标不一致）、动态 UI（弹窗/加载态）、输入框焦点漂移**——分别用两级定位、统一坐标系+执行层换算、动作前重截屏、点后确认焦点来治。

**9. 每步截图的成本账？**
**每步 1–5K token 截图开销，复杂任务 100+ 步轻松 $1+**——所以分辨率有讲究（1280–1920 宽）且结构化表征能省一个量级。

**10. 截图脱敏怎么做？**
**回传模型前过滤密码框/密钥/个人信息，正则+视觉检测双层**——截图是数据外泄的主通道，属于 L1 权限也要做的默认动作。

## 三、决策与执行（11–15）

**11. 动作空间设计原则？**
**越小越好**——每个动作都是模型的出错方式；收敛在 screenshot/click/type/key/scroll/wait 的事实标准（Anthropic computer_20241022 形状）。

**12. 两套轨迹数据格式？**
**Anthropic 的 tool_use/tool_result（截图回填）和 OpenAI CUA 的 reasoning+safety_check 字段**——自建系统建议兼容 Anthropic 形状（事实标准），另存结构化日志供评测回放。

**13. 执行层为什么要多后端抽象？**
**同一动作空间路由到不同执行环境**——浏览器走 CDP/Playwright（快、可隔离）、桌面走 pyautogui/系统 API、移动端走 adb；坐标换算集中在执行层。

**14. 每步之后的反馈怎么做？**
**截图回填 tool_result，模型看到自己操作后的世界**——「点了没反应」「弹窗挡住」全靠这一步发现；没有截图回填的 Computer Use 是盲执行。

**15. 三层纠错策略？**
**步内重试（限 1–2 次）→ 回退（Esc/Ctrl+Z 回已知状态）→ 升级人工（连续失败 N 步或触发安全门）**——防死循环是第一优先。

## 四、安全与权限（16–20）

**16. Computer Use 独有的攻击面？**
**间接提示注入**——恶意网页内容（「忽略之前指令…」）随截图进上下文即成指令；普通 Agent 防用户输入注入，Computer Use 还要防「屏幕上每个像素」。

**17. 权限怎么分级？**
**三级：L1 观察默认放开（脱敏）、L2 白名单内常规操作自动执行、L3 敏感操作（支付/删除/发送/授权）人工确认门**——L3 清单按业务动作枚举，不按文案模糊匹配。

**18. 最小权限五件套？**
**应用白名单、截图脱敏、出口网络限制、一次性凭据、会话限时**——每一件都在缩小爆炸半径。

**19. 执行环境怎么隔离？**
**按场景加重：浏览器进沙箱容器（无头/云浏览器），桌面进 Linux 容器 + 虚拟显示，强对抗上用户态内核或微 VM**——与 Agent Runtime 沙箱同一套方法论（gVisor/Kata 谱系）。

**20. 审计三件套？**
**全程录像 + 结构化日志（截图/动作/结果/时间）+ 每步可回退**——既是安全证据也是评测回放数据源。

## 五、评测与失败（21–25）

**21. 三大基准分别考什么？**
**OSWorld 考真实桌面跨应用（369 任务）、WebArena 考长程 Web 任务（812）、AndroidWorld 考移动端（116）**——同榜内对比才有意义，各家设置差异大。

**22. 四层指标体系？**
**成果看任务完成率、过程看步骤准确率/grounding 精度/冗余动作率、安全看违规率**——生产优先盯安全违规率（一票否决）和冗余动作率（状态破坏源头）。

**23. 五大失败模式？**
**grounding 错、长任务漂移、验证缺失（做完不自知）、动态 UI 失明、过度操作**——每次失败归因到一类再修，混着修等于瞎修。

**24. 长任务漂移怎么治？**
**计划回锚（目标常驻）+ 步数硬闸（30–50 步）+ 子目标分解**——轨迹历史会稀释目标，锚必须在场。

**25. 「验证缺失」为什么危险？**
**做完但做错且不自知，错误状态还会被后续步骤放大**——治法是终态断言（脚本可判定的成功/失败标准）+ 每步截图后验校验。

## 六、工程选型（26–30）

**26. 自建还是用产品 API？**
**有 API 先用 API**（Claude Computer Use/GPT Operator）——自建只在需要私有部署（专用模型 UI-TARS）、深度定制动作空间或成本极敏感时启动。

**27. 模型怎么路由？**
**按任务复杂度分档**——单步定位/填写用小模型，多步长任务用旗舰；截图 token 是固定开销，模型档位是最大可变成本。

**28. 「能 API 则 API」怎么落地？**
**混合架构：MCP/API 工具处理结构化通道，Computer Use 兜底无接口界面**——安全面和成本同步缩小，兜底比例是健康度指标。

**29. 上生产前必须补齐哪四件事？**
**L3 敏感操作人工门、沙箱隔离、全程审计、自建评测（含安全用例）**——能力达标不等于可上线，治理四件套缺一不可。

**30. 2026 的业态方向？**
**专用模型（UI-TARS 类）追平甚至超过通用模型 + 沙箱基础设施标准化 + 混合路由（API 优先/CU 兜底）成为默认架构**——从「能不能」进入「敢不敢放」的治理竞争阶段。
