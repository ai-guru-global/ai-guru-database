## 1. 任务编排与工作流引擎

### 1.1 复杂任务分解与依赖建模

#### DAG 模型

任务分解的根本目标是将不可原子的大问题拆分为可独立执行的小任务，形成 **有向无环图 (DAG)**。

三个关键性质：
- **无环性**：不允许循环依赖，保证任务最终终止
- **拓扑排序**：存在执行顺序使所有依赖被满足
- **并行潜力**：无直接依赖的任务可并行执行

#### Claude Code 的 7 种 Task 类型

| Task 类型 | 执行环境 | 适用场景 | 隔离 |
|-----------|---------|---------|------|
| local_bash | 本地 shell | 系统命令、文件操作 | 否 |
| local_agent | 本地 Agent | 代码分析、生成 | 是 |
| remote_agent | 远程 Harness | 分布式计算 | 是 |
| in_process_teammate | 内存中子 Agent | 轻量级分工 | 是 |
| workflow | Lobster 引擎 | 复杂工作流 | 部分 |
| monitor_mcp | MCP 监听 | 长期监控 | 是 |
| dream | 后台异步 | 并发非关键路径 | 是 |

**Task ID 格式**：`{parent_id}#{task_type}#{sequence}`，支持嵌套追踪。

#### 任务生命周期

```
pending(待执行) -> [调度] -> running(执行中)
  -> [成功] -> completed
  -> [错误] -> failed -> [重试] -> running
  -> [取消] -> killed -> [重新入队] -> pending
```

### 1.2 状态机与工作流引擎

确定性工作流引擎（如 OpenClaw 的 Lobster）支持 YAML 定义的流程，关键特性：
- **确定性**：给定相同输入，执行顺序总是相同
- **可重放**：可从任何步骤重新开始
- **可审计**：完整操作历史，精确到每一步

### 1.3 多智能体编排

编排引擎在确定性与灵活性之间的权衡：
- **Claude Code Coordinator**：动态智能体生成、任务分解、结果合并，适合灵活场景
- **OpenClaw Lobster**：YAML 定义精确流程，适合需要完全控制和审计的场景

### 1.4 智能体间通信

通信模式：
- 共享记忆空间（黑板式）
- 消息传递（直接通信）
- 事件广播（发布-订阅）
- 层级委派（parent -> child 的单向命令链）

## 2. MCP 与工具生态集成

### 2.1 Harness 对 MCP 的消费模式

Harness 与标准 MCP 客户端的差异在于引入了中间抽象层：

```
用户请求 -> Harness 调度器 -> 工具抽象层 -> [MCP Client] -> MCP Server
                              |
                         状态机管理
```

优势：
- 跨 Server 事务一致性
- 单 Server 故障不影响整体工作流
- 统一审计日志

### 2.2 传输层：stdio 与 Streamable HTTP

- **stdio**：进程级通信，适合本地 Server，低延迟
- **Streamable HTTP**：网络通信，适合远程 Server，支持健康检查

配置示例：
```yaml
mcp_servers:
  - name: filesystem
    command: "mcp-server-filesystem"
    args: ["--root", "/workspace"]
    transport: stdio
  - name: postgres
    command: "mcp-server-postgres"
    transport: streamable_http
    health_check: { interval: 30s, timeout: 5s }
```

### 2.3 MCP 服务端开发

Harness 在启动时动态发现 MCP Server：
1. 启动进程或连接 HTTP 端点
2. 调用 `tools/list`, `resources/list`, `prompts/list` 特性发现
3. 缓存 Schema 减少运行时开销
4. 监控 Server 健康状态

**版本协商**：连接时握手 `protocolVersion: "2025-11-25"`，Server 返回支持版本后发送 `notifications/initialized`。

### 2.4 性能优化

#### Schema 缓存策略

- **冷启动**：一次性获取所有 Server 的 tools/list，存入本地缓存（SQLite/内存），计算哈希
- **热启动**：调用前检查缓存版本，哈希不匹配才全量同步

关键注意：MCP 工具枚举顺序必须 **确定**，否则顺序变化破坏前缀一致性，导致提示词缓存未命中。Codex 曾发现此 bug 导致长会话性能严重下降。

## 3. 生产级 Harness 构建

### 3.1 系统提示词工程

#### 模块化架构

系统提示词是智能体行为的 DNA，采用模块化设计：

| 模块 | 内容 | 可缓存性 |
|------|------|---------|
| Core Identity | 身份定义、核心原则 | 不可缓存 |
| Capabilities | 工具使用说明 | 可缓存 |
| Domain Knowledge | 领域知识 | 可缓存 |
| Context-Specific | 上下文特定信息 | 不可缓存 |

**缓存边界设计**：静态模块（Capabilities + Domain）利用提示词缓存降低成本，动态模块（Identity + Context）每次重新生成。工程设计上不应把字节数硬编码为最佳实践，而应关注静态/动态分层和缓存边界。

#### 提示词缓存机制

- 重复的提示词模块可被 API 层缓存
- 降低 Token 消耗（缓存读取远便宜于重新计算）
- 确保行为一致性和可预测性

### 3.2 插件与扩展体系设计

扩展点：
- **工具插件**：通过 Tool Registry 注册新工具
- **MCP 扩展**：通过 MCP Server 增加能力
- **Skills 系统**：包含 SKILL.md 的文件包，带配置、脚本和元数据
- **Hook 机制**：在生命周期关键点注入自定义逻辑

### 3.3 性能优化与成本控制

#### 多模型路由

根据任务复杂度、成本预算、延迟要求动态选择模型：
- 简单任务路由到低成本模型（Haiku 级）
- 复杂任务使用高能力模型（Opus 级）
- 账期预算紧张时自动降级

#### 提示词缓存 + 异步上下文压缩

将推理成本从对话长度的二次增长降为线性增长。

#### 仓库即上下文

以代码仓库本身作为智能体的首要上下文来源（AGENTS.md），通过版本控制实现确定性、可审计的智能体行为。

### 3.4 配置管理与特性门控

- **远程功能标志**（如 GrowthBook）：每个子系统由远程标志控制，30 秒内远程禁用故障子系统
- **40+ 特性门控**（Claude Code）：细粒度行为控制
- **配置文件驱动**：模型选择、权限策略、工具配置全部外部化

## 4. 容错与可靠性工程

### 4.1 可观测性体系

#### 行业现状（LangChain 调研，1300+ 从业者）

- **89%** 组织已部署 Agent 可观测性基础设施
- **94%** 生产阶段组织拥有完整可观测性
- **62%** 实现步骤级追踪 (step-level tracing)
- **质量 (32%)** 是生产环境首要障碍，而非成本

#### 三大支柱

**指标 (Metrics)**：
- 底层收集器：计数器 (counter)、仪表 (gauge)、直方图 (histogram)
- Agent 特定指标：任务完成率、工具调用成功率、平均步骤数、Token 使用量、漂移检测频率

**日志 (Logs)**：
- 结构化 JSON 日志（包含 trace_id 关联全链路）
- DEBUG / INFO / ERROR / CRITICAL 四级

**追踪 (Traces)**：
- Span 链记录完整执行路径
- OpenTelemetry 标准集成
- 性能计时与瓶颈定位

### 4.2 反馈循环与人机协同

#### 人机协同模式

- **执行前审批**：高风险操作等待人工确认
- **执行中通知**：自动执行并实时推送进度
- **执行后审计**：定期审查执行记录和结果质量
- **异常时介入**：检测到漂移或错误时自动暂停，等待人工指导

### 4.3 容错模式与系统级恢复

#### 分层防御组合

以 Claude Code 的故障假设实现为例：

1. **远程功能标志 (GrowthBook)**：每个内存层由远程标志控制，30 秒禁用故障子系统
2. **3 失败断路器**：梦想 Agent 连续 3 次失败自动禁用，恢复计时器启动
3. **锁文件互斥与陈旧检测**：PID+时间戳锁文件，进程异常退出后新进程检测 PID 已死亡自动清除

三者组合：监控检测 -> 故障隔离 -> 自动恢复 -> 可观测性 -> 学习改进

#### 系统级恢复策略

- **检查点恢复**：从失败步骤的上一检查点继续
- **断路器保护**：防止级联故障蔓延
- **优雅降级**：主路径失败时切换到备选方案
- **任务重试**：基于指数退避的智能重试

### 4.4 幻觉防护的工程实践

#### 多层防御

1. **输入层**：系统提示词明确约束输出格式和行为边界
2. **输出层**：结构化解析 + 语义验证 + 安全检查（四步防御流程）
3. **执行层**：工具调用参数验证、权限检查、沙箱隔离
4. **验证层**：自我验证循环（PreCompletionChecklistMiddleware）
5. **监控层**：执行后审计，对比预期与实际结果

#### 工具调用幻觉检测

- LLM 是否调用了不存在的工具
- 参数是否在合理范围内
- 是否存在自相矛盾的调用序列
- 是否试图执行未授权操作

## 5. Harness 安全体系

### 5.1 威胁模型

#### 威胁分类

| 威胁类别 | 典型表现 | 影响 | 难度 |
|---------|---------|------|------|
| 恶意工具调用 | shell 命令删除文件 | 系统完整性 | 低 |
| 路径穿越 | `../../../etc/passwd` | 访问控制 | 低 |
| 权限提升 | 受限 user 执行 root | 系统安全 | 中 |
| 沙箱逃逸 | 容器内访问宿主 | 隔离机制 | 高 |
| 提示注入劫持 | 恶意输入改变工具调用链 | 控制流 | 低 |
| 凭据外泄 | API 密钥在日志暴露 | 账户安全 | 低 |
| 资源耗尽 | 无限递归消耗 CPU/内存 | 可用性 | 中 |
| 模型供应链攻击 | 投毒模型权重 | 系统完整性 | 高 |
| 间接提示注入 | 工具返回中隐藏恶意指令 | 控制流 | 中 |
| 智能体间信任滥用 | 被攻陷 Agent 利用信任 | 系统安全 | 中 |
| 时间旁路 | 执行时间推断敏感信息 | 隐私 | 高 |

### 5.2 权限系统与沙箱设计

#### 梯度化权限模型

```
Free(自动放行) -> Ask-first(事前询问) -> Approve-once(任务级一次授权)
```

实现机制：
- **权限检查拦截**：工具调用前验证权限等级
- **审批流程**：高危操作发起人工确认请求，超时则拒绝
- **审计记录**：所有权限决策记录完整日志

#### 沙箱隔离层级

| 层级 | 机制 | 安全性 | 性能开销 |
|------|------|--------|---------|
| 1 | 异常捕获 (try/except) | 最低 | 几乎无 |
| 2 | 进程隔离 (subprocess) | 中 | 低 |
| 3 | 容器隔离 (Docker) | 高 | 中 |
| 4 | 系统级沙箱 (seccomp/Bubblewrap) | 最高 | 中高 |

#### 双层安全模型 (Codex)

- **execpolicy 策略引擎**：控制智能体"可以尝试什么"（Starlark 策略语言）
- **平台原生沙箱**：控制"能做什么"（Bubblewrap + seccomp / sandbox-exec）
- 两层独立运作，形成纵深防御

### 5.3 工具调用护栏

#### 黑名单/白名单机制

```python
DANGEROUS_PATTERNS = [
    r"DROP\s+TABLE",     # SQL 注入
    r"rm\s+-rf",         # 破坏性命令
    r"format\s+[A-Z]:",  # 格式化磁盘
    r"curl.*\|.*sh"      # 下载并执行
]
```

#### AST 分析

对 shell 命令进行抽象语法树分析，而非简单的字符串匹配：
- 解析命令结构，识别管道链
- 检测嵌套的危险操作
- 理解参数上下文

#### Protected Files

系统维护保护文件列表，Agent 尝试访问前拦截：
```python
PROTECTED_FILES = ["/etc/passwd", "/etc/shadow", "~/.ssh/id_rsa", "~/.aws/credentials"]
```

### 5.4 路径校验与注入防护

#### 5 层路径防护 (Claude Code 风格)

1. **路径规范化**：解析 `..`、符号链接、URL 编码、Unicode 标准化
2. **基础路径验证**：确保解析后路径在允许的目录内
3. **符号链接检测**：拒绝符号链接目标
4. **权限检查**：验证文件操作权限
5. **实时监控**：记录所有路径访问尝试

#### 注入防护

- **提示注入检测**：检测 "IGNORE PREVIOUS INSTRUCTIONS" 等模式
- **间接注入防护**：对工具返回结果进行安全检查
- **输出过滤**：在将 Agent 决策转化为实际操作前进行安全检查

## 6. 评估与质量保障

### 6.1 评估方法论

#### 行业现状（LangChain 调研）

- **52.4%** 组织在测试集上运行离线评估
- **37.3%** 实施在线评估
- **22.8%** 生产阶段组织根本不做评估
- **关键落差**：可观测性 89% vs 评估 52%

大多数团队能"看到"智能体在做什么，却缺乏系统化方法判断"做得好不好"。

### 6.2 三层评估架构

#### 层级 1：步骤级评估

评估单个工具调用是否正确。

| 指标 | 定义 | 计算 |
|------|------|------|
| 工具准确率 | 选择正确工具的比例 | correct工具 / total_calls |
| 参数准确率 | 参数正确的比例 | correct_params / total_params |
| 执行成功率 | 不出错的比例 | successful_calls / total_calls |

#### 层级 2：轨迹级评估

评估工具调用序列的效率和正确性。

| 指标 | 定义 | 计算 |
|------|------|------|
| 轨迹长度效率 | 实际 vs 最优调用数 | optimal_steps / actual_steps |
| 错误恢复率 | 错误后成功恢复的比例 | recovered / total_errors |
| 重复调用率 | 相同工具连续调用次数 | duplicates / total |
| 平均调用深度 | 完成任务平均步骤数 | sum(lengths) / num_tasks |

#### 层级 3：任务级评估

评估最终任务是否成功完成。

| 指标 | 定义 |
|------|------|
| 任务完成率 | 成功完成任务的比例 |
| 部分完成率 | 完成部分子任务的比例 |
| 用户满意度 | 用户对结果的主观评价 |

### 6.3 端到端测试策略

#### 测试金字塔

- **单元测试**：单个工具的输入/输出正确性
- **集成测试**：运行时引擎 + 工具层 + 记忆子系统的协作
- **端到端测试**：完整任务流程，从用户输入到最终输出
- **混沌测试**：注入故障，验证容错和恢复能力

#### 确定性重放

利用 Lobster 等确定性工作流引擎，给定相同输入精确重放执行过程，验证行为一致性。

### 6.4 基准测试

#### Terminal Bench 2.0

终端任务能力基准，衡量 Agent 在真实系统任务上的表现。Harness 层改进（不改变模型）可带来 +13.7pp 的提升。

#### 基准测试注意事项 (Anthropic 建议)

- 排行榜上低于 3pp 的差距值得怀疑——很可能反映基础设施配置差异
- 固定模型、只改变 harness 配置，可产生 +6pp 的成绩漂移
- 正确反应不是"模型有差距"，而是"先问 harness 是否一样"

### 6.5 持续评估与监控

#### 在线评估闭环

```
可观测(看到在做什么) -> 可评估(判断做得好不好) -> 可优化(持续改进)
```

- **A/B 测试**：Harness 配置变更的对照实验
- **回归检测**：新版本上线后自动对比历史基线
- **漂移监控**：长期运行中检测性能退化

## 7. Harness 工程的未来

### 7.1 智能体原生应用

基础软件不再给人用，给 Agent 用。设计范式从"人类友好"转向"Agent 友好"：统一结构化接口、最大化信息密度、基于风险的约束。

### 7.2 标准化演进

- MCP 成为工具生态的标准协议
- OpenTelemetry 成为可观测性标准
- JSON-RPC 成为循环通信协议基础

### 7.3 开放问题

- 长期运行 Agent 的上下文管理
- 多 Agent 协作的信任与授权模型
- Harness 层的形式化验证
- Agent 行为的合规性框架
