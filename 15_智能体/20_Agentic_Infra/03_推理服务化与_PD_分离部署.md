# 推理服务化与 PD 分离部署：vLLM/SGLang 从单卡脚本到生产双池

> 中文简称：推理服务化与 PD 分离部署

> **一句话理解**: 服务化是把模型从「跑一次就退出的脚本」变成「常驻的 OpenAI 兼容 HTTP 服务」——这是 [[15_智能体/20_Agentic_Infra/02_生产环境组件清单|生产组件清单]] 里 GPU 推理层的入场券；PD 分离是规模上来之后，把服务内部的「读题（Prefill）」和「写字（Decode）」拆到两批 GPU 上各干各的——这是大规模才需要的架构优化。前者必做，后者按需。

## 1. 两个词各指什么、什么关系

| 概念 | 回答的问题 | 一句话 | 什么规模需要 |
|------|-----------|--------|-------------|
| **vLLM/SGLang 服务化** | 模型怎么变成可供调用的服务？ | 脚本 → 常驻 OpenAI 兼容 API 服务 | 单卡就该做，生产第一步 |
| **PD 分离部署** | 服务规模大了以后，内部架构怎么摆？ | Prefill/Decode 拆双池 + KV Cache 迁移 | 百卡级 / 严格 SLO 才划算 |

用一个餐厅类比贯穿全文：

- **脚本推理** = 在家自己做饭：每顿都要买菜生火洗碗（加载权重），做完就收摊（进程退出），一次只伺候一桌；
- **服务化** = 开餐厅：后厨常驻（模型常驻显存）、统一点菜口（OpenAI 兼容 API）、排单系统（调度器 + continuous batching）；
- **PD 分离** = 后厨拆成「切配间」（Prefill，一次性处理整单食材）和「出餐间」（Decode，一道一道往外出），中间有个传菜口（KV Cache 迁移），门口再站个领班（Router）分单。

两者是**递进关系**：先服务化（不开餐厅谈不上后厨分工），后 PD 分离（餐厅没客流就别拆后厨）。

## 2. 服务化：从脚本到生产服务

### 2.1 脚本推理和服务化差在哪

| 维度 | 脚本推理（`transformers` + `generate()`） | 服务化（`vllm serve` / `sglang.launch_server`） |
|------|------------------------------------------|------------------------------------------------|
| 权重 | 每次运行从磁盘加载，几分钟起步 | 常驻显存，请求来了直接算 |
| 并发 | 一个进程一个请求，排队干瞪眼 | continuous batching 动态拼批，几十到上百并发 |
| 调用方式 | `import` 写进代码，改模型要发版 | OpenAI 兼容 HTTP API，任何语言/框架直接调 |
| 显存管理 | 裸奔：KV Cache 连续分配，碎片严重 | 分页管理（PagedAttention / RadixAttention），浪费 < 4% |
| 调度 | 没有 | 队列、优先级、抢占、chunked prefill 全在引擎里 |
| 可运维 | 无 | `/health` 健康检查、`/metrics` 监控、多副本滚动升级 |

**本质：服务化是把「调度和资源管理」从你的应用代码里拿走，交给推理引擎。** 应用侧从此只关心业务逻辑，模型侧变成一个可独立扩缩、独立升级的标准后端服务。

深入两大引擎的原理差异见 [[10_部署推理/02_推理引擎/32_vLLM_SGLang_原理_零基础|vLLM/SGLang 原理零基础]]。

### 2.2 最小可用服务：两引擎对照

vLLM：

```bash
vllm serve Qwen/Qwen3-32B \
  --tensor-parallel-size 2 \      # 2 张卡拼起来放一个模型（TP=2）
  --gpu-memory-utilization 0.9 \  # 显存预算：权重 + KV Cache 占卡上显存的比例
  --max-model-len 32768 \         # 单请求最长 token 数
  --served-model-name qwen3-32b   # 对外 API 里的 model 字段名
```

SGLang：

```bash
python -m sglang.launch_server \
  --model-path Qwen/Qwen3-32B \
  --tp 2 \
  --mem-fraction-static 0.88 \
  --port 30000
```

起来之后都是 OpenAI 兼容接口，应用侧换 `base_url` 即可接入（AI 网关对接的就是这一层）：

```bash
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "qwen3-32b", "messages": [{"role": "user", "content": "你好"}]}'
```

关键参数的人话版：

| 参数 | 人话 | 调大了 / 调小了会怎样 |
|------|------|---------------------|
| `--tensor-parallel-size` / `--tp` | 几张卡拼着放一个模型 | 大 → 能装更大模型，但卡间通信开销上升 |
| `--gpu-memory-utilization` / `--mem-fraction-static` | 显存里多大比例给引擎（权重 + KV Cache） | 大 → KV 多、并发高，但留不出余量容易 OOM（惯例留 ~10%） |
| `--max-model-len` | 单请求最长上下文 | 大 → 每请求 KV 预留变多，能同时服务的请求数变少 |
| prefix caching（vLLM V1 默认开 / SGLang RadixAttention 默认开） | 相同前缀的 KV Cache 直接复用 | Agent 场景命中一次等于白捡一次 prefill |

### 2.3 服务化栈的四层演进

单实例跑通只是起点，生产上服务化沿着四层长出来：

| 层级 | 形态 | 加了什么 | 解决什么 |
|------|------|---------|---------|
| **L0 单实例** | 一台机器一个 `vllm serve` | — | 跑通 |
| **L1 多副本 + LB** | N 个相同实例挂 SLB/Ingress | 负载均衡、健康检查 | 容量与可用性——但普通 LB 不懂模型语义 |
| **L2 引擎路由器** | sgl-router（cache-aware）/ vLLM production-stack / NVIDIA Dynamo | **前缀感知路由**、按负载路由 | 前缀缓存命中率与负载均衡的双目标 |
| **L3 K8s 编排** | Deployment / LWS + HPA/KEDA + Prometheus | 多机拓扑管理、弹性伸缩 | 发布、故障自愈、多机推理 |

这一层有个最容易被忽略的认知：

> **普通 LB 的轮询会杀死前缀缓存。** 多轮对话的第二轮被轮询到另一台实例，那台实例上没有这轮对话的 KV Cache，缓存全部 miss、prefill 全额重算。所以 L2 层的核心动作是 cache-aware 路由——sgl-router 的 `cache_aware` 策略会优先把请求发给「已经持有这条前缀 KV」的实例，命中率与负载均衡两头兼顾。

另外两条：

- **多机 TP（TP 跨机器）用 LWS（LeaderWorkerSet）**：一组 GPU 节点作为整体扩缩、整体失败重启，是 vLLM 多机部署的官方推荐（组件视角见 [[15_智能体/20_Agentic_Infra/02_生产环境组件清单|组件清单]] §3.3 调度层）；
- **与 AI 网关的分工**：AI 网关（L1 模型接入层）管「调谁、挂了切谁、花多少钱」；引擎路由器（本节 L2）管「这发请求进哪台 GPU」。两者串在同一条链上，不互相替代。

多副本与扩缩容的方法论见 [[10_部署推理/03_推理优化/15_推理_Autoscaling_and_负载均衡|推理 Autoscaling 与负载均衡]]。

### 2.4 服务化的验收指标

服务化做得好不好，看这组指标（两引擎都从 `/metrics` 暴露，SGLang 另有 `/get_server_info`）：

| 指标 | 人话 | 体验映射 |
|------|------|---------|
| **TTFT**（Time To First Token） | 用户等多久听到第一个字 | 「按了发送怎么没反应」 |
| **TPOT / ITL**（每 token 间隔） | 吐字速度 | 「打字机卡不卡」 |
| **吞吐**（token/s） | 单位 GPU 产出 | 成本效率 |
| **KV Cache 利用率 / 前缀命中率** | 缓存有没有白做 | 命中率 < 40% 先查前缀设计（system prompt 是否稳定靠前） |
| **队列深度 / 排队时间** | 容量预警 | 尖峰来了先排队还是先拒绝 |
| **抢占（preemption）次数** | 显存不够被迫换出请求 | 频繁抢占 = 该扩容或压 `max-model-len` 了 |

指标体系与 agent 特化监控的完整版见 [[15_智能体/20_Agentic_Infra/02_生产环境组件清单|组件清单]] §6.2；单指标定义见 [[概念/Inference/ttft|TTFT]]。

## 3. PD 分离：服务化的大规模形态

### 3.1 病因：为什么混部会打架

Prefill（读题）和 Decode（写字）的瓶颈资源几乎正交：

| 阶段 | 干活方式 | 瓶颈资源 | 决定的指标 |
|------|---------|---------|-----------|
| **Prefill** | 一口气并行读完整个 prompt | 算力（compute-bound） | TTFT |
| **Decode** | 一个 token 一个 token 蹦，每步都要读全部权重 + KV Cache | 显存带宽（memory-bound） | TPOT / ITL |

混在同一批卡上时：一个长 prompt 的 prefill 会霸占算力几十到几百毫秒，期间**所有正在 decode 的请求吐字全部卡住**，TPOT 出现 8× 级尖刺；反过来 decode 高峰占满带宽，新请求的 TTFT 恶化。干扰时间线的逐帧分析见 [[10_部署推理/03_推理优化/25_Disaggregated_服务_2026|2026 Disaggregated 服务]] §2。

缓解有两条路线，是「时间切片」与「硬件分池」的区别：

| | Chunked Prefill（单池） | PD 分离（双池） |
|---|---|---|
| 思路 | 把长 prefill 切成小块，与 decode 交替执行，谁也不饿死谁 | 物理拆成两个 GPU 池，各干各的 |
| 消除的干扰 | 时间维度（部分） | 时间 + 硬件维度（彻底） |
| 额外收益 | 实现成本低，调度器改造即可 | 独立扩缩容、异构硬件（算力型卡跑 P、带宽型卡跑 D）、独立 SLO |
| 代价 | 单池硬件错配依旧 | KV Cache 跨机迁移 + 架构复杂度 |
| 适合 | 中小规模（< 几十卡）、短进短出 | 长输入 / 独立 SLO / 有 RDMA / 百卡级 |

### 3.2 架构四件套

```text
请求 ──► Router（领班：按输入长度、SLO、前缀命中选实例）
            │
            ▼
   ┌─────────────────┐  KV Cache 迁移   ┌─────────────────┐
   │  P 池（切配间）   │ ──RDMA/NVLink──► │  D 池（出餐间）   │
   │  算力型、大 TP    │   （传菜口）      │  带宽型、大 batch │
   │  小 batch 大序列  │                  │  高密度打包       │
   └─────────────────┘                  └────────┬────────┘
                                                 │ 流式 token（SSE）
                                                 ▼
                                               用户
```

| 组件 | 职责 | 要点 |
|------|------|------|
| **P 池** | 把 prompt 一口气算成 KV Cache | 大 TP 宽并行、小 batch，算力打满 |
| **D 池** | 拿着 KV Cache 逐 token 吐字 | batch 可打到几百~上千序列（访存密集，算力闲置） |
| **Router** | 选 P 实例、选 D 实例、决定迁移路径 | 前缀命中优先（省 prefill）、剩余 KV 容量、网络就近 |
| **KV 传输层** | 把 KV 从 P 搬到 D | RDMA / GPU Direct / NVLink；代表实现：NIXL、Mooncake TransferEngine |

### 3.3 命门与必背数字

PD 分离的命门只有一条：**T_transfer < T_prefill**——迁移必须能被「边算边传」藏进 prefill 的时间里，否则分离的收益全被传输吃掉。

KV Cache 大小公式（FP16）：

```text
KV_size = 2 × seq_len × n_layers × n_kv_heads × head_dim × 2 bytes

例：Llama-3 70B（80 层，GQA 8 KV heads，head_dim=128），seq_len = 8192：
    ≈ 2.68 GB
```

| seq_len | FP16 KV 大小 | 400 Gbps + FP8 传输 |
|---------|-------------|---------------------|
| 8K | 2.68 GB | ~27 ms |
| 32K | 10.7 GB | ~107 ms |
| 128K | 42.9 GB | ~430 ms |

隐藏迁移延迟的三板斧：

1. **Pipeline 传输**：prefill 算完一个 block 立刻传，不等全部算完（传菜口不攒单）；
2. **KV 量化传输**：FP8 传输、decode 侧反量化，带宽直接 ×2；
3. **前缀复用**：多轮对话共享前缀的 KV 只传增量 delta，命中时 T_transfer → 0。

P:D 配比的经验值（按负载形态，来源 DistServe；动态调整原则是两池「瓶颈产能」相等）：

| 负载形态 | P : D |
|----------|-------|
| 短进短出（chat） | 1 : 2 ~ 1 : 3 |
| 长进短出（RAG / 摘要） | 2 : 1 ~ 3 : 1 |
| 长进长出（写作） | 1 : 1 |
| 超长上下文（> 128K） | 3 : 1 ~ 5 : 1 |

收益量级：DistServe 双池相对混池 goodput（满足 SLO 的有效吞吐）**2–4×**；Chunked Prefill 单池方案 TPOT 降低 **2–10×**。推导与实测见 [[10_部署推理/03_推理优化/25_Disaggregated_服务_2026|2026 Disaggregated 服务]] §5、§10。

### 3.4 两大引擎怎么开：实操层面

**vLLM（V1 架构）**——组件化拼装，KV 传输做成可插拔的 connector：

```bash
# Prefill 节点：只算 KV，往外发
vllm serve MODEL --kv-transfer-config \
  '{"kv_connector": "NixlConnector", "kv_role": "kv_producer"}'

# Decode 节点：只收 KV，往外吐字
vllm serve MODEL --kv-transfer-config \
  '{"kv_connector": "NixlConnector", "kv_role": "kv_consumer"}'
```

- `NixlConnector` 基于 NIXL（NVIDIA 推理传输库，RDMA 直传）；另有 LMCache、Offloading 等连接器可选；
- 前面再架一层路由（vLLM production-stack / NVIDIA Dynamo / 自研网关）做 P→D 调度。

**SGLang**——原生一体化，两个角色用启动参数声明：

```bash
# Prefill 实例
python -m sglang.launch_server --disaggregation-mode prefill ...
# Decode 实例
python -m sglang.launch_server --disaggregation-mode decode ...
# 传输后端默认 Mooncake；sgl-router 负责 P→D 调度与 cache-aware 路由
```

**Mooncake（Moonshot / Kimi 生产范式）**——把 KV Cache 升格为一等公民的三件套：

1. **TransferEngine**：GPU Direct RDMA 传 KV；
2. **全局 KVCache 池**：HBM → DRAM → SSD 分层存储，计算与存储解耦；
3. **KV 中心化调度**：请求路由变成「KV 的生产—传输—消费」管理，多轮对话前缀复用把迁移开销打到 ≈ 0。

一句话选型：vLLM = 插件拼装自由度高；SGLang = 原生支持跟进快、配 RadixAttention 前缀复用顺；超大规模 + 多轮复用 = Mooncake 式 KV 池范式。

### 3.5 什么时候不要上

PD 分离不是免费午餐（KV 双份显存、故障域变大、双调度器运维），决策树速记：

```text
卡数 < 几十、短进短出          → 单池：continuous batching + chunked prefill，到此为止
长输入（RAG/长文档）占比高      → 上双池
  ├ 有独立 TTFT/TPOT SLO       → 必上
  ├ 多轮对话 / 前缀复用频繁     → 双池 + KV 池（Mooncake 式）
  └ MoE 模型                    → 双池 + 专家感知分离（DeepSeek 式）
超长上下文（> 128K）           → 双池 + 大 TP prefill + KV 量化传输（必选组合）
```

完整决策依据与 FAQ 见 [[10_部署推理/03_推理优化/25_Disaggregated_服务_2026|2026 Disaggregated 服务]] §9、§12；概念层的白话版见 [[概念/Inference/pd-disaggregation-plain|PD 分离大白话]]。

## 4. Agent 场景：为什么 PD 分离收益放大

[[15_智能体/20_Agentic_Infra/02_生产环境组件清单|组件清单]] §3.3 说过「agent 场景 prompt 长、decode 步数多，PD 分离收益比纯 chat 更大」，展开成四类流量模板：

| Agent 流量模板 | 特征 | 对推理池的压力 |
|---------------|------|---------------|
| RAG 问答 | 长进短出（几十 K 检索内容进，几百 token 出） | prefill 重，脉冲式 |
| 长文生成 | 长进长出（写作、报告） | 两头都重 |
| 多轮追问 | 历史消息滚动增长 | 前缀复用价值极高 |
| 工具调用 | JSON 短输出、高频次 | decode 步数少但请求密 |

混池时这些流量叠加的后果：prefill 脉冲式打断所有进行中的 decode，TPOT 尖刺直接体现在 agent 的流式输出「一顿一顿」。PD 双池 + KV 中心池的完整链路映射：

```text
文档解析 + embedding        → 离线池，不占 LLM 服务（别混进来）
请求到达                    → Router 选 P 实例（前缀命中优先）
P 池 prefill                → 大 TP 并行，边算边传
KV Cache 迁移               → RDMA（FP8 量化）， pipeline 藏进 prefill 时间
D 池 decode                 → 流式 SSE 吐字
多轮追问                    → 前缀命中，只 prefill 增量，迁移开销 ≈ 0
```

一笔账：3 万 token 的 KV Cache FP16 ≈ 10 GB，FP8 传输 ≈ 5 GB，400 Gbps 下 ≈ 100 ms——远小于秒级的长 prompt prefill，pipeline 重叠后几乎完全隐藏。配比上 RAG 档 P:D ≈ 3:1，写作高峰动态调向 1:1。

逐环展开（离线 ingest、多轮追问的 KV 复用、SLO 三档分级、组织级前缀共享、本机 M4 对照）见 [[10_部署推理/03_推理优化/28_办公Agent_PD分离_链路推演|办公 Agent × PD 分离链路推演]]。

**面试一句话口径**：agent 流量 = RAG 长输入 + 多轮前缀复用 + 工具调用短输出，三个特征叠加必然走向 PD 双池 + KV 中心池（Mooncake 式三件套而非裸 DistServe）；命门是 T_transfer < T_prefill，多轮场景靠 KV 池前缀复用把迁移开销打到 ≈ 0。

## 5. 落地检查清单与常见陷阱

### 5.1 检查清单（按顺序过）

- [ ] **先量化干扰再动架构**：profiling 确认 TPOT P99 尖刺确实来自 prefill 抢占，而不是网络/客户端问题；
- [ ] **先开 chunked prefill**（vLLM V1 / SGLang 默认已开），单池缓解往往已够用；
- [ ] **查 LB 策略**：多副本 + 轮询 LB = 前缀缓存白做，换 cache-aware 路由；
- [ ] **算显存账**：用 KV 公式核对 `max-model-len × 目标并发` 的 KV 总量是否塞得下（别全给权重）；
- [ ] **验网络**：RDMA 带宽与跨机架延迟，实测 `T_transfer`，确认 < `T_prefill`；
- [ ] **配比别写死**：按 goodput 反馈动态调整 P:D 卡数；
- [ ] **分池监控**：TTFT 归 P 池、TPOT 归 D 池、KV 迁移延迟单独告警、迁移链路全埋 trace。

### 5.2 五大陷阱

| 陷阱 | 现象 | 规避 |
|------|------|------|
| 迁移吃掉收益 | 上双池后 TTFT 反而变高 | pipeline 传输 + FP8 量化 + 就近调度三件套 |
| 配比写死 | 负载变化后某池长期过载/空闲 | goodput 反馈动态配比 |
| 前缀复用失效 | 双池后命中率暴跌（KV 分散在各 P 实例） | 引入全局 KV 池，跨池共享前缀 |
| 双份显存 | 迁移途中 P 与 D 各存一份 KV | 零拷贝 / GPU Direct RDMA |
| 调试黑盒 | 故障定位不到环节 | router → P → 迁移 → D 全链路 tracing |

（陷阱详表与现象级分析见 [[10_部署推理/03_推理优化/25_Disaggregated_服务_2026|2026 Disaggregated 服务]] §11。）

## 6. 面试快答（速记口径）

| 问题 | 一句话口径 |
|------|-----------|
| 为什么要服务化？ | 脚本每请求加载权重、无并发无调度；服务化 = 权重常驻 + continuous batching + OpenAI 兼容 API + 可监控可扩缩，把调度和资源管理交给引擎 |
| vLLM / SGLang 各一句定位？ | vLLM：PagedAttention 分页 KV Cache + continuous batching，生态事实标准；SGLang：RadixAttention 前缀树复用 + 零开销调度 + 结构化生成，Agent 场景吞吐更高 |
| PD 分离是什么、为什么？ | 把算力密集的 prefill 和带宽密集的 decode 拆成两个 GPU 池，中间迁 KV Cache——消除混部干扰、两池独立扩缩、可各配异构硬件 |
| PD 分离的命门？ | T_transfer < T_prefill；靠 pipeline 边算边传 + FP8 量化传输 + 前缀复用传 delta |
| P:D 配比怎么定？ | 按负载形态：chat 1:2~1:3、RAG 2:1~3:1、长写 1:1、> 128K 到 5:1；原则是两池瓶颈产能相等，goodput 反馈动态调 |
| Chunked Prefill 和 PD 分离怎么选？ | 时间切片 vs 硬件分池；中小规模 chunked 够用，独立 SLO / 长输入 / 百卡级才上双池 |
| 服务化多副本最容易被忽略的坑？ | 轮询 LB 杀死前缀缓存——必须 cache-aware 路由，把请求粘到已持有该前缀 KV 的实例 |
| Agent 场景为什么 PD 收益更大？ | 长输入（RAG）+ 多轮前缀复用 + 短输出（工具调用）三特征叠加 → 双池 + KV 中心池，多轮迁移开销 ≈ 0 |
