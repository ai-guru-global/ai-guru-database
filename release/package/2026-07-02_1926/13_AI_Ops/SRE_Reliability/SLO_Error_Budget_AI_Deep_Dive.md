# AI 系统 SLO 与错误预算深度指南 - 传统 SRE 如何适配 LLM

> **一句话理解**: 传统 SRE 的 SLO 只管"可用性"（请求成功了吗），但 AI 系统的 SLO 是"可用性+质量+成本"三元组——首 token 延迟决定体验、幻觉率决定可信、token 成本决定生存，三者用错误预算统一权衡，让发布决策从"拍脑袋"变成"看预算条"。

---

## 0. 传统 SLO 为什么不够用？

Google SRE 经典框架：定义 SLI（指标）→ 设定 SLO（目标）→ 推导错误预算（允许的失败额度）。

```
传统 Web 服务 SLO：
  SLI = 成功请求占比
  SLO = 99.9% 请求成功
  错误预算 = 0.1%（可用于发版/实验）

  → 简单清晰，因为"成功"是二元的（200 vs 500）
```

LLM 服务的问题：

```
LLM 请求"成功"了（HTTP 200），但：
  - 回答完全是幻觉（质量失败）
  - 8 秒才出第一个字（体验失败）
  - 消耗了 10000 token（成本失败）

  → HTTP 200 ≠ 用户满意
  → 需要多维度 SLI
```

**核心论点**：AI 系统的可靠性是**三元约束**——可用性、质量、成本，三者互相牵制，必须用多维度 SLO 统一管理。

## 1. AI 特有的 SLI（服务等级指标）

### 1.1 延迟类指标

| 指标 | 定义 | 为什么重要 |
|------|------|-----------|
| **TTFT**（Time To First Token） | 首 token 延迟 | 决定"是否卡住"的体感，>3s 用户流失 |
| **TPOT**（Time Per Output Token） | 每个 token 的生成时间 | 决定流式阅读流畅度 |
| **E2E 延迟** | 请求到完整响应 | 长回答场景的总体等待 |
| **排队延迟** | 请求入队到开始处理 | 反映容量是否充足 |

```
典型 SLO（延迟）：
  TTFT P50 < 800ms
  TTFT P99 < 2500ms
  TPOT  P99 < 50ms/token
  E2E   P99 < 15s（短回答）
```

### 1.2 质量类指标

| 指标 | 定义 | 测量方式 |
|------|------|----------|
| **幻觉率** | 输出含不实陈述的比例 | LLM-judge 抽样 / 人工 |
| **拒绝率** | 模型拒绝回答的比例 | 关键词 / 分类器 |
| **有害率** | 输出有害内容的比例 | 内容审核 API |
| **任务完成率** | 用户任务达成的比例 | 黄金集 / 用户反馈 |
| **满意度** | 用户正面反馈率 | 点赞/点踩、重写率 |

> **难点**：质量指标不像延迟可实时测，需采样评估，有滞后性。

### 1.3 成本类指标

| 指标 | 定义 | SLO 示例 |
|------|------|----------|
| **单请求成本** | 每次 API/GPU 花费 | < $0.05/请求 |
| **Token 效率** | 输出 token / 输入 token | > 0.5（防冗余） |
| **月度总成本** | 全服务支出 | < 预算 × 100% |

## 2. 多维度 SLO 设计

### 2.1 SLO 矩阵

```
┌────────────┬──────────┬──────────┬──────────┐
│            │  可用性   │  质量    │  成本    │
├────────────┼──────────┼──────────┼──────────┤
│ SLO 目标   │ 99.9%    │ 幻觉<5%  │ <$0.05/req│
│ 错误预算   │ 0.1%     │ 5%       │ 5%超支   │
│ 测量窗口   │ 28天滚动 │ 28天     │ 月度     │
│ 警报阈值   │ 预算70%  │ 预算70%  │ 预算80%  │
└────────────┴──────────┴──────────┴──────────┘

任一维度耗尽预算 → 触发对应响应
```

### 2.2 维度间的权衡

```
三维度互相牵制：

  提高质量（用更大模型）
    → 成本上升 ⬆
    → 延迟上升 ⬆（可用性预算受压）

  降低成本（用小模型/量化）
    → 质量下降 ⬇
    → 可能触发质量 SLO 违约

  降低延迟（更激进批处理）
    → 可能牺牲质量（更长上下文被截断）
    → 成本波动

  → SLO 不是独立设定，而是一组平衡配置
```

### 2.3 分级 SLO（Tiered SLO）

不同功能/用户可有不同 SLO：

```
免费用户：  可用性 99% / 无质量保证 / 严格限流
付费用户：  可用性 99.9% / 幻觉<8% / 优先队列
企业客户：  可用性 99.95% / 幻觉<3% / 专属容量 / SLA 赔付
```

## 3. 错误预算（Error Budget）机制

### 3.1 错误预算的本质

```
SLO = 99.9% 可用性（28天）
  → 允许 0.1% 失败 = 错误预算
  → 28天 ≈ 40320 分钟
  → 预算 = 40 分钟停机/28天

错误预算是"创新的燃料"：
  - 有预算 → 可以发版、做实验、冒风险
  - 预算耗尽 → 必须保守，冻结发版，专注稳定
```

### 3.2 AI 系统的"错误"定义更宽

```
传统错误：HTTP 5xx、超时、崩溃
AI 错误（同样消耗预算）：
  ├── 系统错误：5xx、超时、限流 429
  ├── 质量错误：幻觉、有害输出、任务未完成
  ├── 性能错误：TTFT 超阈值（虽 200 但太慢）
  └── 成本错误：单请求超成本上限

  每类错误各自有独立预算，独立消耗
```

### 3.3 预算消耗与发布决策

```
错误预算条（每维度独立）：
  可用性预算  ████████░░  80%  ⚠️ 接近耗尽 → 冻结发版
  质量预算    ████░░░░░░  40%  ✅ 充足 → 可实验
  成本预算    ██░░░░░░░░  20%  ✅ 充足

发布决策规则：
  - 任一预算 < 20%（红灯）→ 冻结所有非紧急发版
  - 预算 20-50%（黄灯）→ 仅允许 bugfix，需审批
  - 预算 > 50%（绿灯）→ 允许功能发版
```

## 4. SLI 测量实践

### 4.1 实时指标（Prometheus + Grafana）

```
# TTFT 分布（直方图）
llm_ttft_seconds_bucket{le="0.5"} 85000
llm_ttft_seconds_bucket{le="1.0"} 92000
llm_ttft_seconds_bucket{le="2.5"} 99000
llm_ttft_seconds_bucket{le="+Inf"} 100000

# PromQL 计算 SLO
# 过去 28 天 TTFT P99 < 2.5s 的比例
sum(rate(llm_ttft_seconds_bucket{le="2.5"}[28d]))
  / sum(rate(llm_ttft_seconds_bucket{le="+Inf"}[28d]))
```

### 4.2 质量指标测量（异步评估）

```
质量无法实时测，采用"采样评估"：

  1. 线上请求按 1% 采样（降低成本）
  2. 异步队列送 LLM-judge 评估
  3. 评估结果（幻觉/有害/质量分）写入时序库
  4. 按小时/天聚合，计算质量 SLO 达成率

  滞后性：质量指标通常滞后 1-6 小时
  → 不能用于实时阻断，用于趋势监控与发版门控
```

### 4.3 用户感知指标（最重要）

```
最能反映用户满意度的指标：
  - 重写率：用户点了"重新生成"的比例（高=不满意）
  - 放弃率：请求发出但未读完的比例
  - 负反馈率：点踩/投诉/截屏反馈
  - 留存率：次日/周留存（终极指标）

  这些比技术 SLI 更贴近真实体验
```

## 5. 基于 SLO 的运维实践

### 5.1 容量规划

```
错误预算反推容量需求：

  当前可用性 99.9%（预算 0.1%）
  流量增长 50% 后，若不扩容 → 延迟上升 → 429 增多 → 预算耗尽

  规划：监控预算消耗速率，预测何时耗尽，提前扩容

  vLLM/SGE 的连续批处理：
    - 自动吸收流量波动（批大小弹性）
    - 但有上限，超限则排队 → TTFT 上升
    - 设容量警戒线：平均利用率 > 70% 即扩容
```

### 5.2 事故响应与 SLO

```
事故分级（基于 SLO 影响）：

  SEV-1（严重）: 核心 SLO 短时大量违约，影响大量用户
    → 立即响应，全员投入

  SEV-2（重要）: 错误预算快速消耗，趋势性恶化
    → 工作时间内响应

  SEV-3（次要）: 单一指标轻度偏离，用户感知弱
    → 排期处理

  事后：事故消耗的预算从剩余预算扣除，
       影响后续发版节奏
```

### 5.3 发版门控（Release Gate）

```yaml
# 发版前 SLO 检查（CI 门控）
release_gate:
  checks:
    - name: 可用性预算
      query: error_budget_availability
      rule: "> 30%"  # 低于 30% 阻断

    - name: 质量预算
      query: error_budget_quality
      rule: "> 30%"

    - name: 回归测试
      query: golden_set_pass_rate
      rule: ">= baseline - 0.02"

  on_fail:
    - require_approval: CTO  # 预算紧张时需高管批准
```

## 6. SLO 陷阱与反模式

### 6.1 常见陷阱

| 陷阱 | 问题 | 解法 |
|------|------|------|
| **SLO 过严** | 99.99% 目标，预算太少，无法创新 | 从 99% 开始，逐步收紧 |
| **SLO 过松** | 95% 目标，用户体验差 | 参考用户流失曲线设定 |
| **只看可用性** | 忽略质量，200 但幻觉满篇 | 多维度 SLO |
| **无错误预算文化** | 违约后无行动，SLO 形同虚设 | 绑定发版权限 |
| **指标测不准** | 质量指标滞后/偏差大 | 多源交叉验证 |

### 6.2 反模式

```
❌ 反模式 1: SLI 永远绿
   把阈值设得很松，指标永远达标
   → SLO 失去意义

❌ 反模式 2: 用平均延迟
   平均 500ms 很好，但 P99 5s 用户体验差
   → 必须用百分位（P95/P99）

❌ 反模式 3: 质量只看抽样
   抽样偏差导致漏掉系统性质量退步
   → 结合用户反馈（重写率等）

❌ 反模式 4: 预算违约无后果
   "超就超了" → 团队不重视 SLO
   → 违约必须冻结发版
```

## 7. 实践：建立 AI SLO 体系

### 7.1 落地步骤

```
Step 1: 选择 SLI（从用户视角）
  问："用户最在意什么？"
  → TTFT、回答质量、是否答对

Step 2: 设定初始 SLO（保守起步）
  基于当前实际表现，设略高的目标
  例：当前 TTFT P99 = 3s → SLO 设 2.5s（有挑战但可达）

Step 3: 计算错误预算
  SLO 99% → 预算 1%（约 7小时/月）

Step 4: 建立测量
  - 延迟：Prometheus 实时
  - 质量：异步采样评估
  - 成本：计费 API + 标签

Step 5: 设置告警
  - 预算快速消耗告警（速率）
  - 预算耗尽告警（绝对值）

Step 6: 绑定行动
  - 预算耗尽 → 冻结发版（写入 CI 门控）

Step 7: 定期评审（季度）
  - SLO 是否仍合理？
  - 是否需要新增维度？
```

│  99.92%    │  幻觉 4.2%  │  $0.03/req   │

## 8. 2026 趋势

1. **AI-native 监控**：用 LLM 自动分析 trace，发现人难察觉的异常模式
2. **质量 SLI 实时化**：更快的轻量 judge 模型，将质量评估延迟从小时降到分钟
3. **SLO 即代码**：SLO 定义 YAML 化，纳入 GitOps，版本化管理
4. **成本 SLO 标准化**：云厂商提供 token 级预算 API，原生成本 SLO
5. **多模态 SLO**：图像/视频生成场景的 SLI（生成质量、一致性）
