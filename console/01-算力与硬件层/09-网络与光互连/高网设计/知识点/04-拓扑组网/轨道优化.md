# 轨道优化（Rail-Optimized）组网

> 让 8 卡服务器中每张 GPU 网卡固定走一条"轨"（rail），全机房同轨网卡汇聚到同一台 leaf，把跨机集合通信的主体流量锁进单台交换机。

## 解决什么问题

- 集合通信流量若在 fabric 里随机游走，会把本可一跳落地的流量推上 spine：spine 容量、光模块成本、拥塞概率全部放大。
- 通信库（NCCL）与调度需要确定性映射"GPU 逻辑位置 → 网络物理位置"，才能稳定把通信环排成低跳数路径。

## 核心原理

- rail 定义：HGX 级 8 卡服务器配 8 张网卡（H100 世代典型为 8×400G ConnectX-7），网卡序号 0~7 对应 rail 0~7；布线保证"所有服务器的 rail i 都落在同一组 leaf-i"，即同轨 GPU 落同一 leaf。
- 流量局部性：
  - 同轨跨机流量（各机同序号 rank 之间）只占 leaf 及其下行口，不占 spine；
  - NCCL 拓扑探测后优先排"轨内环"：环上相邻两点挂同一台 leaf，逐跳一跳直达；
  - 只有跨轨流量（如 TP 组内 8 卡互通）才上 spine，量小且可被 ECMP/自适应路由均摊。
- 与两层 Clos 的关系：rail 是对 leaf 层的"染色"约束，轨与轨之间靠 spine 补全任意两点带宽；rail-optimized 是 Meta 2.4 万卡 RoCE 训练集群（SIGCOMM 2023 论文）以及多数 A100/H100 集群的布线基线。

## 关键数字（H100 世代典型口径）

| 项目 | 数值 |
|---|---|
| 每服务器轨数 | 8（8 GPU ↔ 8 NIC，1:1 对应） |
| 单 NIC 带宽 | 400G（H100 世代）；200G（A100 世代，Meta 2023 集群口径） |
| 单 leaf 挂载密度 | 64 口 leaf 下行 32 口 → 承载 32 台服务器的同一轨 |
| 同轨通信跳数 | 1 台 leaf 内（通信双方挂同一 leaf），不经 spine |
| 轨间通信 | 经 spine，1~2 跳，受收敛比约束 |

## 设计要点与权衡

- 收益：spine 只承载跨轨流量，leaf 下行口就是"域内满带宽"；布线规整、故障按轨可定位。
- 代价：放置约束变强——同轨槽位不足时整机利用率下降，必须与拓扑感知调度联动（见拓扑感知调度篇）。
- 轨内流量不经过 spine 哈希，天然规避 ECMP 大象流问题；跨轨流量仍受 ECMP/自适应路由支配。
- 世代演进：51.2T 交换机时代轨宽升级为 8×800G（或每轨多链路），leaf 挂载台数与单域规模按新 p 重推（见 Clos 与 FatTree 篇）。
- 轨道优化与多平面正交：rail × plane 构成二维约束，NCCL 按"轨内环 + 平面分 channel"组织通信（见双平面与多平面篇）。

## 常见坑

- rail 完整性被故障破坏：某轨 leaf 或网卡故障后若不重排，NCCL 沿旧拓扑建环 → 环绕远路、性能塌方；需逐轨健康监控并触发通信域重排（见弹性与容错续训篇）。
- 异构机型混布：8 卡机、4 卡机、多轨单卡机型混布会打破"网卡序号=轨号"映射，轨道退化为普通 leaf，局部性收益归零。
- 布线纪律：轨错插在部署期几乎无法靠业务流量发现，上线前必须做逐轨连通性、逐轨带宽校验（见监控与拨测篇）。
- 误以为轨道优化能省 spine：跨轨集合通信（TP/专家并行）依然吃满二分带宽，spine 仍按目标收敛比设计，除非流量画像明确支持放宽。
