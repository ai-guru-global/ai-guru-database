## 1. 量化失效机制

### 1.1 三种退化模式

量化不是均匀地"变差一点"，而是有三种不同的退化模式，各自有不同的触发条件和表现：

#### 模式一：长尾知识丢失

```
问题表现：
  模型对冷门知识开始"幻觉"（hallucination）
  热门问题回答正常，冷门问题开始瞎编

根本原因：
  高频知识 → 由大量权重的强信号编码 → 量化后信号仍足够强
  低频知识 → 由少量权重的微小差异编码 → 量化后差异被抹平

示例：
  FP16: "法罗群岛的首都是托尔斯港"  (权重差异: 0.12345 vs 0.12346)
  INT4: "法罗群岛的首都是哥本哈根"  (量化后: 0.12 vs 0.12 → 无法区分)

量化位宽 vs 长尾知识保留率（70B 模型）：
  FP16:   100%（基线）
  INT8:   ~98%（几乎无损失）
  INT4:   ~85-90%（冷门知识开始丢失）
  INT2:   ~50-60%（大量知识丢失）
```

#### 模式二：重复生成

```
问题表现：
  输出开始"复读机"——同一个词/短语反复出现
  尤其在长文本生成中更明显

根本原因：
  量化使 logits 分布变"平"
  原本概率 0.40 和 0.35 的两个 token，量化后可能都变成 0.38
  采样时区分度下降，模型倾向重复已生成的内容

数学解释：
  FP16 logits: [3.2, 2.8, 2.1, 1.5]  → softmax → [0.40, 0.27, 0.13, 0.07]
  INT4 logits: [3.0, 3.0, 2.0, 1.5]  → softmax → [0.35, 0.35, 0.13, 0.07]
                                              ↑ 两个 token 概率相同 → 随机选择 → 可能重复
```

#### 模式三：格式退化

```
问题表现：
  JSON 输出格式错误（缺括号、多余逗号）
  代码缩进混乱
  Markdown 结构破坏

根本原因：
  格式 token（{, }, [, ], 换行符）的概率分布对精度极度敏感
  微小的 logit 扰动就能让模型在 "}" 和 "," 之间选错

影响最大的场景：
  - Function Calling / Tool Use（JSON 格式严格要求）
  - 代码生成（语法正确性）
  - 结构化输出（Outlines/Instructor 依赖精确的 token 概率）
```

### 1.2 退化顺序

不同能力在不同精度阈值开始退化：

```
精度降低方向 →

FP16 ──── INT8 ──── INT4 ──── INT2
 │          │         │         │
 │          │         │         └─ 基础语言能力崩溃
 │          │         └─ 长尾知识丢失 + 格式退化开始
 │          └─ 数学推理轻微退化（通常可忽略）
 └─ 基线（无退化）

退化优先级：格式 > 长尾知识 > 推理 > 基础语言
```

## 2. 层敏感度分析

### 2.1 不同层的精度容忍度

不是所有 Transformer 层对量化同等敏感。理解层敏感度是设计混合位宽量化策略的基础：

| 层类型 | 敏感度 | 原因 | 量化建议 |
|--------|--------|------|----------|
| **Attention Q/K/V 投影** | 极高 | 直接决定注意力分布，微小扰动改变全局关注点 | 保持 FP16 或 INT8 |
| **Attention Output 投影** | 高 | 注意力结果的最终混合 | INT8 安全，INT4 需谨慎 |
| **第一层（Layer 0）** | 高 | 输入编码层，影响所有后续层 | 保持较高精度 |
| **最后一层（LM Head）** | 高 | 直接输出 logits，决定最终预测 | 保持 FP16 或 INT8 |
| **FFN Gate/Up 投影** | 中 | 中间特征变换，相对鲁棒 | INT4 可接受 |
| **FFN Down 投影** | 中 | 特征输出，有一定敏感性 | INT4 可接受 |
| **Layer Norm** | 低 | 归一化操作，数值稳定 | 通常保持 FP32（体积小） |
| **Embedding** | 低 | 查表操作 | 通常保持 FP16（可共享权重） |

### 2.2 敏感度可视化（以 Llama-70B 为例）

```
Layer 0-79 的量化敏感度热力图（概念示意）:

Layer:  0  1  2  3 ... 38 39 40 ... 77 78 79(LM Head)
        ┃  ┃  ┃  ┃     ┃  ┃  ┃      ┃  ┃  ┃
Q/K/V:  █▓▒░...░░░...░░░...░░░...░▒▓█  ← 首尾层高敏感
FFN:    ░░░░...░░░...░░░...░░░...░░░░  ← 整体较鲁棒
Output: ░▒░░...░░░...░░░...░░░...░▒░░  ← 略敏感

█ = 极高敏感  ▓ = 高敏感  ▒ = 中等  ░ = 低敏感
```

### 2.3 混合位宽量化策略

基于层敏感度的量化策略——对敏感层用高精度，对鲁棒层用低精度：

| 策略 | 敏感层精度 | 普通层精度 | 模型大小 | 精度保持 |
|------|-----------|-----------|---------|---------|
| **Uniform INT4** | INT4 | INT4 | ~35 GB | ~95-97% |
| **Mixed INT4/INT8** | INT8 (Q/K/V, 首尾层) | INT4 | ~38 GB | ~97-98% |
| **AWQ 保护** | FP16 (salient channels) | INT4 | ~36 GB | ~98% |
| **Mixed INT4/FP16** | FP16 (Q/K/V only) | INT4 | ~42 GB | ~98-99% |

## 3. 激活值离群点问题

### 3.1 现象

LLM.int8() (Dettmers et al., 2022) 首次系统性发现：

```
LLM 激活值分布特征（与 CNN 截然不同）：

CNN 激活值：
  均匀分布在 [-2, 2] 范围内
  量化友好：直接线性映射到 INT8 即可

LLM 激活值（>6.7B 参数的模型）：
  99.9% 的通道：值在 [-0.5, 0.5] 范围内
  0.1% 的通道：值在 [-60, 60] 范围内（离群值！）
  
  离群通道数量 = 模型规模正相关
  6.7B: ~20 个离群通道
  70B:  ~100+ 个离群通道
```

### 3.2 为什么离群值会破坏量化

```
问题：

正常值范围: [-0.5, 0.5]
离群值:     120

INT8 范围: [-128, 127]

如果用统一缩放因子:
  scale = 127 / 120 ≈ 1.06
  
  正常值 0.3 量化后: round(0.3 × 1.06) = 0    ← 丢失！
  正常值 0.4 量化后: round(0.4 × 1.06) = 0    ← 丢失！
  离群值 120 量化后: round(120 × 1.06) = 127   ← 保留了

  结果：所有正常值都被压到 0，信息完全丢失
```

### 3.3 解决方案对比

| 方案 | 核心思路 | 优点 | 缺点 |
|------|----------|------|------|
| **LLM.int8()** | 离群通道用 FP16 矩阵乘，其余用 INT8 | 精度几乎无损 | 需要混合精度内核，实现复杂 |
| **SmoothQuant** | 数学等价地将激活离群值"转移"到权重 | 纯 INT8 即可，硬件友好 | 需要离线计算迁移系数 |
| **AWQ** | 不量化激活值，只量化权重；保护激活值大的权重通道 | 简单高效 | 激活值保持 FP16，显存占用较高 |
| **Per-channel 量化** | 每个通道独立缩放因子 | 简单直接 | 计算开销增加 |

### 3.4 SmoothQuant 数学推导

```
核心思想：Y = X · W = (X · diag(s)⁻¹) · (diag(s) · W) = X̂ · Ŵ

选择合适的 s，使得：
  X̂ = X / s    → 激活值离群被缩小
  Ŵ = s · W    → 权重值相应放大
  
当 s = max(|X|)^α / max(|W|)^(1-α) 时（α ≈ 0.5）
  X̂ 和 Ŵ 的值范围都变得均匀
  两者都可以安全地量化为 INT8
```

## 4. 校准数据选择策略

### 4.1 什么是校准数据

PTQ（后训练量化）需要一小批代表性数据来确定量化参数（缩放因子 scale 和零点 zero-point）。这不同于训练数据——它只是用来"标定"量化映射的范围。

### 4.2 选择原则

| 维度 | 推荐 | 原因 |
|------|------|------|
| **数据量** | 128-512 条 | 更多收益递减，太少则范围估计不准 |
| **序列长度** | 2048 tokens | 覆盖足够多的激活模式 |
| **语言** | 与部署语言匹配 | 中文部署用英文校准 → 中文精度更差 |
| **领域** | 与目标场景匹配 | 代码场景用代码数据，对话场景用对话数据 |

### 4.3 常用校准数据集

| 数据集 | 适用场景 | 特点 |
|--------|----------|------|
| **C4 (Common Crawl)** | 通用英文 | 默认选择，覆盖面广 |
| **WikiText-2** | 通用英文 | 经典选择，质量较高 |
| **The Pile** | 多领域英文 | 多样性好 |
| **CodeAlpaca** | 代码生成 | 代码场景优选 |
| **MMLU 样本** | 知识问答 | 评估场景对齐 |
| **自建领域数据** | 垂直领域 | 医疗/法律/金融等场景 |

### 4.4 校准数据对精度的影响

```
实验：Llama-70B INT4 GPTQ 量化，不同校准数据

校准数据          英文 MMLU   中文 MMLU   HumanEval
──────────────────────────────────────────────────
C4（英文通用）     82.5%      68.3%      67.5%     ← 基线
WikiText-2        82.8%      67.9%      66.8%
CodeAlpaca        81.2%      66.5%      69.1%     ← 代码提升
中文 Wikipedia     81.8%      70.1%      65.2%     ← 中文提升
混合（C4+Code）    82.3%      68.0%      68.3%     ← 均衡
```

**关键洞察**：校准数据决定了"对哪类文本最优化"。多语言/多场景部署时建议用混合校准数据。

## 5. 困惑度：量化的体温计

### 5.1 为什么用困惑度

Benchmark（MMLU、HumanEval）跑一次需要几小时，且结果波动大。困惑度（Perplexity, PPL）是更快速、更稳定的量化质量代理指标。

```
Perplexity 定义：
  PPL = exp(平均负对数似然)
      = exp(-1/N × Σ log P(token_i | context))

直觉：PPL = 模型在预测下一个 token 时的平均"困惑程度"
  PPL = 5 意味着模型平均在 5 个候选 token 之间犹豫
  PPL 越低 → 模型越确定 → 通常意味着越好
```

### 5.2 PPL 与量化质量的关系

```
量化方案             WikiText-2 PPL    MMLU     评价
───────────────────────────────────────────────────
FP16 基线            5.23             85.0%    基准
INT8 (SmoothQuant)   5.25 (+0.4%)    84.7%    几乎无损 ✓
INT4 GPTQ            5.40 (+3.3%)    82.5%    轻微退化 ✓
INT4 AWQ             5.35 (+2.3%)    83.3%    优于 GPTQ ✓
INT4 (随机量化)       8.50 (+62.5%)   71.2%    严重退化 ✗
INT2                 15.3 (+192%)    58.0%    不可用 ✗

经验阈值：
  PPL 涨幅 < 5%   → 量化方案可接受
  PPL 涨幅 5-10%  → 需要检查敏感层是否保护不足
  PPL 涨幅 > 10%  → 量化方案有问题，不建议上线
```

### 5.3 快速 PPL 评估脚本

```bash
# 使用 lm-evaluation-harness 快速评估量化模型的 PPL
lm_eval --model hf \
  --model_args pretrained=/path/to/quantized_model \
  --tasks wikitext \
  --batch_size auto

# 或使用 llama.cpp 的内置 PPL 测试
./llama-perplexity -m model-Q4_K_M.gguf \
  -f wiki.test.raw \
  -c 2048 -t 8
```

## 6. KV Cache 量化：第二战场

### 6.1 为什么 KV Cache 量化越来越重要

```
KV Cache 显存增长（Llama-70B, FP16）:

上下文长度     KV Cache 大小     模型参数      KV/参数比
──────────────────────────────────────────────────────
4K            4.2 GB           140 GB        3%
32K           33.6 GB          140 GB        24%
128K          134.4 GB         140 GB        96%   ← KV ≈ 模型本身！
1M            1050 GB          140 GB        750%  ← KV >> 模型
```

长上下文场景下，KV Cache 的显存占用远超模型参数，成为真正的瓶颈。

### 6.2 KV Cache 量化策略

| 策略 | 精度损失 | 显存节省 | 推荐场景 |
|------|---------|---------|---------|
| **FP16 → FP8** | 极小（PPL +0.1-0.3%） | 50% | **2026 推荐默认** |
| **FP16 → INT8 (per-head)** | 小（PPL +0.5-1%） | 50% | 无 FP8 硬件时 |
| **FP16 → INT4 (per-head)** | 中（PPL +2-5%） | 75% | 极端长上下文 |
| **FP16 → INT2** | 大（PPL +5-10%） | 87% | 实验性 |

### 6.3 K/V 不对称量化

Key 和 Value 对量化的敏感度不同：

```
敏感度：Key > Value

原因：
  Key 决定注意力权重（softmax 前的 logits）
  → 微小扰动经 softmax 放大后影响巨大
  
  Value 是注意力的"内容"
  → 扰动被加权平均，影响相对平滑

实践建议：
  Key:   保持 FP8 或 INT8（更保守）
  Value: 可以压到 INT4（更激进）
```

## 7. 精度对不同任务的影响

### 7.1 任务敏感度排行

不同任务对量化精度的容忍度差异巨大：

```
敏感度排行（从高到低）：

[极高] Function Calling / JSON 结构化输出
       → 一个 token 错误就完全失败
       
[高]   多步数学推理（GSM8K、MATH）
       → 中间步骤精度损失会级联放大
       
[高]   长尾知识问答（冷门实体、小语种）
       → 低频知识首先被量化抹平
       
[中]   代码生成（HumanEval）
       → 语法 token 敏感，但逻辑通常鲁棒
       
[中]   长文本摘要 / 信息抽取
       → 注意力分布扰动影响关键信息提取
       
[低]   创意写作 / 对话
       → 人类评估对微小质量差异不敏感
       
[极低] 文本分类 / 情感分析
       → 只需粗粒度语义，量化几乎无影响
```

### 7.2 各精度 × 任务矩阵

| 精度 | 创意写作 | 代码生成 | JSON/FC | 数学推理 | 知识问答 | 文本分类 |
|------|---------|---------|---------|---------|---------|---------|
| **BF16** | ★★★★★ | ★★★★★ | ★★★★★ | ★★★★★ | ★★★★★ | ★★★★★ |
| **INT8** | ★★★★★ | ★★★★★ | ★★★★★ | ★★★★☆ | ★★★★★ | ★★★★★ |
| **INT4 AWQ** | ★★★★☆ | ★★★★☆ | ★★★★☆ | ★★★★☆ | ★★★★☆ | ★★★★★ |
| **INT4 GPTQ** | ★★★☆☆ | ★★★☆☆ | ★★★☆☆ | ★★★☆☆ | ★★★★☆ | ★★★★★ |
| **INT2** | ★☆☆☆☆ | ☆☆☆☆☆ | ☆☆☆☆☆ | ★☆☆☆☆ | ★★☆☆☆ | ★★★☆☆ |

### 7.3 长文本生成 vs 短文本生成

```
量化精度对长文本影响更大：

短文本（<512 tokens）：
  INT4 量化几乎看不出差异
  因为每一步的误差很小，且文本短不会累积

长文本（>4096 tokens）：
  每一步的微小误差在自回归中累积
  → 后半段文本质量明显下降
  → 更容易陷入重复循环
  → 主题漂移（topic drift）更严重
```

## 8. 量化质量评估工作流

### 8.1 三步评估法

```
Step 1: PPL 快速筛查（5 分钟）
  └─ 跑 WikiText-2 PPL，涨幅 >10% 直接否决
  
Step 2: 领域 Benchmark（30-60 分钟）
  └─ 选 3-5 个与部署场景匹配的 benchmark
  └─ 与 FP16 基线对比，关注关键指标的退化
  
Step 3: 人工抽样验证（1-2 小时）
  └─ 从真实请求中抽 50-100 条
  └─ FP16 vs 量化模型 side-by-side 对比
  └─ 重点关注：长尾问题、结构化输出、长文本
```

### 8.2 评估 Checklist

```
□ PPL 涨幅 < 5%？
□ 核心 benchmark 退化 < 3pt？
□ JSON/Function Calling 格式正确率 > 95%？
□ 长文本（>2K tokens）无明显重复？
□ 冷门知识问题幻觉率无明显上升？
□ 代码生成语法正确率无明显下降？
□ 多语言场景（如中文）退化在可接受范围？
```

## 9. 精度恢复技术

当 PTQ 量化后精度不满足要求时，有以下恢复手段：

| 技术 | 原理 | 成本 | 精度恢复效果 |
|------|------|------|-------------|
| **换更好的 PTQ 算法** | GPTQ → AWQ，或升级 GGUF 量化等级 | 低（重新量化） | +1-3% |
| **保护敏感层** | Q/K/V 层保持 INT8，其余 INT4 | 中（模型稍大） | +2-5% |
| **QAT（量化感知训练）** | 训练时模拟量化误差 | 高（需训练） | +3-8% |
| **Post-Quantization Fine-tuning** | 量化后用领域数据微调 | 中高 | +5-10% |
| **QLoRA** | 在量化模型上叠加 LoRA 适配器 | 中 | +5-15%（领域任务） |

### QLoRA 精度恢复流程

```
1. 将基础模型量化为 INT4（NF4）
2. 在其上挂载 FP16 的 LoRA 适配器
3. 只训练 LoRA 参数（~1% 参数量）
4. 推理时：INT4 基础模型 + FP16 LoRA → 精度接近 FP16

优势：
  显存需求大幅降低（65B 模型 QLoRA 只需 ~48GB）
  训练速度快（只更新 1% 参数）
  精度恢复效果好（领域任务上接近 FP16）
```

## 10. 实战检查清单

### 量化前

```
□ 明确部署场景（对话/代码/结构化输出/分类？）
□ 确定硬件约束（显存上限、GPU 型号）
□ 准备校准数据（与部署场景匹配，128-512 条）
□ 跑 FP16 基线的 PPL 和 benchmark
```

### 量化中

```
□ 选择量化算法（AWQ > GPTQ > GGUF，按精度优先级）
□ 敏感层保护（Q/K/V 和首尾层用 INT8 或 FP16）
□ 校准数据语言与部署语言一致
□ 记录量化参数（scale、zero-point）以备复现
```

### 量化后

```
□ 跑 PPL（WikiText-2），涨幅 < 5%
□ 跑领域 benchmark，与基线对比
□ 人工抽样 50+ 条，关注结构化输出和长尾知识
□ 长文本生成测试（>2K tokens），检查重复
□ 部署环境实测延迟和吞吐
```
