# 集合通信库全景 2026

> 中文简称：通信库全景

> **一句话理解**: 集合通信库是「并行策略与物理互联之间的翻译官」——每家加速器都要配一个自己的 NCCL 等价物，名字不同（HCCL/ACCL-P/XCCL/RCCL），核心工作相同：把 AllReduce 翻译成本厂互联上的最优数据流。

---

## 1. 全家福一览

| 通信库 | 厂家/生态 | 绑定的互联 | 说明 |
|---|---|---|---|
| **NCCL** | NVIDIA | NVLink/NVSwitch + IB/RoCE | 事实标准，拓扑感知 ring/tree；深水区见 [[概念/GPU/nccl|NCCL]] |
| **ACCL-P / PCCL** | 阿里云 PAI-PPU / 平头哥 | ICN + 自研 RDMA 网卡 | ACCL-P 按 TP 度给出设备顺序；PCCL 与 ICN Switch 配套，见 [[01_数学基础/10_AI硬件/09_PPU_High_Performance_Network|PPU 高性能网络与 ICN 互联]] |
| **HCCL** | 华为昇腾 | HCCS + 参数面 RoCE | CANN 体系内，支撑 CloudMatrix 大域通信，见 [[12_架构基建/08_网络/PPU与高网/08_华为昇腾互联与组网|华为昇腾互联与组网]] |
| **XCCL** | 昆仑芯 | XPU-Link + IB/RoCE | 与 P800 OAM 配套，见 [[12_架构基建/08_网络/PPU与高网/11_昆仑芯互联与组网|昆仑芯互联与组网]] |
| **RCCL** | AMD / 海光（ROCm 系） | Infinity Fabric/xGMI + IB/RoCE | ROCm 生态沿用，海光 DCU 因此复用整套栈，见 [[12_架构基建/08_网络/PPU与高网/10_海光DCU互联与组网|海光 DCU 互联与组网]] |
| **oneCCL** | Intel | Gaudi 片上网卡 + 以太 | oneAPI 体系，见 [[12_架构基建/08_网络/PPU与高网/17_Intel_Gaudi_互联与组网|Intel Gaudi 互联与组网]] |
| **MCCL** | 摩尔线程 | MTLink | MUSA 栈配套（公开资料较少，以官方文档为准） |
| **Gloo** | Meta（通用） | TCP/IB | CPU/异构后备，PyTorch 内置 fallback |
| **DeepEP / AcclEP-P** | 开源 DeepSeek 生态 / 阿里 PPU 版 | 面向 MoE 的 EP 专用库 | All-to-All/分发-组合优化；AcclEP-P 为 PPU 版本 |

## 2. 共同的骨架

尽管各家实现不同，主流通信库都遵循同一套设计骨架：

1. **拓扑探测**：启动时探明卡间/机间互联结构（NVLink 拓扑、ICN 端口、网卡亲和）；
2. **算法选择**：按消息大小与拓扑选 Ring / Recursive Doubling / Tree / Split-Doubling；
3. **通道化**：把一个大算子拆成多个 channel 并行压链路；
4. **传输栈选择**：卡间直连（类 NVLink/ICN）优先，机间走 RDMA verbs，兜底 Socket；
5. ** fused 算子**：与框架融合（梯度归约融合进反向）。

> 算法层原理（Ring 的 2(n-1)/n 流量、Tree 的延迟优势）详见 [[10_部署推理/03_推理优化/19_Communication_系统_深入分析|Communication 系统深入分析]]。

## 3. 选型与使用维度

| 维度 | 关注点 |
|---|---|
| **框架集成** | PyTorch `torch.distributed` 后端、Megatron/DeepSpeed/vLLM 的适配层是否官方支持 |
| **版本匹配** | ACCL-P 明确提示设备顺序随镜像/驱动/库版本变化——升级后必须重新核对官方文档 |
| **算子覆盖** | EP 类（All-to-All、分发/组合）在 MoE 场景是否走专用库（DeepEP 系） |
| **可观测性** | NCCL_DEBUG、各家日志与计数器是否足以回答「走的哪条路、用了几个通道」 |
| **回退路径** | RDMA 不可用时会静默回退 Socket——压测不达预期时先查 transport，见 [[12_架构基建/08_网络/PPU与高网/05_高网性能测量方法_2026|05 测量方法]] |

## 4. 一个真实对照：同一模型换卡，通信层要动什么

以 TP=8 的推理服务从 NVIDIA 迁到 PPU 为例：

| 层 | NVIDIA | PPU | 迁移动作 |
|---|---|---|---|
| 通信库 | NCCL | ACCL-P（镜像内置） | 换库并核对版本 |
| 设备顺序 | `nvidia-smi topo -m` 自查 | 官方按 TP 2/4/8 给定顺序 | **按文档重排 `CUDA_VISIBLE_DEVICES`**（最常见踩坑点） |
| 机间变量 | `NCCL_SOCKET_IFNAME=eth0` | 16 卡整机用 `hpn0` | 用官方镜像默认值，不随意改 |
| 推理引擎 | vLLM/SGLang 原生 | 官方适配版 | 走 PAI-PPU 官方镜像 |

此表即 [[01_数学基础/10_AI硬件/09_PPU_High_Performance_Network|PPU 高性能网络与 ICN 互联]] §5–6 的工程化复述，迁移场景可直接引用。

## 5. 开放问题

1. **统一抽象缺位**：框架层（torch.distributed）给了接口统一，但各家库的性能特征差异大，跨平台调优经验不完全可迁移；
2. **MoE 专用库崛起**：DeepEP 类库把 EP 通信从通用集合通信里独立出来，未来可能出现「通用 CCL + EP 专用库」的双栈常态；
3. **国产库公开资料薄**：MCCL/CNCL 等的算法细节公开资料少，排障高度依赖厂商支持。
