# 网络遥测与监控基线

> 中文简称：网络遥测与监控基线

> **一句话理解**: 每条链路开工时考一次「体测」存下成绩，以后天天量体温——光功率、错包、速率一旦开始慢慢变差，趋势线比报警器先知道。

---

## 一、采集矩阵

| **指标类** | **具体指标** | **建议频率** | **采集手段** |
|---|---|---|---|
| 错包类 | CRC/pcrc/rcrc、SymbolError、接口 drop | 10-30s | 交换机 gNMI/streaming telemetry 优先，SNMP 轮询兜底 |
| 拥塞类 | pause 帧速率、ECN 标记比例、buffer 水位 | 10-30s | 同上；buffer 水位部分平台需要专用水印 counter |
| 光层 | 光功率 RX/TX、模块温度 | 30-60s | 模块 DOM/DDM 读取，随 telemetry 通道上报 |
| 状态类 | 端口协商速率、FEC 状态、up/down 事件 | 事件推送 + 周期快照 | 状态变化事件即时推，周期快照兜底防漏 |

```
# 采集通道优先级
# 1) 交换机原生 gNMI / streaming telemetry：订阅 interface、pfc、buffer、optics 计数器组，10s 推送
# 2) SNMP 轮询兜底：覆盖老旧固件与第三方设备，30s 粒度，只采核心 counter
# 3) 主机侧补充：ethtool -S / ibstat 定时抓取，补齐交换机看不到的网卡侧半段
```

为什么是 10-30s：更粗的采样会错过训练任务一个 step 内的拥塞尖刺，告警滞后到「作业已经失败」才触发；更细的采样对交换机 CPU 与采集管道成本显著上升，收益递减。事件类（端口 down、速率降档）不走轮询，走推送。

存储与回溯口径：30s 粒度原始数据保留数周以支撑趋势分析，之后降采样归档保留一年以上；事故复盘经常要回看数周前的劣化起点。

## 二、基线化方法

告警有没有用，取决于有没有基线可比。基线在集群交付时一次性建立，之后滚动维护：

- 全组 nccl-tests 存档：交付验收时全组跑标准参数基线（allreduce 的 algbw/busbw），作为此后一切回归的参照；
- 两两打流矩阵存档：所有跨机链路的 ib_write_bw 实测值入库，每条链路从此有自己的「出厂带宽数」——是实测数，不是理论线速；
- 周期回归：每周或每次变更后抽样重跑，与存档对比，形成时间序列；
- 基线与参数绑定存档：换进程数、换消息尺寸跑出来的数字不可比，等于污染基线；每次人为变更（换模块、调阈值）后重新钉基线，避免把变更当劣化、把劣化当变更；
- 可重复性：同参数复跑两遍取均值存档，排除单次抖动；两次差异过大的集群本身就有问题。

```bash
# 基线存档目录形态（示意）
# /baseline/<cluster>/nccl_tests/2026-10-27_allreduce_N512.log
# /baseline/<cluster>/pairwise/nodeA-nodeB_ib_write_bw.log
# /baseline/<cluster>/metadata.json   # 参数快照：进程数、消息尺寸、固件版本
```

## 三、告警规则示例

| **告警** | **条件示例** | **说明** |
|---|---|---|
| pause 速率突增 | pause 帧速率环比放大数倍且持续 | 拥塞恶化或 PFC 异常前兆，优先查无损配置 |
| 光功率漂移 | RX 功率相对该链路基线漂移 >2dB | 链路在劣化，计划内换件而不是等断 |
| CRC 计数增长 | 任一链路 CRC >0 且持续增长 | 物理层问题，直接开单，不用等业务感知 |
| 端口速率降档 | 400G 协商为 200G/100G | 宽口裂开，涉及链路带宽腰斩，零容忍即时告警 |
| ECN 比例超阈 | 标记包占比连续 M 分钟超阈值 | 拥塞常态化，查容量与阈值配置而非单点故障 |

规则设计原则：counter 类看增速不看累计值；状态类零容忍即时告警；漂移类看相对该链路基线的差值，而不是全网统一绝对值——不同批次模块的光功率本底差异很大。

```
# 告警分级（示意）
# P1 电话：端口 down、速率降档、CRC 持续增长
# P2 工单：光功率漂移 >2dB、pause 速率突增
# P3 观察：ECN 比例抬升、busbw 周环比下滑
```

没有分级的告警等于没有告警——P3 类观察项攒周报，P1 类才值得半夜叫醒人。

## 四、「慢慢变慢」：趋势优先于绝对阈值

光功率每月漂零点几个 dB、链路质量渐进劣化、buffer 水位缓慢抬升——这类劣化永远不会触发绝对阈值，但会真实吃掉带宽：全组 busbw 每月掉 1%，三个月后没人觉得异常，大家只会认为「这批任务本来就这个速度」。

对策：

- 周环比/月环比趋势告警：对光功率、打流回归值、busbw 基线算趋势斜率，斜率持续为负即预警；
- 趋势面板按链路、按 rail 聚合展示——劣化往往聚集在同一批模块或同一个方向的链路上，聚合视图能看出「一批一起变差」的结构性信号；
- 把趋势预警接到处置流水线：进入观察名单的链路安排计划内更换，而不是等它变成生产事故；
- 与备件策略联动：趋势名单直接生成换件工单，光功率漂移链路在断之前进入计划内更换队列。

趋势方法的边界：它能发现渐进劣化，发现不了突发故障——与绝对阈值告警互补，不是替代。

## 五、Dashboard 三层下钻

排障视角决定 dashboard 结构，按 per-rail、per-spine、per-node 三层组织：

- per-rail：rail-optimized 拓扑下先看哪条 rail 整体异常——rail 级劣化指向交换机或成组线缆的工艺问题；
- per-spine：spine 维度聚合错包与 pause，定位是否单台 spine 的缓冲/队列异常；
- per-node：下钻到具体节点与端口，展示该链路的光功率、counter 历史、速率状态与基线带宽数对照；
- 下钻入口统一：从训练任务视角也能发起下钻（先圈定任务涉及的节点组，再 rail/spine），两个方向共享同一份数据模型。

三层下钻把「全组掉速」这类模糊工单的定位路径固化成两次点击：rail → spine → node，配合慢节点定位的逐机矩阵，从工单到嫌疑链路的时间可控在半小时量级。

面板的时间轴要支持基线叠加：当前曲线与首装基线同屏对比，劣化幅度一眼可见，不需要心算。

## 六、与训练侧联动

网络监控最容易缺失的一环，是和网络的使用方（训练任务）联动起来：

- MFU 劣化自动触发网络回放：训练平台检测到任务 MFU 低于同型号任务历史水平时，自动对该任务涉及的节点组发起打流矩阵 + nccl-tests 回放，与基线对比后产出「网络有罪/无罪」证据；
- 回放结果回写工单：有罪则附带可疑链路清单（直接转入网络诊断命令链流程），无罪则排除网络，转向 GPU/存储侧排查；
- 反向联动：网络侧的变更窗口（阈值调整、计划换件）提前广播给训练平台，长跑任务择机避让；
- 联动的价值：把「训练慢到底是不是网络的锅」从人工吵架变成数据结论，平均定位时间从天级压到小时级；
- 回放的调度礼貌：回放测试优先在低峰执行；必须在线回放时限流，并避开整点变更窗口。
