# 办公 Agent × PD 分离：整条链路推演

> 中文简称：办公 Agent PD 分离链路推演

> **一句话理解**: 办公 Agent 的一次任务（"把这份报告做成 PPT"）在推理引擎眼里不是一次对话，而是一串 prefill / decode 交替的脉冲——PD 分离 + KV 中心池就是把这串脉冲分别汇集到"读题池""写字池"和"草稿池"，本文用千问办公这类产品做例子，把整条链路一步一步推演一遍。

## 2. 流量解剖：办公 Agent 的四类请求模板

### 2.1 四类模板与 token 形态

| 模板 | 输入 | 输出 | 压力特征 | P:D 配比倾向 |
|------|------|------|----------|--------------|
| **RAG 问答** | system + 检索片段 + 问题（几 K～几十 K） | 几百 token | prefill 重，脉冲式 | 3 : 1 |
| **长文生成 / PPT 大纲** | 中长输入 | 几千 token | 两头都重 | 1 : 1 |
| **多轮追问 + 工具循环** | 历史滚动增长 + 工具结果回填 | 短（文本/JSON） | 前缀复用价值极高，请求密集 | 2 : 1～1 : 1 |
| **后台批处理**（导入摘要、定时任务） | 长输入 | 中输出 | 无 TTFT SLO，吞吐型 | 夜间塞 P 池低谷 |

### 2.2 关键观察：agent 链路 = prefill 脉冲串

一次"把这份 50 页报告做成 10 页 PPT"的任务，背后约 15+ 次模型调用：

```
① 读文档出大纲     1 次   长进中出（50 页 ≈ 30K token prefill + 2K decode）
② 逐页生成        10 次   中进中出（前缀 = 大纲 + 文档节选，每页 1K decode）
③ 工具校验/排版    3-5 次   短进短出（JSON 输出，guided decoding）
```

混池部署时，这串任务的每一次 prefill 脉冲都会霸占算力数十至数百毫秒，**打断当时所有正在流式输出的请求**——用户感知就是别人屏幕上"打字机卡了一下"。这就是办公类产品必须做阶段隔离的根因（干扰机理详见 [[10_部署推理/03_推理优化/25_Disaggregated_服务_2026|2026 Disaggregated 服务]] §2）。

## 3. 整条链路推演：从上传到 PPT 导出

### 3.1 全链路图

```
用户上传 50 页 Word
   │
   ▼
[文档解析 + 切片 + embedding]   ← 离线池：解析是 CPU 服务（python-docx 类），
   │                              embedding 走独立的小模型池（bge-m3 级），
   │                              都不占 LLM 推理池——链路里最容易被忽略的一环
   ▼
向量库（切片 + 向量 + 原文块索引）
   │
   ▼
用户提问"总结这份文档"
   │
   ▼
[Router] ──选 P 实例：前缀命中优先（该文档 / 该租户 system 的 KV 在哪，就去哪）
   │
   ▼
[P 池] system + 文档全文 + 问题 ≈ 30K token prefill
   │    大 TP、chunked 分批喂、算力打满；KV 边算边传（pipeline）
   ▼
[KV 池] RDMA / GPU Direct 接收，分层落盘（HBM 热 / DRAM 温 / SSD 冷）
   │
   ▼
[D 池] 流式吐总结（几百 token），大 batch decode → SSE 打字机
   │
   ▼
用户追问"第 3 章展开讲讲"
   │    KV 池里文档前缀还在 → 只 prefill 增量几百 token → 回 D 池续
   ▼
"做成 PPT" → Agent 编排器拆任务 → 循环：小 prefill（工具结果）+ decode（正文/JSON）
   │
   ▼
[导出服务]  docx/pptx 生成是纯 CPU/模板服务，与 LLM 池无关
```

### 3.2 离线环节：解析与 embedding 不占 LLM 池

- 文档解析（PDF/Word 转 Markdown、OCR）是 CPU/专用服务；embedding 是独立小模型。把它们和 LLM 服务混部是常见初学者错误——embedding 洪峰会和 LLM 抢 GPU。
- 导入文档时的"摘要 / 自动打标签"属于**无 SLO 的批处理**：排到夜间 P 池低谷跑，白天 P 池产能全部留给交互 RAG。这是 PD 分离后"prefill 池白天黑夜负载互补"的隐藏收益。

### 3.3 在线 RAG 问答：P 池 → KV 池 → D 池

1. **P 池视角**：目标只有一个——把 30K token 尽快变成 KV。配置取向：大 tensor 并行、小 batch、高算力型；chunked prefill 把超长 prompt 分批喂入（避免单请求独占过久）。
2. **KV 池视角**：不点对点直传，而是先落全局池（Mooncake 式），D 池按需取。这一步是后面多轮复用的前提。
3. **D 池视角**：目标只有一个——TPOT 稳定且低。配置取向：大 batch（几百序列）、带宽打满、算力闲置 70%+ 无所谓；SSE 流式输出直接决定打字机体验。

### 3.4 多轮追问：KV 池的胜负手

- 裸 DistServe 双池（KV 点对点直传、不落池）：每轮追问都要重传全量 KV，30K 文档上下文每轮 ≈ 5 GB（FP8）迁移，多轮下迁移开销爆炸。
- KV 中心池：文档前缀 KV **只算一次、传一次**，后续每轮追问 T_transfer → 0，P 池只 prefill 增量（新检索片段 + 新问题）。
- 这就是为什么生产级 Agent 产品是"**PD 双池 + KV 池**"三件套，而不是裸双池。

### 3.5 工具循环与结构化输出

- 工具调用（function calling）的 JSON 输出由 **guided decoding**（结构化约束解码）保证，它运行在 **D 池**，会和普通文本生成混在同一个大 batch 里（引擎层面见 [[10_部署推理/03_推理优化/25_Disaggregated_服务_2026|25 号文档]] FAQ Q5 与调度章节）。
- 每次工具返回都触发一轮小 prefill（把工具结果拼进上下文）。高频工具循环意味着**这类负载的 prefill 请求数远高于"一问一答"直觉**——是脉冲串的主要来源。

### 3.6 长文 / PPT 生成：任务级编排

- 大纲 → 逐页 → 校验的编排发生在 **Agent 层**（业务编排器），不在推理层；推理层只看到一批前缀高度重叠的请求。
- 逐页生成的前缀 = system + 大纲 + 文档节选，10 次调用共享同一个大前缀 → 在 KV 池 + 前缀复用下，只有每页的增量部分需要 prefill。
- 对用户可见的"进度条式生成"允许更宽的 TTFT（3～5 s），可以走 D 池的非流式/低优先级队列，把交互问答的 TPOT 让出来（见 §6 SLO 分级）。

## 4. 数字账：KV 迁移与容量

### 4.1 迁移时间表（70B 级模型，KV 公式见 [[10_部署推理/03_推理优化/05_KV_Cache_深入分析|KV Cache 深度]]）

`KV_size = 2 × seq_len × n_layers × n_kv_heads × head_dim × 2 bytes`（FP16）

| 场景 | KV（FP16） | FP8 传输量 | 400 Gbps 迁移 | 同场景 prefill 耗时（P 池） |
|------|-----------|-----------|---------------|---------------------------|
| 8K 问答 | 2.68 GB | 1.34 GB | ≈ 27 ms | 0.4～0.8 s |
| 30K 文档（本篇主例） | ≈ 10 GB | ≈ 5 GB | ≈ 100 ms | 1.5～3 s |
| 128K 长篇 | ≈ 43 GB | ≈ 21 GB | ≈ 430 ms | 6～13 s |

结论：**T_transfer ≪ T_prefill**，再用 pipeline 边算边传 + FP8 量化 + 前缀复用三件套，迁移延迟几乎完全隐藏。若不做这三件事，128K 场景迁移会反超 prefill，分离收益归零——这是双池的命门（必背）。

### 4.2 容量账（KV 池为什么要分层）

30K 文档一条序列 10 GB（FP16），一张 80 GB 卡的 HBM 塞不下几条热文档。所以 KV 池必须分层：**热（当次会话）在 HBM、温（本会话历史/本租户热门文档）在 DRAM、冷（组织共享文档库）在 SSD**，按"前缀引用计数 + LRU"驱逐。多轮追问的增量 prefill 依赖前缀 KV 还在池里——命中率直接决定 P 池的重复工作量。

## 5. 架构要点

### 5.1 三件套各自的配置取向

| 组件 | 目标 | 配置取向 | 关键监控 |
|------|------|----------|----------|
| **P 池** | 最短 T_prefill | 大 TP、小 batch、算力型、chunked prefill、前缀命中路由 | TTFT、prefill 吞吐、前缀命中率 |
| **KV 池** | 迁移快 + 复用高 | GPU Direct RDMA、FP8 传输、HBM/DRAM/SSD 分层、引用计数 | 迁移延迟、命中率、分层驱逐率 |
| **D 池** | 最稳 TPOT | 大 batch、带宽型、guided decoding 混批、优先级队列 | TPOT P99、批密度、队列深度 |

### 5.2 配比与动态调整

- 办公流量主档是 RAG 长进短出 → **P : D ≈ 3 : 1**；早晚高峰写作类（长进长出）占比上升时向 1 : 1 调。
- 按 goodput（满足 SLO 的有效吞吐）反馈动态调整卡数，不要写死——配比静态是双池五大陷阱之一（DistServe 理论与经验值见 [[10_部署推理/03_推理优化/25_Disaggregated_服务_2026|25 号文档]] §7.1）。

### 5.3 组织级前缀共享：B 端场景的特有收益

办公产品的 B 端属性带来一个纯 chat 没有的红利：**同一份文档/同一个团队 system prompt 会被多人反复使用**。

- 全公司共用的长 system（角色设定 + 工具定义）+ 热门文档前缀，在 KV 池按 `(model, 前缀 hash)` 去重、引用计数共享——100 个人问同一份文档，全量 KV 只算一次。
- 这把"组织热文档"变成了 KV 池的天然驻留层，前缀命中率远高于 C 端 chat。也是 Mooncake 式 KV 池在办公场景收益放大的直接原因。

### 5.4 多租户与容错

- **洪峰隔离**：双池天然把"某租户批量导入触发 prefill 洪峰"挡在 P 池，D 池不受冲击；D 池内部再做 per-tenant 公平调度（防止单租户的长生成挤占他人 TPOT）。
- **decode 实例故障**：KV 在池中有副本（或可从 SSD 重载 / 从 P 池重算），Router 把在途请求重路由到新 D 实例续跑——这是"KV 中心化"把容错变成池管理问题的价值（对比裸双池：KV 随实例一起丢）。

### 5.5 MoE 加成

千问系后端大概率是 Qwen3-MoE 级模型。MoE 让 prefill 更算力密集、decode 更访存密集，分离收益进一步放大；同时 P 池要处理专家负载波动（EP + 冗余专家），D 池可做热专家缓存——DeepSeek Infra 的"MoE + PD 分离"路线，详见 [[10_部署推理/03_推理优化/22_MoE_推理优化|MoE 推理优化]]。

## 6. SLO 定义：办公场景的 TTFT / TPOT 该怎么定

办公场景的用户体感分三档，SLO 应分开定、分开监控（混在一起定一个数是常见错误）：

| 交互档位 | TTFT 目标 | TPOT 目标 | 说明 |
|----------|-----------|-----------|------|
| **交互问答 / 多轮** | P99 < 1 s（长文档 RAG 放宽） | P99 < 50 ms（≈ 20 tok/s 打字机） | 体验命脉，D 池最高优先级 |
| **逐页生成 / 长文写作** | P99 < 3～5 s | 可放宽 | 用户看进度条，可走 D 池低优先级队列 |
| **后台批处理**（导入摘要、定时任务） | 无 | 无 | 夜间 P 池低谷跑，吞吐优先 |

双池的核心卖点正是**让这三档 SLO 同时成立**：混池时"批处理挤占交互"和"长 prefill 打断打字机"二选一，双池后物理隔离。

## 7. 前缀缓存杀手清单（云上与本机通用）

KV 前缀是**逐 token 从头匹配**的——前面一个字节不同，后面全部作废。办公 Agent 的 prompt 拼装极易踩坑：

| 杀手 | 后果 | 对策 |
|------|------|------|
| system 里塞时间戳 / 随机 ID / 用户名 | 每个请求前缀都不同，缓存全灭 | 易变信息挪到 prompt 末尾 |
| 检索片段插在文档全文**之前** | 中段易变，文档前缀白算 | **稳定在前、易变在后**：system → 文档全文 → 检索片段 → 用户问题 |
| 检索排序抖动（同文档两次检索顺序不同） | 片段段变了 | 片段内定序（按文档位置），或对片段做稳定排序 |
| 工具结果拼接格式抖动 | 多轮前缀在工具轮后失配 | 拼接模板固定，结果统一追加到历史尾部 |
| 负载均衡轮询打散 | 同会话落到不同实例，实例内缓存白做 | cache-aware 路由（会话粘性 / 前缀哈希） |

> 这张表对本地 Ollama/Dify 同样有效——本机没有 KV 池，但引擎内 prefix caching 的命中逻辑一模一样。

## 8. 本机对照：M4 24 GB 单机版怎么办

[[15_智能体/20_Agentic_Infra/04_本地千问办公Agent实战|本地千问办公实战]] 搭的 Ollama + Dify 单机版，和云端架构的对应关系：

| 云端机制 | 本机对应 | 备注 |
|----------|----------|------|
| PD 双池 | **不适用**（单机拆不出两个池） | Ollama 是单池；默认排队串行 = "天然无干扰、吞吐低" |
| Chunked Prefill | 引擎内置（新版 Ollama/llama.cpp 已有类似机制） | 单池消干扰的最低成本方案 |
| KV 中心池 | **无**；引擎内 prefix caching 即全部 | 多轮追问省不省，全看前缀拼得稳不稳（§7 清单直接适用） |
| 组织级前缀共享 | 单用户无此需求 | — |
| KV 容量分层 | 统一内存就是唯一一层，**容量是硬约束** | 见下方数字账 |

本机数字账（Qwen3-30B-A3B：48 层、GQA 4 KV 头、head_dim 128）：

```
8K 上下文 KV ≈ 2 × 8192 × 48 × 4 × 128 × 2 B ≈ 0.80 GB
32K 长文     ≈ 3.2 GB
```

- Q4 权重 ~19 GB 贴着 24 GB 上限，剩给 KV + 激活约 3～4 GB → **一条 32K 长文就顶满**。所以本机"整份文档直接塞上下文" vs "先 RAG 切片检索"的差距是**放不放得下**，不是快慢。
- 有趣的对照：稠密 Qwen3-14B（40 层、8 KV 头）的 KV ≈ 1.34 GB/8K，反而是 MoE 30B（0.80 GB/8K）的 1.7 倍——GQA 头数比参数量更决定 KV 占用。
- 面试加分点：能主动讲"我知道 PD 分离解决什么问题，也知道单机/小规模为什么不用它"——对应 [[10_部署推理/03_推理优化/25_Disaggregated_服务_2026|25 号文档]] FAQ Q4。

## 9. 面试口径与追问预备

**一句话口径**：

> 办公 Agent 的流量是 RAG 长输入 + 多轮前缀复用 + 工具调用短输出，一次任务是十几次模型调用组成的 prefill 脉冲串；混池时长 prefill 会打断所有在生成的请求造成 TPOT 尖刺，所以生产上必然走 **PD 双池 + KV 中心池**：RAG 主档配比约 3:1，命门是 T_transfer < T_prefill（30K 文档 ≈ 5 GB FP8、100 ms 量级，远小于秒级 prefill），多轮追问靠 KV 池前缀复用把迁移开销打到 ≈ 0，B 端组织共享文档还能把前缀命中率进一步推高。

**高频追问预备**：

| 追问 | 答案要点 |
|------|----------|
| KV 池分层怎么设计？ | HBM 热 / DRAM 温 / SSD 冷；前缀引用计数 + LRU 驱逐；命中决定 P 池重复工作量 |
| 双池后前缀命中率为什么跌？ | KV 散在各 P 实例 + 无全局池 → 上 KV 池 + cache-aware 路由 |
| 为什么不是裸 DistServe？ | Agent 多轮需要**跨请求** KV 复用，裸双池点对点直传不沉淀 KV，每轮重传全量 |
| 容错怎么做？ | KV 池有副本/可重载，decode 挂了 Router 重路由续跑；裸双池 KV 随实例丢 |
| 单机/小规模呢？ | Chunked Prefill 单池即可；PD 分离是多机架构，单机拆池不划算 |

## 10. 办公场景特有的陷阱清单

| 陷阱 | 现象 | 规避 |
|------|------|------|
| 批处理挤占白天交互 | 上午导入洪峰，全员问答变慢 | 批处理错峰 + 双池物理隔离 + 租户配额 |

| 只监控整池不监控分档 SLO | "平均延迟正常"但交互档 P99 已爆 | 按 §6 三档分开埋点告警 |
