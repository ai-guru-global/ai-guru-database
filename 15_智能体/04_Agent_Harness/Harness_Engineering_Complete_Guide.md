## 1. Harness 的定义与核心命题

### 1.1 核心公式：Agent = LLM + Harness

**Harness** 是在大语言模型与真实执行环境之间构建的一套系统工程框架。它通过标准化的消息协议、分层的权限管理、多维的执行可见性和完善的错误处理机制，使 LLM 能够在受控约束下安全、可靠地感知环境、执行任务、学习反馈。

```
模型决定了智能体的思维上限，
Harness 决定了智能体的工程下限。
```

一个没有 Harness 的大模型只是一台发动机；一个经过 Harness 工程化的智能体才是一辆能够可靠载人行驶的汽车。

### 1.2 "驾驭"的隐喻

Harness 源自马具——骑手用来驾驭烈马的缰绳、鞍具和套具系统。它不是给马匹增加力量，而是：
- **引导方向**：通过缰绳确保力量用在正确方向
- **分散风险**：通过多个接点均匀分散冲击力
- **标准化协作**：让骑手与马匹之间形成可预期的交互协议

### 1.3 与传统中间件的本质区别

| 维度 | 传统中间件 | Harness |
|------|-----------|---------|
| 交互假设 | 各方行为确定、可预测 | Agent 决策可能包含错误、偏差甚至不当意图 |
| 请求处理 | 高效转发、协议转换 | 拦截验证、权限审批、智能重试、降级 |
| 审计 | 日志为主 | 完整审计日志 + 执行轨迹重放 |
| 故障处理 | 异常转发 | 智能重试、断路器、检查点恢复 |

### 1.4 职责边界

**Harness 做的事**：工具集成、权限授权、执行跟踪验证、状态管理、可观测性和审计

**Harness 不做的事**：推理和决策（LLM 职责）、工具的实际执行（工具自身职责）、模型优化和训练、业务逻辑定义

## 2. 为什么 Harness 比模型更重要

### 2.1 实证数据

#### OpenAI Codex 团队的发现
引入 Harness 层（语法验证 + 类型检查 + 结果验证）后，准确率提升 30-40 个百分点——**没有任何模型改进，只是系统工程**。

#### Bölük 的 "15-LLM-下午" 实验
将"完整文本编辑"改为"行级内容哈希引用"（Hashline 技法），16 个模型一致提升：
- Grok Code Fast 1：6.7% -> 68.3%（+61.6pp，约 10x）
- 平均输出 token 下降约 20%（成本同步降低）

首个以严格对照方式证明 **编辑工具的接口设计对编码 Agent 可靠性可产生一个数量级影响** 的实验。

#### LangChain Deep Agents
纯 Harness 层级改进（模型不变），Terminal Bench 2.0 从 52.8% 提升到 66.5%（+13.7pp），全球排名从 30 名外进入前 5。

#### Anthropic 的反向验证
固定模型只改变基础设施配置，成功率漂移 +6pp。Anthropic 建议：**排行榜上低于 3pp 的差距很可能反映的是 harness 配置差异而非模型能力**。

### 2.2 数学论证

假设 N 个步骤，每步 LLM 成功率 p：

- **无系统工程**：整体成功率 p^N。N=100, R=0.95 时要求 p >= 99.95%
- **有系统工程**：原始 p=90%，引入验证+重试 3 次，有效 p' = 1-(1-0.9)^4 = 99.99%，整体 0.9999^100 ≈ 99%

即使用较弱的模型，通过系统工程干预也能实现高可靠性。

### 2.3 行业验证

OpenAI Codex 团队 5 个月、3 名工程师、约 100 万行代码、零人工编写，平均吞吐量 3.5 PR/工程师/天。

**范式演进**：
1. **Prompt Engineering**：单轮交互，无持久化
2. **Context Engineering**：RAG/记忆机制
3. **Harness Engineering**：系统级执行控制与验证

## 3. 通用参考架构

### 3.1 三层 + 横切关注点

```
┌─────────────────────────────────────────┐
│  接入层 (Access Layer)                   │
│  CLI / Web API / SDK                     │
├─────────────────────────────────────────┤
│  编排层 (Orchestration Layer)            │
│  任务分解 · 多智能体协调 · 工作流管理      │
├─────────────────────────────────────────┤
│  智能体核心层 (Agent Core Layer)          │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌────────┐ │
│  │运行时│ │工具层│ │记忆  │ │模型集成│ │
│  │引擎  │ │      │ │子系统│ │输出治理│ │
│  └──┬───┘ └──┬───┘ └──┬───┘ └──┬─────┘ │
│     └────────┴────────┴────────┘        │
│         (星型拓扑，运行时引擎协调)         │
├─────────────────────────────────────────┤
│  横切关注点 (Cross-cutting Concerns)     │
│  安全 · 可观测性 · 存储                   │
└─────────────────────────────────────────┘
```

**关键架构事实**：模型调用、工具执行、记忆更新不是各自独立的层级，而是在运行时引擎的 **同一个循环中交替发生**。

### 3.2 层间通信设计

- **向下调用**：明确的、类型安全的接口（`AgentCore.run(Task) -> Result`）
- **向上反馈**：事件/回调机制而非异常（`ExecutionEvent` 含 timestamp, level, source, message, context）
- **核心层内部**：星型拓扑，运行时引擎是唯一协调者，其他子系统不直接互相调用

### 3.3 三种生产架构对比

| 维度 | OpenAI Codex | Claude Code | OpenClaw |
|------|-------------|-------------|---------|
| 定位 | 性能型 | 任务型 | 自驱型 |
| 运行时 | Rust core + JSON-RPC 三层原语 | 异步生成器模式 | 线性流水线模式 |
| 编排 | Subagent 层级委派（3+ 层深度） | Coordinator 动态多 Agent | Lobster 确定性工作流 |
| 安全 | execpolicy + 平台沙箱双层 | 权限模式 + protected files | SOUL.md + 三级权限 |
| 记忆 | SQLite + AGENTS.md | 系统提示词缓存 | MEMORY.md + 每日文件 |
| 特点 | 线性成本上下文管理、60+ Cargo Crate | 流式优化、40+ 特性门控 | Gateway 单一控制平面 |

## 4. 五大核心子系统总览

### 4.1 运行时引擎

Harness 的心脏。维护智能体执行的主循环：**感知 -> 推理 -> 决策 -> 执行 -> 学习 -> 判断**。

核心职责：状态机管理（Initializing -> Executing -> Completed -> Stopped）、消息编排、异步执行、超时中断。

两种实现模式：
- **异步生成器模式**（Claude Code）：低延迟高并发，事件驱动，适合交互式
- **线性流水线模式**（OpenClaw）：确定性可追踪，单线程阶段化，适合自驱型

### 4.2 工具层

智能体与真实世界的连接点。

核心职责：工具注册（Tool Registry）、工具发现、参数验证、权限检查、执行隔离（异常捕获 -> 进程 -> 容器 -> 系统级沙箱）、结果标准化。

工具生命周期：注册 -> 发现 -> 选择 -> 调用 -> 隔离执行 -> 结果处理 -> 反馈

### 4.3 记忆子系统

让智能体能够学习和改进的基础。

三层架构：
- **工作记忆**：当前对话上下文窗口，受 LLM 上下文长度限制
- **短期记忆**：会话级摘要和临时状态，数小时到数周
- **长期记忆**：持久化知识，向量索引支持语义检索，数月到数年

### 4.4 模型集成与输出治理

管理与 LLM 的交互，控制和验证模型输出。

四步防御流程：格式解析 -> 自愈修复 -> 语义验证 -> 安全检查

关键能力：模型选择（多供应商故障转移）、提示词管理、输出解析、置信度评估、降级策略

### 4.5 编排引擎

支持复杂多步任务和多智能体协作。

核心职责：工作流定义（顺序/条件/并行/循环）、依赖管理（DAG）、智能体分配、结果聚合、故障恢复

## 5. 两大基础保障

### 5.1 安全层

渗透在所有子系统中的安全机制：
- 梯度化权限模型（Free / Ask-first / Approve-once）
- 沙箱隔离（Docker / seccomp / Bubblewrap）
- 输入验证与防注入
- 输出过滤与安全检查
- 完整审计日志

### 5.2 可观测性层

三个维度的完整可见性：
- **日志 (Logs)**：详细事件序列，支持文本搜索
- **追踪 (Traces)**：单请求完整执行路径，OpenTelemetry 标准
- **指标 (Metrics)**：系统级性能指标（吞吐量、延迟、错误率）

## 6. 五大设计原则

### 6.1 约束优先原则 (Constraint-First)

**核心**：首先考虑的不是"智能体能做什么"，而是"不能做什么"和"做事时的限制是什么"。

1. 首先定义约束（Permission Model）
2. 然后在约束内赋能
3. 最后验证合规

**四个约束维度**：
- **权限维度**：能访问什么资源（工具级/资源级/用户级）
- **操作维度**：什么操作被禁止（绝对禁止/受限/隐藏）
- **时间维度**：什么时候可以操作（时间窗口/速率限制/过期）
- **数据维度**：什么数据可以处理（大小限制/敏感性/流向）

**实现模式**（安全性递减，灵活性递增）：
- 白名单模式 -> 黑名单模式 -> 规则引擎模式

好的约束不会限制能力，反而使智能体更有效：减少歧义、加快执行（搜索空间变小）、提高成功率。

### 6.2 可验证性原则 (Verifiability)

**核心**：系统的每一个行为都应该是可观察的、可审计的、可重放的。对抗"暗码"（Dark Code，运行时动态生成、执行后即消散的行为）的核心武器。

三个层次：
1. **操作日志**：记录发生了什么（OperationLog：timestamp, agent_id, operation_type, input, output, status）
2. **执行追踪**：记录因果关系（ExecutionTrace：trace_id, steps 含 parent_step_id 的树形结构）
3. **可重放性**：给定相同输入能重现（ReplayableExecution：simulation 模式与实际重放模式）

最佳实践：结构化 JSON 日志、trace ID 关联全链路、定期重放验证一致性、用户可读摘要。

### 6.3 渐进信任原则 (Progressive Trust)

**核心**：不期望一下子就完全信任智能体，逐步提升信任等级，持续观察行为。

六个信任等级：
| Level | 名称 | 实现 |
|-------|------|------|
| 0 | Manual Only | 每步人工批准 |
| 1 | Approve Always | 每个操作事前批准 |
| 2 | Approve Once | 任务开始时批准一次 |
| 3 | Ask First | 关键操作事前询问 |
| 4 | Auto + Notification | 自动执行并通知 |
| 5 | Full Trust | 完全自主 |

**提升标准**：基于明确的量化证据（min_operations, min_success_rate, min_duration_days, no_critical_errors）

**降级机制**：一次严重错误、短时间内多次错误、安全事件、用户投诉均可触发降级。

### 6.4 故障假设原则 (Design-for-Failure)

**核心**：主动假设每一步都可能失败，提前设计处理方案。

四种故障类型与处理策略：
- **临时故障** -> 重试策略（指数退避 + 随机抖动，max_retries=3）
- **永久故障** -> 降级/回退（优先级列表的备选方案链）
- **部分故障** -> 隔离模式（Bulkhead，Semaphore 分舱）
- **级联故障** -> 断路器（Closed/Open/Half-Open 三态，failure_threshold=5）

**检查点与事务**：每个步骤前后保存检查点，支持从中间恢复（CheckpointedExecution）

**完整故障恢复流程**：故障发生 -> 检测（监控告警）-> 隔离（断路器）-> 恢复（重试/降级/检查点）-> 学习改进 -> 系统加强

### 6.5 智能体工学原则 (Agent Ergonomics)

**核心**：为 Agent（而非人类）设计更好用的软件系统。由 TiDB CTO 黄东旭在 QCon 2026 系统提出。

三大原则：

1. **最小化使用摩擦**：统一数据存储、一致接口、快速反馈回路、减少概念切换
2. **最大化信息密度**：Markdown 优于 HTML、避免重复、精简格式、删除装饰（相同信息量，Markdown 仅需 HTML 约 20% 字符数）
3. **信任模型能力**：用基于风险的约束替代基于人类习惯的约束（"99% 的人类流程在 Agent 面前是愚蠢的约束"）

关键区别：
| 约束类型 | 目的 | 效果 |
|---------|------|------|
| 人类工作流约束 | 补偿人的不可靠性 | 降低 Agent 效率 |
| 风险基约束 | 防止实际的坏结果 | 保持 Agent 效率 + 安全 |

## 7. 托管 Agent 虚拟化：Brain/Hands 解耦架构

传统 Harness 将"大脑"（推理引擎）和"手"（执行环境）紧密耦合。在长期运行生产环境中面临：假设快速老化（模型升级使 Harness 中的行为假设过时）和容错性不足。

三层虚拟化架构：
- **Session 层**：追加式事件日志，与 Harness 实现无关
- **Harness 层**：无状态循环引擎，从 Session 恢复上下文
- **Sandbox 层**：可替换的执行环境，容器故障不影响 Session

| 问题 | 单体设计 | 虚拟化设计 |
|------|---------|----------|
| 容器故障 | Agent 中断 | 在不同容器继续执行 |
| 模型升级 | 旧假设变死代码 | Harness 灵活适配 |
| 上下文溢出 | 复杂压缩策略 | Session 外部管理 |

## 8. 实战建议

1. **不要过度优化模型**：准确率达 85% 以上后，重点转向系统工程
2. **优先投入高效益 Harness 组件**：工具层 -> 结果验证 -> 重试策略 -> 可观测性
3. **把模型的"最后一英里"交给 Harness**：中等能力模型 + 完善 Harness > 最强模型 + 简单系统
4. **提前规划故障处理**：设计之初就考虑"如果这一步失败了怎么办"
5. **投入强大 Harness 设计往往比投入更强模型更有 ROI**
