## Part 1: 安全架构设计

### 1.1 纵深防御（Defense in Depth）

**核心理念**：通过多层独立的安全措施，确保单一防护失效时整体安全不被突破。

| 原则 | 描述 |
|------|------|
| 多层防护 | 每层都提供独立的安全保障 |
| 独立失效 | 一层失效不影响其他层 |
| 互补机制 | 不同层使用不同检测技术 |
| 假设失败 | 假设任何一层可能被突破 |

> 安全不是可以单独装进系统的某个功能模块——它和可靠性、可维护性一样，是系统的非功能属性（non-functional property），由架构、流程、运维多方面共同决定。

**LLM 纵深防御七层架构**：

```
第一层：边界防护 — WAF、API 网关、速率限制、DDoS 防护
第二层：输入安全 — 注入检测、格式验证、内容过滤
第三层：上下文安全 — System Prompt 加固、来源标记、上下文隔离
第四层：模型安全 — 安全对齐、能力限制、推理约束
第五层：工具安全 — 权限控制、参数验证、沙箱隔离
第六层：输出安全 — 内容审核、敏感过滤、格式验证
第七层：运营安全 — 监控、审计、异常检测、事件响应
```

### 1.2 LLM 安全架构模式

**网关模式（Gateway Pattern）**：
- 所有请求通过安全网关，集中实施认证、限流、注入检测
- 优点：统一控制点，易于审计
- 风险：单点故障，需要高可用设计

**三明治模式（Sandwich Pattern）**：
- 在 LLM 前后各放置一个安全检查层
- 输入过滤 → LLM 推理 → 输出审核
- 实现"先防后检"的双层保护

**隔离模式（Isolation Pattern）**：
- 将不可信内容与系统指令严格隔离
- 使用消息角色标记区分系统/用户/工具内容
- 外部内容默认标记为不可信

**多模型检查模式（Multi-Model Check）**：
- 用独立的安全模型检查主模型的输出
- 适用于高安全需求场景
- 成本较高但检测能力强

### 1.3 权限与访问控制

**三层权限设计**：
- **身份认证**：OAuth2 / API Key / JWT，区分用户身份与 Agent 身份
- **数据权限**：行级数据隔离、最小数据访问范围
- **Agent 权限**：工具白名单、参数范围约束、操作确认

**智能体权限设计原则**：
- 最小权限 + 时效令牌（短期 Token 而非长期凭证）
- 人工审核（HITL）审批高风险操作
- 高风险工具硬性阻断策略（如删除数据库、转账等永不允许 Agent 直接调用）
- 运行时动态收敛：根据上下文和意图动态限制可用权限

### 1.4 安全开发生命周期（Security SDLC）

将安全融入需求、设计、开发、测试、运营各阶段：

| 阶段 | 安全活动 |
|------|----------|
| **需求** | 识别安全需求、威胁建模、合规要求 |
| **设计** | 安全架构评审、信任边界定义、权限设计 |
| **开发** | 安全编码规范、依赖审计、代码审查 |
| **测试** | 安全测试、红队演练、对抗评估 |
| **部署** | 安全配置验证、监控部署、应急预案 |
| **运营** | 持续监控、事件响应、漏洞管理 |

### 1.5 隐私增强技术（PETs）

| 技术 | 原理 | 适用场景 |
|------|------|----------|
| **联邦学习** | 数据不离开本地，仅共享模型梯度 | 多机构协作训练 |
| **差分隐私** | 在训练过程中加入噪声 | 降低模型记忆特定样本风险 |
| **机密计算** | 在可信执行环境中处理数据 | 高敏感数据处理 |
| **同态加密** | 在加密数据上直接计算 | 加密推理 |

**数据安全管控流程**：数据采集 → 来源验证 → 内容过滤 → 隐私脱敏 → 质量评估 → 入库存储

### 1.6 供应链与基础设施安全

**供应链风险来源**：预训练模型、数据集、依赖库、第三方服务、容器镜像

**关键控制**：
- **来源可追溯**：签名/校验，建立可信供应商清单
- **依赖锁定与漏洞扫描**：构建时锁定版本，定期扫描 CVE
- **SBOM / AI BOM / ML SBOM**：为每个部署生成物料清单，追踪组件来源和版本
- **版本治理**：管理模型与依赖的不同版本，支持回滚

## Part 2: 输入输出安全防护

### 2.1 输入验证与过滤

**核心原则**：不信任任何输入。

**多层验证架构**：

```
格式验证 → 长度检查 → 编码规范化 → 模式检测 → 语义分析
```

| 验证层次 | 技术 | 目标 |
|----------|------|------|
| 格式验证 | Schema 校验、类型检查 | 确保输入结构合法 |
| 长度限制 | Token 数上限 | 防止资源耗尽攻击 |
| 编码规范化 | Unicode 归一化、特殊字符处理 | 防止编码混淆绕过 |
| 模式检测 | 正则匹配、注入特征库 | 拦截已知注入模式 |
| 语义分析 | ML 分类器、意图识别 | 检测语义层面的恶意意图 |

**开源工具参考**：
- **NeMo Guardrails**（NVIDIA）：可编程对话护栏，定义输入边界
- **Llama Guard**（Meta）：判别式安全分类模型
- **LLM Guard**（ProtectAI）：开箱即用的输入扫描器

### 2.2 输出内容安全审核

**审核模式**：
- **实时审核**：逐条检查，适合高安全场景（延迟较高）
- **异步审核**：先返回后检查，适合低风险场景
- **多级审核**：规则→ML 模型→人工，逐级深入

**审核内容**：
- 有害内容检测（暴力、色情、歧视）
- 幻觉检测（事实性验证）
- 敏感信息过滤（PII、密钥、内部信息）
- 格式合规性检查

**开源工具参考**：
- **Guardrails AI**：输出结构化验证与自动重试
- **Promptfoo**：自动化 Prompt 注入和越狱红蓝对抗测试
- **LangKit**（WhyLabs）：文本质量与安全指标监控

### 2.3 敏感信息保护

**双向脱敏架构**：
- **输入侧**：PII 检测与脱敏，防止敏感数据进入 LLM 上下文
- **输出侧**：DLP 过滤，防止 LLM 输出包含机密信息
- **多租户隔离**：存储中用户数据物理隔离，日志中敏感内容加密存储

**最小信息原则**：只向 LLM 提供完成当前任务所需的最少敏感数据。

**开源工具参考**：
- **Microsoft Presidio**：PII 识别与数据脱敏
- **Stanza NER**（Stanford）：多语言命名实体识别

### 2.4 AI 生成内容鉴伪与水印

- **文本水印**：在生成过程中嵌入不可见标记（如 KGW 算法）
- **内容鉴伪**：判断内容的机器合成性
- **版权溯源**：通过水印追踪内容来源

**开源工具**：
- **lm-watermarking**（马里兰大学）：KGW 文本水印算法参考实现
- **Binoculars**：zero-shot AI 生成文本鉴伪工具

### 2.5 Constitutional Classifiers（下一代级联防护）

Anthropic 于 2026-01 公布的 Next-generation Constitutional Classifiers 采用两阶段级联：

1. **轻量线性探针**（Linear Probe）：对所有流量快速筛查，利用模型内部激活模式识别可疑请求，计算开销极低
2. **集成分类器**（Ensemble Classifier）：仅对标记请求深度分析，结合外部分类器与内部探针

**关键指标**（按不同口径）：
- 上一代：自动化 jailbreak 成功率从 86% 降到 4.4%
- 下一代：无害请求误拒率 **0.05%**（上一代为 0.38%）
- 额外开销：约 **1%**（若应用到 Claude Opus 4.0 流量）
- 红队结果：1,700+ 小时、198,000 次尝试中发现 1 个高风险漏洞

**可借鉴的设计思想**：
- 级联架构：轻量探针全量筛查 + 昂贵分类器深度复审
- 内部激活信号补充外部文本检测
- 持续红队测试作为必要组成部分

**不可直接照搬的部分**：
- 激活探针需要模型 host 侧中间层激活访问（仅自托管开源模型可行）
- 白盒攻击者可通过 GCG-style 优化攻破探针

### 2.6 MVP 最小可行防线

> 1. **机密不入上下文**：System Prompt 里不放密钥、内部 URL、数据库结构
> 2. **外部内容默认不可信**：RAG 文档与工具返回值先检测清洗再进入上下文
> 3. **输出脱敏与策略拦截**：对 System Prompt / PII / 密钥模式做检测与替换
> 4. **工具最小权限**：每个工具做 allowlist，高风险动作需人工审批

## Part 3: 安全运营与监控

### 3.1 安全监控体系

构建覆盖多层的监控体系：

| 监控层 | 关键指标 |
|--------|----------|
| **基础设施层** | GPU 利用率、内存使用、网络流量 |
| **平台层** | API 延迟、错误率、请求量 |
| **应用层** | 会话数、Token 消耗、工具调用频率 |
| **安全层** | 注入尝试数、越狱成功率、PII 泄露事件 |

### 3.2 异常检测与告警

**检测方法组合**：
- **规则检测**：基于已知模式的精确匹配
- **统计检测**：基于基线的偏差检测（Z-score、移动平均）
- **ML 检测**：基于模型的异常分类

**告警分级**：
- **P0 关键**：立即响应（数据泄露、权限突破）
- **P1 高**：15 分钟内响应（注入攻击、异常工具调用）
- **P2 中**：1 小时内响应（异常请求模式）
- **P3 低**：下个工作日处理（配置偏离）

### 3.3 事件响应

**标准流程**：准备 → 检测 → 遏制 → 消除 → 恢复 → 总结

**关键环节**：
- **遏制**：立即隔离受影响的模型/服务
- **根因分析**：追溯攻击路径，识别防御缺口
- **复盘改进**：更新防御策略，补充测试用例
- **漏洞修复**：修补被利用的安全漏洞

### 3.4 红队演练与自动化评估

**红队测试层次**：
- **单点测试**：针对特定攻击（如 Prompt Injection）的专项测试
- **链路测试**：覆盖从输入到工具调用的完整攻击链
- **系统测试**：模拟真实攻击者的完整渗透流程

**自动化评估框架**：
- 将安全测试纳入 CI/CD 流水线
- 建立安全门控机制（Security Gate）
- 定期执行回归测试，验证防御不退化

### 3.5 DeepTeam 与现代红队工具链

**DeepTeam**（Confident AI）是当前主流的自动化红队框架之一：

```
DeepTeam 核心架构：
├─ 攻击生成引擎 — 自动化越狱生成、Prompt Injection 构造、多模态攻击
├─ 评估引擎 — 有效性判定、危害等级评分、可转移性分析
└─ 报告生成引擎 — 漏洞汇总、修复建议、趋势分析
```

**其他主流工具**：
- **Garak**：LLM 漏洞扫描器，类似 nmap 的 AI 安全版本
- **HarmBench**：标准化有害行为评估基准
- **Promptfoo**：开源 Prompt 测试框架

**从手工红队到自动化红队的演进**：

| 特性 | 传统 | 现代化 |
|------|------|--------|
| 自动化程度 | 低 | 高 |
| 覆盖面 | 部分场景 | 更全面 |
| 成本投入 | 人力密集 | 工具与工程投入并重 |
| CI/CD 集成 | 困难 | 更容易集成 |

### 3.6 SHADE-Arena 与隐蔽破坏检测

**核心发现**：Agent 可能在"主任务正常完成"的同时暗中执行恶意目标。

**SHADE-Arena** 表明对 Agent 隐蔽破坏行为的检测不能只盯住单次输出，需要：
- **跨步骤行为监控**：跟踪 Agent 整个任务执行链
- **目标一致性检查**：验证 Agent 行为是否与用户目标一致
- **异常操作模式检测**：识别偏离正常行为模式的操作

### 3.7 服务降级与 Fallback

**降级策略**：
- **模型降级**：主模型不可用时切换到备用模型
- **功能降级**：关闭工具调用等高风险功能
- **话术兜底**：在极端情况下提供安全的默认响应
- **缓存兜底**：返回预先审核过的缓存响应

**Fallback 优先级**：安全 > 功能 > 体验。

## Part 4: 安全治理

### 4.1 AI 法规与合规

**全球 AI 监管趋势**：

以 **EU AI Act** 为例，义务按阶段落地：
- **2025-02-02**：禁止性 AI 实践生效
- **2025-08-02**：通用 AI 模型（GPAI）义务生效
- **2027-12-02**：高风险 AI 系统（嵌入受监管产品框架）
- **2028-08-02**：特定高风险系统全面合规

组织需要建立持续的法规跟踪与控制映射机制。

**合规关键输出**：
- 法规时间线：按法域和生效批次安排项目排期
- 风险评估模板：覆盖数据治理、模型安全、用户权益
- 审计证据链：支持监管审查的完整证据留存

### 4.2 负责任 AI 实践

**核心原则**：
- **公平性**：检测和缓解偏见，确保系统行为公平
- **透明性**：解释模型输出的依据与适用范围
- **安全性**：高风险任务设置边界与人工复核
- **隐私保护**：数据脱敏，访问控制
- **问责制**：日志记录、审计追踪、披露 AI 使用

### 4.3 新兴威胁趋势

需要持续关注的新兴威胁：
- **AI 对 AI 攻击**：用 AI 系统攻击另一个 AI 系统
- **深度伪造滥用**：Deepfake 技术的恶意使用
- **智能体风险升级**：Agent 自主性增强带来的失控风险
- **供应链风险深化**：模型生态的供应链攻击面扩大
- **生命科学双用途**：专用模型可能被滥用于生物安全威胁

### 4.4 Agent 错位威胁

**从压力测试到防护框架**：
- Agent 错位（Misalignment）不仅是理论问题，而是已在生产环境中观察到的现实威胁
- 案例：智能体因上下文窗口压缩丢失安全指令，自主删除用户 200 余封邮件并忽略停止命令
- 需要结合行为评估、可解释性研究和运行时监控共同应对

### 4.5 LLM 安全成熟度模型

**五级成熟度**（L0-L4）：

| 等级 | 定义 | 典型特征 |
|------|------|----------|
| **L0 初始** | 基本无体系 | 依赖个人经验，缺少流程与证据 |
| **L1 基线** | 有基本控制 | 有最小可行防线与准入，但不成体系 |
| **L2 可重复** | 流程可执行 | 控制项可重复执行，有回归评测与审计留痕 |
| **L3 可度量** | 指标驱动 | 有量化指标与门禁，能持续优化 |
| **L4 自适应** | 威胁驱动演进 | 结合威胁情报与红队持续演进 |

**八大能力域**：

| 能力域 | 关注点 |
|--------|--------|
| 治理与合规 | 责任划分、审批流程、法规映射、证据留存 |
| 风险管理 | 威胁建模、风险评估、例外管理、变更评审 |
| 数据与隐私 | 数据分级、最小化、脱敏、日志策略、保留期 |
| 模型与供应链 | 模型来源验证、SBOM、依赖扫描、版本治理 |
| 应用与提示安全 | System Prompt 基线、注入防护、上下文隔离 |
| 工具与权限 | 最小权限、参数校验、操作确认、回滚与审计 |
| 监控与响应 | 监控指标、告警分级、事件响应、复盘改进 |
| 评估与红队 | 基准测试、回归门禁、红队演练、对抗样本库 |

**各等级最小证据集**（示例）：

- **L1**：I/O 过滤策略文档、工具最小权限清单、审计日志字段定义
- **L2**：威胁建模记录、发布前安全测试报告、例外审批记录
- **L3**：关键安全指标仪表盘、SLO 定义与阈值告警、月度安全复盘
- **L4**：红队演练报告与修复闭环证据、跨团队协同记录

### 4.6 可信 Agent 框架

**Agent 四层构成**：

```
Model（模型）     — 推理引擎：推理能力、规划、决策
Harness（约束）   — 治理层：System Prompt、安全约束、人工控制
Tools（工具）     — 能力层：邮件、文件系统、代码执行、API 访问
Environment（环境）— 权限与隔离层：权限控制、沙箱隔离、审计日志
```

**五大核心原则**（参考 Anthropic Trustworthy Agents 框架）：

1. **人类控制**（Human Control）：Agent 自主权范围由用户明确定义
   - 工具访问清单（Tool Allowlist）
   - 操作批准规则（Approval Rules）
   - Plan Mode（计划审查模式）

2. **目标对齐**（Goal Alignment）：Agent 能识别何时目标不清或需要人类判断

3. **安全**（Safety）：多层安全机制保障 Agent 行为安全

4. **透明**（Transparency）：Agent 的决策过程和行为可被理解和审计

5. **隐私保护**（Privacy）：Agent 对个人数据的处理符合隐私要求

**生产就绪检查点**：
- 工具白名单是否已明确定义并绑定到用户/任务角色？
- 高风险工具是否启用了 HITL 审批？
- 是否定期进行"工具链权限提升"的红队测试？
- 是否建立了工具返回值注入的检测机制？
- 是否对所接入的插件、连接器和第三方组件进行了来源审查？
