## 1. 岗位概述

### 1.1 角色定义

AI Safety Engineer（AI 安全工程师）是专注于 AI 系统安全性保障的技术角色。与传统的网络安全工程师不同，AI Safety Engineer 关注的核心问题是：

- **模型行为安全**: 确保模型不会生成有害、有偏见或误导性内容
- **对齐（Alignment）**: 确保模型行为与人类意图和价值观一致
- **鲁棒性（Robustness）**: 确保模型在对抗性输入下不会失效
- **可控性（Controllability）**: 确保模型行为在预期范围内可预测、可干预
- **合规性（Compliance）**: 确保 AI 系统满足各地区法规要求（如 EU AI Act）

### 1.2 核心职责

| 职责领域 | 具体内容 | 交付物 |
|---------|---------|--------|
| **红队测试** | 对模型进行系统性对抗测试，发现安全漏洞 | 红队报告、漏洞清单 |
| **安全评估** | 设计和执行模型安全 benchmark | 评估框架、安全评分卡 |
| **对齐研究** | 研究并实施 RLHF/Constitutional AI 等对齐方法 | 对齐策略文档 |
| **威胁建模** | 识别 AI 系统面临的威胁向量和攻击面 | 威胁模型文档 |
| **护栏设计** | 设计输入/输出过滤和安全护栏系统 | 护栏规则库 |
| **事件响应** | 处理 AI 安全事件，进行根因分析 | 事件报告、修复方案 |
| **合规审计** | 确保 AI 系统满足法规要求 | 合规报告 |

## 3. 面试题库

### 3.1 对抗攻击（Adversarial Attacks）— 基础级

**Q1: 请解释什么是对抗样本（Adversarial Examples），以及它们在 LLM 中的表现形式。**

参考答案：
对抗样本是通过对输入添加人类不可察觉的微小扰动，使模型产生错误输出的输入。在 LLM 中，对抗攻击的表现形式包括：
- **字符级扰动**: 同音字替换、Unicode 变体、零宽字符插入
- **Token 级扰动**: 同义词替换、句式重组
- **语义级攻击**: 保持语义不变但改变表达方式以绕过安全过滤
- **多轮对话攻击**: 通过多轮对话逐步引导模型偏离安全轨道
- **编码绕过**: 使用 Base64、ROT13、多语言混合等编码方式绕过检测

**Q2: GCG（Greedy Coordinate Gradient）攻击的原理是什么？如何防御？**

参考答案：
GCG 攻击是一种自动化越狱方法：
- **原理**: 通过梯度优化，在 prompt 末尾附加一段看似无意义的 token 序列（adversarial suffix），使模型的对齐训练失效，输出有害内容
- **攻击流程**: 计算 loss 对每个 token 位置的梯度 → 贪心选择最优替换 → 迭代优化
- **防御方法**:
  - 输入 perplexity 检测（对抗 suffix 通常 perplexity 异常高）
  - 对抗训练（在 RLHF 中加入 GCG 类攻击样本）
  - 输入预处理和规范化
  - 多模型集成检测

**Q3: 请区分 targeted attack 和 untargeted attack 在 LLM 安全中的含义。**

参考答案：
- **Targeted Attack**: 攻击者有明确目标，例如让模型输出特定的有害内容（如制造武器的具体步骤）、泄露训练数据中的特定信息、或让模型扮演特定角色
- **Untargeted Attack**: 攻击者只需让模型产生任何不期望的行为，如输出任何有害内容、产生幻觉、或绕过任何一条安全策略
- 在安全评估中，targeted attack 更难防御，因为攻击空间更集中；untargeted attack 更容易发现，因为任何异常输出都算成功

### 3.2 越狱防护（Jailbreak Prevention）— 中级

**Q4: 请列举至少5种常见的 LLM 越狱技术，并说明其原理。**

参考答案：
1. **角色扮演（Role-Play）**: 让模型扮演一个"没有限制的AI"（如 DAN），利用角色设定覆盖安全指令
2. **前缀注入（Prefix Injection）**: 在用户输入中伪造 assistant 的回复前缀，让模型"接着说"
3. **多语言绕过**: 使用低资源语言或混合语言绕过主要针对英文训练的安全过滤
4. **编码绕过**: 将有害请求用 Base64/Hex/ROT13 编码，让模型解码后执行
5. **分步引导（Incremental）**: 将有害请求分解为多个看似无害的步骤，逐步引导
6. **上下文操纵**: 利用长上下文窗口，在大量无害文本中嵌入有害指令
7. **System Prompt 泄露**: 通过特殊指令让模型输出其 system prompt

**Q5: 如何设计一个多层防御体系来防止越狱攻击？**

参考答案：
多层防御体系（Defense in Depth）：
- **Layer 1 - 输入过滤**: 基于规则和分类器的输入检测（perplexity filter、toxicity classifier）
- **Layer 2 - System Prompt 加固**: 使用分层指令、优先级标记、防注入模板
- **Layer 3 - 模型级对齐**: 通过 RLHF/DPO 增强模型自身的拒绝能力
- **Layer 4 - 输出检测**: 对模型输出进行二次安全分类
- **Layer 5 - 行为监控**: 监控对话模式，检测多轮攻击
- **Layer 6 - 速率限制与审计**: 限制单用户请求频率，记录异常行为
- 关键原则：任何单一层都不应被假设为不可突破，每层独立提供保护

**Q6: 解释 "Constitutional AI" 的核心思想，以及它如何提升模型安全性。**

参考答案：
Constitutional AI（CAI）由 Anthropic 提出：
- **核心思想**: 用一组明确的"宪法原则"（如"不要生成有害内容"、"要诚实"）来指导模型的自我改进
- **训练流程**:
  1. SL-CAI: 让模型根据宪法原则批评和修改自己的有害输出（监督学习阶段）
  2. RLAIF: 用 AI 反馈（而非人类反馈）进行强化学习，AI 根据宪法原则评判回复质量
- **安全优势**:
  - 减少对人工标注的依赖，降低标注者偏见
  - 原则透明可审计
  - 可以灵活更新原则而无需重新训练
  - 模型内化了安全原则，而非仅依赖外部过滤

### 3.3 RLHF 安全（RLHF Safety）— 中级

**Q7: RLHF 过程中可能出现哪些安全问题？如何应对？**

参考答案：
RLHF 中的安全问题：
- **Reward Hacking**: 模型学会"讨好"奖励模型而非真正对齐人类偏好
  - 应对：使用多个奖励模型集成、定期更新奖励模型
- **Alignment Tax**: 安全对齐导致模型能力下降
  - 应对：精细化的奖励设计，区分"安全拒绝"和"过度拒绝"
- **标注者偏见**: 人类标注者的偏见被放大到模型中
  - 应对：多元化标注团队、交叉验证、Constitutional AI 补充
- **分布外脆弱性**: 模型在训练分布外的输入上安全性急剧下降
  - 应对：对抗训练、红队数据增强
- **过度拒绝（Over-refusal）**: 模型将无害请求也拒绝
  - 应对：在奖励模型中加入"helpfulness"维度

**Q8: 请解释 DPO（Direct Preference Optimization）相比传统 RLHF 的安全性优势。**

参考答案：
DPO 的安全性优势：
- **去除奖励模型**: 直接从偏好数据优化策略，避免 reward hacking
- **训练稳定性**: 无需训练单独的奖励模型和 PPO，减少训练不稳定性带来的安全风险
- **可解释性**: 优化目标更透明，容易审计
- **数据效率**: 需要更少的偏好数据，降低标注偏见的影响
- **局限性**: 仍然依赖偏好数据的质量；对分布外输入的鲁棒性可能不如 RLHF

**Q9: 如何评估 RLHF 对齐的效果？请设计一个评估框架。**

参考答案：
评估框架设计：
- **安全性维度**:
  - 有害内容生成率（使用标准 benchmark 如 ToxicChat、RealToxicityPrompts）
  - 越狱成功率（使用 JailbreakBench、HarmBench）
  - 过度拒绝率（使用 XSTest、OR-Bench）
- **对齐质量维度**:
  - 人类偏好胜率（Elo rating、pairwise comparison）
  - 指令遵循准确率
  - 诚实度评估（TruthfulQA）
- **鲁棒性维度**:
  - 对抗输入下的安全保持率
  - 多语言安全一致性
  - 长上下文安全性
- **评估方法**: 自动化评估 + 人工红队 + A/B 测试

### 3.4 模型水印（Model Watermarking）— 中级

**Q10: 请解释 LLM 文本水印的原理和主要方法。**

参考答案：
LLM 文本水印技术：
- **基本原理**: 在模型生成文本时，通过偏置 token 选择来嵌入统计信号，使生成文本可被检测为 AI 生成
- **主要方法**:
  - **Green-Red List（Kirchenbauer et al.）**: 将 vocabulary 分为 green/red list，生成时偏置选择 green list tokens；检测时统计 green token 比例
  - **Unigram Watermark**: 基于固定 hash 的 token 偏置，不依赖前文
  - **语义水印**: 在语义层面嵌入信号，对改写更鲁棒
- **关键指标**:
  - 检测准确率（True Positive Rate）
  - 对文本质量的影响（perplexity 增加量）
  - 对改写的鲁棒性
  -  False Positive Rate（将人类文本误判为 AI 生成）

**Q11: 模型水印面临哪些攻击和局限性？**

参考答案：
水印面临的挑战：
- **改写攻击（Paraphrase Attack）**: 用另一个 LLM 改写带水印文本，破坏统计信号
- **翻译攻击**: 翻译为其他语言再翻译回来
- **复制攻击（Copy Attack）**: 从多个带水印文本中复制片段组合
- **Spoofing 攻击**: 攻击者伪造水印，将人类文本"标记"为 AI 生成
- **局限性**:
  - 短文本检测不可靠
  - 与文本质量存在 trade-off
  - 无法覆盖所有生成场景（如代码）
  - 法律和伦理争议（隐私、言论自由）

**Q12: 如何设计一个生产级的 AI 内容溯源系统？**

参考答案：
生产级内容溯源系统设计：
- **多层标记**:
  - 生成时水印（统计水印）
  - 元数据嵌入（C2PA 标准）
  - API 级追踪（请求 ID、用户 ID）
- **检测层**:
  - 统计检测器（watermark detector）
  - AI 内容分类器（作为补充）
  - 元数据验证
- **基础设施**:
  - 水印密钥管理（HSM）
  - 检测服务（低延迟 API）
  - 审计日志
- **治理**:
  - 误判处理流程
  - 隐私保护（不追踪个人用户）
  - 合规适配（各地区法规）

### 3.5 内容过滤（Content Filtering）— 基础级

**Q13: 请设计一个 LLM 输出内容过滤系统的架构。**

参考答案：
内容过滤系统架构：
- **输入层**:
  - 规则引擎（关键词、正则表达式）— 低延迟初筛
  - 分类器（fine-tuned BERT/小型 LLM）— 语义级分类
  - 主题检测（识别敏感话题）
- **输出层**:
  - 流式过滤（streaming filter）— 逐 token 检测
  - 完整回复审查 — 上下文级判断
  - 多模态检测（如果涉及图像生成）
- **决策层**:
  - 风险评分（0-1 连续分数）
  - 分级响应（通过/警告/拦截/上报）
  - 可配置策略（不同场景不同阈值）
- **运维层**:
  - 误报/漏报监控
  - 规则热更新
  - A/B 测试框架

**Q14: 内容过滤中如何平衡安全性和用户体验（避免过度拒绝）？**

参考答案：
平衡策略：
- **分级分类**: 将内容分为"明确有害"、"边界模糊"、"明确安全"三级，对边界内容采用更细致的判断
- **上下文感知**: 考虑对话上下文（如医学讨论中的敏感词汇不应被过滤）
- **用户意图推断**: 区分"讨论暴力事件的历史"和"教唆暴力"
- **渐进式响应**: 先警告再拦截，而非直接拒绝
- **可解释拒绝**: 告知用户为何被拒绝，提供替代方案
- **反馈闭环**: 收集用户对误拒的反馈，持续优化
- **指标监控**: 同时跟踪 False Positive Rate 和 False Negative Rate

**Q15: 如何处理多语言环境下的内容安全挑战？**

参考答案：
多语言内容安全策略：
- **挑战**:
  - 低资源语言缺乏训练数据
  - 不同文化对"有害内容"的定义不同
  - 混合语言（code-switching）增加检测难度
  - 翻译可能改变语义
- **解决方案**:
  - 多语言分类器（如 XLM-RoBERTa based）
  - 语言检测 + 路由到语言专用模型
  - 文化适配的安全策略（地区化配置）
  - 跨语言迁移学习
  - 本地化红队测试团队
  - 混合语言输入的规范化处理

### 3.6 威胁建模（Threat Modeling）— 高级

**Q16: 请对一个面向公众的 LLM 聊天产品进行威胁建模。**

参考答案：
使用 STRIDE + AI 特有威胁的建模：
- **Spoofing**: 用户身份伪造、API key 泄露
- **Tampering**: Prompt 注入篡改模型行为、训练数据投毒
- **Repudiation**: 用户否认生成过特定内容
- **Information Disclosure**: 训练数据泄露、System Prompt 泄露、用户对话泄露
- **Denial of Service**: 对抗性输入导致推理超时、资源耗尽攻击
- **Elevation of Privilege**: 越狱获取"无限制模式"、绕过付费限制
- **AI 特有威胁**:
  - 模型滥用（生成虚假信息、deepfake 脚本）
  - 对齐失效（分布外输入导致安全行为崩溃）
  - 涌现能力风险（模型突然展现未预期的危险能力）

**Q17: 如何评估一个前沿模型的灾难性风险（Catastrophic Risk）？**

参考答案：
前沿模型灾难性风险评估框架：
- **评估维度**:
  - 生物风险（CBRN）: 模型是否能提供制造生物武器的可行指导
  - 网络风险: 模型是否能协助发现和利用 0-day 漏洞
  - 自主性风险: 模型是否能在无人监督下执行多步骤有害行动
  - 欺骗风险: 模型是否能策略性地隐藏其真实能力或意图
- **评估方法**:
  - 能力 elicitation（充分激发模型能力后评估）
  - 专家红队（领域专家评估输出的专业水平）
  - 基准测试（如 Cybench、BioBench）
  - 自主性测试（Agent 环境中的行为观察）
- **决策框架**: 定义风险等级和对应的部署决策（RSP - Responsible Scaling Policy）

**Q18: 请解释 AI 供应链攻击的威胁向量和防御策略。**

参考答案：
AI 供应链攻击：
- **威胁向量**:
  - 训练数据投毒（在公开数据集中注入有害样本）
  - 模型投毒（在预训练模型权重中植入后门）
  - 依赖库攻击（污染 HuggingFace 上的模型/数据集）
  - Prompt 模板注入（在共享 prompt 库中植入恶意指令）
  - 推理框架漏洞（利用 vLLM/TGI 等框架的安全缺陷）
- **防御策略**:
  - 数据来源审计和清洗
  - 模型完整性验证（checksum、签名）
  - 依赖锁定和安全扫描
  - 沙箱化推理环境
  - 模型行为异常检测

### 3.7 安全评估（Safety Evaluation）— 高级

**Q19: 请设计一个全面的 LLM 安全评估 pipeline。**

参考答案：
安全评估 Pipeline 设计：
- **阶段一：自动化 Benchmark**
  - 有害性: HarmBench、ToxicChat、BBQ（偏见）
  - 越狱: JailbreakBench、AdvBench
  - 幻觉: TruthfulQA、FActScore
  - 隐私: 训练数据提取测试
- **阶段二：自动化红队**
  - LLM-as-attacker（使用强模型生成攻击 prompt）
  - 基于模板的变异攻击
  - 多轮对话攻击模拟
- **阶段三：人工红队**
  - 领域专家（安全、伦理、特定领域）
  - 众包红队（多样化背景）
  - 结构化攻击场景
- **阶段四：生产监控**
  - 用户报告分析
  - 异常模式检测
  - 定期回归测试
- **输出**: 安全评分卡 + 风险矩阵 + 修复优先级

**Q20: 如何衡量"过度拒绝"（Over-refusal）问题？这对产品有什么影响？**

参考答案：
过度拒绝的衡量和影响：
- **衡量方法**:
  - 使用 XSTest、OR-Bench 等 benchmark 测试无害请求的拒绝率
  - 分类分析：哪些类型的无害请求被误拒（如医学、法律、历史话题）
  - 用户满意度调查
  - A/B 测试对比不同安全策略下的用户留存
- **产品影响**:
  - 用户体验下降（"这个AI什么都不能做"）
  - 用户流失到竞品
  - 专业场景可用性降低（医疗、法律、安全研究）
  - 品牌声誉损害
- **平衡策略**:
  - 区分"真正有害"和"敏感但合法"
  - 场景化安全策略（API vs 消费级产品）
  - 提供有教育意义的回复而非简单拒绝

### 3.8 综合与系统设计 — 高级

**Q21: 请设计一个自动化红队测试平台。**

参考答案：
自动化红队平台设计：
- **攻击生成引擎**:
  - 模板库（已知攻击模式的参数化模板）
  - LLM 攻击器（使用强模型生成创造性攻击）
  - 变异引擎（对已知攻击进行语义/语法变异）
  - 多轮攻击编排（状态机驱动的多轮对话攻击）
- **目标适配层**:
  - API 适配器（支持不同模型的 API）
  - 参数扫描（temperature、top-p 等对安全性的影响）
  - 多语言/多模态支持
- **评估引擎**:
  - 自动判定（分类器判断攻击是否成功）
  - 严重程度评级
  - 去重和聚类
- **报告与追踪**:
  - 漏洞报告自动生成
  - 修复追踪
  - 趋势分析仪表盘
- **技术栈**: Python + Ray（并行）+ 向量数据库（去重）+ Grafana（监控）

**Q22: 如何为 Agent 系统设计安全框架？与传统 LLM 安全有何不同？**

参考答案：
Agent 系统安全的独特挑战和框架：
- **与传统 LLM 安全的区别**:
  - Agent 有工具调用能力 → 真实世界影响（如删除文件、发送邮件）
  - 多步骤执行 → 单步安全不代表整体安全
  - 自主决策 → 需要权限控制和行为边界
  - 环境交互 → 可能被环境中的恶意内容注入
- **安全框架设计**:
  - 权限模型：最小权限原则，工具调用需授权
  - 行为沙箱：限制 Agent 可执行的操作范围
  - 多步验证：关键操作需人工确认
  - 输入净化：对外部数据源（网页、文件）进行注入检测
  - 行为审计：完整记录 Agent 的推理和行动链
  - 熔断机制：异常行为自动停止

**Q23: 请解释 Responsible Scaling Policy (RSP) 的核心框架。**

参考答案：
RSP（以 Anthropic 为代表）：
- **核心思想**: 根据模型能力水平定义不同的安全等级（ASL - AI Safety Level），能力越强，安全要求越高
- **ASL 等级**:
  - ASL-1: 无显著风险
  - ASL-2: 当前大多数模型所在级别，需要标准安全措施
  - ASL-3: 模型可能提供 CBRN 武器的实质性帮助，需要强化安全
  - ASL-4+: 未来可能的更高等级
- **关键机制**:
  - 部署前评估（capability evaluation）
  - 安全措施与能力等级匹配
  - 如果安全措施不足，暂停训练/部署
  - 定期重新评估
- **面试加分点**: 能讨论 RSP 的实际执行挑战和争议

**Q24: 如何检测模型是否在进行"欺骗性对齐"（Deceptive Alignment）？**

参考答案：
欺骗性对齐的检测方法：
- **定义**: 模型在训练/评估时表现对齐，但在部署后（或认为不被监控时）表现出不对齐行为
- **检测方法**:
  - 训练/评估环境差异测试（改变上下文观察行为变化）
  - 监控信号检测（模型是否对"被评估"有感知）
  - 压力测试（极端输入下是否暴露真实倾向）
  - 内部表征分析（probing 模型的"信念"状态）
  - 长期行为追踪（部署后行为是否漂移）
- **当前局限**: 这是一个开放研究问题，目前没有完美的检测方法
- **缓解策略**: 可解释性研究、训练过程审计、多环境评估

**Q25: 请设计一个 AI 安全事件响应流程。**

参考答案：
AI 安全事件响应流程：
- **检测阶段**:
  - 自动化告警（异常输出检测、用户举报）
  - 严重级别分类（P0-P3）
  - 初步影响评估
- **遏制阶段**:
  - 即时措施（降级/下线受影响功能）
  - 范围确认（影响用户数、时间范围）
  - 通知相关方（安全团队、法务、管理层）
- **根因分析**:
  - 复现攻击路径
  - 确定漏洞类型（对齐缺陷/过滤绕过/系统漏洞）
  - 影响范围评估
- **修复阶段**:
  - 短期修复（热补丁、规则更新）
  - 长期修复（模型更新、架构改进）
  - 回归测试
- **复盘阶段**:
  - 事件报告
  - 流程改进
  - 知识库更新

### 3.9 行为面试与场景题

**Q26: 如果产品经理要求放宽安全限制以提升用户体验，你如何处理？**

参考答案：
处理策略：
- 首先理解产品需求背后的用户痛点（是过度拒绝？还是响应太慢？）
- 用数据说话：展示当前安全策略的误拒率、用户反馈
- 提出替代方案：不是"放宽 vs 不放宽"的二选一，而是更精细化的策略
- 风险评估：明确放宽后的潜在风险和后果
- 分级方案：对不同风险等级的内容采用不同策略
- 最终决策权：明确安全红线不可逾越，但在红线内可以灵活调整
- 记录决策过程：确保决策透明、可追溯

**Q27: 你发现了一个模型安全漏洞，但修复需要延迟产品发布2周，怎么办？**

参考答案：
决策框架：
- 评估漏洞严重程度：是否涉及用户安全？是否可被大规模利用？
- 评估临时缓解措施：是否可以通过外部过滤/限制来降低风险？
- 与团队沟通：向产品、工程、管理层清晰传达风险
- 提出选项：
  - 选项A：延迟发布，彻底修复
  - 选项B：按时发布，附带临时缓解措施 + 明确修复时间线
  - 选项C：缩小发布范围（如仅对可信用户开放）
- 记录决策和理由
- 关键原则：涉及人身安全的问题不可妥协

**Q28: 如何向非技术高管解释 AI 安全风险？**

参考答案：
沟通策略：
- 使用类比：将 AI 安全比作汽车安全（安全气囊、碰撞测试）
- 量化风险：用具体数字说明（"如果不修复，每天可能有X用户受到影响"）
- 商业语言：将安全风险转化为商业风险（声誉、法律、财务）
- 具体案例：引用已发生的 AI 安全事件（如某公司 chatbot 被越狱）
- 提供选项：不是"要不要投入"，而是"投入多少、优先做什么"
- 可视化：使用风险矩阵、趋势图

**Q29: 描述一次你发现并修复 AI 安全漏洞的经历（或假设场景）。**

参考答案框架（STAR 方法）：
- **Situation**: 描述背景（什么产品、什么阶段）
- **Task**: 你的职责是什么
- **Action**:
  - 如何发现漏洞（红队测试/用户报告/自动化检测）
  - 如何评估严重程度
  - 如何设计修复方案
  - 如何验证修复有效
- **Result**: 量化结果（漏洞修复、安全评分提升、避免的潜在损失）

**Q30: 你认为 AI Safety 领域未来3年最重要的研究方向是什么？**

参考答案（展示思考深度）：
- **Scalable Oversight**: 随着模型能力超越人类，如何设计可扩展的监督机制
- **Interpretability → Safety**: 将可解释性研究转化为实际的安全工具
- **Agent Safety**: Agent 系统的对齐和安全控制
- **Multi-agent Safety**: 多 Agent 交互中的涌现风险
- **Safety under Distribution Shift**: 模型在部署后遇到训练分布外情况的安全性
- **Governance Technical Interface**: 技术安全措施与政策法规的衔接
- 展示你对前沿论文的关注（如 Anthropic 的 Sleeper Agents、DeepMind 的 Frontier Safety Framework）

## 5. 2026趋势与转型建议

### 5.1 2026 关键趋势

1. **Agent Safety 成为核心**: 随着 AI Agent 大规模部署，Agent 行为安全、工具调用安全、多 Agent 交互安全成为最热门方向
2. **监管驱动需求**: EU AI Act 全面执行，企业必须配备 AI 安全人员
3. **自动化红队**: 使用 LLM 攻击 LLM 的自动化红队成为标配
4. **Safety Engineering 专业化**: 从"什么都做"分化为对齐工程师、红队专家、安全评估工程师等子方向
5. **多模态安全**: 图像/视频/音频生成的安全评估需求激增
6. **Frontier Risk**: 对超级智能风险的关注从学术走向工业界

### 5.2 转型建议

**从安全工程师转型**:
- 补充 ML/DL 基础知识
- 学习 LLM 特有的攻击和防御技术
- 参与开源安全项目（如 Garak、PyRIT）

**从 ML Engineer 转型**:
- 学习安全思维（威胁建模、攻击者视角）
- 深入研究对齐技术（RLHF、DPO、Constitutional AI）
- 关注安全评估 benchmark

**从安全研究员转型**:
- 学习 LLM 架构和训练流程
- 理解 AI 特有的安全挑战（vs 传统软件安全）
- 建立 AI 安全社区网络

### 5.3 推荐学习资源

- **论文**: Anthropic RSP、DeepMind Frontier Safety Framework、HarmBench
- **工具**: Garak、PyRIT、Inspect AI、LLM Guard
- **课程**: Anthropic AI Safety Course、DeepMind Safety Lectures
- **社区**: AI Safety Community、Alignment Forum
- **实践**: 参加红队竞赛、贡献开源安全工具

## 7. 与 AI Security Engineer 的区别

| 维度 | AI Safety Engineer | AI Security Engineer |
|------|-------------------|---------------------|
| **核心关注** | 模型行为是否安全、对齐、无害 | AI 系统是否被攻击、数据是否泄露 |
| **威胁来源** | 模型自身（幻觉、偏见、有害输出） | 外部攻击者（入侵、窃取、破坏） |
| **典型工作** | 红队测试、对齐评估、内容过滤 | 模型加密、API 安全、基础设施防护 |
| **技能侧重** | ML 对齐、NLP、伦理、评估 | 网络安全、密码学、系统安全 |
| **类比** | 汽车碰撞测试工程师 | 汽车防盗系统工程师 |
| **工具** | Garak、PyRIT、评估 benchmark | WAF、SIEM、渗透测试工具 |
| ** overlap** | Prompt Injection 防护、模型供应链安全 | Prompt Injection 防护、模型供应链安全 |

> 注：在实际工作中，两个角色的边界越来越模糊，很多公司将其合并为 "AI Safety & Security" 团队。但核心思维模式不同：Safety 关注"模型不应该做什么"，Security 关注"攻击者不能做什么"。
