# SRE

> **一句话理解**: SRE 就是「用写代码的方式做运维」，用自动化、SLO、错误预算来让系统更可靠。

## 核心要点

- **SLO/SLI/SLA**: 定义和衡量可靠性
- **错误预算**: 平衡发布速度与稳定性
- **自动化**: 减少人工运维
- **可观测性**: 日志、指标、追踪
- **事故响应**: 流程化故障处理

## SRE 与 DevOps 区别

| SRE | DevOps |
|-----|--------|
| 更强调可靠性工程 | 更强调文化融合 |
| 有明确的 SLO | 更宽泛 |
| 通常有软件工程背景 | 强调开发与运维协作 |

## 阿里云专有云关联

在阿里云专有云环境中，SRE 团队负责 ACK、PAI、AI Stack 等平台的可靠性保障。

## 生产最佳实践

1. **SLO 定义**：为关键服务定义 SLO
2. **错误预算**：用错误预算平衡可靠性与迭代速度
3. **可观测性**：建立完整可观测性体系
4. **自动化**：自动化重复运维任务
5. **事后复盘**：事故后进行无责复盘

## AI 平台 SRE 特殊挑战

| 挑战 | 说明 | 应对策略 |
|------|------|----------|
| GPU 故障 | 硬件故障率高 | 自动故障转移 + 冗余 |
| 模型加载慢 | 冷启动时间长 | 预热 + 模型缓存 |
| 推理延迟波动 | 负载敏感 | 自动扩缩容 + 队列 |
| 训练任务长 | 数小时到数天 | Checkpoint + 断点续训 |
| 资源竞争激烈 | 多租户 GPU 共享 | Kueue 队列 + 配额 |

## 常见问题

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| SLO 无人关注 | 缺乏自动化门控 | CI/CD 集成预算检查 |
| 告警疲劳 | 告警过多无意义 | 优化告警规则 + 分级 |
| 手动运维多 | 自动化不足 | 编写 Runbook + 自动化 |
| 事故复盘流于形式 | 缺乏无责文化 | 建立无责复盘机制 |

## SRE 成熟度模型

| 级别 | 特征 | 典型表现 |
|------|------|----------|
| L1 初始 | 手动运维、救火式 | 没有 SLO，故障后复盘 |
| L2 可重复 | 有基本监控和流程 | 定义 SLO，有告警 |
| L3 已定义 | 标准化流程和工具 | 自动化门控、错误预算 |
| L4 已管理 | 数据驱动决策 | 混沌工程、容量规划 |
| L5 优化 | 持续改进、AIOps | AI 驱动异常检测 |

## On-Call 最佳实践

| 实践 | 说明 | 建议 |
|------|------|------|
| 轮转周期 | 1-2 周一轮 | 避免过长导致疲劳 |
| 告警质量 | 只告警可操作的事件 | 定期清理无意义告警 |
| Runbook | 标准化处理流程 | 每个告警对应 Runbook |
| 升级机制 | 明确升级路径 | 15min 未解决自动升级 |
| 事后复盘 | 无责复盘 | 48h 内完成复盘报告 |

## 事故响应流程

```
发现 → 评估 → 响应 → 恢复 → 复盘
 │       │       │       │       │
监控    严重级   指挥    回滚    无责
告警    分级    协调    修复    报告
```

| 阶段 | 关键动作 | 负责人 |
|------|----------|--------|
| 发现 | 监控告警触发 | 自动化系统 |
| 评估 | 确定严重级别和影响范围 | On-Call SRE |
| 响应 | 启动事故指挥、通知相关方 | 事故指挥官 |
| 恢复 | 回滚/修复/降级 | 工程团队 |
| 复盘 | 无责复盘、改进措施 | SRE + 开发 |

## SRE 核心指标 (KPI)

| 指标 | 计算方式 | 目标 |
|------|----------|------|
| MTTR | 平均恢复时间 | < 30min |
| MTTD | 平均发现时间 | < 5min |
| 变更失败率 | 失败变更/总变更 | < 5% |
| 部署频率 | 每周部署次数 | 按需 |
| SLO 达成率 | 达标服务/总服务 | > 95% |
| 自动化率 | 自动化任务/总任务 | > 80% |

## 生产检查清单

1. **SLO 全覆盖**：所有关键服务都有 SLO 定义
2. **告警可操作**：每个告警都有对应的 Runbook
3. **自动化门控**：错误预算耗尽时自动拦截发布
4. **混沌工程**：定期进行故障注入测试
5. **容量规划**：每季度进行容量预测和规划
6. **无责复盘**：每次事故后 48h 内完成复盘
7. **可观测性**：指标/日志/追踪三支柱完整
