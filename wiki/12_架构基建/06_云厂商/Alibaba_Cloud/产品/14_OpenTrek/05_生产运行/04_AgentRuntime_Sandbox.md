# AgentRuntime 安全沙箱（OpenTrek）

> 中文简称：AgentRuntime 安全沙箱

> **一句话理解**: AgentRuntime 是 OpenTrek 里专门跑智能体的「隔离房间」——Agent 在沙箱里干活，干完房间收走，企业不用自己养一支 K8s 运维团队。

---

## 一、定位：OpenTrek 的 Agent 运行时

AgentRuntime 是 OpenTrek 的 Agent 运行时，为智能体提供**安全沙箱级的隔离执行环境**。它回答生产运行里最底层的问题：Agent 的代码到底跑在哪、跑的时候会不会碰坏别的系统。

一个 Agent 运行时要兜住的事（分析视角的拆解）：

- **进程模型**：Agent 以什么形态存活——常驻服务，还是按任务拉起、干完即走；
- **环境依赖**：运行所需的依赖、工具、凭证如何注入，用后如何回收；
- **资源上限**：CPU、内存、执行时长的边界，防止单个 Agent 失控拖垮宿主；
- **隔离边界**：Agent 之间、Agent 与宿主及内网之间互不越界。

与本目录 01 页的关系：托管调度决定「谁在什么时候跑」，AgentRuntime 决定「跑在什么隔离度的环境里」，两者合起来才是完整的生产运行底座。

## 二、官网三大卖点

| **卖点** | **官网口径** | **定性解读** |
|---|---|---|
| **无需 K8s 团队** | 平台托管运行时 | 企业不必自建容器编排运维体系，没有 K8s 专家也能跑生产级 Agent |
| **闲时缩零** | 无任务时缩容到零 | 没活儿时不占资源，任务来了再拉起，替代 7×24 常驻容器 |
| **成本降低 90%** | 宣传口径 | 缩零与免自建运维的综合账，需自行验证 |

三个卖点层层递进：托管运行时解决「会不会用」的门槛，缩零解决「用不用得起」的成本，90% 是两者叠加的结果呈现。

「无需 K8s 团队」展开说：自建容器编排运维体系意味着集群搭建、镜像治理、发布回滚、监控告警、安全补丁一整条链路，通常需要专职 SRE 团队；平台托管运行时把这条链路收进平台，应用团队只需要关心 Agent 本身。

「成本降低 90%」的验证方法（资源账单对比法）：

1. 取同一负载基线：N 个 Agent、日均任务量 M、峰值并发 P；
2. 方案 A（自建常驻）：K8s 节点与常驻容器 7×24 的资源账单，加上运维人力折算；
3. 方案 B（AgentRuntime）：按实际执行时长计费的资源账单；
4. 对比两份账单得出真实降幅——90% 成立的前提是任务稀疏（大部分时间没活）；若 Agent 是密集常负载，缩零空间很小，降幅会远低于宣传值。

## 三、沙箱级隔离意味着什么

LLM Agent 与传统服务不同：行为由模型生成、天然不可完全预测，还带着敏感上下文去调工具、跑代码、读写数据。沙箱级隔离因此有三层含义：

1. **与宿主隔离**：Agent 的执行环境与宿主操作系统、其他 Agent 的环境相互隔离，一个 Agent 崩溃或行为异常不波及邻居；
2. **与内网隔离**：Agent 对企业内网资源的访问受控，防止数据泄漏——Agent 拿着业务数据干活，不能随意把数据送到外面；
3. **可审计**：沙箱内的执行动作留痕，出事后可回放定位。

这与数字员工 7×24 运行的要求直接挂钩：让 Agent 无人值守常跑的前提，是它的执行环境本身可信可控（见交叉引用数字员工页）。

具体隔离技术（gVisor、Kata 还是 microVM 谱系的哪种实现）官网产品页未披露，属待核实项；选型时应要求厂商说明隔离边界、逃逸防护与凭证注入设计，并对照库内横评页评估（见第五节）。

## 四、自建 K8s + 容器 vs AgentRuntime

| **对比项** | **自建 K8s + 容器** | **AgentRuntime** |
|---|---|---|
| **团队门槛** | 需要 K8s 专家与 SRE 团队 | 平台托管，应用团队专注 Agent 本身 |
| **弹性** | 自建伸缩策略，常驻底座难缩到零 | 闲时缩零，任务驱动拉起 |
| **隔离粒度** | 容器级（namespace/cgroup），要额外加固才到沙箱级 | 沙箱级隔离开箱即用 |
| **运维成本** | 升级、补丁、容量管理全自理 | 由平台承担 |
| **可控性** | 完全自主、可深度定制 | 受平台能力边界约束，深度定制受限 |

定性结论：没有 K8s 底子、任务又稀疏的团队（办公自动化、日报、巡检类场景），AgentRuntime 的账最划算；已有成熟 K8s 平台、Agent 是密集常负载的核心系统，自建未必更贵。这张表是定性对比，决策要拿第二节的账单对比法算实数。

还有第三条路——混合路线：核心常负载系统留在自建 K8s，稀疏型长尾 Agent 上 AgentRuntime。存量企业的现实往往决定这不是二选一。

## 五、沙箱技术谱系：gVisor / Kata / microVM

沙箱隔离是有成熟谱系的技术域，AgentRuntime 这类平台内置沙箱，背后必然是其中一条路线：

```yaml
# 沙箱隔离强度谱系（示意，由轻到重）
spectrum:
  - 容器: namespace/cgroup，共享内核，隔离最弱、开销最小
  - gVisor: 用户态内核拦截系统调用，隔离增强，开销中等
  - Kata_Containers: 轻量虚拟机跑容器，硬件虚拟化级隔离
  - microVM: Firecracker 类微型虚拟机，虚拟机级隔离 + 秒级启动
```

评估 AgentRuntime 时，带着这张谱系问厂商四个问题：隔离边界落在哪一层；沙箱冷启动开销多大（缩零之后，每次拉起都要付这笔钱）；密钥与数据如何注入沙箱、用后如何回收；沙箱内动作的审计粒度到哪一级。逐项横评见交叉引用的沙箱选型页。

## 六、与百炼 Sandbox 的关系（分析视角）

两者同属「云端沙箱」产品家族，定位不同：

| **对比项** | **百炼 Sandbox** | **OpenTrek AgentRuntime** |
|---|---|---|
| **定位** | E2B 兼容的开发沙箱 | 私有化生产运行时 |
| **主要场景** | Agent 开发调试、代码执行验证 | 企业生产环境的多 Agent 常态运行 |
| **部署形态** | 公有云服务 | 私有化部署 |
| **配套能力** | 与百炼应用开发链路集成 | 与托管调度、全景观测、AI 网关集成 |

快速判别：需求是「开发期让 Agent 安全地试跑代码」，看百炼 Sandbox；需求是「生产环境让 Agent 长期可靠运行」，看 AgentRuntime。

组合用法（分析视角）：开发期在百炼 Sandbox 里快速迭代验证，生产流量迁到 OpenTrek AgentRuntime——两者不是替代关系，而是研发态与生产态的分工。
