## 1. 选型核心维度

```
LLM 推理引擎选型维度
═══════════════════════════════════════════════════════════════════

1. 性能维度
───────────────────────────────────────────────────────────────────
• 吞吐量 (Throughput): 单位时间内生成的 token 数
• 首 token 延迟 (TTFT): 从请求到第一个 token 返回的时间
• 输出 token 延迟 (TPOT): 相邻 token 之间的间隔
• 并发能力: 同时处理的请求数量
• 长上下文表现: 32K / 128K / 200K+ 的处理能力

2. 工程维度
───────────────────────────────────────────────────────────────────
• 易用性: 安装、部署、调优的复杂度
• 生态成熟度: 社区规模、文档完善度、模型支持广度
• 监控可观测性: Prometheus / OpenTelemetry / 日志
• K8s 原生支持: Helm / Operator / Sidecar
• 多 GPU 扩展: TP / PP / EP 支持
• 量化支持: FP8 / INT8 / AWQ / GPTQ / GGUF

3. 业务维度
───────────────────────────────────────────────────────────────────
• 部署位置: 云端 / 私有数据中心 / 边缘 / 本地
• 数据隐私: 是否允许数据出域
• 成本结构: 硬件成本 vs API 调用成本
• 团队技术栈: Hugging Face / NVIDIA / 纯开源
• 模型来源: 开源 / 自研 / 微调 / LoRA

4. 场景维度
───────────────────────────────────────────────────────────────────
• 实时交互: 聊天、代码补全、Agent
• 批量处理: 数据标注、离线生成
• RAG: 长文档、重复前缀
• 多模态: 图文理解、语音
• 边缘部署: 手机、IoT、嵌入式
```

```
│   ├── 追求极低延迟 + NVIDIA 环境 → TensorRT-LLM
│   ├── 多轮对话 / RAG → SGLang
│   └── 通用生产 / 快速上线 → vLLM
│
└── 是 → 云 API
    ├── 极致低延迟 + 成本敏感 → Groq
```

```
│   ├── SGLang (RadixAttention 自动缓存，最佳)
```

## 4. 按技术指标决策

### 4.1 追求极致吞吐

| 排名 | 引擎 | 说明 |
|------|------|------|
| 1 | SGLang | RadixAttention + 高效调度，H100 16K+ tok/s |
| 2 | vLLM | 成熟稳定，PagedAttention + V1 Engine |
| 3 | LMDeploy | TurboMind，中文模型优化 |
| 4 | TensorRT-LLM | 单请求强，高并发需调优 |

### 4.2 追求最低延迟

| 排名 | 引擎 | 说明 |
|------|------|------|
| 1 | Groq | LPU 专用芯片，TTFT < 100ms (70B) |
| 2 | TensorRT-LLM | NVIDIA 定制 kernel，H100 TTFT < 50ms (8B) |
| 3 | SGLang | 前缀缓存降低重复计算 |
| 4 | vLLM | 综合延迟优秀 |

### 4.3 追求最高易用性

| 排名 | 引擎 | 说明 |
|------|------|------|
| 1 | Ollama | 一条命令运行模型 |
| 2 | vLLM | pip install + 一行命令启动 |
| 3 | Groq | 改 base_url 即可迁移 |
| 4 | TGI | Docker 一键部署 |

### 4.4 追求最低成本

| 排名 | 方案 | 说明 |
|------|------|------|
| 1 | llama.cpp (CPU) | 无需 GPU，旧硬件可跑 |
| 2 | Groq | 云 API 中成本最低 |
| 3 | vLLM (自建) | 单卡高吞吐，单位 token 成本低 |
| 4 | Fireworks AI | 批量场景性价比高 |

## 5. 成本模型

### 5.1 自建 GPU 成本估算

```
自建推理成本模型 (2026)
═══════════════════════════════════════════════════════════════════

假设: H100 80GB 月租金 ~ $2,500 (云厂商按需)
       月运行 730 小时

单卡 H100 跑 Llama 3.1 8B:
• 吞吐量: ~15,000 tok/s
• 月总 token: 15,000 × 3,600 × 730 ≈ 39.4 T tokens
• 硬件成本: $2,500
• 每百万 token 成本: $2,500 / 39,400,000 ≈ $0.00006

单卡 H100 跑 Llama 3.1 70B (TP=4, 单节点):
• 吞吐量: ~7,500 tok/s
• 月总 token: ~19.7 T tokens
• 硬件成本: $10,000
• 每百万 token 成本: ~$0.0005

注意:
• 以上为理想满负荷，实际需考虑并发、空闲、维护
• 通常按 30-50% 利用率估算，实际成本乘以 2-3
```

```
成本决策树
═══════════════════════════════════════════════════════════════════
```

## 6. 常见误区

### 6.1 误区一：只看吞吐量，忽略延迟

```
❌ 错误: 选吞吐量最高的引擎
✅ 正确: 实时交互场景优先看 TTFT/TPOT，批量场景优先看吞吐
```

### 6.2 误区二：云 API 一定比自建贵

```
❌ 错误: 自建 GPU 一定更便宜
✅ 正确: 低用量时云 API 更便宜；高用量且团队有运维能力时自建更便宜
```

### 6.3 误区三：一个引擎打天下

```
❌ 错误: 全链路用一个推理引擎
✅ 正确: 不同场景用不同引擎，通过 AI Gateway 统一路由
  示例:
  • 实时聊天 → Groq
  • RAG → SGLang
  • 批量生成 → vLLM
  • 本地测试 → Ollama
```

### 6.4 误区四：忽略量化带来的精度损失

```
❌ 错误: 所有场景都用 Q4 量化
✅ 正确:
  • 通用对话: Q4_K_M 足够
  • 数学/代码/推理: Q8_0 或 FP16
  • 医疗/法律: FP16 或更高精度
```

### 6.5 误区五：只看短期上线速度

```
❌ 错误: 为快速上线选择黑盒方案
✅ 正确: 评估长期可维护性、社区活跃度、团队熟悉度
```

## 7. 迁移建议

### 7.1 引擎迁移成本评估

| 迁移方向 | 难度 | 主要工作 |
|----------|------|----------|
| vLLM → SGLang | 低 | 改 base_url，验证前缀缓存效果 |
| vLLM → TGI | 低 | 改 base_url，调整 Docker/Helm |
| vLLM → TensorRT-LLM | 高 | 重新编译 engine，调整量化 |
| 云 API → 自建 | 中 | 硬件采购、部署、监控、成本切换 |
| Ollama → vLLM | 低 | 模型格式转换，API 兼容 |
| llama.cpp → Ollama | 低 | 直接导入 GGUF |

### 7.2 平滑迁移策略

```
迁移路线图
═══════════════════════════════════════════════════════════════════

阶段 1: 并行运行
───────────────────────────────────────────────────────────────────
• 新引擎部署为 shadow 服务
• 对比延迟、吞吐、精度
• 灰度 5% 流量

阶段 2: 渐进切换
───────────────────────────────────────────────────────────────────
• 按场景分批次切换
• 实时场景先切延迟更优的引擎
• 批量场景先切吞吐更优的引擎

阶段 3: 统一网关
───────────────────────────────────────────────────────────────────
• 通过 LiteLLM / Kong / Portkey 做统一路由
• 配置 fallback 策略
• 监控各引擎健康状态
```
