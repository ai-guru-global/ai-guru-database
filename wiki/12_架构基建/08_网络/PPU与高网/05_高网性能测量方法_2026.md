# 高网性能测量方法 2026

> 中文简称：高网测量方法

> **一句话理解**: 高网测速最大的坑不是工具不会用，而是数字口径不对——busbw 和 algbw 差一个 2(n-1)/n 因子，单向和双向差一倍，先统一口径，基线才有意义。

---

## 1. 三层测量框架

| 层级 | 工具 | 回答的问题 |
|---|---|---|
| L1 链路层 | perftest（`ib_write_bw`、`ib_read_lat` 等） | 单条 RDMA 链路的带宽/时延是否达标 |
| L2 算子层 | nccl-tests（`all_reduce_perf` 等）及各家等效工具 | 集合通信在真实拓扑上的有效带宽 |
| L3 端到端 | 训练/推理基准（loss 曲线、tokens/s、TTFT/TPOT） | 网络问题是否真实影响业务指标 |

**纪律**：三层都要留数。只有 L3 好/坏而缺 L1/L2，无法定位；只有 L1/L2 而缺 L3，无法证明业务影响。PPU 场景的排障清单见 [[01_数学基础/10_AI硬件/09_PPU_High_Performance_Network|PPU 高性能网络与 ICN 互联]] §8。

---

## 2. 口径课：busbw 与 algbw

以 `all_reduce_perf` 为例（n 卡、消息大小 S、耗时 t）：

| 指标 | 定义 | 用途 |
|---|---|---|
| **algbw** = S / t | 算法带宽：数据「逻辑上」流动的速率 | 衡量算法本身吃到的带宽 |
| **busbw** = algbw × 2(n-1)/n | 总线带宽：物理链路上实际流量折算 | 衡量网络/互联的真实压力 |

**要点**：

1. 对比两份报告必须先确认是 busbw 还是 algbw（Ring AllReduce 下 busbw 恒大于 algbw）；
2. AllReduce 的 busbw 理论上限≈最慢链路带宽；测出 90%+ 视为健康（与 [[12_架构基建/08_网络/02_AI_网络|AI 网络基础设施]] §4 的 80–90% 经验值一致）；
3. 小消息看时延（μs 级），大消息看带宽（GB/s 级）——单点数字没有意义，要画「消息大小-性能」曲线。

## 3. 工具速查

### 3.1 perftest（链路层）

```bash
# 服务端（节点 A）
ib_write_bw -d <网卡> -R
# 客户端（节点 B）：--report_gbits 输出 Gb/s 口径
ib_write_bw -d <网卡> -R <A 的 IP> --report_gbits
# 时延（来回程）
ib_write_lat -d <网卡> -R <A 的 IP>
```

要点：双向测加 `--dual`；多次运行取分布而不是取最大；记录 MTU 与网卡固件版本。

### 3.2 nccl-tests（算子层）

```bash
# AllReduce 带宽曲线：消息从 8B 扫到 1G
mpirun -np 16 --bind-to numa \
  ./build/all_reduce_perf -b 8 -e 1G -f 2 -g 1 | tee base.txt
```

要点：`-g 1` 表示每进程 1 张卡；`NCCL_DEBUG=INFO` 确认 transport 用了 RDMA/ICN 而非 Socket 回退；通道数（channels）异常少时先查拓扑与网卡绑定。

### 3.3 拓扑与设备侧

| 厂家 | 工具 | 用途 |
|---|---|---|
| NVIDIA | `nvidia-smi topo -m` | 查看 NVLink/PCIe 亲和矩阵，规划 TP 设备顺序 |
| PPU | `ppu-smi`（拓扑/状态查询，详见 [[概念/GPU/ppu-smi|ppu-smi]]）；ACCL-P 官方文档的 TP 设备顺序表 | 设备顺序必须匹配官方拓扑建议 |
| 通用 | `ibstat`、`ibdev2netdev`、ethtool | 链路状态、速率、网卡↔接口映射（见 [[12_架构基建/08_网络/05_网络_Diagnostics_命令|网络 Diagnostics 命令]]） |

## 4. 基线法（可直接抄的流程）

1. **固定变量**：实例型号、卡数、镜像/驱动/通信库版本、节点布局、消息范围——全部写进报告头；
2. **建基线**：新集群/新镜像首日跑 L1+L2 全套并存档（L3 用固定小任务）；
3. **对比判读**：性能劣化时同参数复测，与基线逐层对比——L1 掉→链路/网卡问题；L1 正常 L2 掉→拓扑/通信库/慢节点；L2 正常 L3 掉→框架层/调度/数据侧；
4. **常见坑**：消息大小不一致、双向当单向报、跨交换机端口不计、CPU 亲和没绑定导致抖动、把首跑（含建连/JIT）当稳态。

---

## 5. 慢节点（straggler）专项

AllReduce 类算子的完成时间由最慢者决定，一个慢节点可以拖垮整个任务：

- 定位：逐节点 L1 压测对比分布，关注长尾而不仅是均值；
- 高频根因：网卡降速（link flap 后 100G 掉到 25G）、NUMA 错绑、健康检查进程抢核、某个 ToR 端口 CRC 错包；
- 关联实战：[[07_模型训练/04_分布式训练/04_分布式训练_Hang_操作手册|分布式训练 Hang 操作手册]]。
