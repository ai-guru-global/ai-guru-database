# 数据中心拥塞控制演进：DCQCN → TIMELY/HPCC/SWIFT → UEC

> 从"ECN 信号 + 网卡启发式"走向"精确遥测 + 规范化传输层"：AI 集合通信的同步爆发与 incast 把 DCQCON 的慢收敛与难调参逼到极限，UEC 在规范层重造拥塞与多路径。

## 解决什么问题

- DCQCN 商用最广但两大痛点：收敛慢（速率调整以数十毫秒计，追不上微秒级突发）、参数多（RP/NP/定时器十余个）且逐集群手工整定，扩容/换业务就要重调。
- AI 训练流量进一步恶化问题：所有 rank 同步爆发（同步屏障后齐发）、incast 大量目的端汇聚（DP 梯度聚合、MoE 专家汇聚）、控制消息对时延敏感——慢收敛直接表现为通信长尾拖慢全局步时间。

## 核心原理

- DCQCN（SIGCOMM 2015，微软）：信号链 ECN → CNP → RP 降速（详见 RoCE 无损三件套篇）。缺陷根源：ECN 只说"拥塞了"，不说"拥塞多深、离拥塞多远"，RP 只能试探性降速。
- TIMELY（SIGCOMM 2015，Google）：以 RTT 为信号，网卡端速率随 RTT 梯度调整；需要高精度时间戳与稳定时钟，Google 内部部署验证。
- HPCC（SIGCOMM 2019，阿里）：交换机用 INT（In-band Telemetry）把逐跳队列长度/链路负载内联进数据包，接收端回传精确反馈，发送端按"链路利用率目标"直接算速率——毫秒级内收敛、接近免 PFC；代价：要求交换机支持 INT、头部开销、跨厂商互通难。
- SWIFT（SIGCOMM 2020，Google）：把 RTT 拆成基线传播时延与排队时延分别响应，兼顾反应速度与稳态公平（Google 内部生产经验）。
- UEC（Ultra Ethernet Consortium，1.0 规范 2025-06 发布）：在规范层重新设计传输——多路径与包级喷洒、独立于 ECN 补丁的拥塞反馈、在网计算特性方向；思路是把"事后补丁"（PFC/ECN/DCQCN 叠床架屋）换成传输层原生的多路径+精确反馈。

## 落地现状对照

| 方案 | 反馈信号 | 部署前提 | 收敛速度 | 商用现状（2026 口径） |
|---|---|---|---|---|
| DCQCN | ECN + CNP | 商用网卡/交换机基本能力 | 慢（数十 ms 量级） | 商用主流，事实默认 |
| TIMELY | RTT | 网卡高精度计时 | 中（ms 级） | Google 内部 |
| SWIFT | RTT（基线/排队分离） | 同上 + 规模运营 | 快 | Google 内部 |
| HPCC | INT 遥测 | 交换机 INT 支持 + 生态 | 快（ms 内量级） | 研究/局部验证为主 |
| UEC | 规范化传输层（多路径/包级喷洒/在网计算方向） | 新一代网卡与交换机 | 设计目标：与多路径协同 | 规范落地阶段（1.0 于 2025-06 发布） |

## 设计要点与权衡

- 选型现实：2026 年前后新建以太网 RoCE 集群仍以 DCQCN 为主，UEC 尚处规范与早期产品阶段——设计上应要求设备具备 ECN/PFC/DCQCN 全套可调能力，并预留 UEC 演进路径（见 IB-RoCE-UEC 路线篇）。
- 拥塞控制不能替代负载均衡：incast 场景下再快的收敛也只是"排队浅一点"，根源路径热点要靠多路径/包级喷洒消除（见自适应路由篇）。
- 参数整定工程化：固定压测集（nccl-tests + incast 复现）+ 自动扫描（ECN 阈值 × DCQCN 参数），避免人工凭经验；基线见性能基线与验收篇。
- 交换机缓冲与队列水位是拥塞控制的另一半：同样算法，缓冲切分不同表现迥异（见 QoS 与隔离篇）。

## 常见坑

- 把 DCQCN 参数从一个集群拷到另一个集群：规模、缓冲、业务分布都变了，性能天差地别。
- 只调拥塞控制不改拓扑/路由：热点是结构问题（ECMP 哈希、收敛比），算法只能缓解。
- 追新 HPCC 类方案但交换机 INT 生态不齐：跨芯片 INT 格式与语义不一致，落地即碎片化。
- 评估只看吞吐不看尾时延：AI 负载痛在 p99 长尾，平均吞吐正常但步时间被拖长。
- 期待 UEC "即插即用"：规范到芯片、网卡、通信库全链条落地需要周期，过渡期无损三件套仍是必修课。
