# Applied Scientist 面试题实例答案

> 中文简称：Applied Scientist 面试题实例答案

> 每个答案采用 **结论 → 展开 → 案例/框架 → 追问预判** 结构。

---

## 业务建模

### Q1: 如何把模糊业务目标（"提升用户留存"）转化为可建模的 ML 问题？

**结论**: 这是 Applied Scientist 的核心能力——"问题形式化"。流程是：业务目标 → 可观测指标 → 代理指标 → ML 任务 → 标签定义，每步都要警惕"替代偏差"。

**展开**:

**转化流程**:
```
1. 业务目标（北极星）: 提升用户留存
2. 可观测指标: 7日/30日留存率（但难直接优化，反馈慢）
3. 代理指标（Proxy）: 次日留存/使用时长/互动率（更可观测）
4. ML 任务: 预测用户流失概率（分类）
5. 标签定义: 未来7天未登录 = 流失
6. 优化目标: 召回流失用户 + 推送干预策略
```

**关键陷阱**:
- **代理指标偏差**: 优化"点击率"可能损害"留存"（标题党短期点击高，长期伤体验）
- **标签时间窗**: 太短（次日）噪声大，太长（30日）反馈慢
- **可行动性**: 模型预测流失后，运营能否有效干预？否则模型无价值

**案例（电商）**:
```
业务目标: 提升 GMV
↓ 转化
代理指标: 转化率 + 客单价
↓ ML 任务
1. 购买意图预测（召回有需求用户）
2. 推荐相关性（提升转化）
3. 价格弹性模型（优化定价）
↓ A/B 验证
核心: GMV 提升是否归因于模型（因果，非相关）
```

**追问预判**: "代理指标和业务指标冲突时怎么办？"
→ 建立两者相关性的离线分析，用 A/B 验证代理指标提升是否带来业务指标提升；若长期冲突，说明代理选错了，需重新定义。永远以最终业务指标为决策依据。

### Q2: 多目标优化（CTR + 时长 + 多样性）如何设计 loss 和权衡？

**结论**: 多目标是推荐/内容业务的核心难题。主流方案分三类：损失加权、pareto 搜索、约束优化，实践中常用"加权 + 业务规则"组合。

**展开**:

**方案对比**:
| 方案 | 原理 | 优劣 |
|------|------|------|
| **损失加权** | L = w1·L_ctr + w2·L_dur | 简单，但权重难调 |
| **Pareto 多任务** | 多梯度下降（MGDA） | 自动找 pareto 前沿 |
| **约束优化** | 最大化主目标，约束次目标下限 | 业务可控 |
| **规则后处理** | 各目标单独建模，规则融合 | 灵活，工程友好 |

**工程实践（推荐系统）**:
```python
# 多模型打分 + 业务规则融合
final_score = (
    w_ctr * ctr_score        # 点击概率
    + w_dur * dur_score      # 预测时长
    + w_div * diversity_pen  # 多样性惩罚
)
# 业务规则: 每个类目至少展示 N 个，打散相邻相似内容
```

**权重调优**:
- 离线: 网格搜索 + 业务约束
- 在线: A/B 测试不同权重组合，找业务指标最优
- 动态: 不同场景/时段用不同权重（如早上重新闻，晚上重娱乐）

**追问预判**: "时长和多样性常常负相关（长内容单一），如何破？"
→ 用"约束优化"而非纯加权——设定时长下限后最大化多样性；或引入"新颖性"维度，对长尾内容给曝光倾斜。

## 算法与模型

### Q3: GBDT vs 深度学习，表格数据如何选？

**结论**: 表格数据（结构化特征）上，GBDT（XGBoost/LightGBM/CatBoost）多数情况仍是首选，深度学习的优势在高维稀疏（如用户行为序列）或多模态场景。不应盲目用 DL。

**展开**:

**决策维度**:
| 维度 | GBDT | 深度学习 |
|------|------|---------|
| **表格数据** | 强（不规则特征/缺失值） | 弱（需大量预处理） |
| **高维稀疏** | 中（需特征工程） | 强（embedding 自动） |
| **数据量** | 中小数据优 | 大数据优 |
| **可解释性** | 强（特征重要性） | 弱 |
| **训练成本** | 低（CPU） | 高（GPU） |
| **特征工程** | 重要 | 可端到端 |

**实践原则**:
1. **先 GBDT 做 baseline**: 表格数据 80% 场景 GBDT 是强 baseline
2. **DL 在以下场景考虑**:
   - 有丰富的序列/文本/图像特征（需 embedding）
   - 数据量极大（>千万样本）
   - 多模态融合
3. **不要为 DL 而 DL**: 若 GBDT 已经 SOTA，DL 的边际提升不值得工程复杂度

**追问预判**: "Wide & Deep / DeepFM 这种混合模型何时值得？"
→ 当同时有"记忆性"特征（如高频共现，GBDT/Wide 擅长）和"泛化性"特征（如用户兴趣，Deep 擅长）时，混合模型能把两者优势结合，是推荐/广告的成熟方案。

## 研究到生产的转化

### Q4: 实验室 SOTA 在生产中表现下降的原因和对策？

**结论**: "离线 SOTA ≠ 线上有效"是 Applied Scientist 最常遇到的现实。核心原因：分布偏移、离线-在线指标不一致、工程损耗、反馈循环。

**展开**:

**常见原因与对策**:
| 原因 | 表现 | 对策 |
|------|------|------|
| **分布偏移** | 训练数据是历史，线上是当下 | 在线学习/定期重训/分布鲁棒训练 |
| **指标不一致** | 离线 AUC 提升，线上 GMV 不动 | 找到与业务强相关的离线代理 |
| **特征不一致** | 训练用离线特征，线上实时特征不同 | Feature Store 统一 |
| **反馈循环** | 模型影响用户行为，改变未来数据 | 反事实评估/离开线 holdout |
| **工程损耗** | 延迟约束下被迫简化模型 | 蒸馏/量化，权衡精度与延迟 |
| ** novelty 效应** | 上线短期涨，长期回落 | 长周期 A/B + 留存观察 |

**诊断流程**:
```
离线好 + 线上差:
1. 检查特征一致性（Training-Serving Skew）
2. 检查离线/线上指标相关性
3. 小流量影子验证（不真正干预）
4. 增量 A/B（只改一处）
5. 长期观察（排除 novelty）
```

**追问预判**: "离线 AUC 提升多少才值得上线？"
→ 没有绝对阈值，取决于业务。高基数场景（如搜索）AUC +0.001 可能有价值；低基数需 +0.01 以上。关键是关联到业务指标（"AUC+0.005 历史对应 GMV+0.3%"）。

## 实验设计与因果

### Q5: A/B 测试常见的坑（辛普森悖论/peeking/交互效应）？

**结论**: A/B 测试不是"上线看数字"。常见陷阱会让结论完全错误，Applied Scientist 必须能识别并避免。

**展开**:

**三大陷阱**:

**1. Peeking（偷看）**:
- 问题: 反复查看 p-value，达到显著就停止（增加假阳性）
- 对策: 预设固定时长/样本量，或用序贯检验（Sequential Testing, 如 mSPRT）

**2. 辛普森悖论**:
- 问题: 分组看 A 优于 B，合并看 B 优于 A（因组间样本比例不均）
- 示例: 新模型在 PC 端和移动端都更好，但移动端样本占比高且整体表现差 → 合并后看似更差
- 对策: 分层分析（stratified），CUPED 调整协变量

**3. 交互效应（Network Effect）**:
- 问题: 用户间相互影响（如社交/打车供需），独立 A/B 假设失效
- 对策: 集群随机化（按城市/社交簇分桶）、合成控制法

**样本量计算**:
```python
# 简化版样本量计算
import math
def sample_size(p_baseline, mde, alpha=0.05, power=0.8):
    """p_baseline: 基线转化率, mde: 最小可检测效应"""
    z = 1.96 + 0.84  # alpha=0.05, power=0.8
    p2 = p_baseline * (1 + mde)
    p_avg = (p_baseline + p2) / 2
    return (z ** 2 * p_avg * (1-p_avg)) / (p2 - p_baseline) ** 2

# 基线转化率 5%，想检测 1% 相对提升
print(sample_size(0.05, 0.01))  # 约需 76万样本/组
```

**追问预判**: "A/B 测试结果不显著，但产品经理想上线，怎么办？"
→ 区分"不显著"和"无效果"——可能是样本量不足（功效不够）。建议延长测试或用 CUPED 提升功效；若真无效果，诚实说明风险，让 PM 基于业务判断决策（技术给数据，业务做决定）。

### Q6: 离线指标提升但 A/B 不显著，如何解读？

**结论**: 这是高频痛点。要系统排查"离线-在线 gap"的来源，核心是确认离线指标是否真的代理了业务目标。

**展开**:

**排查清单**:
```
1. 离线指标相关性
   □ 离线提升的指标（如 AUC）与业务指标（如 GMV）历史相关性如何？
   □ 是否优化了错误的代理指标？

2. 数据一致性
   □ 训练/线上特征是否一致（Training-Serving Skew）
   □ 训练数据是否代表线上分布

3. 实验设计
   □ 样本量是否足够（功效不足 → 不显著）
   □ 测试时长是否覆盖周期性（如工作日 vs 周末）
   □ 是否有交互效应污染

4. 业务机制
   □ 模型改善是否被业务流程"吃掉"（如人工运营覆盖）
   □ 是否触及业务天花板（指标已接近上限）
   □ novelty 效应（短期涨长期回落）
```

**深度分析手段**:
- **CUPED**: 用预实验协变量降低方差，提升功效
- **分层分析**: 看细分人群（新/老用户，高/低活）是否有效果异质
- **长期 holdout**: 保留一部分用户长期不暴露新模型，观察真实增量

**追问预判**: "CUPED 如何降低 A/B 方差？"
→ CUPED 用实验前的相关协变量（X）调整指标（Y）：Y_adj = Y - θ(X - E[X])，θ 是协方差比。前提是 X 与 Y 相关且 X 不受实验影响，能显著降方差（提升功效 20-50%）。

## LLM 应用

### Q7: RAG vs 微调，何时用哪个，能否结合？

**结论**: RAG 适合"动态知识/需溯源/频繁更新"，微调适合"固定能力/风格/领域适配"。两者非互斥，最佳实践常是"微调基础能力 + RAG 注入实时知识"。

**展开**:

**决策矩阵**:
| 需求 | RAG | 微调 | 结合 |
|------|-----|------|------|
| 实时变化的知识 | ✅ | ❌（重训成本高） | — |
| 特定领域术语/风格 | 部分 | ✅ | ✅ |
| 需要引用溯源 | ✅ | ❌ | ✅ |
| 推理能力提升 | ❌ | ✅ | ✅ |
| 低延迟 | ❌（检索开销） | ✅ | 权衡 |
| 数据量有限 | ✅ | ❌（过拟合） | ✅ |

**结合方案（行业最佳实践）**:
```
1. 基座模型微调（领域适配）
   - 注入领域术语、回答风格、任务格式
   - 提升基础能力（如医疗问答的推理）

2. RAG 注入实时知识
   - 检索最新文档/数据库
   - 提供可溯源的 factual 信息

3. 效果
   - 微调让模型"会回答这类问题"
   - RAG 让模型"知道最新事实"
```

**成本权衡**:
- RAG: 检索延迟 + 向量库维护，但知识更新即时
- 微调: 一次性训练成本高，但推理快、能力内化

**追问预判**: "微调用什么数据？业务数据不够怎么办？"
- 用真实业务日志（问答对/反馈）
- 合成数据（用强模型生成训练对，注意质量过滤）
- 公开领域数据 + 少量业务数据混合

## 行为面试

### Q8: 描述一次你把研究成果转化为业务收益的项目（STAR）

**答题框架**:
```
S: "电商搜索场景，长尾 query（如'适合送妈妈的生日礼物'）召回率低"

T: "目标是提升长尾 query 的搜索满意率"

A:
  - 分析: 传统关键词匹配无法理解语义意图
  - 方案: 引入基于 LLM 的 query 改写 + 语义召回
    1. 用 LLM 把模糊 query 改写为多个具体 query
    2. 双塔语义模型召回（补充关键词召回）
    3. LLM 重排序（理解 query-商品相关性）
  - 落地挑战:
    - LLM 延迟高 → 改写结果缓存 + 异步预计算
    - 成本 → 高频 query 用缓存，长尾才调 LLM
    - 评测 → 建立人工标注的长尾 query 集

R:
  - 长尾 query 满意率（人工评估）提升 18%
  - 整体搜索 GMV A/B 提升 2.3%（显著）
  - 沉淀为"语义搜索"通用方案，推广到推荐场景
  - 论文投稿 SIGIR，兼顾学术与业务
```

**追问预判**: "为什么不全用 LLM 召回？"
→ 延迟和成本约束。LLM 召回不适合高 QPS（毫秒级），所以混合架构（传统召回保速度 + LLM 重排提质量）是工程最优。
