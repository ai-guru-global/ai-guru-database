# Architecture（架构设计阶段）

## 目标

把"项目定义"转化为"可执行的技术方案"。架构是 FDE 的**翻译层**——把业务语言翻译成技术语言。

## 核心活动

### 1. 技术选型决策框架

```
决策四象限：

高适配 + 低风险 → 首选 ✅
高适配 + 高风险 → 评估后使用 ⚠️
低适配 + 低风险 → 备选方案 💡
低适配 + 高风险 → 坚决不用 ❌
```

**选型检查清单**：
1. 能在客户环境跑起来吗？（ARM64？离线？）
2. 客户团队能学会运维吗？
3. 开源协议商业友好吗？
4. 社区活跃吗？（GitHub stars / issues）
5. 信创兼容吗？

### 2. 部署方案设计

**三种经典拓扑**：

```
方案A：单机 Docker Compose
适合：POC / <50 用户 / 预算有限
优点：简单、快速、易维护
缺点：无高可用

方案B：K3s 小集群
适合：50-500 用户 / 需要 HA
优点：高可用、可扩展
缺点：运维复杂度增加

方案C：企业级 K8s 集群
适合：500+ 用户 / 多租户
优点：企业级能力
缺点：运维成本高、需要专业团队
```

### 3. 安全方案设计

**政企 AI 安全六要素**：

| 要素 | 方案 |
|---|---|
| 身份认证 | SSO/LDAP/OIDC 对接 |
| 访问控制 | RBAC（角色-权限-资源） |
| 数据传输 | TLS 1.3 加密 |
| 数据存储 | AES-256 静态加密 |
| 审计日志 | 全量操作记录，不可篡改 |
| 国密合规 | SM2/SM3/SM4 算法 |

### 4. 应急预案

```
场景1：模型推理服务挂了
→ 自动重启（systemd/k8s restart policy）
→ 降级方案：返回预设回答
→ 告警通知（企业微信/钉钉/短信）

场景2：向量数据库挂了
→ 主从切换/多副本
→ 定时备份（每天凌晨）
→ 恢复演练（每月一次）

场景3：整个系统不可用
→ 回滚到上一个稳定版本
→ 保留回滚脚本和备份
→ RTO < 4 小时，RPO < 1 小时
```

### 5. 架构评审（必做）

在开始写代码之前，**和客户技术团队一起评审架构**：

- 架构图易懂吗？（一页纸能看清楚）
- 安全方案认可吗？（符合客户安全规范）
- 技术选型合理吗？（客户能接受）
- 预案可行吗？（真的能执行）
- 运维复杂度可控吗？（客户能接手）
