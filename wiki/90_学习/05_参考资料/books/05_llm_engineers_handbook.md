# LLM Engineer's Handbook

> 中文简称：LLM 工程师手册

> **一句话理解**: 面向 LLM 工程师的全栈实战手册，从数据工程到模型部署提供端到端工程化方案，强调可复现、可扩展的生产级 LLM 系统构建。

## 书籍概述

### 作者背景

**Paul Iusztin** 是资深 ML/LLM 工程师，长期专注于 LLM 系统的工程化落地，是 Decoding ML 社区的创始人，在 MLOps 与 LLM 工程领域有大量实战与教学经验。**Maxime Labonne** 是知名的 LLM 微调专家（Hugging Face 社区活跃贡献者，开发了多个流行微调模型）。两位作者的组合确保了本书既有系统工程视角，又有模型训练的实战深度。

### 本书定位

本书的核心价值在于**端到端的工程化**：

- **不是**讲单一技术的书（如只讲 RAG 或只讲微调）
- **而是**带你从零搭建一个**完整的 LLM 系统**：数据管道 → 训练 → 评估 → 部署 → 监控
- 强调**可复现、可扩展、生产级**，配套完整 GitHub 项目模板

与 [[90_学习/05_参考资料/books/15_ai_engineering_huyen]] 的对比：
- AI Engineering 偏**架构设计与方法论**（"为什么这样设计"）
- 本书偏**工程实现与工具链**（"具体怎么搭"）
- 两者互补，建议搭配阅读

## 关键概念与公式

### LoRA 低秩适配

```
原始权重: W (d × k)
LoRA 分解: ΔW = B × A, 其中 B (d × r), A (r × k), r << min(d,k)
微调时: 冻结 W, 只训练 A 和 B
推理时: W' = W + ΔW (可合并, 无额外开销)

优势: 可训练参数减少 100-1000 倍, 显存大幅降低
```

### RAG 检索-生成流程

```
1. 索引: 文档 → 分块 → Embedding → 向量数据库
2. 检索: 查询 → Embedding → 向量相似度搜索 → Top-K 文档
3. 生成: Prompt(查询 + 检索文档) → LLM → 回答

检索质量: Recall@K, MRR
生成质量: 准确性, 相关性, 引用正确性
```

### LLM-as-a-Judge 评估

```
评估 Prompt = 系统指令 + 评估标准 + 待评估输出 + (参考答案)
Judge 输出 = 分数 (1-5) + 理由

注意事项:
- Judge 模型偏差 (偏好长输出、自身风格)
- 位置偏差 (Position Bias)
- 需要校准与人工抽检
```

### 训练成本估算

```
训练 FLOPs ≈ 6 × N × D
其中 N = 模型参数量, D = 训练 Token 数

微调成本 ≈ 预训练成本 × (微调 Token / 预训练 Token) × PEFT 折扣
LoRA 通常可将微调成本降至全量微调的 10-20%
```

## 亮点与局限

### 亮点

- **工程化视角全面**: 数据 → 训练 → 评估 → 部署 → 监控完整链路
- **配套代码仓库**: 完整可运行的项目模板
- **覆盖 MLOps 工具链**: ZenML、MLflow、CI/CD 等实战
- **真实项目驱动**: 贯穿始终的写作助手项目
- **作者实战经验丰富**: 来自一线的工程经验

### 局限

- **工具链绑定较强**: ZenML/Hugging Face 生态，换工具需适配
- **版本更新快**: 工具迭代快，需注意兼容性
- **理论深度有限**: 偏工程实现，不深入算法原理
- **某些环节较浅**: 如安全、对齐覆盖较少

## 工具链速查表

本书涉及的工具链汇总，便于搭建 LLM 系统时选型：

| 环节 | 工具 | 用途 |
|------|------|------|
| **管道编排** | ZenML | 可复现的 ML 管道 |
| **实验跟踪** | MLflow / W&B | 记录超参、指标、模型 |
| **模型库** | Hugging Face | 模型、数据集、训练 |
| **微调框架** | PEFT / TRL | LoRA、QLoRA、RLHF |
| **向量数据库** | Qdrant / Pinecone | RAG 向量存储 |
| **推理引擎** | vLLM / TGI | 高性能推理服务 |
| **应用框架** | LangChain / LlamaIndex | RAG、Agent 编排 |
| **CI/CD** | GitHub Actions | 自动化测试与部署 |
| **容器化** | Docker / K8s | 部署与编排 |
| **监控** | Prometheus / 专用工具 | 可观测性 |

### 工具选型原则

1. **优先成熟工具**: 不要重复造轮子，用经过验证的工具
2. **避免过度绑定**: 核心逻辑与工具解耦，便于替换
3. **可复现优先**: 数据、代码、环境都要版本化
4. **从小处开始**: 先用简单工具跑通，再按需升级

## 端到端项目检查清单

构建生产级 LLM 系统时，用此清单自查完整性：

### 数据层

- [ ] 数据采集管道是否自动化？
- [ ] 数据清洗与去重是否到位？
- [ ] PII 脱敏是否处理？
- [ ] 数据是否版本化？
- [ ] 合成数据质量是否验证？

### 训练层

- [ ] 是否选择了合适的微调方法（SFT/LoRA）？
- [ ] 训练数据格式是否正确？
- [ ] 实验是否可复现（固定种子、记录超参）？
- [ ] 是否跟踪了训练指标？
- [ ] 模型是否注册与版本化？

### 评估层

- [ ] 是否建立了评估集（黄金集）？
- [ ] 是否有自动化评估管道？
- [ ] 是否用了 LLM-as-a-Judge？
- [ ] 评估是否集成到 CI/CD？
- [ ] 是否有人工抽检校准？

### 推理层

- [ ] 是否选择了合适的推理引擎？
- [ ] 是否做了量化优化？
- [ ] API 是否支持流式响应？
- [ ] 是否有缓存机制？
- [ ] 并发与限流是否处理？

### 应用层

- [ ] RAG 检索质量是否优化？
- [ ] Agent 工具调用是否可靠？
- [ ] 上下文管理是否合理？
- [ ] 输出格式是否约束？

### 运维层

- [ ] 是否有完整的可观测性（日志/指标/追踪）？
- [ ] 是否监控质量分与成本？
- [ ] 是否有告警与响应机制？
- [ ] 是否有降级与回滚方案？
- [ ] 是否建立了数据飞轮？
