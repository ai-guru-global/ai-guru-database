# 小模型与端侧 LLM 深度解读: 从高效模型到端侧部署

> 中文简称：小模型与端侧 LLM 深度解读: 从高效模型到端侧部署

## 2. 高效小模型

### 2.1 小模型定义

| 规模分类 | 参数量 | 内存需求 (FP16) | 可运行设备 |
|----------|--------|----------------|-----------|
| **微型** | < 1B | < 2 GB | 手机、嵌入式 |
| **小型** | 1-4B | 2-8 GB | 手机、笔记本 |
| **中型** | 4-8B | 8-16 GB | 笔记本、台式机 |
| **大型** | 8-70B | 16-140 GB | 服务器、高端 GPU |

### 2.3 Phi 系列: 「教科书即数据」的启示

**核心理念**: 用 GPT-3.5 生成的「教科书质量」合成数据训练小模型，达到大模型 80-90% 的性能。

```
Phi 训练数据策略:

Phi-1 (2023, 1.3B):
├── 1B tokens: GPT-3.5 生成的教科书质量 Python 教材
├── 1B tokens: GPT-3.5 生成的 Python 习题 + 解答
└── 180M tokens: 教科书质量网络数据

Phi-2 (2023, 2.7B):
├── 同 Phi-1 数据
├── + 更多教科书质量网络数据
└── 1.4T tokens 总计

Phi-3-mini (2024, 3.8B):
├── 4.9T tokens (7× Phi-2)
├── 高质量过滤: 基于分类器筛选
├── 合成数据: 数学推理、代码、逻辑
└── 结果: 超越 Mistral 7B (参数少一半)
```

| Phi 启示 | 说明 |
|----------|------|
| **数据质量 >> 数量** | 2.7B + 精选数据 > 13B + 粗糙数据 |
| **合成数据有效** | GPT 生成的教科书数据比网络数据更有效 |
| **小模型有上限** | 复杂推理/创作任务仍需要大模型 |
| **效率甜蜜点** | 3-7B 参数在效率/质量间最优平衡 |

### 2.4 知识蒸馏方法

| 方法 | 原理 | 效果 |
|------|------|------|
| **输出蒸馏** | 学生拟合教师的输出分布 (KL 散度) | 经典，效果有限 |
| **特征蒸馏** | 学生拟合教师中间层特征 | 更好 |
| **数据蒸馏** | 教师生成训练数据，学生 SFT | 最实用（Phi, Orca） |
| **渐进蒸馏** | 逐步减少学生层数 | 极端压缩 |

## 3. 模型量化 (Quantization)

### 3.1 量化基础

```
量化原理:

FP32 权重 (32-bit): 高精度, 大内存
     │
     ↓ 量化
     
INT8 (8-bit): 精度损失 ~0.5%, 内存减少 4×
INT4 (4-bit): 精度损失 ~1-3%, 内存减少 8×

关键: 如何在低精度下最小化信息损失？

量化公式:
q = round(w / scale) + zero_point
w_approx = (q - zero_point) × scale
```

### 3.2 量化方法对比

| 方法 | 位数 | 校准 | 精度损失 | 速度 | 适用场景 |
|------|------|------|----------|------|----------|
| **GPTQ** | 4-bit | 需要校准数据 | 低 | 快 | GPU 推理 |
| **AWQ** | 4-bit | 需要校准数据 | 最低 | 快 | GPU 推理 (优于GPTQ) |
| **GGUF Q4_K_M** | 4-bit | 无需 | 低 | 中 | CPU/GPU 混合 |
| **GGUF Q5_K_M** | 5-bit | 无需 | 最低 | 中 | CPU/GPU 混合 |
| **bitsandbytes (NF4)** | 4-bit | 无需 | 中等 | 中 | QLoRA 微调 |
| **SqueezeLLM** | 3-bit | 需要 | 较高 | 快 | 极端压缩 |

### 3.3 GPTQ vs AWQ

| 维度 | GPTQ | AWQ |
|------|------|-----|
| **原理** | 逐层最优量化 (OBQ) | 激活感知量化 |
| **核心创新** | 基于 Hessian 矩阵补偿量化误差 | 保护「显著权重」(高激活通道) |
| **校准数据** | 需要 128 条样本 | 需要 128 条样本 |
| **精度** | 好 | 更好 (保护显著权重) |
| **推理速度** | 快 (GPU kernel) | 更快 (高效 dequant) |
| **生态** | AutoGPTQ 库 | vLLM 原生支持 |

### 3.4 GGUF 格式与 llama.cpp

**GGUF** 是 llama.cpp 生态的标准量化格式：

| 量化级别 | 大小 (相对FP16) | 困惑度增加 | 推荐场景 |
|----------|----------------|-----------|----------|
| **Q2_K** | 30% | +0.5-1.0 | 极端资源受限 |
| **Q3_K_M** | 35% | +0.2-0.5 | 低内存设备 |
| **Q4_K_M** | 40% | +0.05-0.1 | **最佳性价比** |
| **Q5_K_M** | 50% | +0.02-0.05 | 追求质量 |
| **Q6_K** | 60% | +0.01 | 接近无损 |
| **Q8_0** | 50% | +0.01 | 无损级 |

## 4. 端侧推理引擎

### 4.1 推理引擎对比

| 引擎 | 平台 | 格式 | 硬件加速 | 生态 |
|------|------|------|----------|------|
| **llama.cpp** | 全平台 | GGUF | CPU/GPU/Metal | 最广泛，社区驱动 |
| **MLC-LLM** | iOS/Android/Web | 多种 | Vulkan/Metal/CUDA | 学术驱动，跨平台 |
| **ONNX Runtime** | Windows/Linux | ONNX | NPU/DirectML/CUDA | 微软生态 |
| **Apple MLX** | macOS/iOS | MLX | Apple Silicon | Apple 原生 |
| **MediaPipe LLM** | Android | TFLite | NNAPI/GPU | Google 移动生态 |
| **ExecuTorch** | 移动端 | PyTorch | NPU/GPU | Meta 移动生态 |
| **PowerInfer-2** | 手机 | GGUF | CPU | 稀疏激活，手机可用 |

### 4.2 llama.cpp 实战

```bash
# 安装
git clone https://github.com/ggerganov/llama.cpp
cd llama.cpp && make -j

# 下载 GGUF 模型
# 从 HuggingFace 下载 Qwen2-1.5B-Instruct-Q4_K_M.gguf

# 推理
./llama-cli -m qwen2-1.5b-instruct-q4_k_m.gguf \
  -p "解释什么是量子计算" \
  -n 256 \
  --temp 0.7 \
  -t 4    # 4 线程

# 服务器模式 (OpenAI 兼容 API)
./llama-server -m qwen2-1.5b-instruct-q4_k_m.gguf \
  --port 8080 \
  -t 4 \
  -c 4096  # 上下文长度
```

### 4.3 Apple MLX 实战

```python
# MLX: Apple Silicon 原生 LLM 推理
from mlx_lm import load, generate

# 加载模型 (自动转换为 MLX 格式)
model, tokenizer = load("mlx-community/Qwen2-1.5B-Instruct-4bit")

# 推理
prompt = "写一首关于春天的诗"
messages = [{"role": "user", "content": prompt}]
text = generate(model, tokenizer, prompt=tokenizer.apply_chat_template(
    messages, tokenize=False), max_tokens=256, temp=0.7)
print(text)

# 性能: M1 Pro 上 Qwen2-1.5B-4bit 约 80 tokens/s
```

## 5. 端侧 LLM 的模型架构创新

### 5.1 针对端侧的架构优化

| 技术 | 原理 | 代表模型 | 效果 |
|------|------|----------|------|
| **GQA** | 分组查询注意力，减少 KV 缓存 | LLaMA 3, Phi-3 | 内存减少 2-4× |
| **MoE** | 稀疏激活，只计算部分专家 | Mixtral, Qwen2MoE | FLOPs 减少 3-5× |
| **滑动窗口注意力** | 局部注意力，减少内存 | Mistral, Phi-3 | 上下文内存线性 |
| **KV 缓存压缩** | 稀疏 KV 缓存 | H2O, StreamingLLM | 长上下文友好 |
| **推测解码** | 小模型草稿+大模型验证 | Medusa, EAGLE | 速度提升 2-3× |

### 5.2 小模型的 Scaling Laws

| 发现 | 说明 |
|------|------|
| **Chinchilla 定律** | 最优 token 数 ≈ 20 × 参数量 |
| **小模型需要更多数据** | 1B 模型需要 20B+ tokens |
| **数据质量更重要** | Phi-2 (2.7B) 用精选数据超越 LLaMA-2 7B |
| **能力涌现减弱** | 小模型不会有突然的能力涌现 |
| **特定任务可超越大模型** | 代码/数学: Phi-3-mini 超越 Mistral 7B |

## 7. 局限与开放问题

1. **能力上限**: 小模型在复杂推理、长文本生成、多步任务上仍逊于大模型
2. **知识容量**: 参数量限制了模型可存储的知识量
3. **多语言**: 小模型的多语言能力通常弱于大模型
4. **安全对齐**: 小模型的 RLHF/DPO 对齐效果不如大模型
5. **量化退化**: 4-bit 以下量化在某些任务上性能下降明显
6. **硬件碎片**: 不同设备的 NPU/GPU 生态不统一

## 8. 工程实践

| 关注点 | 建议 |
|--------|------|
| **模型选择** | 手机: 1-4B + Q4 量化; PC: 7-8B + Q4; 服务器: 70B+ |
| **量化选择** | Q4_K_M (llama.cpp) 或 AWQ-4bit (GPU) 是最佳性价比 |
| **内存估算** | FP16: 2GB/1B 参数; Q4: 0.5GB/1B 参数; KV 缓存额外 |
| **延迟优化** | 减少上下文长度、启用推测解码、选择 GQA 模型 |
| **测试** | 量化前后对比 benchmark，确保目标任务无退化 |
