# 论文深度解读: RAG — 检索增强生成

> **论文**: *Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks* (Lewis et al., 2020, Facebook AI)
> **重要性**: 将检索与生成端到端结合，解决了 LLM 知识过时和幻觉问题，成为企业 AI 应用的标准架构
> **引用**: 5000+

---

## 1. 一句话理解

> **RAG = 先查后答：让 LLM 在回答问题前，先从外部知识库中检索相关文档片段，将检索到的上下文作为生成答案的依据——既利用 LLM 的语言理解和生成能力，又借助外部知识保证事实准确性。**

---

## 2. 研究背景

### 2.1 LLM 的知识困境

```
纯参数化 LLM 的知识问题:

┌────────────────────────────────────────────────────────────┐
│  LLM 将知识存储在模型权重 (参数) 中                         │
│                                                            │
│  问题1: 知识过时 — 训练后的新信息无法获取                     │
│  问题2: 知识幻觉 — 模型可能生成看似合理但错误的事实           │
│  问题3: 知识容量 — 参数量限制了可存储的知识量                 │
│  问题4: 可追溯性 — 无法追溯答案的来源                        │
│  问题5: 更新成本 — 重新训练以更新知识代价极高                 │
└────────────────────────────────────────────────────────────┘
```

### 2.2 RAG 之前的方法

| 方法 | 原理 | 局限 |
|------|------|------|
| **纯 LLM** | 知识存在参数中 | 知识过时、幻觉 |
| **搜索引擎** | 返回文档列表 | 不能直接回答问题 |
| **Open-Domain QA** | 检索 + 抽取式回答 | 回答受限于原文片段 |
| **知识图谱 QA** | 查询结构化知识 | 覆盖不完整 |

## 3. RAG 核心架构

### 3.1 原始 RAG 架构

```
RAG 原始架构 (Lewis et al., 2020):

输入问题 q
    │
    ↓ 检索器 (DPR: Dense Passage Retrieval)
从知识库 W 中检索 top-k 文档: {z_1, ..., z_k}
    │
    ↓ 生成器 (BART)
P(y|q) = Σ_i P(z_i|q) · P(y|q, z_i)
         ↑ 检索概率    ↑ 给定文档和问题的生成概率

端到端训练: 检索器和生成器联合优化
```

### 3.2 RAG-Sequence vs RAG-Token

| 变体 | 生成方式 | 优点 | 缺点 |
|------|----------|------|------|
| **RAG-Sequence** | 每个文档生成完整答案，选最优 | 答案一致性 | 计算 k 倍 |
| **RAG-Token** | 每个 token 可参考不同文档 | 灵活 | 可能不一致 |

### 3.3 核心公式

**检索概率**:
\[
p_\eta(z|q) = \frac{\exp(d(z) \cdot f(q))}{\sum_{z'} \exp(d(z') \cdot f(q))}
\]

其中 \(d(z)\) 是文档向量，\(f(q)\) 是问题向量（DPR 双编码器）

**边际生成概率**:
\[
p(y|q) = \sum_{z \in \text{top-k}} p_\eta(z|q) \cdot p_\theta(y|q, z)
\]

## 4. RAG 的进化：从论文到产业

### 4.1 RAG 技术进化时间线

```
RAG 技术进化:

RAG (Lewis 2020) — 检索+生成联合训练
    │
├── FiD (Izacard 2022) — Fusion-in-Decoder
│   检索后用 T5 编码器独立编码每个文档，decoder 融合
│
├── RETRO (Borgeaud 2022) — DeepMind
│   将检索嵌入 Transformer 层内，chunk-level 检索
│
├── Self-RAG (Asai 2023)
│   LLM 自主判断是否需要检索，检索后自我反思
│
├── CRAG (Yan 2024)
│   纠正性 RAG: 评估检索结果质量，低质量时切换策略
│
├── Adaptive-RAG (Jeong 2024)
│   自适应选择检索策略: 无需检索/简单检索/复杂检索
│
└── Agentic RAG (2024-2026)
    Agent 多轮检索、查询改写、结果综合
```

### 4.2 现代 RAG 系统架构

```
现代 RAG 系统 (2025-2026):

┌───────────────────────────────────────────────────────────────────┐
│                        现代 RAG 系统架构                            │
├───────────────┬───────────────────┬───────────────────────────────┤
│   离线索引      │   在线检索          │   生成与后处理               │
├───────────────┼───────────────────┼───────────────────────────────┤
│ 文档加载       │ 查询理解/改写       │ 上下文组装                   │
│ 文档分块       │ 向量检索 (ANN)      │ LLM 生成                    │
│ 嵌入计算       │ 关键词检索 (BM25)   │ 忠实性验证                   │
│ 向量索引       │ 混合检索 + RRF      │ 引用标注                    │
│ 元数据标注     │ 重排序 (Reranker)   │ 答案评估                    │
└───────────────┴───────────────────┴───────────────────────────────┘
```

## 5. 现代 RAG 关键技术

### 5.1 检索策略

| 策略 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **密集检索** | 向量相似度 (ANN) | 语义匹配 | 精确匹配弱 |
| **稀疏检索** | BM25/TF-IDF | 精确匹配好 | 语义理解弱 |
| **混合检索** | 密集 + 稀疏 + RRF | 综合最优 | 复杂度高 |
| **查询改写** | HyDE, Step-back | 提升召回率 | 需要额外 LLM |
| **多路召回** | 多检索器 + 融合 | 覆盖全面 | 延迟增加 |

### 5.2 分块策略

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| **固定长度** | 512 tokens + 50 overlap | 通用基线 |
| **语义分块** | 按段落/标题分割 | 结构化文档 |
| **递归分块** | 从大到小递归分割 | 长文档 |
| **文档感知** | Markdown/HTML 结构 | 技术文档 |
| **句子窗口** | 检索句子 + 上下文窗口 | 问答场景 |

### 5.3 重排序 (Reranking)

```
RAG 检索流程:

查询 → 稀疏检索 (top-100) → 密集检索 (top-100)
       │                      │
       └─── RRF 融合 (top-50) ──→ Cross-Encoder Reranker (top-5)
                                     │
                                     └── 送入 LLM 生成答案
```

| 重排序器 | 类型 | 速度 | 质量 |
|----------|------|------|------|
| **Cohere Rerank** | API | 快 | 好 |
| **BGE-Reranker** | 开源 | 中 | 好 |
| **ColBERT v2** | 延迟交互 | 快 | 很好 |
| **Cross-Encoder** | 交叉编码 | 慢 | 最好 |

## 6. Advanced RAG 模式

### 6.1 Graph RAG

```
Graph RAG (Microsoft, 2024):

传统 RAG: 文档 → 分块 → 向量 → 检索 → 生成
Graph RAG: 文档 → 知识图谱 → 社区检测 → 摘要 → 检索 → 生成

优势:
- 捕获实体间关系 (传统 RAG 只看文本相似度)
- 全局理解 (跨文档综合)
- 适合需要推理链的复杂问题
```

### 6.2 Self-RAG

```
Self-RAG (Asai et al., 2023):

模型自学生成特殊 token:
[Retrieve]  — 需要检索
[ISREL]     — 检索结果是否相关
[ISSUP]     — 生成内容是否被检索支持
[ISUSE]     — 生成内容是否有用

推理时:
模型自主决定:
1. 是否需要检索 (简单问题直接回答)
2. 检索结果是否有用 (无用则重新检索或换策略)
3. 生成的答案是否有依据 (无依据则标记不确定)
```

### 6.3 Agentic RAG

```
Agentic RAG (2024-2026):

Agent 控制检索-生成循环:

用户问题
    │
    ↓ Agent 分析
    ├── 直接回答 (简单事实问题)
    ├── 单轮检索 (标准 RAG)
    ├── 多轮检索 (复杂问题，需要多个证据)
    ├── 查询分解 (子问题分别检索)
    ├── 工具调用 (搜索引擎、API、数据库)
    └── 反思与验证 (检查答案是否被证据支持)
```

## 7. RAG vs Fine-tuning vs Long Context

| 维度 | RAG | Fine-tuning | 长上下文 LLM |
|------|-----|-------------|-------------|
| **知识更新** | 即时更新索引 | 需要重新微调 | 每次塞入全部文档 |
| **成本** | 低 (索引 + API) | 高 (GPU 训练) | 高 (长上下文 token 费) |
| **可追溯性** | 可引用来源 | 不可追溯 | 可追溯但成本高 |
| **适用场景** | 企业知识库 QA | 风格/格式适配 | 文档分析/合同审查 |
| **知识容量** | 无限 (外部存储) | 受参数限制 | 受上下文窗口限制 |
| **延迟** | 检索 + 生成 | 仅生成 | 长上下文处理慢 |

## 8. RAG 评估

### 8.1 RAGAS 框架

| 指标 | 衡量 | 计算方式 |
|------|------|----------|
| **Faithfulness** | 答案是否忠实于检索上下文 | LLM 判断 |
| **Answer Relevancy** | 答案是否与问题相关 | LLM 判断 |
| **Context Precision** | 检索的上下文是否精准 | 排序评估 |
| **Context Recall** | 是否检索到所有需要的信息 | 与标准答案对比 |

### 8.2 常见失败模式

| 失败模式 | 表现 | 解决方向 |
|----------|------|----------|
| **检索失败** | 相关文档未检索到 | 改进索引/查询改写 |
| **上下文噪声** | 检索到不相关内容 | 更好的分块/重排序 |
| **幻觉** | 忽略上下文，自行编造 | 忠实性验证/约束生成 |
| **丢失中间** | 只使用上下文首尾 | 位置感知的注意力 |
| **过度保守** | "根据提供的信息无法回答" | 调整 system prompt |

## 9. RAG 对产业的影响

| 影响 | 说明 |
|------|------|
| **企业 AI 标准架构** | 90%+ 的企业 LLM 应用使用 RAG |
| **知识库即服务** | Pinecone, Weaviate, Qdrant 等向量数据库兴起 |
| **RAG 框架生态** | LangChain, LlamaIndex, Haystack 成为标准工具 |
| **替代微调** | 许多场景 RAG 比微调更经济有效 |
| **合规与审计** | RAG 的可引用性满足金融/医疗合规需求 |

## 10. 工程实践

| 关注点 | 建议 |
|--------|------|
| **分块大小** | 从 512 tokens + 50 overlap 开始调优 |
| **检索数量** | top-5 通常是效率和质量的平衡点 |
| **混合检索** | BM25 + 向量检索 + RRF 融合是当前最佳实践 |
| **重排序** | 检索 top-20 → 重排序取 top-5 |
| **评估** | 构建评估集，用 RAGAS 框架定期评估 |
