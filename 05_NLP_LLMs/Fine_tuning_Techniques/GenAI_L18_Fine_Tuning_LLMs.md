## 从提示工程到微调：技术演进路径

使用大型语言模型构建生成式人工智能应用带来了新的挑战。一个关键问题是确保模型为特定用户请求生成的内容在响应质量（准确性和相关性）方面表现良好。

在之前的课程中，我们讨论了两种主要技术来解决这一问题：

**第一种：提示工程（Prompt Engineering）**

通过精心设计提示词来引导模型的输出。包括：
- **指令提示**：提供显式指导，明确告诉模型期望的响应格式和内容
- **少样本学习（Few-shot Learning）**：在提示中给出若干示例，让模型通过隐式学习理解期望的输出模式

**第二种：检索增强生成（RAG）**

通过外部知识库检索相关信息，将检索到的内容作为上下文注入提示中，增强模型回答的准确性和时效性。

以上两种技术的共同点是：它们都试图通过**修改模型的提示输入**来改善输出质量，而不改变模型本身。

**第三种：微调（Fine-tuning）**

微调是一种从根本上不同的方法——它通过**使用额外数据重新训练模型本身**来提升模型在特定任务或领域上的表现。

## 什么是语言模型的微调

根据定义，大型语言模型是在来自包含互联网的多样化来源的大量文本上**预训练**的。预训练赋予了模型广泛的语言理解和生成能力，但在特定任务或特定领域上的表现可能不够理想。

### 少样本学习的局限

少样本学习虽然简单有效，但存在两个关键限制：

1. **Token限制约束**：模型的上下文窗口（context window）有限，可能限制你能提供的示例数量，从而影响学习效果。例如，如果模型上下文窗口为 8K token，而每个示例需要 500 token，那么最多只能提供约 16 个示例。

2. **成本问题**：模型按 token 计费，在每个提示中添加大量示例意味着每次调用都要为这些示例的 token 付费。对于高频调用的应用场景，这种成本会迅速累积。

### 微调的定义与原理

微调是机器学习系统中的一种常见做法，具体到语言模型场景：

- **输入**：一个已经过大规模预训练的语言模型
- **过程**：使用为特定任务或应用领域精心挑选的一组示例数据，对该预训练模型进行额外的训练
- **输出**：一个针对该特定任务或领域更准确且相关的**定制模型**

微调的核心优势包括：

- **减少示例需求**：微调后的模型需要的少样本示例数量大幅减少，甚至可以实现零样本（zero-shot）良好表现
- **降低推理成本**：由于不再需要在每次提示中携带大量示例，token 使用量和相关成本显著降低
- **提升一致性**：微调后的模型在特定任务上的输出格式和风格更加一致可靠

### 监督微调 vs 无监督微调

需要特别说明的是，本课讨论的微调指的是**监督微调（Supervised Fine-tuning, SFT）**：

| 类型 | 描述 | 数据来源 |
|------|------|----------|
| **监督微调** | 通过添加原训练数据集之外的**新标注数据**来进行重新训练 | 任务特定的新数据集 |
| **无监督微调** | 在原始训练数据上使用不同的超参数进行再训练 | 原始训练数据 |

监督微调是我们关注的重点，因为它能有效地将模型适配到新的任务和领域。

## 何时以及为何要微调模型

微调是一种高级技术，要求一定的专业知识才能获得预期效果。**如果操作不当，可能无法带来预期的改进，甚至会降低模型在目标领域的性能。**

在决定是否进行微调之前，你需要从以下四个维度进行系统评估：

### 1. 用例（Use Case）

首先明确你进行微调的具体用例：
- 你想在哪些方面提升当前预训练模型的表现？
- 是为了提升特定领域的专业准确性？
- 是为了让模型遵循特定的输出格式？
- 是为了让模型学习特定的行为模式或风格？

### 2. 替代方案（Alternatives）

在考虑微调之前，务必先尝试其他更简单的技术，并建立性能基线：

- **提示工程**：尝试少样本提示（few-shot prompting），在提示中提供相关示例，评估响应质量
- **RAG**：尝试用查询结果增强提示，从你的数据源检索相关信息并注入提示中，评估响应质量

只有当这些替代方案无法满足需求时，才应考虑微调。

### 3. 成本（Cost）

微调的成本包括多个方面：

| 成本维度 | 具体考量 |
|----------|----------|
| **可调性** | 预训练模型是否支持微调？某些闭源模型可能不支持 |
| **人力投入** | 准备训练数据、设计评估方案、优化模型超参数所需的工作量 |
| **计算资源** | 运行微调任务所需的 GPU/TPU 资源，以及部署微调模型后的持续推理成本 |
| **数据获取** | 获取足够数量的高质量标注示例，以对微调效果产生实质性影响 |

### 4. 收益（Benefits）

确认微调能带来的实际收益：

- **质量提升**：微调后的模型是否确实优于基线（提示工程/RAG）？
- **成本降低**：是否通过简化提示中的示例数量而降低了 token 使用量？
- **可扩展性**：是否能将同一个基础模型微调后用于多个新领域？

### 决策流程总结

理想的决策路径如下：

1. 先用提示工程建立基线性能
2. 如果不够，尝试 RAG 方案
3. 如果仍不满足，评估微调的成本收益比
4. 只有当收益明显大于成本时，才启动微调流程

## 如何微调预训练模型

一旦决定进行微调，你需要准备以下四项核心资源：

### 1. 预训练模型

选择一个支持微调的基础模型。考虑因素包括：
- 模型规模与你的计算资源是否匹配
- 模型是否开放微调权限
- 模型的许可证是否允许你的使用场景
- 基础模型的通用能力是否足够好

### 2. 微调数据集

数据质量是微调成功的关键：
- 数据必须与目标任务高度相关
- 数据量需要足够（通常数百到数千条高质量样本）
- 数据格式需要符合模型要求（如对话格式、指令格式等）
- 数据质量远比数量重要——少量高质量数据优于大量低质量数据

### 3. 训练环境

运行微调任务需要合适的计算环境：
- GPU/TPU 资源（数量和型号取决于模型规模）
- 训练框架（如 PyTorch、TensorFlow）
- 微调工具库（如 Hugging Face TRL、PEFT）

### 4. 托管部署环境

微调完成后，需要将模型部署到生产环境：
- 云端推理服务（如 Azure ML、AWS SageMaker）
- 本地/边缘部署方案
- API 服务封装

## 微调的关键技术细节

### 数据准备最佳实践

1. **数据格式**：大多数微调框架要求数据以指令-响应（instruction-response）对的形式组织
2. **数据清洗**：移除重复项、低质量样本和不相关内容
3. **数据平衡**：确保不同类型的样本分布合理
4. **数据量**：
   - 最少约 100-500 条高质量样本可以开始看到效果
   - 1000-10000 条样本通常能产生显著改善
   - 超过一定数量后，质量比数量更重要

### 超参数调优

微调过程中需要关注的关键超参数：

| 超参数 | 说明 | 典型值 |
|--------|------|--------|
| **学习率（Learning Rate）** | 控制每次权重更新的步长 | 1e-5 到 5e-5 |
| **训练轮数（Epochs）** | 完整遍历训练数据的次数 | 1-5 轮 |
| **批次大小（Batch Size）** | 每次训练步骤处理的样本数 | 4-32 |
| **权重衰减（Weight Decay）** | 正则化参数，防止过拟合 | 0.01-0.1 |
| **Warmup Steps** | 学习率从零逐渐增大的步数 | 总步数的 5-10% |

### 过拟合风险

微调最常见的风险是**过拟合**——模型过度记忆训练数据，丧失泛化能力。防范措施包括：

- 使用验证集监控训练过程中的性能变化
- 早停策略（Early Stopping）：当验证集性能不再提升时停止训练
- 适当的学习率和训练轮数
- 数据增强和正则化技术

### 参数高效微调（PEFT）

对于大型模型，全参数微调的计算成本极高。PEFT 技术通过只训练少量参数来降低成本：

- **LoRA（Low-Rank Adaptation）**：在模型权重矩阵旁添加低秩矩阵，仅训练这些低秩矩阵
- **QLoRA**：在 LoRA 基础上结合量化技术，进一步降低内存需求
- **Adapter**：在模型层之间插入小型适配器模块

## 知识检查

**问题**：微调与提示工程的根本区别是什么？

1. 微调通过修改提示词来改善输出，而提示工程通过重新训练模型来提升性能
2. 微调通过使用额外数据重新训练模型本身来提升性能，而提示工程仅通过修改提示输入来改善输出
3. 两者本质相同，只是使用的数据量不同

**答案**：2

**解析**：

微调（Fine-tuning）是一种从根本上不同的方法——它通过使用额外数据重新训练模型本身来提升模型在特定任务上的表现。而提示工程（包括少样本学习和 RAG）都是通过修改模型的提示输入来改善输出质量，不改变模型本身。两者在技术原理、成本结构和适用场景上都有本质区别。
