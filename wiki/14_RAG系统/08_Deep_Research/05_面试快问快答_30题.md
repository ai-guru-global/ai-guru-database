## 一、基础与定位（1–6）

**1. Deep Research 和 RAG 的本质区别？**
**检索决策权归属不同**——RAG 是固定流水线查一次，Deep Research 由模型规划整个研究计划并迭代补检；RAG 解决「知识在哪」，Deep Research 解决「研究怎么做」。

**2. 和 Agentic RAG 又差在哪？**
**循环长度与目标形态不同**——Agentic RAG 是 2–5 轮的「要不要再查一次」循环，输出还是答案；Deep Research 是 10–100+ 次检索的长程循环，输出是带引用地图的报告。

**3. 为什么 Deep Research 必须用推理模型驱动？**
**循环里的每一步都是长推理任务**——拆子问题、检测信息缺口、裁决信源冲突，非推理模型只能做「搜三次拼答案」，循环直接退化。

**4. 为什么它是 Web Agent 里最先大规模商业化的形态？**
**动作空间天然可验证、风险低**——搜索和阅读不像点击 GUI 那样有破坏性，错了最多浪费钱，所以产品敢先放开。

**5. 一句话给非技术同学解释 Deep Research？**
**像一个带实习生的分析师团队**——你说题目，它列提纲、分工查资料、互相核对来源，几分钟后给你一份带脚注的报告。

**6. 和 Computer Use 什么关系？**
**同一谱系的两端**——Deep Research 动作收敛在搜索阅读（低风险、可验证），Computer Use 操作任意 GUI（通用、高风险）；前端代理执行平台时两者会合流。

## 二、规划器（7–11）

**7. 为什么规划前要先澄清提问？**
**阻塞歧义会放大成整份报告的偏差**——时间范围、地域口径没定，后面所有检索都白跑；但澄清 ≤ 2 个问题，非阻塞歧义自行假设并声明。

**8. 子问题拆解的原则？**
**MECE + 依赖排序**——相互独立、合起来覆盖原问题；把阻塞性子问题排前面，让前置结论参与后续查询生成。

**9. 什么时候触发重规划？**
**环境证明计划错了才重规划**——关键子问题连续失败、发现计划外重要维度；每次重规划必须回锚原始问题，防止计划本身漂移。

**10. 过度分解的症状和危害？**
**20 个子问题的报告是拼凑清单**——子问题过多导致上下文互相稀释、任务漂移，控制在 3–8 个，宁可两轮计划。

**11. 「计划回锚」怎么做？**
**研究计划常驻上下文 + 每节综合前重读原始问题**——窗口里的阅读内容会冲淡规划状态，锚定物必须在场，这是防漂移的第一手段。

## 三、检索编排（12–17）

**12. multi-query 扩展为什么必要？**
**单一查询 = 单一信源生态**——同义改写 + 角度切换（数据/案例/反方）各来一路，才打破信源单一化。

**13. 并行度设多少？**
**4–8 路**——再高触发搜索 API 限速，且结果在窗口里相互覆盖；并行度是墙钟时间的第一杠杆。

**14. 信息增益饱和怎么判定？**
**新笔记占已有笔记比例 < 10%（经验值）即停**——配合硬预算双闸：宁可报告单薄，不可循环失控。

**15. 笔记本外置（scratchpad）解决什么问题？**
**几十个网页塞爆窗口**——逐页抽取写结构化笔记，窗口只留笔记与计划状态；它同时是省 token 的第一杠杆。

**16. 信源单一化怎么治？**
**配额制**——每个子问题强制至少 2 个独立域名，报告层再统计域名分布做监控。

**17. 搜索 API 和无头浏览器怎么选？**
**API 为主、浏览器兜底**——API 快且便宜但拿不到动态页；无头浏览器慢 10 倍、要管指纹与反爬，只给 JS 渲染页用。

## 四、交叉验证与引用（18–22）

**18. claim→source 映射为什么是核心数据结构？**
**它是引用准确率的物理保证**——综合阶段只允许从映射表取引用编号，模型凭记忆写链接的通道被关死。

**19. 多源一致的判定标准？**
**关键论断 ≥ 2 个独立信源**——注意「独立」指不同域名且非转载关系，两家媒体转同一条通稿只算一个源。

**20. 信源冲突的四类处理策略？**
**数值取权威并标注分歧、时间取新注明截至、观点并列标立场、无法判定显式存疑**——原则：显式存疑好过静默选边。

**21. 引用幻觉的根因和根治手段？**
**根因是综合时模型凭记忆补链接**——根治是结构化约束：引用编号只能来自 evidence 映射表，「无引用不落笔」写进系统提示。

**22. 高载荷单源论断怎么办？**
**降级或补检**——要么触发一轮定向补检索找第二信源，要么在报告里显式标注「单一信源，待核」。

## 五、评测与失败模式（23–26）

**23. GAIA 和 BrowseComp 各考什么？**
**GAIA 考通用助手多步能力（466 题分三级），BrowseComp 考浏览坚持度（1,266 题、简单检索刻意失效）**——前者像试用期考卷，后者专测「查得到吗」。

**24. 为什么 RAGAS 不能直接评 Deep Research？**
**评估对象变了**——RAGAS 评「生成与给定上下文的一致性」，Deep Research 要评「生成与真实世界的一致性」，单位从问答降到论断和引用。

**25. 失败归因怎么做？**
**四分类标注：规划错 / 检索漏 / 验证松 / 综合编**——四类修法完全不同（改计划策略 / 补检索源 / 加验证规则 / 加引用约束），混在一起修等于瞎修。

**26. 报告质量怎么评才不主观？**
**LLM-as-Judge 打结构化 rubric + 人类盲评兜底**——rubric 评结构/深度/可读性，人类盲评防「指标好但体验差」。

## 六、工程与选型（27–30）

**27. 自建还是采购？**
**按「时延 × 成本 × 数据敏感度」三角定**——通用研报直接调产品 API；数据敏感或高频调用走自建（开源框架起步，模型可换 Tongyi 权重）。

**28. 本地复现的最低配置？**
**32B 级模型做规划 + 免费搜索 API + depth 2 / breadth 4 的递归循环**——24GB 内存机器可跑；最常见的翻车点是用小模型做规划，分解质量撑不住。

**29. 间接提示注入怎么防？**
**内容沙箱 + 来源分级 + 指令剥离**——网页内容是数据不是指令，检索进来的文本不得触发工具调用；高危场景给来源设白名单。

**30. 2026 的业态方向？**
**API 化（成为其他 Agent 调用的原语）+ 垂域化（金融/医药/法律研报）+ 与记忆系统结合（研究员画像跨会话累积）**——从产品功能变成 Agent 生态的基础设施。
