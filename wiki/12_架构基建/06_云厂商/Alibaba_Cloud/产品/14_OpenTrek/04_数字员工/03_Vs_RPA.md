# OpenTrek 数字员工与 RPA 之辨

> 中文简称：数字员工与 RPA 之辨

> **一句话理解**: RPA 是照着写死的说明书一步步操作的机器人，数字员工是给个目标自己去想办法、还能攒经验的员工。

---

## 一、基本差异总览

先给七维总览，再挑最容易踩坑的两个维度（触达、容错）展开：

| **维度** | **传统 RPA** | **数字员工** |
| --- | --- | --- |
| **驱动方式** | 规则驱动：按预设脚本执行 | 目标驱动：自规划任务路径 |
| **维护方式** | 脚本维护：流程变更需人工修改 | 记忆进化：从运行历史中沉淀改进 |
| **触达方式** | 以界面抓取为主，界面改版即受影响 | 以 API/工具调用为主，接口稳定时更耐用 |
| **运行形态** | 定时或触发式任务执行 | 常驻沙箱 7×24 小时工作 |
| **能力扩展** | 靠新增脚本 | 靠 Skills Hub 增配技能 |
| **场景迁移成本** | 流程或界面变化即失效，迁移成本高 | 目标不变时对流程变化容忍度更高 |
| **容错方式** | 异常即中断，人工处理后重跑 | 可重试、可换路径、可上报，容错空间更大 |

注意：以上为**定性对比**，基于两类产品的工作原理差异，不代表具体项目的量化结论。「触达方式」「容错方式」两行为本页深化项（分析视角）：RPA 的经典短板是依赖界面抓取、界面一改就断；数字员工的常规触达是 API/工具调用，异常时有规划与重试的空间。RPA 在高确定性、强合规的规则化场景仍有成本与稳定性优势，两者是互补而非替代关系。

---

## 二、逐维深化：触达脆弱性与容错

**触达脆弱性（分析视角）**：RPA 通过模拟人操作界面完成任务，天然绑定具体界面结构——按钮挪位、流程多一步确认，脚本就断。数字员工以工具调用为主要触达（查知识库、调 API、用 Skill），接口语义比界面坐标稳定；但对没有 API 的老旧系统，数字员工同样面临触达难题（见第四节混合形态）。

一个对比例子（分析视角）：同样「每月从三个系统取数合并报表」——RPA 的做法是写死每个系统的取数脚本，系统改版即重写；数字员工的做法是给目标 + 挂接三个系统的取数 Skill，取数路径由规划决定，某个系统改版时只需更新对应 Skill。

**维护与容错（分析视角）**：RPA 的维护单位是脚本——流程变更即改脚本，异常即中断等人工。数字员工的维护单位是「目标 + 记忆」：流程小变时靠自规划吸收，异常时可以换路径重试或上报人审；但这也意味着行为不完全可预测，需要靠沙箱隔离与审批边界兜底——可控性的实现方式从「脚本确定性」换成了「环境隔离 + 人审门」。

维护成本的量级感（分析视角，定性）：RPA 的成本随「流程 × 界面版本数」增长，数字员工的成本集中在「技能建设 + 记忆治理」——前者怕变化，后者怕失管。

一句话记住权衡：RPA 用「确定性」换「脆弱」，数字员工用「柔性」换「不确定性管理成本」。

## 三、何时仍选 RPA

```text
选型速记（定性）：流程高度固定、界面稳定 → RPA 仍划算
目标明确、路径多变、需要持续积累经验 → 数字员工更合适
```

RPA 仍是更优解的场景（分析视角展开）：

- **高确定性结构化流程**：输入输出格式固定、规则完全可枚举（批量对账、定时报表搬运），RPA 更省、更稳。
- **无 LLM 必要的场景**：任务不需要理解非结构化输入（自然语言、文档、邮件），引入大模型只增加成本与不确定性。
- **强合规留痕要求**：需要每一步可复现、可审计到指令级时，脚本执行比自规划路径更贴合。

反向提醒（分析视角）：不要因为「智能化」潮流把确定性流程硬塞给数字员工——大模型调用有成本，非必要不上；同理，也不要把模糊多变的任务硬塞给 RPA，脚本维护成本会吞掉自动化收益。

---

## 四、混合形态：RPA 作为数字员工的手脚（分析视角）

两者不是二选一。合理的混合形态是：**数字员工做大脑，RPA 做手脚**——

- 数字员工负责理解非结构化输入（邮件、单据、口述需求）、规划步骤、处理异常。
- 对只有界面可操作的老旧系统，把既有 RPA 机器人封装成一个 Skill/工具，由数字员工在规划中调用。
- 确定性环节交给 RPA 执行（快且稳定），模糊环节留给数字员工判断，异常回流人审。

这种形态的收益：存量 RPA 资产不被丢弃，而是被「编排」进智能体工作流；数字员工获得触达无 API 系统的能力。前提是 RPA 调用本身有权限与审计控制——手脚可以借，缰绳要在人手里。

## 五、选型问句表

| **选型问句** | **答「是」的倾向** | **说明** |
| --- | --- | --- |
| **流程高度固定、输入高度结构化吗？** | RPA | 规则可枚举时脚本更稳更省 |
| **需要理解非结构化输入吗？** | 数字员工 | 邮件、文档、自然语言是 LLM 主场 |
| **目标明确但路径多变吗？** | 数字员工 | 自规划 + 记忆进化的适用区 |
| **需要 7×24 常驻并越用越好吗？** | 数字员工 | 常驻沙箱 + 记忆体是前提 |
| **目标系统无 API 且界面稳定吗？** | RPA 或混合 | 界面稳定时 RPA 可行；界面也多变则考虑混合形态 |
| **每一步都要指令级可复现审计吗？** | RPA | 脚本确定性天然贴合强合规 |

用法建议（分析视角）：逐问打分而不是拍脑袋——前四问决定主形态，后两问决定是否混合与人审强度；同一企业内两类工具并存是常态，关键是各自待在合适的场景里。
