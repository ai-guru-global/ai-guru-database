# 提示词工程完整指南：核心技术与设计模式

> 中文简称：提示词工程完整指南：核心技术与设计模式

本文融合《大模型提示词工程指南》第 1-7 章的核心知识，系统讲解提示词的结构设计、最佳实践、少样本学习、思维链推理、提示词链与任务分解等核心技术。

## 1. 提示词的六大核心要素

一个结构完整的提示词通常由以下六大要素组成：

| 要素 | 功能 | 设计要点 |
|------|------|----------|
| **角色/身份** | 设定专业领域和行为风格 | 复合角色、视角限定 |
| **任务指令** | 定义目标和具体操作 | 使用动词开头、分步表达 |
| **上下文** | 提供背景知识和约束条件 | 相关性、准确性、简洁性 |
| **输入数据** | 待处理的具体内容 | 用分隔符或标签明确边界 |
| **输出格式** | 定义回复的结构和风格 | JSON/XML/Markdown/列表 |
| **示例** | 展示期望的输入输出对 | 代表性、多样性、一致性 |

### 完整提示词示例

```text
# 角色
你是一位专业的产品评论分析师，擅长从用户评论中提取洞察。

# 任务
分析电商平台的产品评论，提取关键信息并进行情感分类。

# 上下文
- 这是一款新上市的无线蓝牙耳机
- 分析结果将用于产品改进决策
- 需要识别的维度：音质、舒适度、续航、价格

# 输出格式
请以 JSON 格式输出：
{
  "overall_sentiment": "正面/负面/中性",
  "dimensions": {
    "音质": {"sentiment": "...", "comment": "..."},
    "舒适度": {"sentiment": "...", "comment": "..."}
  },
  "improvement_suggestions": ["建议 1", "建议 2"]
}

# 示例
输入：音质很棒，低音很有力，就是戴久了耳朵有点疼。
输出：{
  "overall_sentiment": "正面",
  "dimensions": {
    "音质": {"sentiment": "正面", "comment": "低音表现好"},
    "舒适度": {"sentiment": "负面", "comment": "长时间佩戴不适"}
  },
  "improvement_suggestions": ["优化耳罩材质提升舒适度"]
}

# 待分析评论
"""
买来一个月了，音质确实可以，降噪效果也不错...
"""
```

## 2. 指令设计七大原则

### 2.1 清晰明确
避免模糊表达，具体化任务目标：
```text
❌ 写一些关于这个产品的内容
✓ 为这款智能手表撰写一段 100 字的产品卖点描述
```

### 2.2 具体细致
量化要求、定义质量标准：
```text
❌ 列出一些建议
✓ 列出 5 条具体可行的改进建议，每条包含：具体措施、预期效果、实施难度（高/中/低）
```

### 2.3 行动导向语言
使用明确的动词开始指令：

| 动词类别 | 示例 | 适用场景 |
|----------|------|----------|
| 生成类 | 写、创建、生成、设计 | 内容创作 |
| 分析类 | 分析、评估、比较、诊断 | 数据分析 |
| 转换类 | 翻译、转换、改写、简化 | 格式转换 |
| 提取类 | 提取、总结、归纳、识别 | 信息抽取 |

### 2.4 逻辑顺序
按时间序列、层次结构或优先级结构组织指令。

### 2.5 正向表达
告诉模型"应该做什么"比"不要做什么"更有效：
```text
❌ 不要使用复杂的专业术语
✓ 使用通俗易懂的日常语言
```

### 2.6 考虑边界情况
预先处理不确定性、缺失信息和多种可能。

### 2.7 迭代优化
```text
初始指令 → 测试输出 → 识别问题 → 调整指令 → 再次测试 → ...
```

## 3. 角色设定与人格赋予

### 角色设定的层次

**基础层：简单角色标签**
```text
你是一位 Python 编程专家。
```

**中级层：角色+背景+风格**
```text
你是一位拥有 10 年经验的前端开发工程师，专注于 React 和 Vue 框架。
回答问题时，偏好给出可运行的代码示例，并解释关键技术决策的原因。
```

**高级层：完整角色画像**
```markdown
# 角色定义：企业培训顾问

## 身份背景
资深企业培训师，15 年培训行业经验...

## 核心能力
- 培训需求诊断
- 课程设计与开发
- 培训效果评估

## 沟通风格
- 专业但平易近人
- 善于使用案例和类比

## 行为准则
- 建议须基于成熟的管理理论和实践
- 承认培训有其局限性，不夸大效果
```

### 多角色协作
```text
请从以下三个角色的视角分析这个商业决策：
1. 【CFO 视角】关注财务可行性和 ROI
2. 【CTO 视角】关注技术实现和资源需求
3. 【CMO 视角】关注市场影响和品牌价值
最后，作为 CEO 综合三方意见给出决策建议。
```

## 4. 系统提示词设计

### 结构化系统提示词四模块

```markdown
[身份与使命]
你是一位拥有 10 年经验的资深 Python 架构师。
你的使命是帮助初级开发者审查代码。

[行为准则]
1. 【防御性代码】始终考虑空指针和异常处理
2. 【不知为不知】涉及不熟悉的业务逻辑时直接询问
3. 【代码安全】拒绝审查恶意代码

[审查规则清单]
- Step 1: 检查 PEP8 规范
- Step 2: 评估时间和空间复杂度
- Step 3: 检查单元测试

[输出格式]
## 代码总评
[百字以内的概述]
## 改进建议
1. **[行号/函数名]**: [问题] -> [建议]
```

### 长系统提示词管理
- **模块化拼接**：分为 base_prompt、dynamic_context、user_preferences
- **使用分隔符建立层次**：防止"注意力漂移"（Lost in the middle）
- **核心指令后置**：将关键格式约束放在最末尾，提升遵循概率

### IDE 集成方案
- **CLAUDE.md**（Claude Code）：项目根目录定义系统上下文
- **.cursorrules**（Cursor IDE）：AI 助手行为约束
- **AGENTS.md**（Codex）：多智能体协作系统提示词

## 5. 少样本学习（Few-Shot Learning）

### 三种提示方式对比

| 特性 | 零样本 | 单样本 | 少样本 |
|------|--------|--------|--------|
| 示例数量 | 0 | 1 | 2-6+ |
| 指令依赖 | 高 | 中 | 低 |
| 格式一致性 | 低 | 中 | 高 |
| Token 消耗 | 最低 | 低 | 较高 |

### 选择策略
- **零样本**：任务定义清晰、模型已熟悉、格式灵活、快速验证
- **少样本**：任务规则复杂、需要边界处理、高一致性要求、非标准任务

### 示例设计四原则
1. **代表性**：选择常见的典型情况
2. **多样性**：覆盖不同类型或情况
3. **清晰性**：正确、清晰、无歧义
4. **一致性**：所有示例遵循相同格式

### 示例选择策略

**覆盖边界情况**
```text
任务：判断年龄是否成年（>=18 岁）
常规示例：25 岁 → 成年、10 岁 → 未成年
边界示例：18 岁 → 成年（边界值）、无年龄信息 → 无法判断（异常）
```

**动态示例选择**
```text
1. 接收用户输入
2. 从示例库中检索与输入最相似的 N 个示例
3. 将这些示例组装进提示词
4. 发送给模型处理
```

### 上下文学习的本质
少样本学习是**上下文学习**——模型在推理时通过示例"临时学习"任务规则，而无需更新模型参数。示例的核心价值在于定位任务模式，而非提供知识。

## 6. 思维链与推理增强（Chain-of-Thought）

### CoT 的核心机制

思维链通过引导模型展示中间推理步骤来提升复杂任务表现：
```text
问题：商店有 23 个苹果，卖出了 15 个，又进货了 12 个，现在有多少个？

让我们一步步思考：
1. 初始数量：23 个
2. 卖出后剩余：23 - 15 = 8 个
3. 进货后总数：8 + 12 = 20 个

答案：20 个
```

### 为什么有效
1. **分解复杂问题**：将大问题拆分为简单子问题
2. **利用中间结果**：生成的中间步骤成为后续推理的上下文
3. **激活训练模式**：激活模型在训练时接触的推理过程
4. **以长度换深度**：将"压缩式"推理转化为分步执行

### 与模型规模的关系
- 小模型（<10B）：效果有限
- 中型模型（10-50B）：有一定提升
- 大模型（>50B）：效果显著
- **注意**：2024 年后，通过 SFT/distill 等技术，小模型也能获得稳定的 CoT 能力

### 自一致性（Self-Consistency）
通过生成多条推理路径并进行一致性投票提升可靠性：

```python
def self_consistency(prompt, question, n_samples=5):
    answers = []
    for i in range(n_samples):
        response = call_llm(prompt + question, temperature=0.7)
        answer = extract_answer(response)
        answers.append(answer)
    
    from collections import Counter
    vote = Counter(answers)
    final_answer = vote.most_common(1)[0][0]
    confidence = vote.most_common(1)[0][1] / n_samples
    return final_answer, confidence
```

**采样策略**
- 简单问题：3-5 次采样
- 中等问题：5-10 次采样
- 困难问题：10-20 次采样
- Temperature 推荐：0.5-0.8

### 思维树（Tree of Thoughts）
将推理组织为树形结构，在每个决策点探索多个方向：

```text
你需要解决一个问题。请使用以下方法：

1. 生成阶段：列出 3 个可能的解决方向
2. 评估阶段：给每个方向评分（1-10）并说明理由
3. 选择阶段：选择最有前途的方向继续深入
4. 重复直到找到解决方案
```

### 推理策略选择
| 问题类型 | 推荐策略 |
|----------|----------|
| 简单推理 | 标准思维链 |
| 需要探索多个方案 | 思维树 |
| 需要反复优化 | 递归自我改进 |
| 大问题可分解 | 分解-组合 |
| 需要全面视角 | 多视角推理 |
| 需要高可靠性 | 自一致性 |

## 7. 提示词链与任务分解

### 六大设计模式

#### 模式一：顺序链
前一步的输出是后一步的输入，适用于流水线式处理。
```text
步骤 1：文档预处理 → 清理后的文本
步骤 2：关键信息提取 → 关键信息列表
步骤 3：摘要生成 → 最终摘要
```

#### 模式二：分支链
根据条件选择不同的处理路径：
```python
def process_query(user_input):
    intent = classify_intent(user_input)
    if intent == "product_inquiry":
        return handle_product_inquiry(user_input)
    elif intent == "order_status":
        return handle_order_status(user_input)
    elif intent == "complaint":
        return handle_complaint(user_input)
    else:
        return handle_general(user_input)
```

#### 模式三：并行链
多个步骤同时执行，最后合并结果：
```text
并行任务：
任务 A：情感分析 → {"sentiment": "positive", ...}
任务 B：主题提取 → {"topics": ["质量", "价格"], ...}
任务 C：建议提取 → {"suggestions": ["改进包装"], ...}
合并步骤：综合三个分析结果生成完整报告
```

#### 模式四：循环链
重复执行直到满足条件：
```text
初始文本 → 改写版本 1 → 质量评估(不满足)
                          ↓
          改写版本 2 ← 反馈优化方向
                ↓
          质量评估(满足) → 输出最终版本
最大迭代次数限制：3 次
```

#### 模式五：验证链
生成结果后进行验证，必要时重新生成：
```text
步骤 1：生成 JSON
步骤 2：验证
检查项：
- JSON 格式是否有效？
- 必填字段是否完整？
- 字段值是否在有效范围？
验证通过 → 返回结果
验证失败 → 附带错误信息重新生成（最多 3 次）
```

#### 模式六：层级链
多层级的任务分解和执行：
```text
主控：报告规划
├── 子链 1：数据收集与处理
│   ├── 数据提取
│   └── 数据清洗
├── 子链 2：分析模块
│   ├── 趋势分析
│   ├── 对比分析
│   └── 异常检测
└── 子链 3：报告生成
    ├── 内容撰写
    ├── 图表建议
    └── 格式化输出
```

### 模式选择指南
| 任务特征 | 推荐模式 |
|----------|----------|
| 线性处理流程 | 顺序链 |
| 需要根据类型分类处理 | 分支链 |
| 多个独立分析可并行 | 并行链 |
| 需要迭代优化 | 循环链 |
| 输出需要验证 | 验证链 |
| 多层级复杂任务 | 层级链 |

## 8. 结构化输出设计

### 主流格式对比

| 格式 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| JSON | 生态最完善，OpenAI 有特殊优化 | 括号引号占用 Token | API 交互、数据抽取 |
| XML | 结构清晰，Claude 原生偏好 | 闭合标签占用 Token | Claude 任务、长文本处理 |
| YAML | Token 消耗最少，人类可读性佳 | 缩进敏感 | 配置生成 |
| Markdown | 最自然的输出方式 | 解析成结构化数据较复杂 | 表格、报告 |

### JSON 输出三步法

**1. 明确的输出指令**
```text
✅ 正确示范：
你是一个数据提取 API。请严格以 JSON 格式输出结果。
你的输出必须是合法的、可解析的单一 JSON 对象，不要包含任何自然语言解释。
```

**2. 提供 JSON Schema**
```json
{
  "user_intent": "提取的用户意图（字符串）",
  "confidence_score": 0.95,
  "extracted_entities": [
    {
      "entity_type": "实体类型：'PERSON', 'LOCATION', 'DATE'",
      "entity_value": "实体具体内容（字符串）"
    }
  ]
}
```

**3. 设计容错逃生通道**
```json
{
  "success": true,
  "error_message": null,
  "data": { ... }
}
```

### 错误处理策略
1. **自动清理**：使用正则剥离多余前缀/后缀
2. **多重重试机制**：解析失败触发重试
3. **反射纠错**：将报错信息重新发给 LLM 修复
