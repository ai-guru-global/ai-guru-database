## 政企安全的特殊性

政企客户的安全要求不是"best practice"，而是"**合规底线**"。不满足 = 项目直接否决。

## 安全六层模型

```
Layer 6: 审计合规层 ← 等保、信创、行业监管
Layer 5: 数据安全层 ← 加密、脱敏、防泄漏
Layer 4: 应用安全层 ← 输入校验、注入防护
Layer 3: 网络安全层 ← 防火墙、VPN、微分段
Layer 2: 身份认证层 ← SSO、MFA、权限最小化
Layer 1: 物理安全层 ← 机房、机柜、硬件加密
```

## 等保 2.0 三级要求速查

| 要求 | FDE 需要做什么 |
|---|---|
| 身份鉴别 | 对接客户 LDAP/SSO，强制密码复杂度 |
| 访问控制 | RBAC 权限模型，最小权限原则 |
| 安全审计 | 全量操作日志，不可删除/修改 |
| 入侵防范 | 最小化攻击面，只开放必要端口 |
| 数据完整性 | 数据传输/存储校验 |
| 数据保密性 | 传输加密（TLS）+ 存储加密（AES） |
| 剩余信息保护 | 用户登出后清除敏感缓存 |
| 通信保密性 | 全链路 TLS，支持国密 |

## 国密算法适配

```
国际算法 → 国密算法 对照：

RSA/ECDSA → SM2（非对称加密/签名）
AES → SM4（对称加密）
SHA-256 → SM3（哈希）
— → SM9（基于身份的密码）

FDE 需要确保：
├── TLS 支持国密套件（通过 Tongsuo/GmSSL）
├── 数字签名支持 SM2
├── 文件加密支持 SM4
└── 哈希校验支持 SM3
```

## FDE 安全 Checklist

### 部署前
- [ ] 确认客户安全合规要求（等保级别/信创要求）
- [ ] 确认数据传输和存储加密要求
- [ ] 确认审计日志范围和保留期限
- [ ] 获取客户安全团队对方案的书面认可

### 部署中
- [ ] 所有服务使用非 root 用户运行
- [ ] 只开放必要端口（Nginx: 80/443, API: 内网）
- [ ] Docker 容器启用安全配置（no-new-privileges）
- [ ] API 强制鉴权（无鉴权接口为 0）
- [ ] 数据库密码/API Key 使用 K8s Secret 或环境变量
- [ ] 日志中过滤敏感信息（密码/手机号/身份证）

### 交付时
- [ ] 渗透测试报告（至少基础扫描）
- [ ] 安全加固报告
- [ ] 应急预案（含安全事件处理流程）
- [ ] 安全运维手册

## 常见安全失误

| 失误 | 后果 | 预防 |
|---|---|---|
| 用默认密码部署 | 极易被入侵 | 强制首次登录改密 |
| 日志打印敏感信息 | 信息泄露 | Code Review + 自动化扫描 |
| 未关闭 DEBUG 模式 | 暴露内部信息 | 生产环境配置检查 |
| 端口全开 | 攻击面大 | 最小化开放端口 |
| 未做 SQL 注入防护 | 数据库被拖库 | ORM 参数化查询 |

> **安全铁律**：在政企项目中，**安全合规是门票，不是加分项**。没有门票，技术再强也进不了门。
