# FDE 解决方案能力

## 解决方案能力的定位

占 FDE 能力的 **30%**。位于工程能力和业务能力的交叉点——**把业务问题翻译成技术方案，再把技术方案落地为可运行系统**。

## 核心能力维度

### 1. 架构设计

**FDE 架构设计的特殊性**：不是设计"理想架构"，而是设计"能在客户环境落地的架构"。

| 考虑因素 | 问题 | 示例 |
|---|---|---|
| 客户现有系统 | 能不动就不动 | 对接现有 SSO 而非新建 |
| 网络环境 | 内网/无互联网/防火墙 | 离线部署方案 |
| 硬件限制 | 可能只有 CPU 服务器 | CPU 推理优化 |
| 运维能力 | 客户团队能维护什么 | 简化运维复杂度 |
| 合规约束 | 数据不能出某区域 | 全链路内网部署 |

**常见架构模式**：

```
模式 1：轻量级 RAG 部署
客户环境 → [Nginx] → [FastAPI + LangChain] → [Milvus] + [Ollama]
适合：知识库问答、客服 AI

模式 2：企业级 AI 平台
客户环境 → [K8s 集群] → [AI Gateway] → [多模型服务] + [向量库集群]
适合：大型政企/金融客户

模式 3：混合部署
客户内网（推理 + 数据） ↔ 云端（模型更新 + 监控）
适合：允许部分数据出网的场景
```

### 2. 技术选型

**FDE 技术选型原则**：

| 优先级 | 原则 | 说明 |
|---|---|---|
| 1 | **能跑起来** | 不要选客户环境不支持的技术 |
| 2 | **客户能维护** | 客户团队能接手运维 |
| 3 | **稳定优先** | 新技术很好但 bug 也很多 |
| 4 | **信创兼容** | 能跑在国产 CPU/OS 上 |
| 5 | **成本可控** | 开源优先，商业版酌情 |

### 3. 风险识别与管理

**FDE 项目常见风险**：

| 风险类型 | 典型表现 | 缓解策略 |
|---|---|---|
| 数据风险 | 数据质量差/格式乱/有隐私问题 | 提前做数据评估 |
| 集成风险 | 老系统的 API 不工作 | 预留集成缓冲时间 |
| 性能风险 | 客户硬件太弱 | 提前做性能基准测试 |
| 人员风险 | 关键对接人离职 | 要求多方对接 |
| 范围风险 | 需求不断蔓延 | 严格的 scope 文档 + 变更流程 |
| 合规风险 | 突然增加合规要求 | 提前了解合规底线 |

### 4. 方案沟通能力

**不同对象，不同语言**：

| 对象 | 关注点 | 沟通方式 |
|---|---|---|
| CEO/一把手 | ROI、战略价值、风险 | 一页纸总结 + 三句话讲清楚 |
| CIO/CTO | 技术可行性、架构 | 架构图 + 技术选型理由 |
| 业务负责人 | 业务流程改善 | 场景演示 + 前后对比 |
| IT 运维 | 运维复杂度、安全 | 部署文档 + 安全方案 |
| 最终用户 | 好不好用 | 产品 demo + 操作培训 |

---

> **核心**：FDE 的解决方案能力 = 把模糊需求转化为清晰方案 + 在受限环境中找到可行路径 + 让各方都理解并认同方案
