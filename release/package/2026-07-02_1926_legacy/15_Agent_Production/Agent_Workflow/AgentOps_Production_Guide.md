## 1. 开发框架全景与选型

### 1.1 六种框架形态

| 形态 | 代表框架 | 核心特征 | 适用场景 |
|------|---------|---------|---------|
| **A. 链式编排** | LangChain LCEL, Haystack | 固定顺序串联调用 | 简单线性管道 |
| **B. 图编排/状态机** | LangGraph, LlamaIndex Workflows | 条件路由、循环、检查点、中断恢复 | 企业级业务流 |
| **C. 多智能体协作** | CrewAI, AG2/AutoGen | 角色分工、对话/任务编排 | 创意/自动化流程 |
| **D. 数据/RAG 驱动** | LlamaIndex | 索引/检索/权限隔离为一等公民 | 知识密集型任务 |
| **E. 企业级 SDK** | Microsoft Agent Framework | 身份、权限、审计、治理为核心 | 既有系统集成 |
| **F. 低代码平台** | Dify, LangFlow, Flowise | 可视化拖拽, 零/低代码 | 快速原型 |

### 1.2 选型决策矩阵

| 维度 | 链式 | 图编排 | 多智能体 | 数据/RAG | 企业级 SDK |
|------|------|--------|---------|---------|-----------|
| 可控性 | 中 | **高** | 中-高 | 中 | **高** |
| 易用性 | **高** | 中 | 中 | 中 | 中 |
| 代码闭环 | 依赖外部 | 可集成 | **强** | 依赖外部 | 可集成 |
| 知识检索 | 依赖外部 | 依赖外部 | 依赖外部 | **强** | 依赖外部 |
| 治理审计 | 依赖外部 | 可增强 | 需额外设计 | 需额外设计 | **强** |

### 1.3 选型建议

1. **企业级业务流** (审批/客服): 优先图编排/状态机
2. **知识密集型** (法律/政策): 优先数据/RAG 驱动
3. **创意自动化** (内容/运营): 优先角色任务编排
4. **代码生成执行闭环**: 优先沙箱执行 + 评审回路
5. **传统企业集成**: 优先企业级 SDK/连接器

> **核心定律**: 智能体本质是 While 循环, 框架只是封装了循环里的脏活累活。理解底层 Prompt 设计、工具调用和记忆管理才是核心。

### 1.4 多智能体框架实战

#### 对话编排范式 (对话即计算)

核心: 规划/生成智能体 + 执行智能体, 在沙箱中 "生成->执行->反馈->修复" 闭环

**风险提示**:
- 成本失控: 重试循环中 Token/工具成本飙升, 需步数上限与熔断
- 安全边界: 执行必须在沙箱内, 对文件/网络/高风险操作设硬限制

#### 角色任务编排范式

三个核心问题:
1. **Who**: 角色、目标、背景设定
2. **What**: 任务描述、预期输出
3. **How**: 顺序式或层级式流程

**生态现状** (2026):
- Microsoft AutoGen -> maintenance mode, 新项目转向 Microsoft Agent Framework
- AG2 (formerly AutoGen) 为社区主线
- CrewAI 稳定在 1.14.x

## 2. AgentOps 设计模式

### 2.1 静态编排 vs 自主编排

| 维度 | 静态编排 (Code-driven) | 自主编排 (Model-driven) |
|------|----------------------|----------------------|
| 核心 | 代码预定义执行路径 | LLM 自主决定步骤 |
| 可控性 | **高** | 低 |
| 适应性 | 低 | **高** |
| 适用 | 可清晰分解的任务 | 未知/动态情况 |

> 实践中两者结合: 越接近自主编排越灵活但不可控; 越接近静态编排越稳定但泛化弱。

### 2.2 六种核心设计模式

#### (1) 提示词链 (Prompt Chain)

```
Input -> LLM(生成大纲) -> LLM(扩写内容) -> LLM(格式化) -> Output
```

- 每个节点可用不同规格模型
- 风险: 中间错误级联传导

#### (2) 路由分发 (Router)

```
Input -> Router LLM -> 类型 A (客服) / 类型 B (销售) / 复杂 (高级智能体)
```

- Router 可以是微调分类小模型或 Embedding 匹配
- 模型分层: 简单问题 -> 低成本模型, 复杂问题 -> 高质量模型

#### (3) 并行执行

- **切片**: 大任务拆解为独立子任务并行 (安全/性能/风格同时检查)
- **投票**: 同一任务多次运行, 多数票减少幻觉

#### (4) 编排者-工作者 (Orchestrator-Workers)

- 中心编排者动态分派任务给 Worker
- Worker 执行后汇报结果
- 适合子任务无法预知或需动态生成的场景

#### (5) 评估者-优化者 (Evaluator-Optimizer)

```
Generator -> Evaluator -> (不满意) -> Generator (改进) -> ... -> (满意) -> Output
```

- 两个独立 LLM: 一个生成, 一个评审
- 适合质量要求高的场景 (代码审查、文案创作)

#### (6) 自主智能体 (Autonomous Agent)

```
Goal -> Think -> Act -> Observe -> Think -> ... -> Result
```

- 完整 ReAct 循环, 最大自主度
- 需要完善的护栏和可观测性

## 3. Harness 架构: 执行与治理层

### 3.1 什么是 Harness

> **模型是 CPU, 上下文窗口是 RAM, Harness 是操作系统。**

```
Agent = Model + Harness
```

Harness 是包裹在 AI 模型外围的软件基础设施, 负责模型推理之外的一切: 工具执行、状态持久化、安全边界、错误恢复、生命周期管理。

### 3.2 工程范式三次跃迁

| 阶段 | 范式 | 核心关注 | 工程对象 |
|------|------|---------|---------|
| 2023 | **Prompt Engineering** | 这一轮推理怎么答 | 单次输入文本 |
| 2024-25 | **Context Engineering** | 模型每一步看到什么 | 系统提示 + 检索 + 工具 + 历史 |
| 2025-26 | **Harness Engineering** | 智能体如何在环境中持续运行 | 工具执行 + 状态 + 安全 + 生命周期 |

三者是递进关系, 非替代关系。Harness 包含 Context Engineering 作为子系统。

### 3.3 Harness 四大核心子系统

#### (1) 工具执行层 (Tool Integration Layer)

- **调用校验**: 参数合法性 + 权限范围
- **沙箱隔离**: 文件系统隔离 + 网络隔离
- **结果清洗**: 过滤敏感信息, 截断过长输出
- **超时与熔断**: 单次调用超时, 连续失败熔断

#### (2) 状态与记忆管理

| 记忆层 | 生命周期 | 内容 | 实现 |
|--------|---------|------|------|
| 工作上下文 | 单次推理 | 当前提示词 + 工具结果 | 上下文窗口 |
| 会话状态 | 单次任务 | 执行日志、中间结果、检查点 | 文件/数据库 |
| 长期记忆 | 跨任务 | 用户偏好、历史经验、知识库 | Vector DB / KG |

#### (3) 安全与权限层 (TCB 实现)

- **输入清洗**: PII 遮蔽 (如 Salesforce Einstein Trust Layer)
- **输出校验**: 每个动作经策略引擎审核
- **最小权限**: 每会话仅授予完成任务的最小工具集
- **审计日志**: 每次调用附带 `trace_id`, 完整证据链

#### (4) 生命周期管理

- **检查点**: 定期保存状态, 支持断点续传
- **恢复策略**: 失败后重试/回退/人工接管
- **优雅终止**: 超时/预算耗尽时安全退出

### 3.4 Agent 体工学

为 Agent 设计更好用的软件 (黄东旭):
1. **最小化使用摩擦**: 统一平台集成, 简化接口设计
2. **可观测性优先**: 让 Agent 的行为可追踪、可审计
3. **人机协作**: 设计清晰的介入点和回退机制

## 4. 可观测性与调试

### 4.1 为什么智能体难以调试

1. **非确定性**: 同样提示词, 上午通过, 下午失败
2. **黑盒推理**: LLM 为什么选择工具 A 而非 B
3. **多步级联**: 第 5 步错误可能是第 1 步偏差的蝴蝶效应
4. **成本隐患**: 死循环智能体可能一夜烧掉数千美元
5. **行为即逝**: 决策链运行时生成、运行后消散 (暗码问题)

### 4.2 核心数据模型: 链路与跨度

- **链路 (Trace)**: 用户一次请求的完整处理过程
- **跨度 (Span)**: 链路中的执行片段 (工具调用、规划、子步骤)

### 4.3 OpenTelemetry: 统一标准

**优先对齐**: OpenTelemetry (OTel) + OTLP 传输协议

**关键语义字段** (GenAI namespace):
- `gen_ai.operation.name`
- `gen_ai.request.model` / `gen_ai.response.model`
- `gen_ai.tool.name`
- `gen_ai.usage.input_tokens` / `gen_ai.usage.output_tokens`

> 截至 2026-05, GenAI 语义约定仍在 Development 成熟度, 尚未稳定定版。

**架构建议**: OTel = "底层数据面", Langfuse/LangSmith = "上层分析面"

### 4.4 跨节点上下文透传

1. **注入**: 网关生成全局 `trace_id`, 初始化 `ContextPack`
2. **透传**: 工具调用、RAG 检索、智能体间任务委派, 强制携带 `trace_id` + 衍生 `span_id`
3. **聚合**: 按 `trace_id` 查询, 拼装所有内部状态流转

### 4.5 评估体系: 从离线到在线

| 类型 | 时机 | 方法 |
|------|------|------|
| **离线评估** | 发布前 | 标准测试集, 回归门禁 |
| **在线评估** | 运行中 | A/B 测试, 实时监控, 人工抽检 |

## 5. 性能优化与成本控制

### 5.1 成本结构分析

智能体系统的主要成本:
- **LLM 调用**: 按 Token 计费, 多步调用累积
- **工具调用**: API 费用、计算资源
- **存储**: 向量数据库、日志存储
- **基础设施**: 计算实例、网络带宽

### 5.2 优化策略

1. **模型分层**: 路由简单任务到小模型, 复杂任务到高能力模型
2. **缓存**: 重复查询结果缓存, 提示词前缀缓存
3. **并行化**: 独立子任务并行执行, 减少总延迟
4. **上下文压缩**: 减少每轮 Token 消耗
5. **预算熔断**: 单任务成本上限, 防止失控
6. **异步化**: 长任务异步执行, 流式回传进度

## 6. 企业级智能体平台

### 6.1 多租户与隔离架构

**异步事件驱动架构**:
```
Client -> API Gateway -> Task Queue (Redis/RabbitMQ)
                              |
                    Agent Worker Cluster
                    (Dispatcher -> Worker Pod)
                              |
                    Model Gateway + External APIs + State DB
```

- 提交: 返回 TaskID + Accepted
- 执行: Worker 异步执行, 状态持久化
- 流式: WebSocket 推送进度

**多租户隔离**:
- 计算隔离: K8s Namespaces / Node Pools
- 网络隔离: Egress Control + Service Mesh (Istio/Cilium)

### 6.2 深度防御体系

| 层级 | 技术 | 作用 |
|------|------|------|
| L1-3 | Prompt 工程、护栏、应用鉴权 | 防越权与不当调用 |
| L4 | 结构化输出约束 (FSM/Logits Masking) | Schema 一致性保证 |
| L5 | 基础设施沙箱 | 隔离代码执行环境 |
| L6 | 侧车代理安全联网 | 外网密钥与域名白名单 |

### 6.3 结构化输出约束

生产环境中, 完全依赖 Prompt + 事后校验不可接受。现代推理引擎 (vLLM, SGLang, TensorRT-LLM) 在生成循环底层引入:
- **有限状态机 (FSM)** 或 **正则表达式**
- **Logits Masking**: 动态屏蔽不合规词汇
- 从物理层面提供 Schema Reliability, 且不拖累原生吞吐

## 7. 故障模式与韧性设计

### 7.1 四种运行时故障类型

1. **控制流故障**: 死循环、异常重试、过早终止、长时间卡住
2. **认知故障**: 上下文漂移、目标遗忘、幻觉、错误工具选择
3. **依赖与执行故障**: API 超时、Schema 变更、工具返回不完整、权限异常
4. **级联故障**: 一个步骤的错误输出被下游当成可信输入继续放大

> 真正昂贵的事故通常不是进程崩溃, 而是系统继续"正常运行"却在错误方向上稳定放大。

### 7.2 故障诊断标准流程

1. **先止血**: 暂停高风险动作, 触发 kill switch / 熔断器
2. **定位症状**: 成本激增 / 延迟异常 / 成功率下降 / 事实性错误
3. **回放链路**: 查看完整 trace, 确认错误阶段
4. **识别首个异常点**: 第一个偏离预期的跨度
5. **分类根因**: 控制流 / 认知 / 依赖 / 级联
6. **验证恢复策略**: 重试/回滚/人工接管/降级路由

> 目标: 把 MTTD (平均诊断时间) 和 MTTR (平均恢复时间) 压到足够低。

### 7.3 典型案例与修复策略

#### 死循环与成本雪崩 (控制流故障)

**修复**:
- 三种硬限制: `MAX_ITERATIONS` + `MAX_TOOL_CALLS` + `MAX_WALL_CLOCK_TIME`
- 错误去重: 连续相同 (tool, args, error) 立即判定循环
- 成本熔断: 单链路成本超预算自动终止
- 策略降级: 从自主重试切换到人工接管

#### 上下文漂移与目标遗忘 (认知故障)

**修复**:
- 系统提示与任务目标**固定置顶**, 不参与 FIFO 轮转
- 状态分层: 系统约束/任务目标/事实摘要/最近对话 拆成不同槽位
- 记忆摘要而非硬截断
- 目标心跳检查: 定期评审 "当前动作是否仍服务初始目标"

## 8. 架构陷阱与反模式

### 8.1 反模式一: 万能 Prompt

```python
# 反模式: 所有工具 + 所有规则 + 所有历史 -> 一个大 Prompt
prompt = f"{serialize_all_100_tools()}\n{all_system_rules}\n{full_user_history}\n{task}"
```

**问题**: 工具选择噪声高, 推理链混乱, 成本线性放大, 调试无从下手

**修复**: 分层路由 + 职责隔离, 每个专家 Agent 只携带必需的工具和上下文

### 8.2 反模式二: 把长上下文当作记忆系统

```python
# 反模式: 加载全部历史 + 全部知识库 + 全部文档
prompt = f"{all_history}\n{entire_kb}\n{all_related_docs}\n{query}"
```

**问题**: 检索精度下降, 注意力偏差, 成本延迟同步膨胀

**修复**: 预算化上下文 + 分层记忆 (按需检索, 而非全量加载)

### 8.3 反模式三: 暗码 (Dark Code)

Agent 的决策链在运行时生成、运行后消散, 缺乏追踪机制无法事后审计。

**修复**: 全链路追踪 (OTel), 强制 trace_id, 完整轨迹日志

### 8.4 反模式四: 忽视护栏

不设最大步数、不设成本预算、不做错误去重 -> 一个失控 Agent 可能在一夜之间消耗大量资源。

**修复**: 必须配置 max_steps, token_budget, 连续重复检测, 成本熔断

### 8.5 反模式五: 过度工程

一开始就堆叠多智能体、复杂路由、全套可观测性 -> 系统复杂度超过团队维护能力。

**修复**: 从单体 Agent + 简单护栏开始, 按需演进到多智能体

## 9. 智能体编程实践 (Agentic Coding)

### 9.1 编程范式转移

```
Vibe Coding (自然语言驱动, 快速原型)
    |
    v  (进化)
Agentic Coding (理解 -> 规划 -> 执行 -> 验证 -> 迭代)
```

**Vibe Coding 的生产边界**: 极其适合黑客马拉松/PoC, 但绝不能将未经审查的代码直接推向生产。

### 9.2 Agent Loop: 核心工作机制

> Agent Loop 的详细工程实现（异步生成器模式 vs 线性流水线模式、六步执行循环、漂移检测、Token 预算管理）详见 [[Harness_Core_Subsystems#1.1-智能体循环的工程实现]]。此处仅保留三个观察视角：

- **微观循环**：Think → Act → Observe（单次迭代）
- **中观视角**：Gather → Action → Verify（执行阶段）
- **任务级工作流**：Plan → Decompose → Execute → Review（开发者协作）

> Workflow 包裹多个 Agent Loop; Agent Loop 是 Workflow 真正落地执行时反复转动的引擎。

### 9.3 工程化最佳实践

#### 上下文管理

- **让智能体自己找上下文**: 不要手动 @每个文件, 描述意图让 Agent 搜索
- **标准化 AGENTS.md**: 机器可读的项目说明书 (目标、约定、陷阱)
- **Agent Legibility**: 为 Agent 优化代码可读性 (扁平结构, 自描述命名, 显式类型)

#### 对话策略

| 开启新对话 | 继续对话 |
|-----------|---------|
| 切换不同任务/功能 | 迭代同一功能 |
| Agent 困惑或重复犯错 | 需要早期上下文 |
| 完成一个逻辑工作单元 | 调试刚构建的东西 |
| 对话超过 20 轮 | 对话仍然聚焦 |

> 长对话导致智能体失去焦点。经过多轮对话和摘要后, 上下文噪声积累。

#### 回退优于修补

> **黄金法则**: 如果实现偏离轨道, 不要通过后续对话修补 -> 先 `git diff`, 优先有边界的回退, 然后从更清晰的 spec 重新开始。一次正确的全新生成, 永远优于十次修补。

#### 并行智能体与 Git 工作树


## 10. 从实验到生产: 决策路线图

### 10.1 决策检查清单

- [ ] 系统提示词清晰明确, 含身份、能力边界、约束
- [ ] 工具描述完整 (名称、参数、返回值、限制)
- [ ] 安全规则含防注入措施
- [ ] 静态内容前置, 适配提示词缓存
- [ ] 护栏完备 (最大步数、成本预算、错误去重、熔断)
- [ ] 可观测性就位 (trace_id 透传、链路追踪、关键指标监控)
- [ ] 评估体系建立 (能力评估 + 回归评估)
- [ ] 记忆系统分层 (短期窗口 + 长期存储 + 检索策略)
- [ ] 多智能体角色边界清晰, SOP 版本化管理
- [ ] 人机协作节点已设计 (审批、回退、取消)
- [ ] 实际测试覆盖: 正常路径 + 边界情况 + 攻击场景
